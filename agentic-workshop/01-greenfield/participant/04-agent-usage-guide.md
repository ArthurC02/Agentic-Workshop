# Coding Agent Usage Guide

> 讀者：參與者與其 Coding Agent。時機：Greenfield 22 分鐘實作。前置：閱讀任務、需求與驗收條件；已下載 G0；環境在檢查點 1 由 Agent 建立。可見性：Participant。

今天全程你不寫、不讀程式，也不自己打指令；程式、測試與指令操作都交給 Agent。每一步的提示詞都在 Runbook 的 Greenfield 頁，複製貼給 Agent 即可，你只看回報、做決定。

## 1. 規則寫進 AGENTS.md（4 分鐘）

請 Agent 在專案根目錄寫 `AGENTS.md`：「怎麼跑」由 Agent 從 README 整理，「工作規則」照下方範本。多數 Coding Agent 每次開新對話都會自動讀它，之後的提示詞就不用重複叮嚀「先計畫、做完停下、附測試結果」。同時建立 `check` Skill：之後每一步說「用 check 檢查剛才這一段」就好。

## 2. 先要計畫再動手（4 分鐘）

Agent 先不改程式，提出 4 步計畫，每一步標出規則編號、驗收條件與預計修改的檔案，寫進 `notes/greenfield.md`。需求文件沒寫清楚的地方，Agent 列成問題並附建議答案，你回「同意」或「第 N 題改成…」，再核准最前面兩小步。

## 3. 小步執行、每步驗收（10 分鐘）

每次只放行一小步。Agent 做完會停下，附驗收對照表和變更審查。你判斷三件事：改的檔案都在核准的計畫裡；測試數沒有變少，也沒有新增跳過；沒有刪除測試，也沒有改既有期待值。都成立才放行。

## 4. 親自驗證並交付（4 分鐘）

不再加功能。Agent 補齊測試、更新文件、寫交付摘要並啟動伺服器；你在瀏覽器開 `/docs` 親自試訂票和付款，回 Agent 一行結果，它寫入「人工驗證」後存成「Greenfield 交付」。

## AGENTS.md 的「怎麼跑」要寫到的事（Agent 從 README 整理）

- Python 固定 3.13，虛擬環境在 `.venv`，不用啟用、直接呼叫裡面的 Python；Windows 和 macOS 各寫一行建立指令和 Python 路徑。找不到 3.13 就停下問我，不改用其他版本。
- 安裝與跑測試的指令；要實際呼叫 API 時用 Python 的 httpx，不用 curl（Windows 的 curl 會弄亂中文）。
- 在背景啟動伺服器（埠號 8000）並確認 `/health`。8000 被不是你啟動的程式占用：不要停它，告訴我它的名稱和 PID（程序編號），改用 8001，並把實際埠號寫進 notes。
- 換版本、重新啟動或結束時，先停掉你啟動的伺服器，連同它開出的子程序；不是你啟動的不要停。
- Git 只在這個專案設定身分（不用 `--global`）：名字 `workshop`、Email `you@example.com`；`.gitignore` 至少有 `__pycache__/`、`.venv/`、`.pytest_cache/`。
- 紀錄寫在 `notes/`。

## AGENTS.md 的「工作規則」範本（Agent 照抄）

```markdown
## 工作規則
1. 程式、測試和指令都由你做；我不讀程式，請用白話說明，英文術語第一次出現時加中文。
2. 改程式前先提計畫，等我核准；只做核准的步驟，做完停下等我。
3. 商業規則放在 domain／application，Router 只做輸入輸出轉換；不新增套件、不改 Seed 資料、不動 /health。
4. 功能做完才移除對應的 skip；不刪除、不修改既有測試的期待值，不用 skip／xfail 藏住失敗。
5. 每次做完都跑測試，用驗收對照表回報：每條驗收條件或規則一列，欄位是「編號、白話內容、結果（通過／失敗／未驗證）、依據的測試名稱」，最後一行寫通過／失敗／跳過數。只給摘要，不貼原始輸出。
6. 每次修改後附變更審查：改了哪些檔案、各改什麼、為什麼，有沒有計畫外的檔案（notes/ 不算）；測試數有沒有變少、有沒有新增 skip 或 xfail；有沒有刪除測試或修改既有期待值（用 git diff 看 tests 資料夾）；哪些原本跳過的測試變成通過。最後一句建議「可以放行」或「不建議放行（原因）」。
7. 我核准時，把核准內容和電腦的目前時間記進這段的 notes。
8. 沒有實際執行的事一律標「未驗證」。
```

## check Skill 範本（Agent 依自己的工具放到會自動載入專案 Skill 的位置，資料夾 `check`、檔名 `SKILL.md`）

```markdown
---
name: check
description: 檢查剛完成的一段工作是不是真的完成。使用者說「用 check 檢查」「確認結果」，或要驗收一段工作時使用。只讀不改。
---

# check：檢查一段工作

只讀：不建立、修改或刪除任何檔案，不 Commit，不修程式。

1. 找出這一段該完成什麼：已核准的計畫、任務卡或驗收條件，以及使用者這次另外指定的條件。
2. 自己執行指令取得實際結果，不憑記憶：測試、git status／git log、檔案和段落是否存在，有伺服器就查 /health。
3. 對照三樣：notes 裡寫的、實際結果、核准的計畫與驗收條件。
4. 列出對不上的地方，每條附證據（檔案位置或指令結果）；都對得上就不用列。
5. 最後一行只寫「成功」，或「失敗：」加一句原因。
```

## 完成條件

計畫經你核准、每一步都有驗收紀錄、你親自在 `/docs` 試過訂票和付款，依 [提交清單](05-submission-checklist.md) 準備交付。未完成時如實說明；第 25 分停止擴充，第 29 分停止修改。
