# Brownfield：讓 Agent 當隊友，一起接手既有系統

> 讀者：學員。時機：Brownfield（已有程式碼的既有專案）實作後的 45 分鐘講解。前置：做過個人分析、共同脈絡、B1 與 B2。

這份講義整理技巧與人要判斷的事，不含任務解答。指令是示範用；沒有實際執行的結果一律視為未驗證。

## 1. 接手既有系統：Agent 當隊友

第三階段 · Brownfield（已有程式碼的既有專案）／Teammate（隊友：與 Agent，也就是 AI 助手，一起工作） · 概念與技巧

- **今天回看**：個人分析、共同脈絡、B1（第一個變更任務：修 Bug）、B2（第二個：改規則）：四段各用了什麼技巧。

- **今天帶走**：接手陌生系統、讓團隊共用規則、修 Bug 與改規則時，人該在哪裡判斷。

**人工確認**：能說出剛才四段裡，自己核准過的一份計畫或選過的一個方案。

## 2. Tool → Teammate：人改成核准計畫

差別不在 Agent 多聰明，而在人怎麼介入：Tool 逐步下指令，Teammate 先一起分析，人核准計畫後才動手。

Tool：人逐步下指令 → Teammate：一起分析，人核准計畫 → Digital Worker（數位員工）：下一場

- **Agent 多做的**：讀檔、跑測試、比較做法、寫紀錄，附來源回報。

- **人保留的**：選哪份計畫、範圍多大、證據夠不夠、接不接受。

**人工確認**：每段開始動手前，都有一個由人說「核准」的時間點。

## 3. 先要一張地圖，不先問 Bug 在哪

接手陌生專案，第一個問題是「分幾塊、規則在哪、測試現況」，不是「哪裡壞了」。

- **系統地圖**：各部分負責什麼業務、依賴誰；不是一串檔名。

- **規則在哪**：商業規則寫在哪份文件、對應到哪一部分。

- **測試現況**：通過、失敗、跳過各幾個；先不推論原因。

### 交給 Agent 的指令

先不要修改程式。請帶我讀這個專案：先列資料夾結構，只挑必要的重點檔讀。用白話說明系統分哪幾部分、規則寫在哪、測試現況，每個結論標事實、假設或缺口，最後列出你讀了哪些檔，然後停下。

**人工確認**：地圖說得出「誰負責什麼、依賴誰」；Agent 列得出實際讀了哪些檔。

## 4. 技巧：模型選擇與推論強度

分析陌生程式要想深一點：選較強的模型、調高推論強度。機械性工作用快速、便宜的模型就夠。

- **模型選擇**：跑測試、整理格式用快速模型；分析、比較取捨用較強模型。

- **推論強度（Reasoning Effort）**：同一個模型「想多深」；越深越慢，也越耗 Token（詞元）。

- **沒有推論強度設定時**：有設定就直接調整；沒有，才在提示詞寫「先仔細想過再回答」替代。

**人工確認**：說得出剛才分析時用的是哪一種設定，以及為什麼。

## 5. Token 節費（加深一層）：指名檔案，只要摘要

Speech 02 學過開新對話與指名要讀的檔；陌生專案還不知道該指名哪些，就先列目錄、挑重點檔。

- **先列目錄再挑**：先讀 README、架構文件與決策紀錄，回報讀了哪些；其他需要時才讀。

- **只要摘要**：測試結果只報通過／失敗／跳過數，不貼完整輸出。

- **交接用摘要**：給別人的 Agent 用 5 行摘要，是 Speech 02 交接檔的短版。

**人工確認**：Agent 回報裡有「讀了哪些檔」；沒有出現整段原始輸出。

## 6. 文件是線索，不是結論

Speech 02 的三方對照（文件、測試、程式），這裡落到每個結論：標出它是哪一種。

- **事實**：附文件位置、測試名稱或實際執行過的指令。

- **假設**：說明依據，以及還缺什麼證據。

- **缺口**：查不清楚，需要問人。

### 交給 Agent 的指令

我要追問第 2 條事實：請引用規則或文件原文、測試名稱，並重新執行相關測試貼出結果摘要。拿不出證據就改標為假設，告訴我改了什麼，然後停下。

**人工確認**：挑一個「事實」追問證據；說「可能」「應該」的地方已改標為假設。

## 7. 幾個 Agent 讀同一份系統，說法不同怎麼辦

每人的 Agent 先濃縮成 5 行摘要，小組才比得起來；比的是證據，不是誰的語氣最肯定。

各自 5 行摘要 → 說法一樣且附來源：共同事實 → 說法不同或沒證據：分歧 → 寫下用什麼驗證分歧

- **主要 Agent**：小組選定、代表全組執行工作的那一個 Agent。

- **人員核准者**：小組指定說「核准」的人；之後的紀錄都記他。

**人工確認**：說得出一條附來源的共同事實、一個分歧，以及要重跑哪個測試才分得出對錯。

## 8. 口頭講過的，Agent 下次就忘了

共同脈絡（Shared Context）：小組的共同事實、分歧與待決事項，由主要 Agent 寫成檔案。

```text
notes/shared-context.md
  ## 共同事實      多人一致，附來源
  ## 仍有分歧      附驗證方式
  ## 已知限制      只記限制，不預先核准修改
  ## 待決事項      要等任務揭露才能決定
  ## 分工          主要 Agent 與核准者
```

**人工確認**：主要 Agent 複述時，沒有把分歧或假設說成事實，也沒有自己加修改計畫。

## 9. 技巧：Skill，把規則寫成開工先讀的檔

Skill（技能檔）：本課程用簡化版，就是 skills/ 裡一份 Markdown 說明檔；工具內建的 Skill 另有固定格式。

- **之後每段的第一句**：「請先讀 skills/team-rules.md」，不再整段重貼規則。

```text
skills/team-rules.md
  ## 開工先讀    notes/shared-context.md
  ## 工作規則    7 條，含過時期待值須經核准才更新
  ## 回報格式    驗收對照表、改了哪些檔與原因
```

**人工確認**：說得出 team-rules.md 的三節；之後的提示詞都以它開頭。

## 10. 用失敗測試找 Bug

「修前失敗、修後通過」是你不讀程式也能信任的證據。先重現，才算找到 Bug。

重現：一個現在會失敗的測試 → 定位：分開事實與推論 → 最小修正：只做核准的步驟 → 驗證：同一批測試變成通過

**人工確認**：修好的證據是同一批測試的前後對照，而不是 Agent 說「完成了」。

## 11. 人核准的是一份小計畫

Teammate 的介入點：Agent 先交原因與計畫，人看證據夠不夠、範圍夠不夠小，再說核准或退回。

- **原因分兩欄**：有規則或測試證據的事實，和還只是推論的部分。

- **計畫最多 3 步**：每步標規則編號（Rule ID）或驗收條件（AC，Acceptance Criteria）。

- **寫出不改什麼**：其他票種、既有優惠與順序都不動。

### 交給 Agent 的指令

先不要核准，也不要修改程式。請補證據：你的原因有沒有規則原文或測試結果支持？說不出依據的標成「推論」，計畫裡超出任務卡範圍的步驟刪掉，再告訴我改了哪裡，然後停下等我。

**人工確認**：證據夠、範圍小才核准；證據不足或計畫太大就退回補證據。

## 12. 改完先停：變更審查三題

Greenfield 的四題審查，B1 留前三題；只看答案與附上的指令，三題都是「是」才放行。

- **1. 範圍**：改的檔案都在核准計畫裡。

- **2. 測試沒變少**：總數沒少，也沒新增跳過（skip）或預期失敗（xfail）。

- **3. 期待值沒被動**：沒刪測試、沒改既有期待值，用變更內容（Diff）核對。

**人工確認**：任一題是「否」或「不確定」，就請 Agent 解釋並還原超出範圍的修改，不放行。

## 13. Skill（加深一層）：存的是一套做法

重複的程序就該長成 Skill。team-rules.md 存規則；fix-bug-with-test.md 存修 Bug 的做法。

```text
skills/
  team-rules.md          規則：每段開工先讀
  fix-bug-with-test.md   做法：重現 → 定位 → 最小修正 → 驗證
                         每步要交的證據、禁止事項、回報格式
```

**人工確認**：fix-bug-with-test.md 是通用說明，沒有寫進這次 Bug 的原因或修改內容。

## 14. 改規則時，不接受第一個答案

修 Bug 有明確的對錯；改規則常有不只一種做法。請 Agent 提 2–3 個可行方案，人來選。

- **真的可行**：不是一個方案配兩個陪襯。

- **對照禁止事項**：違反任務卡禁止事項的方案直接標出來。

- **假設附依據**：沒有依據的標「未確認」，再決定要不要追問。

**人工確認**：選方案前，至少問過一次：哪個「未確認」的假設錯了會改變選擇？

## 15. 結構化輸出（加深一層）：固定欄位的比較表

Greenfield 用固定欄位寫驗收表；這裡用同樣方法並排比較方案，幾個方案才能逐欄對照。

```text
| 方案 | 改動範圍 | 風險 | 測試影響 | 建議 |
|------|----------|------|----------|------|
| A    | 一定要改／可能影響／不應改，附證據 | … | … | … |
| B    | …        | …    | …        | …    |
```

**人工確認**：每個方案都填滿同一組欄位；改動範圍附檔案或測試名稱當證據。

## 16. 推論強度（加深一層）：比較調高，實作調回

同一個任務的不同階段，需要的「想多深」不一樣。用對地方，既準又省。

比較方案、找風險：調高 → 人選方案並核准 → 小步實作：調回低或預設

- **為什麼實作調回**：核准後是照計畫的小步修改，想太深只是更慢、更耗 Token。

**人工確認**：比較方案時有調高（沒有這項設定才改用提示詞），核准後有調回。

## 17. 規則改了，舊測試怎麼辦

有些既有測試只在舊規則下才對。Agent 要先停下列出來，人核准後才更新；其他期待值一律不改。

- **三點都成立才核准**：舊期待只在舊規則下才對；新規則要求不同結果；附了 Rule ID。

- **變更審查多兩題**：政策不放在 API 路由層，訂票與改票共用同一套；挑一位多優惠旅客實際驗證。

- **核對到每位旅客**：看每人採用的優惠類型與折扣率，不只核對總額。

**人工確認**：改過的既有期待值，每一處都附 Rule ID 和小組的核准紀錄。

## 18. 每一步，人判斷的是什麼

Agent 負責讀、跑、寫；人負責四種判斷。這張表就是 Teammate 階段的分工。

```text
分析      這個「事實」附得出來源嗎？
共同脈絡  有沒有把分歧或假設說成事實？
B1 核准   證據夠嗎？計畫夠小嗎？寫了不改什麼嗎？
B1 驗收   同一批測試修前失敗、修後通過？審查三題都是「是」？
B2 選擇   方案真的可行嗎？未確認的假設會改變選擇嗎？
B2 驗收   每位旅客的結果符合新規則？改過的期待值都核准過？
```

**人工確認**：說得出自己在其中一步曾經退回或追問過什麼。

## 19. 下一場：任務更大，你沒辦法盯每一段

這次每做完一段都停下看證據。任務再大一點，人就得先寫清楚範圍，只在幾個關鍵點做決定。

Tool：逐步下指令 → Teammate：核准計畫 → Digital Worker：只在關鍵點決定

- **帶到下一場的檔**：notes/shared-context.md、skills/team-rules.md、skills/fix-bug-with-test.md。

- **帶到下一場的問題**：如果不能盯每一小段，你會先寫清楚哪些事，才敢讓 Agent 自己往前走？

**人工確認**：離場前寫下一條自己團隊值得寫成 Skill 的規則或做法。

## 完成條件
說得出 Teammate 的介入方式（核准計畫，不盯每一步），並能為自己的工作寫下一份開工先讀的規則 Skill，以及一個先重現再修、或先比較再選的做法。
