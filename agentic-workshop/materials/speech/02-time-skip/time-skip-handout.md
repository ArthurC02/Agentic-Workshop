# Time Skip：系統演化與接手

> 讀者：學員。時機：25 分鐘觀念與技巧講解。前置：已聽過 Greenfield 講解，備妥可用的 Coding Agent（能讀寫檔案、協助寫程式的 AI 助手）。

本段不寫程式、不打指令。提示詞只供示範；沒有實際執行的結果，一律標為未驗證。

## 1. 為什麼 Agent 會「越聊越笨」

剛才你接手一個長了 12 個月的專案，並開了新對話。這一場講背後的原因：Agent 的工作桌有多大。

- **剛才做的**：開新對話、指名要讀的檔、記下起點、留交接檔。

- **今天補上的**：脈絡視窗、Token 成本、壓縮與交接、規則檔，以及何時該重開。

**人工確認**：想一次經驗：對話越拉越長之後，Agent 開始忘記或搞混什麼？

## 2. 脈絡視窗：是工作桌，不是倉庫

Context Window（脈絡視窗）：Agent 這一次回答時「攤在桌上」的全部內容，有固定上限。

規則檔 → 你的訊息 → 讀過的檔案 → 指令輸出 → Agent 的回答

- **全部都佔位子**：不只你打的字；讀的每個檔、跑的每個測試輸出都算。

- **滿得很快**：讀幾個大檔、貼一次長輸出，桌面就堆滿了。

- **越滿越不準**：官方文件直說：視窗越滿，表現越差。

**人工確認**：說出兩樣你沒有打字、卻也佔了 Agent 工作桌的東西。

## 3. 給越多越好？剛好相反

Context Rot（脈絡劣化）：內容越多，Agent 越難在裡面找到真正重要的那幾句。

- **注意力有預算**：每多一段無關內容，就從重要內容那裡分走一點注意力。

- **目標是「少而準」**：給最少、但最有用的資訊，而不是全部倒進去。

- **大視窗不是解藥**：官方說每個模型都會劣化；能放得下，不代表讀得好。

**人工確認**：下次想說「把整個專案讀一遍」時，改成說出哪三個檔最重要。

## 4. 長對話為什麼越來越貴

Token（詞元）是計費單位。Agent 每回答一次，都要把整段對話歷史重新讀一遍。

第 1 問：讀 1 份 → 第 10 問：讀 10 份歷史 → 第 50 問：讀 50 份歷史

- **成本跟著桌面變大**：官方文件：處理的脈絡越多，用掉的 Token 越多。

- **量級參考**：某工具官方估計：每人每個工作日約十幾美元；價格常變。

- **省錢＝省干擾**：同一招讓 Agent 更準，也讓帳單變小。

**人工確認**：你的對話裡，哪一段長輸出其實只要一行結論就夠？

## 5. 讀很多檔？請它先摘要再回來

要找東西時，讓 Agent 在另一個對話裡讀，只把結論帶回主對話。

- **指名範圍**：你剛才說了只讀哪些檔，這就是最便宜的省法。

- **子 Agent 探索**：有些工具能派子 Agent 去讀，只回傳一兩千 Token 的摘要。

- **沒有子 Agent 時**：開一個新對話專門探索，把摘要貼回主對話。

### 交給 Agent 的指令

先不要修改檔案。請另外探索 tests/ 資料夾，回來只給我：測試分成哪幾類、各自在測什麼，最多 8 行。不要貼原始輸出，最後列出你讀了哪些檔，然後停下。

**人工確認**：回報裡有沒有混進整段原始輸出？讀了哪些檔有沒有列出來？

## 6. 糾正兩次還錯，就重開

對話裡累積的錯誤嘗試也佔位子，而且會一直誤導 Agent。

- **換任務就開新的**：兩件不相關的事，不要擠在同一段對話裡。

- **同一問題糾正兩次**：還是錯，就停：先整理學到的，再開新對話重來。

- **重開不是浪費**：乾淨對話加更好的提示詞，幾乎總是勝過越補越長的對話。

### 交給 Agent 的指令

先停下，不要再修改。請整理成一份新的提示詞：目標、已確認的事實、試過但無效的做法、限制、完成條件。我會把它貼到新對話重新開始。

**人工確認**：新提示詞裡有沒有寫出「試過但無效的做法」，避免新對話重蹈覆轍？

## 7. 壓縮：快滿時，把對話摘要成一段

Compaction（壓縮）：對話接近上限時，把歷史摘要成短版，帶到新的視窗繼續。

- **好處**：不用從零開始，桌面清出空間。

- **代價**：摘要會丟細節；被丟掉的可能正好是那條規則。

- **人的做法**：重要決定先寫進檔案，不要只活在對話裡。

**人工確認**：如果現在對話被壓縮，哪一個決定一定要先寫進檔案？

## 8. 交接檔：每個新對話都是新上班的人

新對話不記得上一段做過什麼；能接上的，只有寫在檔案裡的東西。

- **像輪班交接本**：上一班沒寫下的事，下一班就不知道。

- **人查三件事**：數字有依據、未驗證有列出、下一步只有一件。

```text
notes/handoff.md
  目前狀態：做到哪、測試幾個通過（附實際數字）
  已做決定：選了什麼、為什麼
  未驗證：沒實際執行過的事
  下一步：下一段先做哪一件（只寫一件）
  怎麼驗證：用什麼證明下一步做完了
```

**人工確認**：挑交接檔裡一個數字追問：這是實際執行看到的，還是推測的？

## 9. 案例：把狀態寫在檔案，不寫在對話

兩個公開的長任務實驗，都靠檔案而不是長對話撐下來。

- **功能清單只准改一欄**：長任務實驗：清單一開始全標未通過，Agent 只能改「是否通過」。

- **中斷也能接著跑**：大型遷移：每次從檔案重建待辦；輸出檔已存在就算完成。

- **要留意**：兩者都是工具廠商自己的案例；做法可參考，成效別直接套用。

**人工確認**：你手上的長任務，中斷後靠什麼知道做到哪裡？

## 10. 規則檔：每次對話都會先讀的那一份

把每次都要講的事寫成一份規則檔，Agent 每開一次新對話就自動讀進來。

- **開放慣例 AGENTS.md**：像給 Agent 的 README；由 Linux 基金會旗下組織維護，多數 Coding Agent 都讀。

- **各家也有自己的**：例如 CLAUDE.md、GEMINI.md；多半可以改讀 AGENTS.md。

- **越近越優先**：多數工具由根目錄往下合併，離工作檔案越近的規則越優先。

**人工確認**：你團隊每次開工都要重講的一句話是什麼？它適合放進規則檔嗎？

## 11. 規則檔要短：每一行都在佔桌面

規則檔每次對話都整份讀進來，寫越長，越擠掉真正的工作內容。

- **逐行自問**：「刪掉這行，Agent 會做錯嗎？」不會，就刪。

- **會互相打架**：兩條規則矛盾時，Agent 可能任選一條照做。

- **業界評估**：技術雷達：規則檔膨脹列為警示；團隊共同維護的規則列為建議採用。

### 交給 Agent 的指令

先不要修改檔案。請逐行檢查我們的規則檔：哪些行刪掉也不會讓你做錯、哪些互相矛盾、哪些應該改成自動檢查。用表格列出（行號、問題、建議），然後停下等我決定。

**人工確認**：刪不刪由人決定；被建議刪掉的那行，真的沒有出過錯嗎？

## 12. 帶走五個習慣

這些不是省錢技巧而已，是讓 Agent 保持準確的基本功。

少而準的脈絡 → 大量讀檔先摘要 → 糾正兩次就重開 → 決定寫進交接檔 → 規則檔保持短

- **下一場**：Brownfield（既有專案）／Teammate（隊友）：讀懂舊系統、選模型與推論強度、把團隊做法寫成 Skill。

**人工確認**：選一個習慣，說出你下週第一次會在哪個工作情境用上。

## 完成條件
能用自己的話說明：為什麼對話越長 Agent 越不準也越貴；何時該開新對話、何時讓它先摘要；交接檔要寫哪幾項、人要查哪幾項；規則檔為什麼要短、一定要發生的事為什麼要交給自動檢查。
