# Greenfield：從 Idea 到可開發的專案

> 讀者：學員。時機：主課 Greenfield 之後的 45 分鐘講解。前置：已體驗 Greenfield。

本場講概念與技巧，不需要寫程式或打指令。頁面上的提示詞是示範，想試再貼給自己的 Agent；沒有實際執行的結果，一律視為未驗證。

**這一段帶走什麼**

- 先給 Agent 能自己跑的檢查，再請它做事
- 驗收條件寫成可判定的句子，預期值先從規則推
- 用五段式提示詞與脈絡告訴它要做什麼
- 先計畫、小步放行、用固定欄位回報
- 審查看證據，不看宣稱

## 1. 剛才的順利，不是運氣

G0（Greenfield 起始程式包）先備好了 16 條規則、15 項驗收條件與測試骨架；Agent（能自己讀寫檔案、執行指令來完成工作的 AI）因此知道什麼叫做對。

- **本場回答三個問題**：Agent 怎麼知道做對了？怎麼知道要做什麼？人怎麼確認？

- **講法**：每個做法：白話概念 → 官方說法 → 怎麼用在你的工作 → 業界案例。

這份講義是給課後回頭讀的。投影片只放得下幾個字，這裡補上每個做法為什麼重要、證據是什麼、常見的誤解，以及下週怎麼用。數字都附上誰量的、哪一年；廠商自家的案例會特別註明。

剛才 Greenfield 順利，是因為起始程式包先準備好三樣東西：編號的業務規則、能判定對錯的驗收條件，以及會告訴 Agent「還差什麼」的測試骨架。回到工作上，這三樣不會自己出現；你交辦的專案缺哪一樣，Agent 就只能用猜的。

**人工確認**：說得出剛才 Greenfield 哪一步最順、哪一步卡住。

## 2. Tool：人一步一步介入

Tool（工具）→ Teammate（隊友）→ Digital Worker（數位員工）差在人怎麼介入，不是人寫多少程式。

Tool：逐步下指令、每步驗收 → Teammate：核准計畫後才動手 → Digital Worker：只在核准關卡決定

- **剛才的 Greenfield 是 Tool**：步驟由你定；Agent 做完一步就停，你看證據才放行下一步。

- **為什麼從 Tool 開始**：先學會「怎麼判斷做對了」，之後才能放手讓 Agent 多做。

三種方式的差別不在 Agent 多強，而在人什麼時候介入：Tool 是你決定每一步、每步驗收；Teammate 是你先核准整份計畫；Digital Worker 是你只在事先設好的核准關卡（Gate）做決定。後兩種在第三、四場展開。

常見的誤解是「越後面越好」。其實這是依風險選擇：做錯代價高、難以復原、或還沒有自動檢查的工作，就該停在 Tool，一步一步看證據放行。

**人工確認**：說出 Greenfield 中你「放行」了幾次，每次看了什麼證據。

## 3. 新概念：Agent 在迴圈裡看結果做事

Agent 不是一次寫完答案：它讀檔、動手、看執行結果，再決定下一步，一圈一圈往前。

讀需求與檔案 → 修改或執行 → 看結果：測試、錯誤訊息 → 決定下一步

- **白話比喻**：很快、很勤勞，但第一天上班的新同事：不知道你們的規則，也不會讀心。

- **經驗法則**：迴圈裡沒有檢查，你就是那個檢查：每一步都得等你看過才知道對不對。

- **📖 延伸閱讀**：〈Building effective agents〉（Anthropic，2024）

Agent 的運作方式是「做一點、看結果、再決定」。Anthropic 在〈Building effective agents〉（2024-12）強調，Agent 每一步都要從環境取得真實結果，例如測試輸出、錯誤訊息、指令的回傳值。它看到的結果越可靠，下一步就越準。

所以問題不在 Agent 勤不勤勞，而在它的迴圈裡有沒有可靠的回饋。如果唯一的回饋是它自己覺得「完成了」，那每一步都要靠你檢查。G0 先準備測試骨架，就是讓測試結果成為 Agent 的真相來源。

這個迴圈也是 Agent 和聊天式 AI 助手的差別。Claude Code 官方詞彙表的說法是：聊天助手只回一段文字，要你自己貼上、自己執行；Agent 有工具，能讀檔、改檔、執行指令，看到結果再決定下一步。官方把這一圈稱為 agentic loop：收集脈絡、動手、驗證結果，重複到完成。常見誤解是「Agent 夠聰明，就不用給檢查」：迴圈轉得再快，沒有可靠的回饋，也只是很快地猜。

**人工確認**：說得出剛才 Agent 每一步「看了什麼結果」才回報：是測試輸出，還是它自己覺得完成了。

## 4. 技巧：先給檢查，再請它做事

官方建議：給 Agent 一個能自己執行的檢查（測試、建置、可比對的畫面），它才能自己收斂。

- **沒有檢查時**：「看起來完成」是唯一訊號，你只能相信或自己試。

- **有檢查時**：Agent 自己跑、自己修，附上結果；你只看結果對不對。

- **📖 延伸閱讀**：〈Best practices for Claude Code〉（Anthropic，官方文件）

### 交給 Agent 的指令

先不要修改任何檔案。請告訴我這個專案現在有哪些你能自己執行的檢查（例如測試、建置、啟動後的畫面），各自目前的結果是什麼。再對照需求，列出哪些需求還沒有任何檢查能證明，並建議要補什麼檢查。列完就停下等我。

Claude Code 官方文件〈Best practices for Claude Code〉建議：給 Agent 一個能自己執行的檢查，例如測試、建置、可比對的畫面。OpenAI Codex、GitHub Copilot 的官方文件也建議讓 Agent 執行測試來驗證，這不是單一產品的說法。

剛才 G0 一開始是 1 個測試通過、8 個跳過；跳過的就是還沒做完的檢查，所以 Agent 每做一步都看得到進度。常見的誤解是「有測試就好」：測試只證明它檢查到的那部分，對照需求找出沒有任何檢查的項目，才是人要補的。

下週怎麼用：接手任何專案，先貼上方的提示詞，請 Agent 盤點現有檢查、找出沒被檢查到的需求，再開始交辦工作。

**人工確認**：每條需求都對得到一個檢查；沒有檢查的，先決定要補檢查還是由你親自試。

## 5. 驗收條件：把「正確」寫成可判定

AC（Acceptance Criteria，驗收條件）：事先寫好、能明確判定符合或不符合的完成標準。它是人和 Agent 共同的真相來源。

- **好的寫法**：AC-G-005：成人＋學生訂 T001，總價 1225 且為整數。

- **不好的寫法**：「計價正常」「錯誤處理完善」：Agent 和你都無法判定。

- **預期值先從規則推**：成人 700＋學生 75%：看 Agent 回報前就先算好。

- **寫給 Agent 的好處**：條件可判定，Agent 才能把它轉成測試，自己檢查。

驗收條件寫得可判定，有兩個好處：人不讀程式也能判斷，因為你事先算好了預期數字；Agent 也能把條件直接變成測試，自己檢查。像「計價正常」這種句子，誰都沒辦法說它到底有沒有達成。ISTQB 詞彙表的定義也是這個方向：驗收條件是元件或系統要被使用者、客戶或其他授權者接受前，必須滿足的條件。

以 AC-G-005 為例：成人付基礎票價 700；學生是基礎票價的 75%，也就是 525；合計 1225，而且是整數。預期值要從規則推，而且要在看 Agent 回報之前就算好；先看回報再判斷，人很容易被一個看起來合理的數字說服。下週交辦任務前，先問自己：「完成時，我要看到什麼數字或畫面？」寫不出來，就請 Agent 先把需求改寫成可判定的條件，再由你確認。

📖 延伸閱讀：〈Glossary〉（ISTQB，acceptance criteria 條目）

**人工確認**：每一條都能判斷「符合／不符合」；預期數字指得回一條規則編號。

## 6. Given／When／Then：可判定的好寫法

Gherkin 用 Given（前提）／When（操作）／Then（結果）寫情境：業務方讀得懂，也能接上測試自動驗證。

- **人看什麼**：Then 寫看得到的結果；一個情境只有一個 When。

- **📖 延伸閱讀**：〈Gherkin Reference〉（Cucumber，官方文件）

```text
Scenario: 成人與學生一起訂票
  Given T001 基本票價 700，剩餘 20 座
  When 為 T001 訂一位成人與一位學生
  Then 總價為 1225 且為整數
  And 訂票為待付款，T001 剩餘 18 座
```

Cucumber 官方文件把 Gherkin 稱為「可執行的規格」：用固定的關鍵字寫情境，業務人員讀得懂，測試工具也能接上。適合用在需求還在跟業務方討論、需要用具體例子對齊的時候。

要注意兩件事。第一，Gherkin 檔本身不會執行，要接上測試工具，情境才算被驗證；沒接上的只是寫得比較整齊的需求。第二，主課 Greenfield 並沒有使用 Gherkin 檔，測試是 Agent 直接依驗收條件補上的。

下週怎麼用：請 Agent「把這份需求的驗收條件改寫成 Given／When／Then，每個 Then 寫看得到的結果，不確定的標待確認」，你只審每個 Then 對不對。

**人工確認**：每個 Then 都能在 Agent 的回報裡找到實際結果；情境沒接上測試的標「未驗證」。

## 7. 規格驅動開發：先寫規格再動手

Spec-driven development（規格驅動開發）：把需求、設計、任務寫成檔案，Agent 照規格做、人照規格審。

需求（含驗收條件） → 設計（例如分層架構） → 任務清單 → 逐項實作與驗證

- **三種深度**：只在開工前寫（多數做法）→ 規格隨程式維護 → 只改規格、程式由它產生。

- **經驗法則：別用大鐵鎚敲核桃**：小改動不必走完整流程；規格大小要和任務大小相稱。

- **業界現況**：仍在試：相關工具多列在「評估」，還不是業界標準。

- **📖 延伸閱讀**：〈Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl〉（martinfowler.com，2025）

Birgitta Böckeler 在 martinfowler.com（2025-10）把規格驅動開發分成三種深度：只在開工前寫規格、規格隨程式長期維護、只改規格而程式由它產生。她觀察到多數工具停在第一種；用小 Bug 試完整流程時，她形容像「用大鐵鎚敲核桃」；她也發現 Agent 常沒照全部規格做，而且大量的規格文件本身就很難審。

Thoughtworks 技術雷達第 34 期（2026-04）把 GitHub Spec Kit、OpenSpec 這類工具列在「評估」（Assess），不是「建議採用」，所以不要說規格驅動是業界標準。實際的做法是規格大小跟著任務走：一句話說得清楚的小改動直接做，牽涉多個檔案或規則的工作才先寫規格。剛才 G0 的需求、驗收條件與架構文件，就是第一種深度的規格。

📖 延伸閱讀：〈Technology Radar Vol. 34〉（Thoughtworks，2026）

**人工確認**：說得出 Greenfield 的規格在哪：需求、驗收條件、架構文件各是哪一份。

## 8. 技巧：規格從短開始，請 Agent 訪談你

先寫幾行高層次的構想，請 Agent 一次問一個問題補齊，再擴寫成規格；人只審，不從零寫。

- **為什麼有效**：Agent 擅長找出缺口；你只要回答它問的題，不必自己想到每一件事。

- **📖 延伸閱讀**：〈How to write a good spec for AI agents〉（Addy Osmani，2026）

### 交給 Agent 的指令

請讀 docs/idea.md，先不要寫程式。一次問我一個問題，釐清使用者、範圍外項目、失敗時怎麼處理。問完後寫成 docs/spec.md，分三段：需求（每條附可判定的驗收條件）、設計重點、任務清單。來源沒寫的標「待確認」，不要自行補成需求。寫完停下等我。

Addy Osmani〈How to write a good spec for AI agents〉（2026-01）建議：先寫精簡的高層規格，再請 AI 擴寫成詳細計畫；而且一次只交一個聚焦的任務，不要把所有事情塞進一段提示詞。Claude Code 官方文件也建議，大功能先請 Agent 訪談你、寫成規格，再開始實作。

讓 Agent 一次問一個問題，是因為它擅長找缺口，你只要回答，不必自己想到每一件事。最常見的問題是 Agent 會「熱心補需求」，例如自己加上登入或會員功能。審規格時最重要的事，就是把來源沒寫的東西刪掉，或標成待確認由你決定。

**人工確認**：規格裡每個「待確認」都由你決定；沒有出現來源以外的功能（例如登入、會員）。

## 9. 案例：每一步都有自動驗證

Airbnb 用大型語言模型把近 3,500 個前端測試檔換到新的測試框架；原估 1.5 年，6 週完成。

- **做法**：逐檔、分步驟；每一步都跑驗證，失敗就把錯誤帶回去重試。

- **結果**：4 小時自動完成 75%；調整 4 天後 97%；剩 3% 人工約一週。

- **關鍵**：不是一次生成全部，而是「小步＋檢查＋重試」的迴圈。

- **📖 延伸閱讀**：〈Accelerating Large-Scale Test Migration with LLMs〉（Airbnb Tech Blog）

這是 Charles Covey-Brandt 在 Airbnb 技術部落格公開的案例（原頁面沒有標示發布日期）。近 3,500 個 React 前端測試檔要換到新的測試框架，原本估計要 1.5 年。做法是逐檔、分步驟處理，每一步都跑驗證，失敗就把錯誤訊息帶回去重試。

結果：4 小時內自動完成 75%，調整提示詞與脈絡 4 天後達到 97%，剩下 3% 由人工處理約一週，總共 6 週完成。值得帶走的不是「6 週」，而是方法：能放大規模，是因為每一步都有自動驗證。這是公司自己公布的成果，換到你的專案不一定有一樣的比例。

**人工確認**：說出這個案例裡的「檢查」是什麼，以及沒有它時會發生什麼。

## 10. 新概念：脈絡工程

Context engineering（脈絡工程）：提供讓任務「有可能被解出來」的全部資訊。重點從「怎麼問」移到「給它看什麼」。

- **要給**：目標與完成標準、指名要讀的檔、限制與範圍外、一段真實範例、怎麼驗證。

- **不要給**：整個資料夾、不相關的舊對話；多不等於好，雜訊會蓋過重點。

- **經驗法則**：一段真實範例，勝過三段文字描述。

- **📖 延伸閱讀**：〈Context engineering〉（Simon Willison，2025）

Simon Willison〈Context engineering〉（2025-06）引用 Shopify 執行長 Tobi Lütke 的定義：提供讓任務「有可能被模型解出來」的全部脈絡。Thoughtworks 技術雷達第 34 期（2026-04）把脈絡工程列為「建議採用」（Adopt）。

常見的誤解有兩個。一是「提示詞工程過時了」：其實只是用詞轉向，寫清楚的提示詞仍是基本功。二是「給越多越好」：整個資料夾、不相關的舊對話反而會蓋過重點，原因下一場用脈絡視窗說明。GitHub 分析兩千五百多個專案的規則檔後建議：一段真實範例，勝過三段文字描述。

下週怎麼用：交辦前問自己，Agent 不問你，能不能從你給的資料推出「什麼算做完」？推不出來，就補上目標、完成標準、要讀的檔、限制與一段範例。

📖 延伸閱讀：〈Effective context engineering for AI agents〉（Anthropic，2025）；〈How to write a great agents.md: Lessons from over 2,500 repositories〉（GitHub，2025）

**人工確認**：交辦前檢查：Agent 不問你，能從你給的資料推出「什麼算做完」嗎？

## 11. 技巧：工作規則是每次都要的脈絡

每一步都會用到的要求（流程、邊界、回報格式）先講一次；之後每段提示詞就能短。

- **流程**：改之前先提計畫；只做核准的步驟，做完就停。

- **邊界**：照分層放規則；不新增套件；不刪測試，不用跳過藏失敗。

- **回報**：固定格式的驗收對照表與審查答案；沒執行的標「未驗證」。

- **注意**：規則只能提醒；一定要發生的事，交給 hook 或權限把關。

工作規則是把每一步都會用到的要求（流程、邊界、回報格式）先講一次，之後每段提示詞就能很短。剛才 Greenfield 檢查點 1 貼的 7 條規則就是這樣：做完一步就停、照分層放規則、不刪測試、固定格式回報。

要知道它的限制：規則是給 Agent 的脈絡，只能提醒，不能強制，Agent 可能漏做。Anthropic〈The AI-native SDLC playbook〉說得很直接：Skill 是建議性的控制，hook（在固定時機一定會自動執行的檢查）才是背後確定會發生的那一層。一定要發生的事（例如不得刪測試），要靠 hook、測試、持續整合（CI：成員頻繁把變更合併回共用的程式碼，每次合併都自動建置與測試）或權限把關，這是第四場的主題。另外，開新對話時，貼過的規則不會自動帶過去；寫成每次自動讀的規則檔，是第二場的內容。

📖 延伸閱讀：〈Adding repository custom instructions for GitHub Copilot〉（GitHub，官方文件）；〈The AI-native SDLC playbook〉（Anthropic，2026）；〈Automate actions with hooks〉（Anthropic，官方文件）

**人工確認**：Agent 每做完一步真的停下；每次回報都附上驗收對照表與審查答案。

## 12. 技巧：五段式提示詞

Agent 能推測意圖，但不會讀心。五段寫齊，它就不必自己猜。

- **模糊 vs 指名**：「修好訂票」→「AC-G-008 座位不足時不應建立訂票，請讓它通過」。

- **缺一塊會怎樣**：沒寫停止條件，Agent 寫完計畫可能直接動手改程式。

```text
【目標】先不要修改程式，提出 4 步實作計畫
【背景／要讀的檔】只讀需求、驗收條件、README、docs/
【限制】固定 4 步；不放範圍外項目；付款失敗照我定的處理
【輸出格式】寫進 notes/greenfield.md「計畫」：每步列規則與檔案
【停止條件】寫完就停下等我
```

Claude Code 官方文件的說法是：Agent 能推測意圖，但不會讀心。它建議提示詞指名檔案、情境與「什麼算修好」；模糊的提示詞會讓 Agent 掃過大量檔案，又慢又容易偏。

五段各擋掉一種常見問題：少了【背景／要讀的檔】，Agent 會讀整個資料夾或憑印象；少了【限制】，它會擴大範圍、自己假設沒講清楚的處理方式；少了【停止條件】，寫完計畫可能直接動手改程式。下週每次交辦前，對照五段檢查一次；寫不出來的那一段，通常就是你自己還沒想清楚的地方。

📖 延伸閱讀：〈Prompting best practices〉（Anthropic，官方文件）；〈Prompt engineering〉（OpenAI，官方文件）

**人工確認**：提示詞指名了檔案、情境和「什麼算修好」；決策點用短回覆：「同意」「選 B」。

## 13. 技巧：先探索、再計畫、再實作

先讓 Agent 讀懂現況、提出計畫，你核准後才動手；錯在計畫上，比錯在程式上便宜得多。

探索：只讀不改 → 計畫：每步對應驗收條件 → 人核准 → 實作與驗證 → 存一版

- **經驗法則**：一句話講得完的改動，不用寫計畫；說不清楚的，一定要先計畫。

- **📖 延伸閱讀**：〈Vibe engineering〉（Simon Willison，2025）

### 交給 Agent 的指令

先不要修改任何檔案。請先讀需求與相關檔案，再提出實作計畫：每一步寫要改哪些檔案、對應哪條驗收條件、用什麼檢查證明完成。如果這個改動一句話就說得完，直接告訴我不需要計畫。寫完停下等我核准。

Claude Code 官方文件建議四步：探索、計畫、實作、存一版；並說「如果一句話就能描述這次改動，就跳過計畫」。Simon Willison〈Vibe engineering〉（2025-10）也說，先有高層計畫再動手，結果好得多。

先計畫的理由是成本：計畫錯了，改幾行字；程式改錯了，要找出來、還原、再重做。很多工具有「只規劃、不修改」的模式，但不是必要；在提示詞寫「先不要修改任何檔案」就做得到。審計畫時看三件事：每一步有沒有對應的驗收條件、有沒有說用什麼檢查證明完成、有沒有範圍外的項目。

**人工確認**：計畫每一步都有檔案、驗收條件與檢查；沒有範圍外的項目才核准。

## 14. 小步驗證：錯了只退一小步

一次只放行一小段；每段都有檢查和存檔點，錯了只退回上一段。大型專案也是這樣做的。

核准計畫 → 做第 1、2 步 → 審查後放行 → 做第 3、4 步 → 審查後放行

- **案例：先試 6 個檔**：一次大型遷移先只轉 6 個檔，抓到 2 個規則問題，才擴大到 1,448 個檔。

- **案例：測試當裁判**：近百萬行的程式換語言，既有測試全部通過才合併。

- **放行前三問**：改的檔案都在計畫裡？測試數沒變少？沒改既有期待值？

- **📖 延伸閱讀**：〈How Anthropic runs large-scale code migrations with Claude Code〉（Anthropic，2026）

Anthropic〈How Anthropic runs large-scale code migrations with Claude Code〉（2026-07）公開了兩次大型改寫：Bun 從 Zig 改成 Rust，約百萬行、兩週內完成；另一次 Python 改成 TypeScript，約 16.5 萬行、一個週末。做法是先只轉 6 個檔試水溫，抓到 2 個規則問題才擴大到 1,448 個檔；既有測試在持續整合裡 100% 通過才合併，合併後發現的 19 個回歸問題也全數修好。這是廠商自家的案例，數字由他們公布。

小步的價值在於退回的成本只有一段。Google Cloud 發布的 DORA 研究也把「小批量工作」列為放大 AI 效益的能力之一。下週怎麼用：Agent 一口氣做了好幾步時，請它停下來，補上每一步的回報，再一段一段放行；每次放行前問三題：改的檔案都在計畫裡嗎？測試數沒變少嗎？沒改既有期待值嗎？

**人工確認**：說得出你哪一次差點放行了不該放行的變更，靠什麼發現的。

## 15. 技巧：結構化輸出

Structured Output（結構化輸出）：要求 Agent 照固定欄位回報，人才看得快、能前後比對，也能交給下一個工具處理。

- **人看什麼**：每條驗收條件都有一列；「未驗證」不等於「通過」；跳過數沒有增加。

- **業界評價**：固定格式輸出被列為「建議採用」：可比對、可自動檢查。

```text
編號     | 白話內容           | 結果   | 依據的測試名稱
AC-G-005 | 成人＋學生總價1225 | 通過   | 混合訂票測試
AC-G-014 | 付款失敗不建立訂單 | 未驗證 | （尚無）
通過 6／失敗 0／跳過 3（示意，非實際輸出）
```

固定欄位有三個好處：人一眼就找到要看的那一格；前後兩次回報可以直接比對；下一個工具也能自動處理。Thoughtworks 技術雷達第 34 期（2026-04）把「從大型語言模型取得結構化輸出」列為建議採用。

本課程的結構化輸出，指的是用提示詞要求固定欄位或標題；有些 API（應用程式介面）提供的結構化輸出功能，則是用結構定義強制格式，目的相同。用提示詞要求時，Agent 仍可能漏列或漏欄，所以第一件事是檢查有沒有漏；第二件事是記得「未驗證」不等於「通過」。下週怎麼用：任何要比對的回報（測試結果、方案比較、風險清單），先定好欄位再請 Agent 填。

📖 延伸閱讀：〈Structured outputs〉（Anthropic，官方文件）；〈Structured model outputs〉（OpenAI，官方文件）；〈Technology Radar Vol. 34〉（Thoughtworks，2026）

**人工確認**：對照表沒有漏列、漏欄；結果和你從規則推出的預期值一致。

## 16. 審查變更：看證據，不看宣稱

不讀程式也能審：要求 Agent 拿出執行結果當證據，再親眼看一次真實行為。

- **要證據**：「測試全過」要附實際執行的結果；沒執行的標「未驗證」。

- **看範圍**：有沒有計畫外的檔案、刪測試、新增跳過、改期待值。

- **親眼看**：沒看過它做對，就當它還沒做好；你在 /docs 試的就是這一步。

- **📖 延伸閱讀**：〈Your job is to deliver code you have proven to work〉（Simon Willison，2025）

### 交給 Agent 的指令

請審查剛才的變更，先不要修改任何檔案。用證據回答：改了哪些檔案、有沒有超出計畫；實際執行了哪些檢查、結果是什麼；有沒有刪測試、新增跳過或改期待值；最後列出你沒有驗證的部分。只回報事實，不要宣稱完成。

Claude Code 官方文件建議：要 Agent 拿出證據，而不是宣稱成功；也建議用另一個乾淨的對話來審查。但它同時提醒，被要求找問題的審查者，即使成品沒問題，通常也會報出一些，所以審查結果也要你判斷。Simon Willison（2025-12）說得更直接：沒親眼看過程式做對，就當它還沒做好。

要誠實面對盲點：只看證據、不看程式，抓不到「測試全過但寫法有問題」的情況。所以 Greenfield 的工作規則把分層寫進去，並禁止刪改測試。下週怎麼用：Agent 說「完成了」時，先貼上方的審查提示詞，再挑一個最重要的行為親自試一次。

📖 延伸閱讀：〈Best practices for Claude Code〉（Anthropic，官方文件）

**人工確認**：每個「通過」都附了實際執行的結果；你親自試過至少一個關鍵行為。

## 17. 案例：大規模使用的共同點

近一年的公開案例，Agent 每週產出成百上千個變更；共同點不是模型更聰明，而是驗證與人審。

- **Stripe**：隔離環境、大量自動測試，產出全部經人審查。

- **Spotify**：背景 Agent 改完仍跑格式與靜態檢查，人審後才合併。

- **數字與細節**：Spotify 在 Speech 03，Stripe 與 GitHub 在 Speech 04 詳談。

這頁只看共同點，數字留到後面兩場：Spotify 的背景 Agent 在第三場，Stripe 與 GitHub 在第四場。要記住的只有一句：規模能放大，前提是每個變更都過自動檢查與人審。

這些看起來像 Digital Worker 的大場面，地基就是今天 Tool 階段練的三件事：先給檢查、小步放行、看證據審查。少了這些，產出越多，風險只會越大。

**人工確認**：說得出這些案例共同的「檢查」與「人審」在哪裡，對應你今天練的哪一步。

## 18. 平衡提醒：差一點就對，最花時間

開發者普遍在用 AI，但信任度不高；AI 會放大團隊原有的長處，也會放大短處。

- **差一點就對**：66% 開發者最大的挫折是 AI 的答案「差一點就對」；只有 33% 信任其準確度。

- **放大器**：DORA：90% 在工作中用 AI；採用與交付量正相關，但與交付穩定度仍負相關。

- **所以**：檢查、小步、審查不是多餘的手續，是讓速度不變成風險的方法。

- **📖 延伸閱讀**：〈2025 Developer Survey — AI〉（Stack Overflow，2025）；〈Announcing the 2025 DORA Report〉（Google Cloud，2025）

Stack Overflow 2025 年開發者調查：84% 使用或打算使用 AI 工具，但只有 33% 信任它的準確度、46% 不信任；66% 說最大的挫折是答案「差一點就對」；45.2% 認為除錯 AI 產生的程式碼更花時間。當年在工作中使用 AI Agent 的約 31%；到 2026 年的調查，用 AI 的開發者已有 66% 用 Coding Agent，第五場再談。

Google Cloud 公布的 DORA 2025 報告（2025-09）：90% 受訪者在工作中使用 AI，超過 80% 認為生產力提升，但 30% 幾乎或完全不信任 AI 產生的程式碼；AI 採用與交付量正相關，與交付穩定度卻仍是負相關。原文的結論是：AI 不會修好一個團隊，只會放大原本就有的東西。

兩個常見的誤讀：「90% 用 AI」不等於「90% 用 Agent」；任何單一的「快了幾 %」也不能當通則。差一點就對的結果最危險，因為它看起來像完成，這正是檢查、小步與審查要擋的東西。

**人工確認**：你的團隊有哪一項基本功（測試、小批量、版本控制）還不夠，會被 AI 放大？

## 19. 把決定寫進檔案，不留在對話裡

計畫、核准、每步驗收與交付摘要，都請 Agent 寫進 notes/greenfield.md；你不用抄。

- **為什麼寫下來**：對話會結束，檔案會留下；下一個人或下一段對話照著讀就能接手。

- **如實交付**：未完成項目與「未驗證」照實列出，不把部分完成寫成完整交付。

對話會結束，檔案會留下。計畫、核准、每步驗收和交付摘要寫進 notes/，下一個人或下一段對話照著讀就能接手，不必重猜當時為什麼這樣決定。核准紀錄就是一種決策紀錄；Michael Nygard 提出的架構決策紀錄（ADR）也是同一個想法：寫下決定與理由。

交付摘要有七項：完成的功能與對應規則、驗收條件；修改的檔案；最後一次測試指令與總數；文件更新；未完成項目、仍被跳過的測試與風險；人和 Agent 各做了什麼；人工驗證。最容易被省略的是「未完成」與「未驗證」，偏偏這兩項是下一個人最需要的。

Nygard 原文的 ADR 是一份短文字檔，只記一個重要決定，分五段：標題、背景（當時有哪些考量）、決定（我們要怎麼做）、狀態（提議中、已接受，或已被新決定取代）、後果（包含壞處）。下週可以請 Agent 把一個已核准的決定照這五段寫進 notes/；寫不出「後果」那段，通常代表取捨還沒想清楚。

📖 延伸閱讀：〈Documenting Architecture Decisions〉（Michael Nygard，2011）

**人工確認**：交付摘要如實列出未完成項目與「未驗證」，沒有把部分完成寫成完整交付。

## 20. 討論：交辦前的五個問題

兩人一組，各挑一件自己工作上想交給 Agent 的事，互相問這五題；答不出來的，就是要先補的地方。

檢查：怎麼證明完成？ → 規格：驗收條件可判定嗎？ → 脈絡：要讀哪些檔？ → 計畫：一句話講得完嗎？ → 審查：要看什麼證據？

- **答不出「檢查」**：先請 Agent 盤點現有檢查（第 4 頁的提示詞）。

- **答不出「驗收條件」**：先請 Agent 訪談你、寫短規格（第 8 頁的提示詞）。

五個問題各對應今天的一個做法：檢查（第 4 頁）、可判定的驗收條件（第 5 頁）、脈絡（第 10 頁）、先計畫（第 13 頁）、看證據審查（第 16 頁）。它們都不綁特定工具，換任何 Coding Agent 都適用。

答不出來不是壞事，它告訴你交辦前要先補什麼。下週挑一件真實工作先問這五題；答不出的那一題，就變成你給 Agent 的第一個任務，例如先盤點檢查，或先訪談你、寫一份短規格。

**人工確認**：每人說出一題自己答不出來的，以及下一步要請 Agent 先做什麼。

## 21. 下一場：Time Skip（時間快轉）

今天讓新專案順利；接下來專案長大、換了對話，要怎麼接得上？

- **今天帶走**：先給檢查、可判定的驗收條件、脈絡、先計畫、小步驗證、結構化輸出、看證據審查。

- **Speech 02 會談**：對話越長為什麼越不準、怎麼開新對話，用交接檔接手長大的系統。

**人工確認**：說出一項回到工作時，你最想先寫成文件或規則交給 Agent 的事。

## 完成條件
說得出 Agent 怎麼知道做對了（先給檢查、可判定的驗收條件）、怎麼知道要做什麼（規格、脈絡、工作規則、五段式提示詞）、人怎麼確認（先計畫、小步驗證、結構化輸出、看證據審查），以及大規模案例的共同點；交辦自己的工作前問得出五個問題。

**下週可以做的事**

- 挑一個專案，請 Agent 盤點現有檢查與沒被檢查到的需求（第 4 頁的提示詞）
- 交辦一件工作前，先寫下完成時要看到的數字或畫面
- 用交辦前的五個問題檢查一次，答不出的那題先補

| 結構化輸出（Structured Output） | 本課程指用提示詞要求固定欄位或標題回報；API 的同名功能則用 JSON 結構定義強制格式。 | Anthropic〈Structured outputs〉 |
| hook | 在固定時機（例如執行工具前、改檔後）自動執行的處理程式；和規則檔不同，它一定會執行。 | Claude Code 官方文件〈Glossary〉；Anthropic〈The AI-native SDLC playbook〉 |
| 持續整合（CI，Continuous Integration） | 團隊成員頻繁（至少每天）把變更合併回共用的程式碼，每次合併都由自動建置與測試驗證。 | Martin Fowler〈Continuous Integration〉 |
| PR（Pull Request） | 把一組程式變更提議合併進專案；合併前讓別人討論與審查。 | GitHub 官方文件〈Pull requests〉 |
| ADR（Architecture Decision Record，架構決策紀錄） | 一份短文字檔，只記一個重要的架構決定：背景、決定、狀態與後果。 | Michael Nygard〈Documenting Architecture Decisions〉 |
| DORA | DevOps Research and Assessment：Google Cloud 旗下的軟體交付研究計畫，每年發布報告。 | Google Cloud〈Announcing the 2025 DORA Report〉 |
