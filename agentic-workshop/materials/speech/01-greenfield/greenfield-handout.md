# Greenfield：從 Idea 到可開發的專案

> 讀者：學員。時機：主課 Greenfield 之後的 45 分鐘講解。前置：已體驗 Greenfield。

本場講概念與技巧，不需要寫程式或打指令。頁面上的提示詞是示範，想試再貼給自己的 Agent；沒有實際執行的結果，一律視為未驗證。

## 1. 從 Idea 到可開發的專案

Greenfield（從頭開始的新專案）為什麼順利？先看事先準備了什麼，再看你怎麼一步步帶 Agent（能讀寫檔案、協助寫程式的 AI 助手）。

- **前半：準備工作鏈**：從構想、驗收條件到測試情境與分層架構，每一環人要判斷什麼。

- **後半：Tool（人逐步下指令）階段的技巧**：工作規則、五段式提示詞、驗收對照表、變更審查與 notes/ 紀錄。

**人工確認**：說得出剛才 Greenfield 哪一步最順、哪一步卡住。

## 2. 剛才的順利，哪些來自事先準備？

G0（Greenfield 起始程式包）不是空的：需求、驗收條件與骨架都先備好了。

- **需求先寫清楚**：四個 API（應用程式介面）、16 條商業規則、15 項驗收條件，範圍先限定。

- **骨架先搭好**：分層目錄與測試骨架已在，留 11 個 TODO（待完成標記）；起始 1 個通過、8 個跳過。

### 交給 Agent 的指令

先不要修改任何檔案。請閱讀這個專案的 README、docs/ 與上一層的需求文件，用白話列出：已準備好的需求、規則、架構與驗證方式各在哪個檔案、消除了什麼不確定性；最後列出仍需要我決定的事，然後停下。

**人工確認**：指出一項準備和它所在的檔案，說明它讓你少猜了什麼。

## 3. Tool：人一步一步介入

Tool（工具）→ Teammate（隊友）→ Digital Worker（數位員工）差在人怎麼介入，不是人寫多少程式。

Tool：逐步下指令、每步驗收 → Teammate：核准計畫後才動手 → Digital Worker：只在核准關卡決定

- **剛才的 Greenfield 是 Tool**：步驟由你定；Agent 做完一步就停，你看證據才放行下一步。

**人工確認**：說出 Greenfield 中你「放行」了幾次，每次看了什麼證據。

## 4. 讓 Greenfield 順利的準備工作鏈

每一環都從上一環推出來；新專案沒有這些文件時，就請 Agent 一環一環補上。

構想（Idea）放入 docs 資料夾 → 最小可行產品（MVP）範圍 → 使用者故事／使用案例 → 驗收條件 → 業務流程 → Gherkin 測試情境 → 分層架構

- **一次只往前一步**：Agent 讀來源、提草稿；人確認後才存檔，再往下一環。

- **可以往回修**：下一環暴露問題，就回頭補前一環，並寫下理由。

**人工確認**：每份文件都沿用同一套規則編號與驗收條件編號；Agent 補的假設先標「待確認」。

## 5. 構想放入 docs：來源與假設分開

構想文件寫下問題、使用者、核心流程與規則；哪份來源算數，由人決定。

- **Agent 做**：整理成專案摘要，每項結論標出來源。

- **人判斷**：來源沒寫的就是假設：保留待確認，或補成規則，由你決定。

### 交給 Agent 的指令

請閱讀 docs/idea.md，先不要寫程式。整理問題、使用者、核心流程、已明定的規則與限制，寫入 docs/01-project-brief.md。每項結論標示來源；來源沒提到的列為待確認問題，不要自行補成需求。完成後停下等我。

**人工確認**：在摘要裡至少找出一個假設或缺口，並決定保留待確認還是補成規則。

## 6. MVP：最少功能走完核心流程

MVP（Minimum Viable Product，最小可行產品）：用最少功能做出能實際使用的版本，盡快驗證想法。本課程的範圍＝查班次→訂票→模擬付款→查訂單。

- **範圍內**：四個 API；計畫固定 4 步：票價、班次查詢、建立訂票、付款與查詢訂單。

- **範圍外**：前端、登入、會員、優惠、改退票、新套件。

**人工確認**：計畫裡沒有範圍外項目；每一步完成後都有能驗證的成果。

## 7. 使用者故事與使用案例

先說清楚使用者要什麼，再安排實作；技術工作不必硬寫成使用者需求。

- **使用者故事（User Story）**：誰、想做什麼、為了什麼：旅客替同行成人與學生一次訂票，各付正確票價。

- **使用案例（Use Case）**：一步步的互動與例外：人數不合法、班次不存在、座位不足。

**人工確認**：故事寫出價值，使用案例寫出例外；兩者擇一即可，不必兩份都做。

## 8. 驗收條件：把「正確」寫成可判定

AC（Acceptance Criteria，驗收條件）：事先寫好、能明確判定符合或不符合的完成標準。

- **好的寫法**：AC-G-005：成人＋學生訂 T001，總價 1225 且為整數。

- **不好的寫法**：「計價正常」「錯誤處理完善」：無法判定通過與否。

- **預期值從規則來**：成人 700＋學生 75%（FARE-002）：看 Agent 回報前就定好。

### 交給 Agent 的指令

請依 docs/idea.md 與專案摘要寫 docs/04-acceptance.md：沿用 AC-G 編號與規則編號，每列寫前置、操作、可觀察的結果。不要新增來源沒有的錯誤碼，缺口列為待確認，寫完停下等我。

**人工確認**：每一條都能判斷「符合／不符合」；預期數字能指回一條規則編號。

## 9. 業務流程：成功和失敗都要有出口

業務流程（Business Flow）把功能串成狀態與資料的變化。

查詢可售班次 → 驗證人數與座位 → 逐人計價 → 建立待付款訂票、保留座位 → 模擬付款成功 → 建立唯一訂單

- **訂票被拒**：不建立訂票、不扣座位。

- **付款失敗**：不建立訂單；維持待付款，座位不釋放，之後可再付款。

**人工確認**：付款前不會有訂單；付款成功只會有一筆訂單；失敗不會被標成已付款。

## 10. 討論：用流程反查驗收條件

兩人一組：一人說明流程，另一人只追問狀態與證據。

- **追問一**：付款成功後又收到一次付款，會不會多一筆訂單？

- **追問二**：票價算好了但座位不足，會不會留下半筆訂票？

- **追問三**：付款失敗時，訂票、訂單、座位各是什麼狀態？

**人工確認**：流程與驗收條件說法一致；答不出來的分支記為待確認，不讓 Agent 自己決定。

## 11. Gherkin：讓測試情境像業務範例

Gherkin 用 Given（前提）／When（操作）／Then（結果）寫情境，業務與開發都讀得懂。

- **人看什麼**：Then 寫看得到的結果；預期數字指得回規則。

- **誰寫測試**：Agent 把情境轉成可執行的測試；你看回報裡的測試名稱。

```text
@AC-G-005 @AC-G-009
Scenario: 成人與學生一起訂票
  Given T001 基本票價 700，剩餘 20 座
  When 為 T001 訂一位成人與一位學生
  Then 總價為 1225 且為整數
  And 訂票為待付款，T001 剩餘 18 座
```

**人工確認**：一個情境只有一個 When；每個 Then 都能在 Agent 的回報裡找到結果。

## 12. 分層架構：規則放在固定位置

分層架構依責任把程式分成幾層；每層只做一類事，規則才找得到、改得動。

API／Schemas（資料格式定義）：輸入與輸出 → Application（應用層）：協調訂票流程 → Domain（領域層）：模型與票價規則 → Infrastructure（基礎設施層）：記憶體資料、模擬付款

- **人不讀程式也能管**：把分層寫進工作規則：商業規則放領域層與應用層，API 入口只做輸入輸出。

**人工確認**：Agent 回報的修改檔案，和這一步該動的那一層對得上。

## 13. 技巧：先給 Agent 一份工作規則

規則先講好，之後每一步就不用再叮嚀「先計畫」「做完停下」「附測試結果」。

- **流程**：改之前先提計畫；只做核准的步驟，做完就停。

- **邊界**：照分層放規則；不新增套件；不刪測試，不用跳過（skip）藏失敗。

- **回報**：固定格式的驗收對照表與四題審查；沒執行的標「未驗證」。

**人工確認**：Agent 每做完一步真的停下；每次回報都附上驗收對照表與審查答案。

## 14. 技巧：五段式提示詞

好的提示詞有五個部分；缺任何一塊，Agent 就會自己猜。

- **缺一塊會怎樣**：沒寫停止條件，Agent 寫完計畫可能直接動手改程式。

```text
【目標】先不要修改程式，提出 4 步實作計畫
【背景／要讀的檔】只讀需求、驗收條件、README、docs/
【限制】固定 4 步；不放範圍外項目；付款失敗照我定的處理
【輸出格式】寫進 notes/greenfield.md「計畫」：每步列規則與檔案
【停止條件】寫完就停下等我
```

**人工確認**：計畫每一步都有規則編號、驗收條件與預計修改的檔案；每個問題都附建議答案。

## 15. 小步放行：錯了只退一小步

核准計畫後，一次只放行一小段；Agent 停下，你看證據再放行下一段。

核准計畫 → 做第 1、2 步 → 審查後放行 → 做第 3、4 步 → 審查後放行 → 親自試用並交付

- **放行前判斷三件事**：改的檔案都在計畫裡；測試數沒變少、沒新增跳過；沒改既有期待值。

**人工確認**：說得出你哪一次差點放行了不該放行的變更，靠什麼發現的。

## 16. 技巧：驗收對照表

結構化輸出（Structured Output）：用提示詞要求 Agent 照固定欄位回報，人才看得快、能前後比對。

- **人看什麼**：每條驗收條件都有一列；「未驗證」不等於「通過」；跳過數沒有增加。

```text
編號     | 白話內容           | 結果   | 依據的測試名稱
AC-G-005 | 成人＋學生總價1225 | 通過   | 混合訂票測試
AC-G-014 | 付款失敗不建立訂單 | 未驗證 | （尚無）
通過 6／失敗 0／跳過 3（示意，非實際輸出）
```

**人工確認**：對照表沒有漏列、漏欄；結果和你從規則推出的預期值一致。

## 17. 變更審查：不讀程式也能判斷

Agent 用白話回答四題固定問題，最後建議放不放行；判斷的人是你。

- **改了什麼**：改了哪些檔案、為什麼；有沒有計畫外的檔案。

- **測試有沒有被動手腳**：測試數變少、新增跳過、刪測試或改期待值。

- **換來什麼**：哪些原本跳過的測試變成通過。

**人工確認**：審查答案附了實際執行的指令；答案和驗收對照表的數字對得上。

## 18. 親自試用：在 /docs 看真實行為

/docs 是 Agent 啟動伺服器後提供的 API 試用網頁；你親自試訂票和付款。

按 Try it out → 貼上範例 → 按 Execute → 看狀態碼與內容

- **你判斷**：訂票總價 1225、待付款；付款回傳金額 1225、付款成功。

- **照實回覆**：回 Agent「兩項都一致」或「第 N 項不一致：我看到…」。

**人工確認**：你看到的結果和驗收條件一致；不一致就照實回報，不放行。

## 19. 把決定寫進 notes/

計畫、核准、每步驗收與交付摘要，都請 Agent 寫進 notes/greenfield.md；你不用抄。

- **為什麼寫下來**：對話會結束，檔案會留下；下一個人或下一段對話照著讀就能接手。

```text
notes/greenfield.md
  起點：測試數字、Git 基準
  計畫：4 步與待決問題
  核准紀錄：你的決定與時間
  第 1、2 步／第 3、4 步：對照表、審查答案
  最終驗收、交付摘要（七項）
```

**人工確認**：交付摘要如實列出未完成項目與「未驗證」，沒有把部分完成寫成完整交付。

## 20. 下一場：Time Skip（時間快轉）

準備工作鏈讓新專案順利；接下來專案長大、換了對話，要怎麼接得上？

- **今天帶走**：準備工作鏈；工作規則、五段式提示詞、驗收對照表、變更審查、notes 紀錄。

- **Speech 02 會談**：為什麼換專案要開新對話，怎麼用交接檔接手長大的系統。

**人工確認**：說出一項回到工作時，你最想先寫成文件或規則交給 Agent 的事。

## 完成條件
說得出準備工作鏈每一環人要判斷什麼，以及 Tool 階段五個技巧（工作規則、五段式提示詞、小步放行、驗收對照表、變更審查）為什麼這樣問 Agent；知道決定要請 Agent 寫進 notes/，下一場從接手開始。
