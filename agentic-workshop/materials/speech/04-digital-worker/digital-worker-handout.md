# Digital Worker：工作授權、審查與治理

> 讀者：學員。時機：B3 與交付之後的 45 分鐘概念講解。前置：做過 B3，或手邊有自己的 `notes/b3.md`、`notes/delivery.md` 與 `skills/b3-work-order.md`。

本段講業界怎麼安全地把整件工作交給 Agent：工作單、自主等級、核准關卡、權限與沙箱、防護、評估與治理，附官方說法與真實案例。不寫程式、不打指令。範例提示詞是選用示範，貼給你自己的 Coding Agent，結果由你檢查；沒有實際執行的，一律當作未驗證。

**這一段帶走什麼**

- 工作單是五段式提示詞放大到整件任務
- 自主程度是設計出來的；關卡設在不可逆動作之前
- 最小權限與沙箱；私密資料、不可信內容、對外傳送三缺一
- 禁止事項做在平台上，不只寫在提示詞
- 寫的人不能核准自己：另開只讀的審查對話，依審查準則寫審查紀錄
- 每一步留一個檔案，下一步先讀它；出事時查得到誰核准了什麼

## 1. 把整件工作交給 Agent，要先設計什麼？

第四段 · Digital Worker（數位員工：在核准範圍內獨立完成整件任務的 Agent） · 概念講解

- **今天談的不是 B3 本身**：而是業界怎麼安全地委派：工作單、自主等級、關卡、權限、防護、評估與治理。

- **怎麼聽**：心裡選一件工作上想交給 Agent 的事，每頁都拿它對照。

Digital Worker 是把整件任務交出去，人只在事先設好的關卡做決定。能不能安全交出去，不取決於 Agent 多聰明，而取決於事前的設計：授權範圍、停止條件、關卡、權限與審查方式。這份講義整理業界做法、官方說法與真實事故，不包含 B3 的做法或例外事件內容。

**人工確認**：想好一件你想委派的工作：它做錯了，誰會受影響？

## 2. 剛才你其實做了三件管理者的事

你沒寫程式，但做了委派最難的三件事：事先授權、在關卡決策、憑證據簽收。

寫工作單：一次授權 → 守三道 Gate：需求、設計、交付 → 讀交付摘要：憑證據簽收

- **人負責**：設邊界、核准或退回、要求補證據，承擔最終交付責任。

- **Agent 負責**：分析、設計、改程式、測試、寫紀錄；碰到停止條件就停下來問。

委派最難的三件事和管理者一樣：事前把範圍寫清楚授權出去、在關鍵時刻做決定、最後憑證據簽收。Agent 負責分析、設計、改程式、測試、寫紀錄；人負責設邊界、核准或退回、要求補證據，並承擔最終的交付責任。

回想你在哪一道 Gate 最猶豫：通常不是因為不懂程式，而是缺了某一項證據。接下來每一頁，都在回答真實工作上怎麼把這三件事做得更穩。

**人工確認**：說得出 B3 裡你在哪一道 Gate 最猶豫，以及當時缺什麼證據。

## 3. 從「問 AI」到「交辦給 AI」

問答是一來一回；交辦是 Agent 自己規劃、動手、檢查結果，再決定下一步。

- **整圈交給它**：第一場的迴圈，這次由 Agent 自己跑完，直到完成或卡住。

- **人要先給**：清楚的目標、能自己跑的檢查，以及卡住時停下來問人的規則。

問答是一來一回；交辦是整個「規劃、動手、看結果、決定下一步」的迴圈都由 Agent 自己跑，直到完成或卡住。Anthropic〈Building effective agents〉也說，Agent 可以在檢查點或碰到阻礙時停下來，等人回饋。

所以交辦的品質取決於人事先給了什麼：清楚的目標、Agent 自己能跑的檢查、卡住時停下來問人的規則。少了檢查，它只能憑感覺說完成；少了停止規則，它會自己猜下一步。

📖 延伸閱讀：〈Building effective agents〉（Anthropic，2024）

**人工確認**：你那件工作，有沒有一個 Agent 自己就能跑的檢查（測試、比對、截圖）？

## 4. 好工作單回答五個問題

Work Order（工作單）就是五段式提示詞放大到整件任務；寫不出來的那一段，就是你還沒想清楚的地方。

要做成什麼 → 該讀哪些資料 → 能動與不能動 → 怎麼回報 → 何時停下來問

### 交給 Agent 的指令

先不要修改任何檔案。我想把一件工作交給你：（我會口頭描述）。請先問我問題，再依目標、要讀的資料、允許與禁止的範圍、回報格式、停止與升級條件五段，寫一份工作單草稿。我答不出來的，標「待決定」，不要自己補。寫完停下等我審。

工作單就是第一場的五段式提示詞放大到整件任務：要做成什麼（目標）、該讀哪些資料（背景）、能動與不能動（限制與授權範圍）、怎麼回報（輸出格式）、何時停下來問（停止與升級條件）。寫不出來的那一段，就是你還沒想清楚的地方。

讓 Agent 先訪談你再寫草稿，是第一場「規格從短開始」的加深：從一份規格放大到整件任務的授權。關鍵是答不出來的標「待決定」，不讓 Agent 自己補；開工前把每個待決定都回答完。

**人工確認**：草稿裡標「待決定」的項目，你都能在開工前回答嗎？

## 5. 自主程度是設計出來的，不是能力換來的

同一個強 Agent，可以設成每步都問人，也可以只在關卡問；差別在人扮演什麼角色。

操作者：人下每一步 → 協作者：一起做 → 顧問：Agent 主導、人給意見 → 核准者：人只在關鍵點核准 → 觀察者：人只看紀錄

Feng、McDonald、Zhang 的論文〈Levels of Autonomy for AI Agents〉（arXiv，2025）以「人扮演的角色」分五級：操作者、協作者、顧問、核准者、觀察者。大致對照工作坊：Tool 接近操作者，Teammate 接近協作者與顧問，Digital Worker 接近核准者。

論文的重點是：自主程度是設計選擇，能力強不代表就該放手。要不要升一級，問三個問題：做錯的代價多大？能不能復原？有沒有 Agent 自己能跑的檢查？有一題答不好，就先停在目前這一級。

📖 延伸閱讀：〈Levels of Autonomy for AI Agents〉（Feng 等，2025）

**人工確認**：你那件工作，現在適合人當哪一種角色？為什麼不是下一級？

## 6. 有效監督：不是每步都按核准

監督的重點是關鍵時刻能踩煞車，而不是盯著每一步。（Anthropic，2026-02）

- **新手**：約 20% 的工作階段開啟全自動核准。

- **熟手（750 次以上）**：超過 40% 開啟全自動核准，但中途打斷的比例從約 5% 升到約 9%。

- **真正難回頭的動作**：只占約 0.8%；關卡要設在這裡。

Anthropic〈Measuring AI agent autonomy in practice〉（2026-02）分析自家產品的實際使用紀錄：使用不到 50 次的新手，約 20% 的工作階段開啟全自動核准；用到 750 次以上的熟手超過 40%，但中途打斷的比例也從約 5% 升到約 9%。最長的連續工作時間，三個月內從 25 分鐘以下增加到 45 分鐘以上；看起來不可逆的動作只占約 0.8%。

解讀：熟手不是不監督，而是從「每步按核准」變成「看到不對就踩煞車」。原文說，有效的監督不需要核准每個動作，而是在重要時刻能介入。限制：這是單一廠商自家產品的資料，不一定適用你的環境。

📖 延伸閱讀：〈Measuring AI agent autonomy in practice〉（Anthropic，2026）

**人工確認**：你那件工作裡，哪一個動作做了就很難回頭？那裡就該設關卡。

## 7. 關卡要設在哪裡？

Human-in-the-loop（人在迴圈中）不是到處設關卡，而是設在「錯了代價最大」的前一刻。

- **需求確認之後**：Agent 懂的要什麼、為什麼、限制，和你要的一樣。

- **動手修改之前**：核准要改哪些地方、怎麼測，這就是授權邊界。

- **上線放行之前**：Agent 最多做到上線前；刪資料、付款、對外寄送也先問人。

關卡設在三種地方：需求確認之後（Agent 懂的「要什麼、為什麼、限制」和你要的一樣）；動手修改之前（核准要改哪些地方、怎麼測，也就是授權邊界）；上線放行之前。Anthropic〈The AI-native SDLC playbook〉把最後一道說得很清楚：Agent 可以一路做到上線關卡前，但不能自己通過；正式上線要等指名的負責人放行。刪資料、付款、對外寄送這類不可逆動作也一樣。資安社群 OWASP 的〈LLM06:2025 Excessive Agency〉也把「高影響動作要人核准」列為緩解方法。

關卡的力度也看風險。Claude Code 團隊公開的審查做法（2026-10）依變更本身的風險分級：低風險變更在自動檢查都通過後不需要人核准，一般變更一人審，最高風險兩人審；原文說，修文件和改自動更新程式的風險不同，審法也該不同。限制：這是單一廠商自家的做法。

📖 延伸閱讀：〈The AI-native SDLC playbook〉（Anthropic，2026）；〈How the Claude Code team does code review〉（Anthropic，2026）

**人工確認**：每一道關卡，你都說得出要看哪一項證據才放行嗎？

## 8. 問太多次，人就開始亂按

Approval fatigue（核准疲勞）：關卡太多，核准就變成反射動作，等於沒有關卡。

- **官方提醒**：按到第十次核准，你已經不是在審查，只是在點過去。

- **解法**：用權限和隔離環境圈好邊界，邊界內不必問；只把真正的決策留給人。

核准疲勞是真的：Claude Code 官方文件說，按到第十次核准，你已經不是在審查，只是在點過去。關卡一多，核准就變成反射動作，等於沒有關卡。

解法不是少審，而是把邊界做在環境上。Anthropic（2025-10）的沙箱文章說，用檔案系統與網路兩道隔離後，權限詢問減少 84%。邊界內的事不必問，只把真正的決策留給人；B3 只設三道 Gate、每道 1–3 分鐘，就是這個設計。

這句話說的是「每個動作都要人按核准」的模式。現在有些工具改用另一個模型（分類器）先審查每個動作，只擋下或詢問看起來有風險的，例如 2026 年 Claude Code 在多數互動情境的預設模式。這減少了詢問，但審查的仍是模型，不是你；不可逆、高影響的動作，還是要在工作單裡寫成必須停下來問人的關卡。

📖 延伸閱讀：〈Beyond permission prompts: making Claude Code more secure and autonomous〉（Anthropic，2025）；〈Best practices for Claude Code〉（Anthropic，官方文件）

**人工確認**：你的關卡，每一道都有人真的會停下來看嗎？

## 9. 最小權限：門禁卡只開要去的樓層

OWASP 把「Agent 權力過大」列為十大風險之一，根因有三個「給太多」。

- **功能給太多**：任務只要讀，卻給了能刪、能寄信的工具。

- **權限給太多**：用管理員帳號跑，碰得到正式資料。

- **自主給太多**：高影響動作不用人核准就能做。

OWASP〈LLM06:2025 Excessive Agency〉列出 Agent 權力過大的三個根因：功能給太多、權限給太多、自主給太多。緩解方法是最小權限、高影響動作要人核准，而且授權檢查要做在下游系統，不交給模型自己判斷。白話說，給權限像給門禁卡：只開要去的樓層。

OWASP 也在 2025-12 發布了專談 Agent 應用風險的十大風險清單。下週替你的工作列出 Agent 真正需要的權限，每多一項都要說得出理由。

美國國家標準技術研究院（NIST）的資安詞彙表把最小權限定義為：把使用者，或代表使用者執行的程式，所能取得的存取權限限制在完成指派工作所需的最小範圍。Agent 就是代表你執行的程式，所以同一條原則直接適用。

📖 延伸閱讀：〈LLM06:2025 Excessive Agency〉（OWASP，2025）；〈Glossary〉（NIST CSRC，least privilege 條目）

**人工確認**：列出你那件工作 Agent 真正需要的權限，多一項都要說得出理由。

## 10. 沙箱：先圍好場地，再放手

Sandbox（沙箱：隔離的執行環境）讓 Agent 在邊界內自由動手，邊界外什麼都碰不到。

- **兩道邊界**：檔案只能動指定資料夾；網路只能連指定位置。

- **平台做法**：Agent 只推到自己的分支，不能核准或合併自己的變更。

### 交給 Agent 的指令

先不要修改任何檔案。請依我們的工作單，列出這件工作需要的權限：要讀與要改的資料夾、要執行的檢查、是否需要網路、是否碰到正式資料。每一項附理由；不需要的明寫「不需要」。最後列出你建議由人核准的動作，然後停下。

沙箱就是先圍好場地：檔案只能動指定的資料夾，網路只能連指定的位置。邊界外什麼都碰不到，邊界內就可以放手，不必逐步問人。

GitHub 官方文件說明它的雲端 Coding Agent 怎麼把護欄做在平台上：在暫時性的雲端環境工作，只能推到自己的分支，不能把自己的變更標成可審查，也不能核准或合併；人審查之前，持續整合（CI）的檢查流程也不會執行。下週可以貼上方的提示詞，請 Agent 依工作單列出需要的權限，再把「碰到正式資料」和「對外傳送」拿掉或加上關卡。

📖 延伸閱讀：〈Risks and mitigations for GitHub Copilot cloud agent〉（GitHub，官方文件）；〈Beyond permission prompts: making Claude Code more secure and autonomous〉（Anthropic，2025）

**人工確認**：清單裡有沒有「碰到正式資料」或「對外傳送」？有的話先拿掉或加關卡。

## 11. 事故一：「凍結」只寫在對話裡

2025 年 7 月，一位創業者測試 Replit 的 Agent，在凍結期間正式資料庫被刪。

- **發生什麼**：Agent 無視「程式與動作凍結」執行未授權指令，刪掉 1,200 多位主管、1,190 多家公司的資料。

- **事後補強**：廠商加上開發與正式資料庫自動分離、只規劃不執行的模式。

- **教訓**：禁止事項要做在權限上；對話裡的約定不是保險。

Fortune 在 2025-07-23 報導：SaaStr 創辦人 Jason Lemkin 測試 Replit 的 Agent 時，雖然已宣告「程式與動作凍結」，Agent 仍執行了未授權的指令，刪掉 1,200 多位主管、1,190 多家公司的資料，還說資料無法復原（實際上可以）。Replit 執行長稱這件事不可接受、不應該發生，事後加上開發與正式資料庫自動分離、只規劃不執行的模式。

重點不是哪一家產品不好，而是任何 Agent 只要拿得到正式資料庫的權限，口頭凍結都擋不住；禁止事項要做在權限上。網路上「捏造 4,000 筆假資料」的說法只見於單一媒體，不要引用。

## 12. 三缺一：提示詞注入的致命組合

Prompt injection（提示詞注入）：輸入或讀到的內容藏著指令，改變了 Agent 原本該做的事。

- **① 讀得到私密資料**：程式碼、客戶資料、金鑰。

- **② 會讀不可信內容**：網頁、外部文件、別人提的問題單。

- **③ 能對外傳送**：發請求、寄信、推到公開位置。

Simon Willison（2025-06）把三種能力同時存在稱為「致命三要素」：讀得到私密資料、會讀不可信的內容、能對外傳送。藏在網頁、文件或問題單裡的指令，可能讓 Agent 把私密資料送出去。白話比喻：新同事桌上有機密文件、會照陌生人的紙條做事、手邊又有寄件權限，三者湊齊就會出事。

目前沒有能完全擋住提示詞注入的方法，所以要從設計上拿掉其中一項，這就是「三缺一」。下週檢查你的工作單授權範圍，至少拿掉一項，例如不給對外網路，或不讓它讀外部內容。

OWASP〈LLM01:2025 Prompt Injection〉把它分成兩種：使用者直接在輸入裡下指令的，叫直接注入；指令藏在網頁、檔案等外部內容裡、被 Agent 讀進來的，叫間接注入，Coding Agent 最常碰到的是後者。OWASP 也說，以生成式模型的特性，目前不清楚有沒有萬無一失的防法，這正是要從設計上拿掉一項的原因。

📖 延伸閱讀：〈The lethal trifecta for AI agents〉（Simon Willison，2025）；〈LLM01:2025 Prompt Injection〉（OWASP，2025）

**人工確認**：三項同時成立就危險；你的工作單至少拿掉了哪一項？

## 13. 事故二：Agent 的供應鏈也會被下毒

2025 年 7 月，Amazon Q Developer 的 VS Code 擴充套件 1.84.0 被植入「清除檔案」的提示詞。

- **怎麼發生**：建置設定裡的 GitHub 權杖權限過大，攻擊者藉此提交惡意內容，被自動打包發布。

- **教訓**：Agent、擴充套件、Skill 都是供應鏈；只從可信來源安裝，建置帳號也要最小權限。

AWS 安全公告 AWS-2025-015（2025-07-23）說明：建置設定裡的 GitHub 權杖權限過大，攻擊者藉此提交惡意內容，被自動包進 Amazon Q Developer 的 VS Code 擴充套件 1.84.0 發布。這段「清除檔案」的提示詞因為語法錯誤沒有實際執行，AWS 已發布修正版；漏洞的公開編號（CVE）是 CVE-2025-8217。

教訓是 Agent 本身與它的供應鏈都需要最小權限：Agent、擴充套件、Skill 都是供應鏈的一環，只從可信來源安裝，負責建置的帳號也只給需要的權限。網路上流傳的安裝數字只見於二手報導，不要引用。

📖 延伸閱讀：〈Security Update for Amazon Q Developer Extension for Visual Studio Code (Version #1.84)〉（AWS，2025）

**人工確認**：你團隊用的 Agent 擴充套件與 Skill，誰負責審核來源？

## 14. 護欄做在平台，不只寫在提示詞

規則檔與提示詞是「建議」；一定要發生或一定不能發生的事，交給自動機制。

- **寫在規則裡**：風格、偏好、怎麼回報。Agent 多半會照做，但不保證。

- **做在平台上**：權限、隔離環境、自動檢查、合併前必須有人審。

規則檔與提示詞是建議，Agent 多半會照做，但不保證。Anthropic〈The AI-native SDLC playbook〉的說法是：Skill 是建議性的控制，hook（在固定時機一定會自動執行的腳本或檢查）才是背後確定會發生的那一層。所以風格、偏好、回報方式寫在規則裡；權限、隔離環境、自動檢查、合併前必須有人審，要做在平台上。

例子：第三場的「絕不提交密碼與金鑰」，寫在規則裡只是提醒，做在平台上就是推送前自動掃描金鑰。下週挑一條你最怕被違反的規則，問它現在只是建議，還是平台擋得住。

## 15. 例外處理：停下來問，不要硬做

Escalation（升級處理）：碰到停止條件，只停受影響的動作，附證據交給人決定。

- **回報六標題**：觸發原因、證據、影響、選項、建議、需要人決定的事。

- **人怎麼判斷**：對照事先寫好的邊界原文：在範圍內嗎？是／否／不確定。

- **拒絕不等於停工**：回到核准範圍繼續做，並記下原因。

碰到停止條件時，好的做法是只停受影響的動作，附上證據交給人決定。真實工作常見的停止條件有：需求互相矛盾、要動範圍外的東西、要新增外部套件、出現無關的測試失敗、時間不夠。

例外提議往往聽起來很合理，所以能擋下越界的，是事先寫好的邊界，不是當下的直覺。判斷時拿邊界原文對照：在範圍內嗎？是、否，或不確定。拒絕也不等於停工，Agent 回到核准範圍繼續做，並記下原因。

📖 延伸閱讀：〈Building effective agents〉（Anthropic，2024）

**人工確認**：你的工作單有沒有寫「碰到什麼要停」？沒有，Agent 只會自己猜。

## 16. 寫的人不能核准自己

另開一個只讀的審查對話，依審查準則看變更與證據，寫下審查紀錄；放行仍由人決定。

- **同一份審查準則**：哪些算重要、哪些不用報；寫的人和審的人讀同一份。

- **只建議，不核准**：審查紀錄最後一句「建議放行／不建議放行」，由人決定。

### 交給 Agent 的指令

這是新的對話，你是審查者：只讀，不要修改任何檔案。先讀 skills/team-rules.md 的審查準則，再讀 notes/delivery.md 與它引用的證據。依準則把發現分成「重要」與「小問題」，每項附證據原文與位置；找不到證據的標「應改為未驗證」，不報風格偏好。寫成「審查紀錄」回覆我，最後一句只寫「建議放行」或「不建議放行」。

Anthropic〈The AI-native SDLC playbook〉說，職責分開之所以成立，是因為寫程式的 Agent 根本沒有辦法核准自己的變更。實務做法是另開一個乾淨的對話當審查者：Claude Code 官方文件指出，獨立審查者只看到變更和你給的標準，不受原對話的想法影響。審查者也只給建議：官方的程式碼審查文件寫明，審查不會核准或擋下變更，合不合併仍由團隊決定。

審查要有依據。審查準則由人事先寫好：哪些算重要（例如超出核准範圍、測試變少、改了期待值、宣稱通過卻沒證據）、哪些不用報、一定要查什麼；官方文件的說法是，用它寫明團隊要標出什麼、算多嚴重、哪些略過。這也處理另一個問題：被要求找問題的審查者，即使工作沒問題通常也會報出一些；有了準則，報的問題就要對得回準則或驗收條件。分工上，測試與格式檢查這類算得出來的先跑，AI 審查只當補充，這是第三場「事前給地圖，事後裝感測器」的延伸。

📖 延伸閱讀：〈The AI-native SDLC playbook〉（Anthropic，2026）；〈Customize Code Review〉（Anthropic，官方文件）；〈Best practices for Claude Code〉（Anthropic，官方文件）

**人工確認**：審查紀錄的每個「重要」問題，你都對得回審查準則或驗收條件嗎？只是偏好的先放一邊。

## 17. 沒盯著的工作，靠證據審

第一場的「看證據，不看宣稱」加深一層：Digital Worker 做事時你不在旁邊，交付摘要的證據就是你唯一看得到的過程。

- **證據要自己站得住**：每句結論指得出檢查結果與檔案；沒有的寫「未驗證」。

- **為什麼**：看證據比自己重跑快，你沒盯著的工作也能審。

Digital Worker 做事時你不在旁邊，交付摘要裡的證據就是你唯一看得到的過程。Claude Code 官方文件指出，檢視證據比自己重跑驗證快，而且適用於你沒看著的工作階段。所以每句結論都要指得出檢查結果與檔案，沒有的寫「未驗證」。

下週收到任何交付，抽一句結論問「證據在哪？」，引用不出的就改成未驗證，再決定要不要補。

## 18. 留下紀錄：事後查得到「憑什麼放行」

每一步留一個檔案，下一步先讀它；出事時查得到誰核准了什麼。

要什麼、為什麼、限制 → 做完的行為與驗收條件 → 改哪些檔、步驟、測試 → 審查紀錄：發現與建議 → 放行：誰、何時、根據什麼

- **職責分開**：寫的人不核准自己；Agent 照人的原話記，不代人核准。

- **定期回看**：每月抽查幾筆紀錄，看關卡有沒有真的擋下問題。

Anthropic〈The AI-native SDLC playbook〉的做法是：每一步做完都把結果寫成一個檔案存進版本控制，下一步先讀它再開始。要什麼、為什麼、限制；做完該有的行為與驗收條件；改哪些檔、步驟、測試；審查發現；最後由人放行。原文說，這些檔案和變更內容合起來，就是事後查核的依據。B3 的 notes/b3.md（Gate 紀錄、驗收對照表、審查紀錄）就是縮小版。下週可以做的：請 Agent 每一步把結果寫進一個固定的檔，下一步先讀它，不要只留在對話裡。

治理不是多填表，而是每個決策都留下誰、何時、根據什麼證據。職責分開要做在平台上：GitHub 的雲端 Coding Agent 從平台上就不讓 Agent 核准或合併自己的變更。最常見的治理失敗是形式性核准：照單接受，卻說不出核對了哪一題。所以要定期回看，每月抽查幾筆紀錄，看關卡有沒有真的擋下問題。

📖 延伸閱讀：〈The AI-native SDLC playbook〉（Anthropic，2026）；〈Risks and mitigations for GitHub Copilot cloud agent〉（GitHub，官方文件）

**人工確認**：三個月後有人問「這次為什麼放行」，你的紀錄答得出來嗎？

## 19. 案例：Stripe 每週上千個 Agent 變更

Stripe 的 Minions：每週超過一千個 PR（變更請求）完全由 Agent 產出，全部經人審查。（2026-02）

- **隔離環境**：每次在與正式環境、網際網路都隔開的開發機執行，所以不必逐步問權限。

- **自動驗證**：本機格式檢查，加上三百多萬個測試的 CI；最多跑兩輪。

- **人審查**：產出是等人審的 PR，不是直接上線。

Stripe 工程部落格（2026-02）介紹它的 Minions：每週超過一千個 PR 完全由 Agent 產出，全部經人審查。每次都在與正式環境和網際網路隔開的開發機上執行，所以不必逐步問權限；改完先跑本機格式檢查，再跑三百多萬個測試的持續整合，最多兩輪；產出是等人審的 PR，不是直接上線。

這是「隔離環境、自動驗證、人審查」三層的教科書案例：邊界做在環境上，所以能放手；放手的產物仍要過測試與人。數字由公司自己公布；後續報導的「每週 1,300 個」未從原始來源確認，不要引用。

📖 延伸閱讀：〈Minions: Stripe's one-shot, end-to-end coding agents〉（Stripe，2026）

## 20. 案例：GitHub 的大數字怎麼讀

成功案例的共同點不是更聰明的模型，而是平台化的驗證與人審；看數字時先問量的是什麼。

- **GitHub（2025-10）**：Copilot coding agent 在 2025 年 5–9 月建立超過 100 萬個 PR。注意是「建立」，不是「合併」。

- **平台先畫好邊界**：Agent 只推到自己的分支，人審前 CI 不跑，也不能合併自己的 PR。

- **Spotify（第三場）**：數字在第三場講過；共同點一樣：改完先過自動檢查，再由人審核合併。

GitHub〈Octoverse〉報告（2025-10）說，Copilot coding agent 在 2025 年 5–9 月建立了超過 100 萬個 PR。這是「建立」的數量，不是「合併」，更不是上線；數字也由公司自己公布。看到任何大數字，先問它量的是什麼。

大量產出之所以可控，是因為平台先畫好邊界：Agent 只推到自己的分支、人審前持續整合不跑、不能合併自己的 PR。和 Stripe、Spotify 一起看，三家都把邊界做在平台，把放行留給人。

📖 延伸閱讀：〈Octoverse: A new developer joins GitHub every second as AI leads TypeScript to #1〉（GitHub，2025）；〈Risks and mitigations for GitHub Copilot cloud agent〉（GitHub，官方文件）

**人工確認**：看到大數字時，先問：量的是建立、合併，還是真的上線？

## 21. 帶走：一張委派前的檢核卡

工作單五段寫完了嗎？人是哪種角色？關卡在不可逆動作前嗎？權限最小、三缺一了嗎？交付附證據嗎？

- **下一段**：第五段：怎麼量出有沒有用、怎麼讓團隊一起用、30 天怎麼開始。

這張檢核卡把今天串起來：工作單、自主等級、關卡、最小權限與三缺一、證據式交付。Tool → Teammate → Digital Worker 是介入方式的階梯，不是只能往上走；風險高、難復原的工作，隨時可以退回前一種方式。

**人工確認**：能說出你那件工作的一道關卡，以及在那裡要看的證據。

## 完成條件
能說出：一份工作單的五個部分、你那件工作適合人當哪種角色、關卡該設在哪個不可逆動作之前、Agent 需要的最小權限與「三缺一」拿掉了哪一項、怎麼用只讀的審查對話與審查準則評估交付、每一步該留下哪個檔案；並說得出 Stripe、Spotify 等案例共同的三層：隔離環境、自動驗證、人審。

**下週可以做的事**

- 替一件想委派的工作寫工作單草稿，標出「待決定」
- 列出 Agent 真正需要的權限，拿掉「三缺一」中的一項
- 找出那件工作裡最難回頭的動作，在它前面設一道關卡

| 提示詞注入（Prompt injection） | 輸入或讀進來的內容藏著指令，改變模型原本該做的事；藏在網頁、檔案裡的叫間接注入。 | OWASP〈LLM01:2025 Prompt Injection〉 |
| 致命三要素（三缺一） | 讀得到私密資料、會讀不可信的內容、能對外傳送，三者同時存在就危險；設計上至少拿掉一項。 | Simon Willison〈The lethal trifecta for AI agents〉 |
| hook | 在固定時機（例如執行工具前、改檔後）自動執行的處理程式；和規則檔不同，它一定會執行。 | Claude Code 官方文件〈Glossary〉 |
