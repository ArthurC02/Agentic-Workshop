TASK-B2-001 · 交付與邊界

要分析的影響，與不能做的事

影響分析

  • 分三欄：一定要改／可能影響／不應改
  • 規則交互作用與跨模組影響
  • 建立訂票與改票重新計價：政策一致
  • API 呈現實際採用優惠；保留原旅客 Request／Response 三欄
  • 若擴充 Booking 回應：根層 applied_discounts（passenger_id、discount_type、rate、amount）

禁止事項

  • 不可疊乘；不對整筆訂票只選同一優惠
  • 不將政策塞入 Router
  • 不引入規則引擎或第三方規則套件
  • 不全面重寫；不新增團體功能
  • 保留付款／改退票、座位、Audit 與同步通知
  • 學生修復與原正確 Regression 不可弱化

來源：TC2「人與Agent合作及交付」段（交付物、API／一致性、禁止事項）原文。本頁只列任務卡寫明的影響面；不點名具體模組或檔案（揭曉頁才列）。

Hint 3（模組）觸發：只改建立流程，忽略使用端 →「核對Fare／Discount與Booking Change是否共用相同政策，以及回應明細與文件；不提供修正Code。」

須立即停止並糾正（BF6 P7）：規則疊乘、弱化 Regression、未經核准的外部套件、提前做團體功能。

需要介入（BF7 P7）：只改一個分支、忽略 Change、用全團共同優惠或疊乘計價、全面重構成 Engine。保留同步 Notification；折扣政策清楚化即足夠，不要求複雜的 Engine（BF5 P7）。
