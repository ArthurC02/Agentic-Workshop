# 主持簡報用詞與語感審查

> 讀者：主持人與維護者。時機：修改簡報或發放前。前置：[操作說明](README.md)。可見性：內部。

本輪審查涵蓋9份投影片原稿、75頁投影文字與講者備註。以一般工程師首次參與時能否理解「誰做什麼、何時做、怎樣才算完成」為準，補充術語意思並修正前後容易誤解的表達。

| 原表達或誤解風險 | 修正方式 |
|---|---|
| Code／Test／Docs、Impact、Challenge 等英文堆疊 | 以程式、測試、文件、影響分析與質疑假設說明；保留必要技術識別字 |
| Agent角色「升級」像產品能力升級 | 說明是協作分工改變，人仍負責決策與成果 |
| 用測試接受結果、API可呼叫即完成 | 核對需求、實際測試與修改；業務API須按需求運作 |
| 解鎖碼都在畫面公布 | 一般活動碼投影；復原基線碼按需個別提供 |
| 00:00 與全場第0分鐘混淆 | 說明段落經過時間與全場時間的對應 |
| 只有完整程式與測試才可交付 | Level1可如實提交分析與策略，無修改／未執行明記；完整功能須另驗收 |
| 不揭露位置與漸進提示矛盾 | 一般回答不主動給答案；停滯時依條件逐級提示 |
| 治理分數等於功能完成或人員能力排名 | 功能等級與治理觀察分開，評分僅用回顧，不公開小組排名 |

數值、商業規則、API及識別字、三個核准關卡、揭露時間與90分鐘安排維持原規格；來源逐字引文保留，澄清說明另列。技術比對及重建結果見[驗證證據](deck-wording-validation.json)。

完成條件：投影與備註意思一致，兩份成品重建檢查及教材測試通過；不因改寫文字宣稱已完成真人理解度或版面驗證。現場閱讀、瀏覽器與90分鐘演練仍待Preflight。
