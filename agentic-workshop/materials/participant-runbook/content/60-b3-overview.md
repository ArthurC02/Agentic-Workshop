# B3｜委派整件任務：工作單 + 三道關卡

```callout info
現在在做什麼
- **情境**：旅行社想一次幫 5–20 人的團體訂同一班車、同一節車廂的連號座位，付款失敗要整團取消。這是任務 `TASK-B3-001` 團體訂票。
- **你的目標**：把整件任務交給 Agent 自主完成；你只在三道關卡（Gate）做決定，13 分鐘內如實交付。
- **今天的技巧**：**委派整件任務：工作單 + 三道關卡**。範圍、禁止事項與停止條件先寫進工作單（Work Order），Agent 就能自己往前走；你只在 Gate 介入。
- **完成的樣子**：`notes/b3.md` 裡有 Agent 寫的需求理解、設計、你的三個 Gate 決策、驗收對照表與變更審查答案；完成等級（Level 1–3，檢查點 4 說明）有證據支持。
```

```callout info
新概念：Gate（核准關卡，加深一層）
前面每一小步你都核准過；這次只在三道 Gate 核准，中間讓 Agent 自己往前走。核准是決策，不等於功能已通過驗收；通過要看驗收對照表與測試。
📖 定義出處：本課程〈B3 人員核准 Gate〉。
```

**每道 Gate 怎麼做**：Agent 把要你核對的事整理成幾個是非題、附證據與建議決策，然後問你。你回一句話，例如「核准」「附條件核准：先補上測試策略」「退回：第 2 題理解錯了，請重寫」，再說核准人和現在第幾分鐘。附條件核准時，條件解除後才可續行。

## 檢查點總覽

每個 Gate 控制 1–3 分鐘。

- **63–64 · 檢查點 1 把工作單交給 Agent**（Gate 1 決策卡可能晚於第 64 分才出來，第 66 分前決策即可）
- **64–66 · 檢查點 2 Gate 1：確認 Agent 懂需求**：第 66 分決策
- **66–70 · 檢查點 3 Gate 2：核准設計與修改範圍**：第 69 分決策；第 69–70 分例外事件
- **70–76 · 檢查點 4 放手執行，Gate 3 決定交付**：第 74 分停止擴充、第 75 分 Gate 3、第 76 分停止

## 檢查點 1 · 把工作單交給 Agent（第 63–64 分鐘）

① 為什麼做這一步

一次把整件任務交代清楚：要做什麼、能動哪裡、什麼情況要停下來、在哪裡等你決定。B2 沒做完的小組，主持人會個別給解鎖碼，先到 [B2 Recovery](#recovery-b2) 切換；B3 開始後就不再換版本。

② 貼給 Agent

1. 在主要 Agent **開一個新對話**（Token 節費）；工具有模型選單就選推論能力較強的模型（模型選擇，加深一層），沒有就用預設。
2. 複製下方提示詞貼給 Agent，先不要送出。
3. 依序打開 [B3 任務卡](#b3-task-card)、[操作規則](#b3-operating-rules)、[工作單](#b3-work-order)、[三道 Gate](#b3-approval-gates)，按各頁文件上方的「複製 Markdown」，接在提示詞後面，再一起送出。

提示詞與文件裡的英文術語（例如 Out of Scope、Escalation、Atomicity）是給 Agent 的，不需要看懂；要你決定的事，Agent 會用白話問你。

```text
請先讀 skills/team-rules.md 並遵守。
請依附在這段後面的任務卡、Digital Worker 操作規則、工作單（Work Order）與三道 Gate，執行 TASK-B3-001 團體訂票：
0. 建立 B3 起點：這個資料夾還沒有 Git 就執行 git init；沒有 .gitignore 就建立一個，內容三行：__pycache__/、.venv/、.pytest_cache/。執行 pytest -q，再把目前狀態 Commit，訊息寫「B3 起點」；如果 Git 要求姓名或 Email，只在這個資料夾設定（不要用 --global），名字用「workshop」、Email 用「you@example.com」。之後的變更審查都和這個 Commit 比。
1. 只把工作單原文，加上三道 Gate 文件裡的「Gate 回報格式」，以及 Escalation 格式（依序六個標題：Trigger、Evidence、Impact、Options、Recommendation、Decision Needed），存成 skills/b3-work-order.md，這是你這次的工作說明（Skill）。任務卡、操作規則與三道 Gate 的其他內容不要重抄，在檔案開頭寫一行「任務卡、操作規則與三道 Gate 全文在這個對話的第一則訊息」。之後我只會說「依 skills/b3-work-order.md」，不再重貼。
2. 讀 notes/shared-context.md，在 notes/b3.md 建立「已核准背景」：小組、接手的程式版本（B2 接手版本或 B2 復原包）、B3 起點的測試結果（通過／失敗／跳過各幾個）、這次對話用的模型與推論強度（不知道就問我；工具沒有這個設定就寫「預設」）、已確認的假設與限制、尚待決定的事項。查不到的寫「待小組確認」，不要猜。
3. 提交 Gate 1 資料：需求摘要、規則清單、關鍵假設、資訊缺口、不做的範圍（Out of Scope），寫進 notes/b3.md 的「Gate 1」段落。對話只用 Gate 回報格式給我 Gate 1 決策卡：「證據」用 5 個是非題確認你的需求理解，每題附任務卡原文位置：5–20 人邊界、同班次（Trip）與同車廂連續座位、不允許部分成功、付款失敗整筆取消並釋放全部座位、每位旅客沿用 B2 最有利單一優惠；「需要人決定的事」列出要我決定的問題，每題附你的建議答案與依據，查不到依據的標「待小組確認」；任務卡沒寫每節車廂有幾個座位，請依程式裡現有的資料提出建議值與依據，列為一題由我核准；「建議結論」給一個建議決策（APPROVE／APPROVE WITH CONDITIONS／REJECT AND REVISE）與一句理由；「風險」寫你最沒把握的地方。
4. 每過一道 Gate 才進下一步：Gate 1 核准才設計；Gate 2 核准且條件解除才改程式；Gate 3 由我決定是否交付。
5. 遇到工作單的停止與升級條件（Stop and Escalate Conditions），停止受影響動作，依 Escalation 格式把證據、選項與建議寫進 notes/b3.md，等我決定。
6. Gate 決策由我說，你照原文記進 notes/b3.md（決策、審查過的證據、條件、核准人、分鐘），不要代我核准。實際執行的命令、結果與未執行的部分都要記錄，不以預期代替實測。
7. 每道 Gate 都用「Gate 回報格式」回報：完整內容寫進 notes/b3.md，對話只給我這個格式的摘要。

這一次只做第 0–3 項：交出 Gate 1 決策卡後停下，不要開始設計。除了 .gitignore、notes/b3.md 與 skills/b3-work-order.md，不要修改任何檔案；不要改程式。
```

③ 確認結果

```text
請檢查下列三件事，不要修改任何檔案：1. 有「B3 起點」這個 Git Commit，skills/b3-work-order.md 已建立；2. notes/b3.md 有「已核准背景」（含起點測試數與模型）與「Gate 1」兩段，Gate 1 有 5 個是非題與需要我決定的問題；3. 除了 .gitignore、notes/b3.md 與 skills/b3-work-order.md，沒有修改任何檔案（用 git status 確認）。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

失敗時：

```text
請用白話說明哪一項不符，只補齊缺的 Commit、skills/b3-work-order.md 或 notes/b3.md 的段落；改到其他檔案就用 Git 還原。不要開始設計，補完重新給我 Gate 1 決策卡，然後停下。
```

```callout tip
技巧：Skill（加深一層）
```

## 檢查點 2 · Gate 1：確認 Agent 懂需求（第 64–66 分鐘）

① 為什麼做這一步

需求理解錯了，後面做得再快都是白做。對照 [B3 任務卡](#b3-task-card) 回答決策卡上的 5 個是非題，每題都對得上任務卡才核准；看不懂就請 Agent 換個說法。「待小組確認」的問題由你們決定，不讓 Agent 自行假設。最晚第 66 分做決策。

② 貼給 Agent

```text
請依 skills/b3-work-order.md 記錄 Gate 1 決策。除了 notes/b3.md，不要修改任何檔案；不要改程式。
先問我：Gate 1 決策、我核對了哪幾題、「需要人決定的事」每題的答案（有建議答案的題目我沒意見就照你的建議；標「待小組確認」的題目一定要問我）、條件（如果有）、核准人、現在第幾分鐘。我回答後，照原文記進 notes/b3.md 的「Gate 1」段落（核對的題目寫進「審查過的證據」，每題答案另列「需要人決定的事」）。
核准時，接著提交 Gate 2 資料：受影響／不受影響的模組、API 合約（API Contract，錯誤碼沿用既有慣例：不符商業規則回 409、輸入資料驗證失敗回 422）、業務模型變更、座位分配方案、整筆成功或整筆失敗（Atomicity）與付款失敗的補償處理（Compensation：釋放座位、把狀態改為已取消）方案、測試策略、文件清單、主要風險與預計修改檔案。寫進 notes/b3.md 的「Gate 2」段落後停下，不要修改程式。
附條件核准時，先只處理條件，回報條件已解除並等我確認後，才提交 Gate 2 資料。
退回時，依我的修正重新提交 Gate 1 決策卡，然後停下等我。
```

③ 確認結果

```text
請檢查下列兩件事，不要修改任何檔案：1. notes/b3.md 的「Gate 1」照原文記著我的決策、核對的題目、每題答案、核准人與分鐘；2. 我核准時已有「Gate 2」資料段落，而且除了 notes/b3.md 與 skills/b3-work-order.md，沒有修改任何檔案（用 git status 確認）。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

失敗時：

```text
請用白話說明哪一項不符，只補齊 notes/b3.md；改到其他檔案就用 Git 還原。不要修改程式，補完停下等我。
```

④ 補充

```callout tip
技巧：結構化輸出（Gate 回報格式，加深一層）
每道 Gate 都用同一組固定標題（Gate、建議結論、證據、風險、需要人決定的事），你才能在 1–3 分鐘內看完；完整內容寫進 `notes/b3.md`，對話只給摘要。
📖 延伸閱讀：Anthropic 官方文件〈Structured outputs〉、OpenAI 官方文件〈Structured model outputs〉；你所用工具的官方文件通常有同名章節。
```

```callout tip
技巧：Prompt 結構（加深一層）
工作單就是把提示詞的五個部分放大到整件任務：需求是目標，已核准背景是背景，修改範圍是限制，Gate 回報格式是輸出格式，停止條件和三道 Gate 是停止條件。
📖 延伸閱讀：Anthropic 官方文件〈Prompt engineering overview〉與〈Prompting best practices〉、OpenAI 官方文件〈Prompt engineering〉；你所用工具的官方文件通常有同名章節。
```

在頁尾「B3 Gate 決策」選 Gate 1 的決策。

## 檢查點 3 · Gate 2：核准設計與修改範圍（第 66–70 分鐘）

① 為什麼做這一步

這一步 Agent 只提設計，不改程式；你核准的範圍，就是它接下來能自己動手的邊界。你判斷是非題的答案都在工作單允許範圍內，不以方案「看起來合理」取代範圍檢查。最晚第 69 分做決策；附條件核准時，條件還沒解除的部分先不要動。

② 貼給 Agent

```text
請依 skills/b3-work-order.md，用 Gate 回報格式把 Gate 2 整理成給我核對的決策卡。除了 notes/b3.md，不要修改任何檔案；不要改程式：
1. 「證據」用是非題回答，每題附 notes/b3.md 或工作單的依據：範圍是否只限團體流程所需；有沒有全面重寫一般訂票；建立失敗與付款失敗是否都有處理；失敗時座位是否全部釋放；有沒有其他入口會讓團體訂票跳過整筆失敗的處理；既有測試是否全部保留；有沒有工作單沒核准的外部依賴。
2. 「風險」寫主要風險；另附預計修改的檔案清單，以及明確不改的部分。
3. 「建議結論」給一個建議決策與一句理由；有條件的話，寫出條件與怎樣算解除。
然後問我：Gate 2 決策、核准的修改範圍、條件、核准人、現在第幾分鐘。我回答後，把決策與核准範圍照原文記進 notes/b3.md 的「Gate 2」段落，然後停下。條件解除、我說「開始執行」之前，不要修改程式。
```

③ 確認結果

```text
請檢查下列兩件事，不要修改任何檔案：1. notes/b3.md 的「Gate 2」照原文記著我的決策、核准的修改範圍、條件、核准人與分鐘；2. 到目前除了 notes/b3.md、skills/b3-work-order.md 與 .gitignore，沒有修改任何檔案（用 git status 確認）。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

失敗時：

```text
請用白話說明哪一項不符，只補齊 notes/b3.md；已經改了程式就用 Git 還原那些檔案。在我說「開始執行」之前不要修改程式。
```

④ 補充

在頁尾選 Gate 2 的決策。Agent 之後做的跟核准的不一樣時，請它補證據，或回到 Gate 2 重新核准。

**第 69–70 分：例外事件。** 主持人宣布例外事件時，到 [例外回應卡](#b3-exception-card) 貼那頁的提示詞，60 秒內決定；時間緊可用 30 秒口頭判斷，再請 Agent 記一行紀錄。

```callout tip
💬 討論一下（例外事件時）
這個提議在 Gate 2 核准的範圍裡嗎？工作單哪一句可以當依據？（口頭快速討論，結論直接告訴 Agent，不用寫下來。）
```

## 檢查點 4 · 放手執行，Gate 3 決定交付（第 70–76 分鐘）

① 為什麼做這一步

這段 Agent 自己做；你只在它停下升級時和第 75 分的 Gate 3 介入。Gate 3 只看 Agent 的回答、不看程式：變更審查三題都答「是」、驗收對照表的失敗與未驗證項目都列出來、建議的完成等級（Level，見 ④）有證據支持，才核准；任何一題是「否」或「不確定」就不核准，請 Agent 解釋或修正。

② 貼給 Agent

Gate 2 核准且條件解除後，貼：

```text
開始執行，依 skills/b3-work-order.md。只修改 notes/b3.md 記錄的 Gate 2 核准範圍內的檔案，建立與執行測試、更新文件。不要擴大範圍；與 Gate 2 計畫有偏差時先停下回報，等我核准。
遇到工作單的停止與升級條件，立即停止受影響動作，依 Escalation 格式把證據、選項與需要我決定的事寫進 notes/b3.md，等我決定。
做完核准計畫就停下，用 5 行以內白話回報改了哪些檔案、為什麼（細節寫在 notes/b3.md），等我確認；不要自行進入交付。
```

Agent 停下升級時，讀它寫的選項與建議，回一句決定即可（例如「照建議做」「不要加，維持原範圍」），並請它把你的決定照原文記進 `notes/b3.md`。

**第 74 分鐘停止擴充。** 不論 Agent 做到哪裡，都貼上：

```text
停止擴充，不要再新增功能，也不要再修改。請完成下列三件事，全部寫進 notes/b3.md：
1. 驗收對照表：每條驗收條件（或規則）一列，欄位是「編號、白話內容、結果（通過／失敗／未驗證）、依據的測試名稱」。最後一行寫測試總數：通過幾個、失敗幾個、跳過幾個。附上你實際執行的指令。尚無修改或未執行測試時，明記「無修改／未執行」、原因與未驗證範圍，不要預填成功。AC-B3-019（文件、API 範例與規則一致）沒有對應的自動測試：請實際執行 docs/ 裡的團體訂票 API 範例（api-examples.md 或 api-summary.md），並確認文件提到的規則編號都在 docs/business-rules.md，用這兩項結果當它的依據。
2. 變更審查：先列出改了哪些檔案、每個檔案改了什麼、為什麼（用 git status 與 git diff 對照「B3 起點」Commit，新增、還沒 Commit 的檔案也要列；notes/ 與 skills/ 是紀錄，不用列）。再回答下列三題（回到最核心的三題，因為 Gate 3 要在 1 分鐘內看完），每題附上實際執行的指令與結果摘要：
   (1) 改的檔案都在 Gate 2 核准範圍內？
   (2) 測試總數沒有比 B3 起點少，也沒有新增 skip 或 xfail？（git diff 看不到還沒 Commit 的新測試檔，請用 pytest -q --collect-only 算出現在的測試數，和 notes/b3.md「已核准背景」記下的 B3 起點測試數比較，不要切換 Commit）
   (3) 沒有刪除任何測試，也沒有修改既有測試的期待值？（請用 git diff 檢查 tests 資料夾後回答）
```
