```callout info

- **情境**：公司要改優惠政策：旅客同時符合多項優惠時，只給一項對他最有利的，不能疊加。
```

## 檢查點 1 · 請 Agent 提方案並比較，人來選（第 52–55 分鐘）

① 為什麼做這一步

起點是小組驗收過的 B1。這一步 Agent 只分析、比較方案，不改任何檔案。你判斷：

- 2–3 個方案都真的可行，不是一個方案配兩個陪襯
- 每個方案都對照過任務卡的禁止事項
- 每個假設都標了依據或「未確認」

② 貼給 Agent

複製下方提示詞，再按上方任務卡的「複製 Markdown」接在後面，一起貼給主要 Agent：

```text
請先讀 skills/team-rules.md 並遵守。先不要修改程式。請先把目前狀態 Commit 成「B2 起點」作為 B2 的基準（沒有變更也要建立，用 git commit --allow-empty；如果這個資料夾還不是 Git Repository，先 git init 再 Commit；如果 Git 要求姓名或 Email，只在這個資料夾設定（不要用 --global），名字用「workshop」、Email 用「you@example.com」），之後你回報的變更就只包含 B2。
再讀 notes/b1.md 的「B1 驗證與交付」（用 Recovery 的組讀 notes/recovery-b1.md），以及附在這段後面的 TASK-B2-001 任務卡；其他檔案需要時再讀，不要讀整個專案。

請不要只給我一個做法。先仔細想過再回答，列出你考慮過的可能。用白話回答：
1. 現況：旅客同時符合多項優惠時，系統現在怎麼算；新規則 FARE-007～FARE-010 要求怎麼算；會影響訂票、改票、付款、文件哪些功能。
2. 提出 2–3 個可行方案，方案依序命名為 A、B、C，用一張固定欄位的表比較，欄位依序是：方案、改動範圍（影響分析：一定要改／可能影響／不應改，附檔案或測試名稱當證據）、風險（對既有功能）、測試影響（要用哪些測試證明）、建議（推薦與否、大約要做幾步）。逐一對照任務卡的禁止事項，違反的方案直接標出來。

4. 為推薦方案列出 3–5 步工作拆解，每一步標出規則編號（Rule ID）或驗收條件（AC），並建議第一段先做到第幾步。
5. 列出你做了哪些假設，每個假設附上依據（任務卡原文、測試名稱或實際執行結果）；沒有依據的標「未確認」。
```

有「未確認」的假設會改變你們的選擇，而且還不到第 54 分鐘，才貼這段「追問假設」；否則直接核准：

```text
先不要修改。你的方案比較裡哪一個假設最沒把握？請拿出依據：任務卡原文、測試名稱或實際執行結果。拿不出依據的，改標「未確認」，並說明它錯了會影響哪個方案。補充寫進 notes/b2.md。
```

```text

先把選定方案、理由、核准人與時間、核准的步驟寫進 notes/b2.md（標題「B2 核准」），再只做這一段核准的步驟。做完執行 pytest -q，用白話說明改了哪些檔案、各改了什麼、為什麼，然後停下等我們確認，不要繼續下一步。
```

Agent 若列出「因新規則而過時的期待值」並停下，先看檢查點 2 ① 的三點；都成立就回「核准更新」，否則回「請改程式，不要改測試」。

③ 確認結果


## 檢查點 2 · 依選定方案實作（第 55–59 分鐘）

① 為什麼做這一步

主要 Agent 做完第一段會停下，換你們看證據：

- 變更審查五題（審查準則三題加這段兩題）都答「是」，才放行
- 多優惠旅客每人只採一項優惠，而且是對他最有利的那一項。先自己對照任務卡，再看 Agent 回報

Agent 列出「因新規則而過時的期待值」時，下面三點都成立才回「核准更新」。說不出 Rule ID 的，請它改程式，不要改測試：

- 舊期待只在舊規則下才對
- 新規則確實要求不同結果
- 附了 Rule ID

② 貼給 Agent

```text
不要再修改。依 skills/team-rules.md 的「審查準則」做變更審查，起點是「B2 起點」Commit（「核准更新」的測試檔算在核准計畫裡）：列出改了哪些檔案、各改了什麼、為什麼，回答準則的三題。再回答下面兩題。五題都答「是／否／不確定」，每題附上實際執行的指令與結果摘要：
4. 優惠政策沒有放在 API 路由層，而且訂票建立與改票重新計價用的是同一套政策。
5. 同時符合多項優惠的旅客，每人只採一項優惠。請挑一位這樣的旅客（例如企業會員 M002 帶一位成人、一位學生）實際驗證：先重新啟動伺服器，讓它跑目前的版本（先停止這個專案原本的伺服器（uvicorn smart_ticket，連同它開出的子程序）；然後在背景用埠號 8000（先前改用 8001 的就用 8001）啟動；8000 若被不是你啟動的程式占用，不要停它，告訴我它的名稱、PID（程序編號）和啟動指令，改用 8001，並把實際埠號寫進 notes/b2.md），再用伺服器實際建立一筆訂票，列出每位旅客實際採用的優惠類型、折扣率與金額；回應沒有每位旅客的優惠明細時，每人的優惠類型與折扣率標「由程式推論，未驗證」，總金額照回應的 total_fare 寫。
最後列出驗收對照表。
把以上答案寫進 notes/b2.md（標題「B2 變更審查」）。沒有問題的話，把目前狀態 Commit 成「B2 第一段」，然後停下。
```

伺服器的日期是固定的，第 5 題那筆訂票拿不到提前購票優惠；金額和之後揭曉頁的例子（含提前購票）不同是正常的。

③ 確認結果

```text
請檢查下列三件事，不要修改任何檔案：1. notes/b2.md 的「B2 變更審查」以最新一次（未標「已重答」）的答案為準，五題都有答案並附了指令；2. 改過的既有期待值，每一處都附 Rule ID 和我們的核准紀錄；3. 已有「B2 第一段」這個 Git Commit。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

失敗時：

```text
不要擴大範圍。請解釋審查裡回答「否」或「不確定」的題目：發生了什麼、為什麼；提出修正做法，我們同意會回「同意修正」，收到後再修正，重跑 pytest -q，再回答一次審查五題。新答案接在 notes/b2.md「B2 變更審查」後面，舊答案保留並標「已重答」。五題都答「是」就把目前狀態 Commit 成「B2 第一段」，然後停下。
```
