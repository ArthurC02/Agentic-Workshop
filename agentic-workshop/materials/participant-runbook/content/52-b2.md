# B2：導入不可疊加的最有利優惠政策

```callout info
現在在做什麼
- **情境**：公司要改優惠政策：旅客同時符合多項優惠時，只給一項對他最有利的，不能疊加。
- **你的目標**：11 分鐘內選定做法、讓 Agent 實作，並用測試證明每位旅客的優惠符合新規則。
- **今天的技巧**：**請 Agent 提 2–3 個方案並比較，人來選**。比較表把做法、影響範圍和風險攤開給你們看。
- **完成的樣子**：`notes/b2.md` 有方案比較、選擇理由、變更審查和驗收對照表；訂票、改票都照新政策計價；全套測試零失敗。
```

## 檢查點 1 · 請 Agent 提方案並比較，人來選（第 52–55 分鐘）

① 為什麼做這一步

起點是小組驗收過的 B1。這一步 Agent 只分析、比較方案，不改任何檔案。你判斷：

- 2–3 個方案都真的可行，不是一個方案配兩個陪襯
- 每個方案都對照過任務卡的禁止事項
- 每個假設都標了依據或「未確認」

② 貼給 Agent

複製下方提示詞，再按上方任務卡的「複製 Markdown」接在後面，一起貼給主要 Agent：

```text
新任務 TASK-B2-001，任務卡附在後面：優惠改成旅客同時符合多項時，只給一項對他最有利的，不疊加。開工前先存一版「B2 起點」（沒有變更也存），之後的變更都和它比。B1 的結果在 notes/ 裡。
先別改程式，先仔細想過：給我 2–3 個可行方案（A、B、C）比較改動範圍（一定要改／可能影響／不應改，附檔案或測試名稱）、風險、測試影響和建議，違反任務卡禁止事項的直接標出來。說明你推薦哪個、為什麼、最大風險是什麼，再把推薦方案拆成 3–5 步（標 Rule ID 或 AC）。你做的假設附依據，沒有依據的標「未確認」。
寫進 notes/b2.md，對話給我 5 行以內的摘要。
```

有「未確認」的假設會改變你們的選擇，而且還不到第 54 分鐘，才貼這段「追問假設」；否則直接核准：

```text
你最沒把握的是哪個假設？拿出依據：任務卡原文、測試名稱或實際執行結果。拿不出的標「未確認」，說它錯了會影響哪個方案，補進 notes/b2.md。
```

討論完要核准時，貼這段「核准方案」。Agent 會先問你們選哪個方案，用一句話回答就好。第 55 分鐘前核准就好；實作可以延續到檢查點 2 的時間，等 Agent 停下回報再貼檢查點 2 ②。核准後是小步修改，不用深想：工具有推論強度設定，就先調回低或預設。

```text
我們要核准方案了。先問我們選哪個、一句理由、這段做到第幾步（沒意見就照你的建議），收到回答再照那個方案做，做完這一段就停下，用 check 檢查，最後一行寫成功或失敗。
```

Agent 依 `AGENTS.md` 會先列出「因新規則而過時的期待值」並停下：先看檢查點 2 ① 的三點，都成立就回「核准更新」，否則回「請改程式，不要改測試」。

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：有「B2 起點」，方案比較的假設都標了依據或「未確認」，核准紀錄寫了選定方案與理由。
```

失敗時：

```text
先停。哪一項不符？只補缺的 Commit 或 notes/b2.md，不要再改程式。
```

④ 補充

```callout tip
技巧：推論強度與結構化輸出（加深一層）
**比較方案時想深一點、用固定欄位；核准後實作時調回來。**
- **推論強度**：比較方案、找風險時，工具有推論強度設定就調到高
- **結構化輸出**：比較表用固定欄位，幾個方案才能逐欄並排比較
📖 延伸閱讀：Anthropic 官方文件〈Effort〉與〈Thinking〉、OpenAI 官方文件〈Reasoning models〉（含 reasoning effort）、Anthropic 官方文件〈Structured outputs〉、OpenAI 官方文件〈Structured model outputs〉；你所用工具的官方文件通常有同名章節。
```

```callout tip
💬 討論一下
**口頭討論就好，結論直接告訴 Agent。**
1. 有沒有「未確認」的假設，錯了就會改變你們的選擇？
2. 你們會選哪個方案？推薦方案最大的風險，你們能接受嗎？
```

## 檢查點 2 · 依選定方案實作（第 55–59 分鐘）

① 為什麼做這一步

主要 Agent 做完第一段會停下，換你們看證據：

- 變更審查五題（`AGENTS.md` 審查準則三題加這段兩題）都答「是」，才放行
- 多優惠旅客每人只採一項優惠，而且是對他最有利的那一項。先自己對照任務卡，再看 Agent 回報

Agent 列出「因新規則而過時的期待值」時，下面三點都成立才回「核准更新」。說不出 Rule ID 的，請它改程式，不要改測試：

- 舊期待只在舊規則下才對
- 新規則確實要求不同結果
- 附了 Rule ID

② 貼給 Agent

```text
先不要再改。照 AGENTS.md 的審查準則做變更審查，起點是「B2 起點」（核准更新的測試算在核准範圍裡），再加兩題：
4. 優惠政策沒放在 API 路由層，訂票和改票重新計價用同一套政策。
5. 挑一位同時符合多項優惠的旅客（例如企業會員 M002 帶一位成人、一位學生），重新啟動伺服器實際建一筆訂票，列出每人採用的優惠、折扣率和金額。
附驗收對照表，寫進 notes/b2.md；五題都是「是」就存成「B2 第一段」。做完用 check 檢查，最後一行寫成功或失敗。
```

伺服器的日期是固定的，第 5 題那筆訂票拿不到提前購票優惠；金額和之後揭曉頁的例子（含提前購票）不同是正常的。

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：改過的既有期待值都附了 Rule ID 和我們的核准紀錄，有「B2 第一段」。
```

失敗時：

```text
先停，不要擴大範圍。回答「否」或「不確定」的那幾題發生了什麼事？提出修正做法，我們回「同意修正」再改；改完重新審查，舊答案保留並標「已重答」，五題都是「是」再存成「B2 第一段」。
```

## 檢查點 3 · 補測試、更新文件並交付（第 59–63 分鐘）

① 為什麼做這一步

不再加新功能，把證據補齊再交付。你判斷：

- 每位旅客的優惠類型與折扣率，是系統實際回應的，也符合任務卡；不要只核對總額
- 改過的既有期待值，都列了 Rule ID 和你們的核准紀錄

摘要和你們看過的證據不一致時以證據為準，看完在頁尾「B2 決定」選第 63 分鐘的決定。

② 貼給 Agent

```text
不再加功能，把證據補齊交付：AC-B2-001～013 每條都要有測試或文件證據，缺的補幾個代表組合（含不同旅客採不同優惠、改票重新計價）；跑全套測試；docs/ 裡講優惠的文件和 API 範例照實際程式更新（含 ADR 002 的狀態）；對照「B2 起點」說明 tests 有沒有刪測試或改期待值。附驗收對照表和交付摘要，寫進 notes/b2.md。做完用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：AC-B2-001～013 每列都有結果和證據，測試沒有比上一段少。
```

失敗時（第 59 分鐘還在實作，或時間不夠）：

```text
停止加功能。把方案設計、代表測試案例和更新過的文件寫進 notes/b2.md，列出還缺什麼、哪些未驗證，不要說已完整交付。
```
