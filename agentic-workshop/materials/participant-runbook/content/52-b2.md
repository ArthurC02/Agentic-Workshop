# B2：導入不可疊加的最有利優惠政策

```callout info
現在在做什麼
- **情境**：公司要改優惠政策：旅客同時符合多項優惠時，只給一項對他最有利的優惠，不能疊加。
- **你的目標**：11 分鐘內選定一個做法、讓 Agent 實作，並用測試證明每位旅客拿到的優惠符合新規則。
- **今天的技巧**：請 Agent 提 2–3 個方案並比較，人來選。Agent 的第一個答案不一定最好；用固定欄位的比較表（**結構化輸出**）把做法、影響範圍與風險攤開，選擇權留在人手上。比較時調高**推論強度**，實作時調回低。
- **完成的樣子**：`notes/b2.md` 有方案比較、你們選的方案與理由、變更審查答案與驗收對照表；建立訂票與改票都依新政策計價；全套測試零失敗。
```

本段 Agent 從 **Teammate**（隊友）過渡到 **Digital Worker**（數位員工：能在核准範圍內獨立執行任務的 Agent）：Agent 分析、比較方案，核准後主導實作與測試，紀錄都寫進 `notes/b2.md`；你們質疑假設、選方案、核准工作拆解（Task Breakdown），最後決定接受與否。

```callout warning

Agent 先只分析、比較方案，不改程式。第 55 分鐘前選定方案並核准，主要 Agent 才開始實作；每段做完都要停下等你們看證據。
```

## 檢查點 1 · 請 Agent 提方案並比較，人來選（第 52–55 分鐘）

起點是小組已驗收的 B1，或主持人核准提供的 B1 復原基線（見本頁最後的「必要時受控接續」）。這一步 Agent **只分析、比較方案，不改任何檔案**。

為什麼要它給 2–3 個方案：只有一個答案時，你只能「接受或不接受」；有比較表，你才看得出每個做法要改哪裡、風險在哪，選擇權才真的在你手上。

```callout tip
技巧：推論強度（加深一層）
個人分析時學過推論強度（同一個模型可以調「想多深」），這次用在比較方案、找風險：若你的工具有推論強度設定，這一步調到高；沒有的話，提示詞裡的「先仔細想過再回答，列出你考慮過的可能」會代替。想越深越慢、越耗 Token，所以核准後實作時要調回來。
📖 延伸閱讀：Anthropic 官方文件〈Effort〉與〈Thinking〉、OpenAI 官方文件〈Reasoning models〉（含 reasoning effort）；你所用工具的官方文件通常有同名章節。
```

```callout tip
技巧：Structured Output（結構化輸出，加深一層）
Greenfield 學過結構化輸出（驗收對照表），這次多加一層：不只回報結果，連「做決定用的比較」也要求固定欄位。幾個方案才能逐欄並排比較，看出各自改哪裡、風險在哪，也能直接交給下一個 Agent 讀。
📖 延伸閱讀：Anthropic 官方文件〈Structured outputs〉、OpenAI 官方文件〈Structured model outputs〉；你所用工具的官方文件通常有同名章節。
```

## 檢查點 2 · 依選定方案分段實作（第 55–59 分鐘）

主要 Agent 做完第一段會停下。**換你們看證據**：不讀程式，改請它回答變更審查問題，再看每位旅客實際拿到的優惠。

```text
不要再修改。請用白話回答下列審查問題，每題附上實際執行的指令與結果摘要：
1. 這次改了哪些檔案？每個檔案改了什麼、為什麼？有沒有不在核准計畫裡的檔案？
2. 測試總數和上一次比有沒有變少？有沒有新增 skip 或 xfail？
3. 有沒有刪除測試，或修改既有測試的期待值？（請用 git diff 對照「B2 起點」Commit 檢查 tests 資料夾後回答）有修改期待值的，逐一列出測試名稱、對應的 Rule ID，以及我們核准的紀錄在 notes/b2.md 哪裡。
4. 優惠政策有沒有放在 API 路由層？訂票建立與改票重新計價是不是用同一套政策？
5. 列出驗收對照表；另外挑一位同時符合多項優惠的旅客（例如企業會員 M002 帶一位成人、一位學生），先停止並用目前版本重新啟動伺服器（埠號 8000），再用伺服器實際建立一筆訂票，列出每位旅客實際採用的優惠類型、折扣率與金額。
把以上答案寫進 notes/b2.md（標題「B2 變更審查」）。沒有問題的話，把目前狀態 Commit 成「B2 第一段」，然後停下。
```

**看到什麼算過關**

- 審查 1–4 題的答案都是「沒有超出範圍、沒有變少、沒有刪除測試、同一套政策」；改過的既有期待值，每一處都附 Rule ID，而且是你們核准過的（因新規則而過時），沒有其他期待值被改。

## 檢查點 3 · 補測試、更新文件並交付（第 59–63 分鐘）

**停止擴充，不再加新功能。** 補代表組合測試、同步文件，讓證據完整。

```text
不要再擴充功能。請：
1. 依任務卡 AC-B2-001～AC-B2-013 逐條確認都有測試或文件證據；缺的補代表組合測試，包含不同旅客採不同優惠，以及改票重新計價。
2. 執行全套測試 pytest -q，不要只跑單一測試。
3. 依實際程式同步更新 docs/ 裡說明優惠的文件與 API 範例（有 discount-overview.md 就改它；Recovery 版沒有時，改 business-rules.md／architecture.md 的優惠段落，以及 context.md 裡描述優惠順序的句子），列出更新了哪些檔案，並用白話說明文件寫的折扣規則和程式實際行為是否一致。
4. 用 git diff 對照「B2 起點」Commit 檢查 tests 資料夾（之前已 Commit 的修改也要算進來），告訴我有沒有刪除測試或修改既有測試的期待值；有修改的，逐一列出測試名稱、Rule ID 與我們的核准紀錄。
5. 請整理驗收對照表：每條驗收條件（或規則）一列，欄位是「編號、白話內容、結果（通過／失敗／未驗證）、依據的測試名稱」。最後一行寫測試總數：通過幾個、失敗幾個、跳過幾個。附上你實際執行的指令。
6. 把以上結果，加上一段交付摘要（選定方案、修改了哪些檔案、代表組合與全套測試結果、更新的文件、未完成項目與風險），寫進 notes/b2.md（標題「B2 驗證與交付」）。沒有實際執行過的項目標為「未驗證」。
做完停下等我們確認。
```

**看到什麼算過關**

- 驗收對照表最後一行失敗 0 個、跳過 0 個，測試總數沒有比上一段少；AC-B2-001～013 每一列都有結果與測試名稱。
- 每位旅客的優惠類型與折扣率是系統實際回應的，而且符合任務卡；不要只核對總額。
- Agent 明確回答沒有刪除測試；改過的既有期待值都列了 Rule ID 與你們的核准紀錄，其餘期待值都沒動，並附上實際檢查的指令。

**做決定**：在頁尾選第 63 分鐘的決定。`notes/b2.md` 的摘要和你們看過的證據不一致時，以實際確認為準，請 Agent 改正。
