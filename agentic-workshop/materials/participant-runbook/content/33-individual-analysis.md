# 個人 Agent 分析

```callout info
現在在做什麼
- **情境**：你接手的 B0 有若干測試沒過，文件寫了很多，但沒人保證文件和程式一致。
- **你的目標**：6 分鐘內，各自讓自己的 Agent 帶你看懂 B0：系統分成哪幾塊、規則寫在哪、哪裡文件和程式說法不一致。
- **今天的技巧**：**讓 Agent 帶你讀陌生專案**。你不用讀程式，只要求每個結論都附來源。
- **完成的樣子**：`notes/analysis.md` 有系統地圖、規則位置、不一致清單，每個結論都標了事實、假設或缺口。
```

```callout warning
這段不修改程式
Agent 只讀、跑測試、啟動伺服器、寫 `notes/analysis.md`。它若開始改檔案，請它立刻停下並還原。繼續用第 31 分鐘開的同一個 Agent 對話；開了新對話，就先貼 [Time Skip 檢查點 2](#time-skip) 的規則與背景。
```

## 檢查點總覽

- **33–36 · 檢查點 1 請 Agent 畫系統地圖、指出規則在哪**
- **36–39 · 檢查點 2 請 Agent 標出文件與程式不一致處**

## 檢查點 1 · 請 Agent 畫系統地圖、指出規則在哪（第 33–36 分鐘）

① 為什麼做這一步

不要一開口就問「Bug 在哪」，先要一張地圖：系統分幾塊、規則寫在哪、測試現況如何。你判斷系統地圖說得出「誰負責什麼、依賴誰」，不是一串檔名；Agent 列得出它讀了哪些檔，而不是「讀了整個專案」。

② 貼給 Agent

```text
先不要修改程式。請帶我讀這個專案，先仔細想過再回答。不要一次讀整個專案：先列出資料夾結構，只挑回答下面問題需要的重點檔來讀，最後列出你讀了哪些檔。
1. 系統地圖：從 README.md、docs/architecture.md 與 docs/adr 開始讀，用白話說明系統分成哪些部分、各負責什麼業務、彼此怎麼依賴（不要只列檔名）。
2. 規則在哪：商業規則寫在哪些文件、對應到程式的哪一部分（用白話說，不用貼程式）。
3. 測試現況：執行 pytest -q，只給摘要、不要貼完整輸出，告訴我通過、失敗、跳過各幾個；列出失敗測試的名稱，各用一句話說明它檢查什麼業務行為。先不要推論失敗原因。
4. 在背景啟動這個專案的伺服器（埠號 8000；啟動前先確認 8000 沒有其他程式在用，有的話就停下告訴我是哪個程式，不要停它），確認 http://127.0.0.1:8000/health 回傳 status=ok，告訴我 /docs 的網址。之後要換版本或結束時，先停止你啟動的伺服器。
請在 notes/analysis.md 先建好下方五個固定標題，這次只填前三節（系統地圖、規則在哪、測試現況），後兩節留白；附上你實際執行的指令，做完停下等我。
固定格式：## 系統地圖／## 規則在哪／## 測試現況／## 文件與程式不一致處／## 還不確定的事；每個結論後面標「事實（來源）」「假設（依據）」或「缺口（缺什麼）」。
```

③ 確認結果

```text
請檢查下列三件事，不要修改任何檔案：1. notes/analysis.md 有五個固定標題，前三節都有內容，每個結論都標了事實、假設或缺口；2. 「測試現況」的數字和 notes/time-skip.md 記下的一致；3. http://127.0.0.1:8000/health 回傳 status=ok。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

失敗時：

```text
請用白話說明哪一項不符、為什麼，只補齊 notes/analysis.md 缺的部分或重新啟動伺服器，不要修改任何程式，做完告訴我。
```

④ 補充

```callout tip
技巧：模型選擇與推論強度
**模型選擇**：機械性的工作（跑測試、整理格式）用快速、便宜的模型；分析陌生程式、比較取捨、自主執行用較強的模型。**推論強度**（Reasoning Effort）：同一個模型可以調「想多深」，想越深越慢、越耗 Token。分析陌生程式要想深一點：工具有模型選單或推論強度設定，就選較強的模型、調高推論強度；沒有的話，提示詞裡的「先仔細想過再回答」會代替。
📖 延伸閱讀：Anthropic 官方文件〈Choosing the right model〉與〈Effort〉、OpenAI 官方文件〈Reasoning models〉（含 reasoning effort）；你所用工具的官方文件通常有同名章節。
```

```callout tip
技巧：Token 節費（加深一層）
不要叫 Agent「讀整個專案」：那最耗 Token，也最容易讀到後面忘了前面。先列目錄、挑重點檔讀，再回報讀了哪些。
📖 延伸閱讀：Anthropic Engineering 文章〈Effective context engineering for AI agents〉；你所用工具的官方文件通常有同名章節。
```

聽不懂系統地圖時，貼：「請用一個訂票的例子，從使用者送出請求開始，用白話再說一次系統地圖，不要用程式名詞。不要修改任何檔案。」

## 檢查點 2 · 請 Agent 標出文件與程式不一致處（第 36–39 分鐘）

① 為什麼做這一步

文件是線索，不是結論。Agent 把「文件說的、測試期待的、程式實際做的」三者對照後，由你挑一個「事實」追問證據：追問是本段最重要的動作。你判斷「事實」都附得出來源，Agent 用「可能」「應該」的地方已標成假設。

② 貼給 Agent

```text
先不要修改程式。先仔細想過再回答，請對照三樣東西：文件寫的規則（docs/ 裡的文件）、測試的期待、程式實際的行為，用白話回答：
1. 每個失敗測試：規則怎麼說、測試期待什麼、程式實際做了什麼；三者哪裡一致、哪裡不一致。
2. 其他文件與程式說法不一致的地方，各寫出文件位置。
3. 每個結論標「事實」（附文件位置、測試名稱或執行過的指令）、「假設」（說明依據與還缺什麼證據）或「缺口」（查不清楚、需要問人）。
把結果寫進 notes/analysis.md 的「文件與程式不一致處」與「還不確定的事」兩節。
4. 寫完後，列出你標為「事實」的結論並加上編號，然後停下等我選一個追問。我選了之後，請引用規則或文件原文、測試名稱，並重新執行相關測試貼出結果；拿不出證據就把它在 notes/analysis.md 改標為假設，並告訴我改了什麼。
```

Agent 寫完會列出編號，你只要回「追問第 N 個」。時間不夠（已到第 39 分鐘）就跳過追問。

③ 確認結果

```text
請檢查下列兩件事，不要修改任何檔案：1. notes/analysis.md 的「文件與程式不一致處」與「還不確定的事」都有內容，每個結論都標了事實、假設或缺口；2. 標「事實」的每一條都附了文件位置、測試名稱或執行過的指令，查不清楚的都列在「還不確定的事」。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

失敗時：

```text
請把沒附來源的「事實」改標為假設，查不清楚的移到「還不確定的事」，只改 notes/analysis.md，改完告訴我改了哪幾條。
```

第 39 分鐘停止，帶著 `notes/analysis.md` 進入 [共同脈絡（Shared Context）](#shared-context)。

## 完成後想一想

先自己想 30 秒，再和旁邊的人聊；主持人會請 1–2 位分享第 2 題。

1. **觀察**：你追問的那個「事實」，Agent 拿得出證據嗎？有沒有哪個結論一追問就改標成假設？
2. **技巧**：如果一開始就叫 Agent「讀整個專案、告訴我 Bug 在哪」，你會拿到什麼？你工作上接手陌生程式時，第一個提示詞會怎麼問？
3. **延伸**：你的 Agent 和隔壁同學的 Agent 讀的是同一份 B0。如果兩份分析說法不同，你們要怎麼決定該信哪一份？
