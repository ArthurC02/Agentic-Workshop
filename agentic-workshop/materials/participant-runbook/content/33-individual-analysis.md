# 個人 Agent 分析

```callout info
現在在做什麼
- **情境**：你接手的 B0 有若干測試沒過，文件寫了很多，但沒人保證文件和程式一致。
- **你的目標**：6 分鐘內，各自讓自己的 Agent 帶你看懂 B0：系統分成哪幾塊、規則寫在哪、哪裡文件和程式說法不一致。
- **今天的技巧**：**讓 Agent 帶你讀陌生專案**。請它畫系統地圖、指出規則在哪、標出文件與程式不一致處；你不用讀程式，只要求每個結論都附來源。提示詞示範三個 Agent 技巧：Token 節費（先列目錄、只讀重點檔）、模型選擇與推論強度（這段第一次學：分析陌生程式要想深一點）、結構化輸出（固定標題寫進 notes）。
- **完成的樣子**：`notes/analysis.md` 有系統地圖、規則位置、不一致清單，每個結論都標了事實、假設或缺口。
```

```callout warning
這段不修改程式
Agent 只讀、跑測試、寫 `notes/analysis.md`；不要讓它修改、刪除或弱化任何程式與測試。它若開始改檔案，請它立刻停下並還原。本段內容已在第 29 分鐘解鎖，用的是第 31 分鐘開的同一個 Agent 對話；如果開了新對話，先貼 [Time Skip 檢查點 2](#time-skip) 的規則與背景。
```

## 檢查點總覽

時間是**最晚**完成的時間；提早完成就直接進入下一個檢查點。

- **33–36 · 檢查點 1 請 Agent 畫系統地圖、指出規則在哪**：Agent 說明系統各部分、規則所在與失敗測試，寫進 `notes/analysis.md` 後停下。
- **36–39 · 檢查點 2 請 Agent 標出文件與程式不一致處**：Agent 對照文件、測試與程式，標事實／假設／缺口；你挑一個結論追問證據。

## 檢查點 1 · 請 Agent 畫系統地圖、指出規則在哪（第 33–36 分鐘）

接手陌生專案時，不要一開口就問「Bug 在哪」。先要一張地圖：系統分幾塊、規則寫在哪、測試現況如何，之後每個判斷才有座標。提示詞已附好紀錄格式，貼上即可。

```callout tip
技巧：模型選擇與推論強度
**模型選擇**：簡單、機械性的工作（跑測試、整理格式、改文字）用快速、便宜的模型；分析陌生程式、設計取捨、自主執行用推理能力較強的模型。**推論強度**（Reasoning Effort）：同一個模型可以調「想多深」，分析、找原因、比較方案調高，小步明確的修改調低；想越深越慢、越耗 Token。分析陌生程式最需要想：若你的工具有模型選單或推論強度設定，這段選較強的模型、調高推論強度；沒有的話，提示詞裡「先仔細想過再回答」就是替代。
📖 延伸閱讀：Anthropic 官方文件〈Choosing the right model〉與〈Effort〉、OpenAI 官方文件〈Reasoning models〉（含 reasoning effort）；你所用工具的官方文件通常有同名章節。
```

```callout tip
技巧：Token 節費（加深一層）
Time Skip 學過 Token 節費，這次多加一招：不要叫它「讀整個專案」──那最耗 Token，也最容易讀到後面忘了前面；先列目錄、挑重點檔讀，再回報讀了哪些。紀錄格式則是 Greenfield 學過的結構化輸出：固定五個標題，小組下一段才比得起來。
📖 延伸閱讀：Anthropic Engineering 文章〈Effective context engineering for AI agents〉；你所用工具的官方文件通常有同名章節。
```

```text
先不要修改程式。請帶我讀這個專案，先仔細想過再回答。不要一次讀整個專案：先列出資料夾結構，只挑回答下面問題需要的重點檔來讀，最後列出你讀了哪些檔。
1. 系統地圖：從 README.md、docs/architecture.md 與 docs/adr 開始讀，用白話說明系統分成哪些部分、各負責什麼業務、彼此怎麼依賴（不要只列檔名）。
2. 規則在哪：商業規則寫在哪些文件、對應到程式的哪一部分（用白話說，不用貼程式）。
3. 測試現況：執行 pytest -q，只給摘要、不要貼完整輸出，告訴我通過、失敗、跳過各幾個；列出失敗測試的名稱，各用一句話說明它檢查什麼業務行為。先不要推論失敗原因。
請依照下方固定格式寫進 notes/analysis.md 的前三節，附上你實際執行的指令，做完停下等我。
固定格式：## 系統地圖／## 規則在哪／## 測試現況／## 文件與程式不一致處／## 還不確定的事；每個結論後面標「事實（來源）」「假設（依據）」或「缺口（缺什麼）」。
```

**看到什麼算過關**：

- 系統地圖說得出「誰負責什麼、依賴誰」，不是一串檔名。
- 測試數字和 `notes/time-skip.md` 記下的一致。
- Agent 列得出它讀了哪些檔，而不是「讀了整個專案」。

**如果卡住**：聽不懂就貼這段：

```text
請用一個訂票的例子，從使用者送出請求開始，用白話再說一次系統地圖，不要用程式名詞。不要修改任何檔案。
```

## 檢查點 2 · 請 Agent 標出文件與程式不一致處（第 36–39 分鐘）

文件是線索，不是結論。這一步請 Agent 把「文件說的、測試期待的、程式實際做的」三者對照，再由你挑一個結論追問證據——追問是本段最重要的動作。

```text
先不要修改程式。先仔細想過再回答，請對照三樣東西：文件寫的規則（docs/ 裡的文件）、測試的期待、程式實際的行為，用白話回答：
1. 每個失敗測試：規則怎麼說、測試期待什麼、程式實際做了什麼；三者哪裡一致、哪裡不一致。
2. 其他文件與程式說法不一致的地方，各寫出文件位置。
3. 每個結論標「事實」（附文件位置、測試名稱或執行過的指令）、「假設」（說明依據與還缺什麼證據）或「缺口」（查不清楚、需要問人）。
把結果寫進 notes/analysis.md 的「文件與程式不一致處」與「還不確定的事」兩節。
4. 寫完後，列出你標為「事實」的結論並加上編號，然後停下等我選一個追問。我選了之後，請引用規則或文件原文、測試名稱，並重新執行相關測試貼出結果；拿不出證據就把它在 notes/analysis.md 改標為假設，並告訴我改了什麼。
```

Agent 寫完會列出編號，你只要回「追問第 N 個」。時間不夠（已到第 39 分鐘）就跳過追問，直接進下一段。

**看到什麼算過關**：

- 「事實」都附得出來源；Agent 用「可能」「應該」的地方標成假設。
- 查不清楚的列在「還不確定的事」，沒有被寫成已證實。

## 完成後想一想

不用填表、不用寫下來，自己想一想就好：

1. **觀察**：你追問的那個「事實」，Agent 拿得出證據嗎？有沒有哪個結論一追問就改標成假設？
2. **技巧**：如果一開始就叫 Agent「讀整個專案、告訴我 Bug 在哪」，你會拿到什麼？你工作上接手陌生程式時，第一個提示詞會怎麼問？
3. **延伸**：你的 Agent 和隔壁同學的 Agent 讀的是同一份 B0。如果兩份分析說法不同，你們要怎麼決定該信哪一份？

```text
請根據 notes/analysis.md 提醒我這段實際發生了什麼（哪些結論標成事實、哪些標成假設、我追問了哪一個、結果如何），幫我回答第 1 題的事實部分，但不要替我下結論。不要修改任何檔案。
```

```callout tip
💬 討論一下
先自己想 30 秒，再跟旁邊的人各說一個答案：你的 Agent 標成「假設」或「缺口」最多的是哪一塊？
```

這段學到的技巧：**讓 Agent 帶你讀陌生專案：要地圖、要規則位置、要不一致清單，每個結論都要來源。** Teammate 階段的 Agent 技巧：分析時用強模型、高推論強度，但只讀重點檔省 Token；結論用固定標題寫進 notes，下一段小組才比得起來。
