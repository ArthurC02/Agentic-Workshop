# 個人 Agent 分析

```callout info
現在在做什麼
- **情境**：你接手的 B0 有幾個測試沒過；文件寫了很多，但沒人保證和程式一致。
- **你的目標**：6 分鐘內讓自己的 Agent 帶你看懂 B0：分成哪幾塊、規則在哪、文件和程式哪裡不一致。
- **今天的技巧**：**讓 Agent 帶你讀陌生專案**。你不用讀程式，只要每個結論都附來源。
- **完成的樣子**：`notes/analysis.md` 有系統地圖、規則位置、不一致清單，每個結論都標了事實、假設或缺口。
```

```callout warning
這段不修改程式
**Agent 只讀檔、跑測試、啟動伺服器、寫 `notes/analysis.md`。**
- 它開始改檔案，就請它立刻停下並還原
- 繼續用第 31 分鐘開的那個 Agent 對話
- 開了新對話，先照 [Time Skip 檢查點 2](#time-skip) 確認 Agent 讀到 `AGENTS.md`
```

## 檢查點總覽

- **33–36 · 檢查點 1 請 Agent 畫系統地圖、指出規則在哪**
- **36–39 · 檢查點 2 請 Agent 標出文件與程式不一致處**

## 檢查點 1 · 請 Agent 畫系統地圖、指出規則在哪（第 33–36 分鐘）

① 為什麼做這一步

先別問「Bug 在哪」，先要一張地圖：系統分幾塊、規則寫在哪、測試現況如何。你判斷地圖說得出「誰負責什麼、依賴誰」，而不是一串檔名。Agent 也要列得出讀了哪些檔，而不是「讀了整個專案」。

② 貼給 Agent

```text
先別改程式，帶我認識這個專案，先仔細想過再回答。不要讀整個專案：先看資料夾結構，只讀需要的檔，最後列出讀了哪些。
我想知道三件事：系統分成哪幾塊、各管什麼業務、彼此怎麼依賴（不要只列檔名）；商業規則寫在哪些文件、對到程式哪一部分；測試現況，失敗的測試各在檢查什麼業務行為（先不推論原因）。也把伺服器跑起來，給我 /docs 網址。
寫進 notes/analysis.md，只用這五個標題、不加別的：系統地圖、規則在哪、測試現況、文件與程式不一致處、還不確定的事；這次只填前三節，每節最多 5 條、一條一行。每個結論標「事實（來源）」「假設（依據）」或「缺口（缺什麼）」。做完用 check 檢查。
```

Agent 讀檔要一兩分鐘，先讀下方 ④ 的兩張技巧小卡，再看它的回覆。

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：五個標題都在，前三節每個結論都有標記，/health 正常。
```

失敗時：

```text
先停。哪一項不符？只補 notes/analysis.md 或重新啟動伺服器，不要改程式。
```

④ 補充

```callout tip
技巧：模型選擇與推論強度
**分析陌生程式要想深一點：選較強的模型、調高推論強度。**
- **模型選擇**：跑測試、整理格式這類機械性工作，用快速、便宜的模型；分析、比較取捨、自主執行，用較強的模型
- **推論強度**（Reasoning Effort）：同一個模型可以調「想多深」，越深越慢、越耗 Token
- 工具沒有這兩種設定時，提示詞裡的「先仔細想過再回答」就是替代做法
📖 延伸閱讀：Anthropic 官方文件〈Choosing the right model〉與〈Effort〉、OpenAI 官方文件〈Reasoning models〉（含 reasoning effort）；你所用工具的官方文件通常有同名章節。
```

```callout tip
技巧：Token 節費（加深一層）
**不要叫 Agent「讀整個專案」：那最耗 Token，也最容易讀到後面忘了前面。**
- 先列目錄、挑重點檔讀，再回報讀了哪些
📖 延伸閱讀：Anthropic Engineering 文章〈Effective context engineering for AI agents〉；你所用工具的官方文件通常有同名章節。
```

聽不懂系統地圖時，貼：「用一筆訂票當例子，從使用者送出請求開始，用白話再講一次系統地圖，不要用程式名詞。」

## 檢查點 2 · 請 Agent 標出文件與程式不一致處（第 36–39 分鐘）

① 為什麼做這一步

文件是線索，不是結論。Agent 對照「文件說的、測試期待的、程式實際做的」之後，由你挑一個「事實」追問證據，這是這段最重要的動作。你判斷每個「事實」都附得出來源，說「可能」「應該」的地方已標成假設。

② 貼給 Agent

```text
接著對照三樣：docs/ 寫的規則、測試期待的、程式實際做的，先仔細想過再回答。每個失敗測試三者哪裡一致、哪裡不一致；其他文件和程式說法不同的地方也列出來，附文件位置。寫進 notes/analysis.md 的後兩節，每節最多 5 條、一條一行，不加別的標題；每個結論照樣標事實、假設或缺口。
最後在對話列出你標為「事實」的結論（最多 5 條，加編號），我會挑一條追問；再用 check 檢查，最後一行寫成功或失敗。
```

Agent 對照時，先想好你最想追問哪一類結論（例如測試期待和文件說法不同的那條）。它列出編號後貼這段，把 N 換成你選的編號；已到第 39 分鐘就跳過追問：

```text
追問第 N 個：拿出規則或文件原文、測試名稱，重跑相關的測試給我看。拿不出證據就在 notes/analysis.md 改標為假設，告訴我改了什麼，再用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：標「事實」的每一條都附了來源。
```

失敗時：

```text
沒附來源的「事實」改標為假設，查不清楚的移到「還不確定的事」，只改 notes/analysis.md，改完告訴我改了哪幾條。
```

第 39 分鐘停止，帶著 `notes/analysis.md` 進入 [共同脈絡（Shared Context）](#shared-context)。

## 完成後想一想

先自己想 30 秒，再和旁邊的人聊；趁等 Agent 回報時聊，這段不另開全場分享。

1. **觀察**：你追問的那個「事實」，Agent 拿得出證據嗎？有沒有哪個結論一追問就改標成假設？
2. **技巧**：如果一開始就叫 Agent「讀整個專案、告訴我 Bug 在哪」，你會拿到什麼？你工作上接手陌生程式時，第一個提示詞會怎麼問？
3. **延伸**：你的 Agent 和隔壁同學的 Agent 讀的是同一份 B0。如果兩份分析說法不同，你們要怎麼決定該信哪一份？
