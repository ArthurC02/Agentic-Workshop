# 個人 Agent 分析

這是 **6 分鐘的個人**任務。請各自使用自己的 Agent 理解同一份 B0，把結果記錄成可比較的成果，供第 39 分鐘的小組比較使用。Agent 在此階段是 **Teammate**（隊友）：協助你分析 Repository、影響、風險與缺口，判斷仍由你負責。

```callout warning
此階段不修改程式
個人分析階段不得修改程式。不要讓 Agent 修改、刪除或弱化任何程式與測試；只閱讀、執行測試與記錄。你不需要讀程式：請 Agent 用白話說明程式、規則、測試三者是否一致，你判斷它說的每個結論是**事實**（Agent 實際查過、附得出來源）、**假設**（推論，還沒有證據）還是**缺口**（查不清楚、要問人），並記下證據。本段分成 2 個檢查點，每個檢查點結束時 Agent 必須停下，等你核對。
```

```callout info
投影畫面和這份 Runbook 怎麼分工
投影畫面只顯示**時間**和**現在進行到第幾個檢查點**。要做什麼、要貼給 Agent 的提示詞、要填的欄位，全部在本頁。本段內容已在第 29 分鐘解鎖，不需要另外輸入解鎖碼。
```

## 檢查點總覽

時間是**最晚**完成的時間；提早完成就直接進入下一個檢查點。

| 檢查點 | 全場分鐘 | 段內時間 | 你要完成的事 |
|---|---:|---:|---|
| 1 · 理解 B0 與測試 | 33–36 | 00–03 | 讀 Context；Agent 用白話說明系統與測試結果後停下；你核對測試數字 |
| 2 · 證據與推論 | 36–39 | 03–06 | Agent 說明程式、規則、測試是否一致後停下；你判斷事實／假設／缺口，填完分析表 |

兩個檢查點都填同一張個人 Agent 分析表（在本頁下方）。

## 檢查點 1 · 理解 B0 與測試（第 33–36 分鐘）

- [ ] 閱讀 [B0 系統 Context 與已知限制](#b0-context)；Repository 的 `README.md`、`docs/architecture.md` 與 ADR 可請 Agent 用白話摘要。
- [ ] 沿用第 30 分鐘在 B0 資料夾開的 Agent Session（已貼過工作規則）。如果開了新對話，先貼上 [Time Skip 檢查點 2](#time-skip) 的「Agent 工作規則」。
- [ ] 把下方提示詞貼給你的 Agent：

```text
先不要修改程式。請閱讀 README.md、docs/architecture.md 與 ADR，用白話說明這個系統分成哪些部分、各負責什麼業務、彼此怎麼依賴（不要只列檔名）。然後執行 pytest -q，告訴我測試總數，以及通過、失敗、跳過各幾個；列出失敗測試的名稱，各用一句話說明它在檢查什麼業務行為。附上你實際執行的指令。先不要推論失敗原因，做完停下等我確認。
```

- [ ] Agent 停下後核對：它回報的測試數字和第 30 分鐘 [Time Skip 檢查點 4](#time-skip) 記下的結果一致嗎？系統摘要有沒有說出各部分負責什麼、彼此怎麼依賴，而不是只列檔名？聽不懂的地方，請 Agent 換個說法再解釋。
- [ ] Agent 若已經開始修改檔案，請它立刻停下並還原，回到只讀狀態。

**確認**：填下方分析表第 1 欄「系統模組摘要／依賴」、第 2 欄「失敗測試及實際輸出」。第 2 欄填 Agent 回報的實際數字與失敗測試名稱；和前一次結果不一致時寫下差異。

## 檢查點 2 · 證據與推論（第 36–39 分鐘）

- [ ] 把下方提示詞貼給 Agent：

```text
先不要修改程式。請對照三樣東西：公開規則（docs/business-rules.md 等文件）、測試的期待、程式實際的行為，用白話回答：
1. 每個失敗測試：規則怎麼說、測試期待什麼、程式實際做了什麼；三者哪裡一致、哪裡不一致。
2. 你的結論清單：每一項標「事實」（附你實際查到的文件位置、測試名稱或執行過的指令）或「推論」（說明推論依據，以及還缺什麼證據）。
3. 可能受影響的部分與理由、相關規則編號（Rule ID）與來源、風險與不宜修改的區域。
4. 還查不清楚、需要人決定或詢問的問題，以及建議的調查順序。
不要修改任何檔案，列完停下等我確認。
```

- [ ] 逐項判斷 Agent 的結論屬於哪一類，不需要讀程式：
  - **事實**：Agent 說得出來源（規則原文、測試名稱、實際執行的指令與結果）。
  - **假設**：Agent 用「可能」「應該」，或說不出來源。
  - **缺口**：Agent 查不到、說不清楚，或需要問人才能決定。
- [ ] 挑一個關鍵結論，請 Agent 再提證據：「〈結論〉的證據是什麼？請引用規則或文件原文、測試名稱，並重新執行相關測試，貼出結果。」說不出證據或結果對不上，就改標為假設。
- [ ] 未執行的測試、未驗證的原因，不寫成已證實；查不清楚的寫進「資訊缺口／待問問題」。
- [ ] 填完分析表第 3–9 欄。
- [ ] 第 39 分鐘停止。匯出或複製 Markdown，準備在 [Shared Context](#shared-context)（小組共同脈絡：小組整理出的共同事實）與小組比較。

```callout tip
不要只列檔名
請 Agent 說明各部分的責任、依賴與可能影響，並為每個關鍵結論附上來源（規則、測試或文件）。Agent 的結論若沒有證據，請標示為假設。
```

**確認**：分析表第 3 欄「可能根因／替代假設」、第 4 欄「受影響檔案與理由」、第 5 欄「相關 Rule ID 與來源」（Rule ID 即規則編號）、第 6 欄「規則／測試／程式是否一致」、第 7 欄「資訊缺口／待問問題」、第 8 欄「建議調查順序」、第 9 欄「風險／不宜修改區域」。
