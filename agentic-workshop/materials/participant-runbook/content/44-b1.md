# B1：修復學生票折扣異常

```callout info
現在在做什麼
- **情境**：客服回報學生旅客的票價好像算錯了，自動測試也有幾個相關案例失敗。
- **你的目標**：8 分鐘內讓 Agent 找出原因、只做最小的修正，並證明修好、沒有改壞其他票種。
- **今天的技巧**：用失敗測試找 Bug：重現 → 定位 → 最小修正 → 驗證。先讓 Agent 用測試證明 Bug 存在，修完再用同一個測試證明修好；「修前失敗、修後通過」是你不讀程式也能信任的證據。這套做法最後請 Agent 存成 **Skill**（可重複使用的工作說明），下次遇到 Bug 直接叫它照做。
- **完成的樣子**：`notes/b1.md` 有修前失敗、修後通過的測試對照與驗收對照表；全套測試零失敗；`skills/fix-bug-with-test.md` 已建立；你只在頁尾選了兩個決定。
```

本段 Agent 是 **Teammate**（隊友）：Agent 跑測試、找原因、修改，並把所有紀錄寫進 `notes/b1.md`；你們只做決定：核准修正計畫、最後接受與否。每一步都是「複製提示詞 → 貼給主要 Agent → 看回報 → 回一句話」。

## 檢查點 1 · 用失敗測試重現並找出原因（第 44–46 分鐘）

先別叫 Agent「修好」。這一步只讓它用失敗測試**證明 Bug 存在**、說出原因與證據，並提最小修正計畫；Agent 不改程式。

```callout tip
技巧：用失敗測試找 Bug
先有一個「現在會失敗」的測試，Bug 才算被重現；修完同一個測試變成通過，才算修好。你不讀程式，也能用「修前失敗、修後通過」判斷。這也是 Greenfield 學過的「先要計畫再動手」：找到原因後先提計畫，你核准才修改。
📖 延伸閱讀：pytest 官方文件〈Get Started〉、Claude Code 官方文件〈Best practices for Claude Code〉；你所用工具的官方文件通常有同名章節。
```

複製下方提示詞，再按上方任務卡的「複製 Markdown」，把任務卡接在提示詞後面，一起貼給主要 Agent。其他成員可以把同一段貼給自己的 Agent，比對找到的原因是否一致；其他成員的 Agent 找不到 `skills/team-rules.md` 與 `notes/shared-context.md` 就略過第一句，照 Time Skip 貼過的規則做。

```text
請先讀 skills/team-rules.md 並遵守；需要細節時再查 notes/shared-context.md，不要讀整個專案。
現在的任務是 TASK-B1-001，任務卡全文附在這段提示詞後面。先不要修改任何程式。請依序做：
1. 確認這個資料夾已經有「B0 baseline」的 Git Commit；有就直接往下做。只有缺少時才補建：沒有 .gitignore 先建立一個（內容三行：__pycache__/、.venv/、.pytest_cache/），再 git init 並把目前所有檔案 Commit 成「B0 baseline」；此時已有的 notes 與 skills 會一起記進去，這沒關係，程式仍是 B0 原樣。之後你才說得清楚改了什麼。
2. 重現：執行 pytest -q，只回報摘要（不要貼完整輸出），列出和學生票價有關的失敗測試；每一個寫出規則怎麼說、測試期待多少錢、系統實際算出多少錢。如果沒有任何測試直接重現任務卡描述的情況，就新增一個最小的測試，證明它現在會失敗（只新增測試，不修程式）。
3. 定位：這些失敗是不是同一個原因造成的？指出原因可能在哪裡，分開寫「有規則或測試證據的事實」和「還只是推論」。
4. 最小修正計畫：最多 3 步，每一步標出規則編號（Rule ID）或驗收條件（AC）；寫出哪些地方不應該改（成人、提前購票、企業會員與既有優惠選擇順序），以及修完要用哪幾個測試證明修好。
把以上結果寫進 notes/b1.md（標題「B1 重現與定位」），在對話用 5 行以內的白話摘要，然後停下等我們核准，不要修改程式。
```

**看到什麼算過關**

- 原因分成「有證據的事實」和「推論」；計畫最多 3 步，而且寫了不改哪些地方。
- Agent 還沒有改程式。

**做決定**：證據夠、範圍小 → 在頁尾「B1 決定」選「核准」，直接進檢查點 2。證據不足或計畫太大 → 選「退回補證據」，貼下方提示詞。

```text
先不要核准，也不要修改程式。請補證據：你的原因有沒有規則原文或測試結果支持？說不出依據的部分標成「推論」。計畫裡任何超出任務卡範圍的步驟都刪掉。把補充寫進 notes/b1.md，再用白話告訴我哪裡改了。
```

## 檢查點 2 · 只做最小修正（第 46–49 分鐘）

核准後，Agent 只照 `notes/b1.md` 的計畫修改；改完不用你讀程式，改請它回答「變更審查」問題，你只看答案是「是」還是「否」。

```text
計畫核准。核准人記 notes/shared-context.md「分工」裡的人員核准者，核准時間記你電腦上的現在時間，不用問我。
現在只依 notes/b1.md 的最小修正計畫修改，遵守 skills/team-rules.md；另外成人、提前購票、企業會員與既有優惠選擇順序都不改，也不全面重寫計價。
改完先只重跑檢查點 1 那幾個失敗測試，再執行 pytest -q；兩次都只回報摘要。然後不要再修改，用白話回答下列變更審查問題，每題附上實際執行的指令與結果摘要：
1. 這次改了哪些檔案？每個檔案改了什麼、為什麼？有沒有不在核准計畫裡的檔案？
2. 測試總數和上一次比有沒有變少？有沒有新增 skip 或 xfail？
3. 有沒有刪除測試，或修改既有測試的期待值？（請用 git diff 檢查 tests 資料夾後回答）
4. 列出驗收對照表。
把核准人與核准時間、修改說明與審查答案寫進 notes/b1.md（標題「B1 最小修正與變更審查」），然後停下等我們確認。
```

**看到什麼算過關**

- 改的檔案都在核准計畫裡；測試數沒有變少、沒有新增跳過。
- 沒有刪除測試、沒有改既有期待值。
- 任何一題是「否」或「不確定」→ 不放行，貼下方提示詞。

**如果卡住**

```text
不要再修改。請解釋變更審查裡回答「否」或「不確定」的那一題：發生了什麼、為什麼。把超出核准範圍的修改還原，重跑 pytest -q，再回答一次變更審查四題，寫進 notes/b1.md。
```
