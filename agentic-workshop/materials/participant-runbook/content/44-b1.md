# B1：修復學生票折扣異常

這是 **8 分鐘的小組**任務：確認根因與影響範圍，完成**最小安全修復**，驗證成人及混合旅客交易。

本階段 Agent 是 **Teammate**（隊友）：比較各自 Agent 的分析、查證規則與測試證據；由人核准修改範圍與主要 Agent 的計畫，Agent 依核准方案執行，人審查 Diff（程式修改內容）與測試。

```callout warning
未核准就不修改
本段分成 4 個檢查點。人核准範圍與計畫之前，主要 Agent 不修改任何檔案；每個檢查點結束時 Agent 必須停下，由你們確認並填好紀錄，才交代下一步。沒有人員核准，或證據仍不足時，先補缺口，不修改程式。
```

```callout info
投影畫面和這份 Runbook 怎麼分工
投影畫面只顯示**時間**和**現在進行到第幾個檢查點**。要做什麼、要貼給 Agent 的提示詞、要填的表單，全部在本頁。主持人換頁時，請跟著跳到本頁對應的檢查點。
```

## 檢查點總覽

時間是**最晚**完成的時間；提早完成就直接進入下一個檢查點。

| 檢查點 | 全場分鐘 | 段內時間 | 你要完成的事 |
|---|---:|---:|---|
| 1 · 分析與核准 | 44–46 | 00–02 | 讀任務卡；主要 Agent 只提根因、影響與計畫；補填 Shared Context；人核准 |
| 2 · 最小修復 | 46–49 | 02–05 | 核對計畫；主要 Agent 依核准範圍修改後停下；你們看 Diff |
| 3 · 完整測試 | 49–51 | 05–07 | 停止擴充；執行全套測試，保留實際結果 |
| 4 · 審查與交付 | 51–52 | 07–08 | 人審查 Diff、AC 與 Regression；填完修復摘要；第 52 分鐘停止 |

確認紀錄有兩處：檢查點 1 填 [Shared Context](#shared-context) 的「任務揭露後補填」欄位；檢查點 2–4 填本頁最下方的「B1 修復摘要」，每個檢查點只填其中幾欄。

## 檢查點 1 · 分析與核准（第 44–46 分鐘）

這一步主要 Agent **只分析與提計畫，不改任何檔案**。

- [ ] 全組讀上方任務卡：固定規則 `FARE-002`、`FARE-003`，以及 AC-B1-001～007（AC：Acceptance Criteria，驗收條件）。
- [ ] 在主要 Agent 的電腦確認有 Git 基準，之後才能用 `git diff` 看 Agent 改了什麼。`git status` 顯示不是 Git Repository 時，在 B0 Repository 資料夾建立：

```cmd
# powershell
git init
git add -A
git commit -m "B0 baseline"
# bash
git init
git add -A
git commit -m "B0 baseline"
```

- [ ] 把任務卡內容與整理好的 Shared Context 交給主要 Agent，貼上下方提示詞：

```text
現在的任務是 TASK-B1-001（任務卡如上）。先不要修改任何檔案。請對照我們的 Shared Context、公開規則 FARE-002／FARE-003 與目前失敗的測試，回答：
1. 根因假設與證據：規則、測試、程式各自指向哪裡；哪些只是推論。
2. 影響分析：一定要改／可能影響／不應改。
3. 最小安全修復的 5 至 8 步計畫，每一步標出 Rule ID 或 AC。
4. 測試計畫：要執行哪些測試，原 Regression 如何保留。
列出需要我們決定的問題，然後停下等我們核准。
```

- [ ] 比較主要 Agent 與各成員 Agent 的分析，保留分歧與假設；以公開規則、測試與程式交叉核對，不直接採用最肯定的那份摘要。
- [ ] 核對計畫只處理任務卡範圍：成人、提前購票、企業會員與既有優惠選擇順序不變；沒有全面重寫、不相關 API Contract（API 合約：對外的請求與回應格式）、新服務或新優惠政策。不合格就要求 Agent 重做計畫。
- [ ] 回到 [Shared Context](#shared-context)，補填全部「任務揭露後補填」欄位：任務 ID `TASK-B1-001`、起點版本 B0、規則來源 `FARE-002`／`FARE-003`、範圍與不處理項目、建議修改區域與不應修改區域、測試計畫、5–8 步計畫，以及核准人、時間、結論與條件。

```callout tip
證據不足時
Agent 的根因說不出規則或測試證據時，先要求補證據，不要核准。第 46 分鐘仍無法核准，就把缺口寫進 Shared Context 的「結論」，繼續補證據，不修改程式。
```

**檢查點 1 確認**：Shared Context 的「人員核准紀錄」四欄（核准人、時間、結論、條件）已填寫。沒有填，就不進入檢查點 2 的修改。

## 檢查點 2 · 最小修復（第 46–49 分鐘）

- [ ] 核對計畫：Agent 要執行的步驟與 Shared Context 記錄的核准計畫一致；超出範圍的步驟先刪掉。
- [ ] 由核准人用下方格式回覆主要 Agent。`〈 〉` 的內容由你們填寫：

```text
計畫核准。核准人：〈姓名〉；時間：第〈 〉分鐘。
核准的步驟：
〈列出核准的步驟〉

條件：最小修復，只處理任務卡範圍；成人、提前購票、企業會員與既有優惠選擇順序都不改；不刪除、弱化或隱藏測試，不用 Skip／XFail，不把正確期待值改成符合錯誤輸出；不全面重寫計價，不改不相關 API Contract，不新增依賴、服務或優惠政策。

現在依核准計畫修改。改完執行 pytest -q，貼出實際輸出與 git diff --stat，然後停下等我們審查，不要做計畫外的修改。
```

- [ ] Agent 執行時，其他成員填下方「B1 修復摘要」的**根因**、**影響分析**、**核准計畫**三欄。
- [ ] Agent 停下後看 Diff：`git diff --stat` 有沒有計畫外的檔案；`git diff -- src` 的修改是否最小、是否只動核准的區域；`git diff -- tests` 沒有刪除、放寬斷言或改期待值。
- [ ] Agent 擴大範圍、未核准就修改、或改了測試期待值 → 要求它停止該修改，回到核准範圍。

**檢查點 2 確認**：在「B1 修復摘要」填好根因、影響分析、核准計畫與**主要修改（Diff）**。

## 檢查點 3 · 完整測試（第 49–51 分鐘）

**停止擴充，不再加新修改。** 請執行**全套**測試（含 Regression 回歸測試：確認既有功能沒被改壞），不要只跑單一測試；記錄實際指令與輸出。

```cmd
# powershell
& '.\.venv\Scripts\python.exe' -m pytest -q
# bash
.venv/bin/python -m pytest -q
```

- [ ] 執行上方命令，確認輸出最後一行沒有 `failed`、`skipped`、`xfailed`。
- [ ] 確認：原本失敗的學生票相關測試全部恢復；成人與混合旅客案例通過（例如 700 基價的成人＋學生訂票總額（Booking Total）為 1225）。
- [ ] 測試仍失敗時，把實際輸出交給主要 Agent 修正，同樣不得擴大範圍；第 51 分鐘還沒全過，就停在現況，如實記錄。

**檢查點 3 確認**：在「B1 修復摘要」填好**完整測試指令**與**實際測試結果**（貼實際輸出，不要改寫或推測）。

## 檢查點 4 · 審查與交付（第 51–52 分鐘）

- [ ] 由人審查：對照 Diff、規則、金額與 AC，決定接受、要求修正或拒絕；不因 Agent 說「完成」就直接交付。
- [ ] 確認商業規則文件（`docs/business-rules.md`）仍記學生 75%，與程式一致；正確文件不必無意義重寫。
- [ ] 要求 Agent 整理簡短摘要，沒有實際執行過的項目標為「未驗證」：

```text
不要再修改。請整理 B1 交付摘要：根因、影響分析、核准計畫、修改檔案與 Diff 摘要、完整測試指令與實際輸出、規則／AC 對照、未完成事項。沒有實際執行過的項目標為「未驗證」。
```

- [ ] 用你們在檢查點 1–3 的紀錄核對 Agent 的摘要；不一致時以你們的實際確認為準。

**檢查點 4 確認**：在「B1 修復摘要」勾選規則／AC 對照（只勾已用實際結果確認的項目），填好對照證據、人員審查結論、簡短摘要與未完成事項。

```callout info
如實宣稱完成
只有實際完成驗收才能宣稱修復完成。8 分鐘到仍未完成時，保留分析與計畫、列明未完成事項後停止擴充。
```
