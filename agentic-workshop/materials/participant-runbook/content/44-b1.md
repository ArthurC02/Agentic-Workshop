## 檢查點 1 · 用失敗測試重現並找出原因（第 44–46 分鐘）

先別叫 Agent「修好」。這一步只讓它用失敗測試**證明 Bug 存在**、說出原因，並提最小修正計畫。

```callout tip
技巧：用失敗測試找 Bug
先有一個「現在會失敗」的測試，Bug 才算被重現；修完同一個測試變成通過，才算修好。「修前失敗、修後通過」是你不讀程式也能信任的證據。
📖 延伸閱讀：pytest 官方文件〈Get Started〉、Claude Code 官方文件〈Best practices for Claude Code〉；你所用工具的官方文件通常有同名章節。
```

複製下方提示詞，再按任務卡上方的「複製 Markdown」接在後面，一起貼給主要 Agent。其他成員也可以貼給自己的 Agent，比對找到的原因是否一致。

```text
請先讀 skills/team-rules.md 並照做（它會帶你讀 notes/shared-context.md），不要讀整個專案。
現在的任務是 TASK-B1-001，任務卡全文附在這段提示詞後面。先不要修改任何程式。請依序做：
1. 確認這個資料夾已經有「B0 baseline」的 Git Commit；有就直接往下做。只有缺少時才補建：沒有 .gitignore 先建立一個（內容三行：__pycache__/、.venv/、.pytest_cache/），再 git init 並把目前所有檔案 Commit 成「B0 baseline」；此時已有的 notes 與 skills 會一起記進去，這沒關係，程式仍是 B0 原樣。之後你才說得清楚改了什麼。
2. 重現：執行 pytest -q，只回報摘要（不要貼完整輸出），列出和學生票價有關的失敗測試；每一個寫出規則怎麼說、測試期待多少錢、系統實際算出多少錢。如果沒有任何測試直接重現任務卡描述的情況，就新增一個最小的測試，證明它現在會失敗（只新增測試，不修程式）。
3. 定位：這些失敗是不是同一個原因造成的？指出原因可能在哪裡，分開寫「有規則或測試證據的事實」和「還只是推論」。
4. 最小修正計畫：最多 3 步，每一步標出規則編號（Rule ID）或驗收條件（AC）；寫出哪些地方不應該改（成人、提前購票、企業會員與既有優惠選擇順序），以及修完要用哪幾個測試證明修好。
把以上結果寫進 notes/b1.md（標題「B1 重現與定位」），在對話用 5 行以內的白話摘要，然後停下等我們核准，不要修改程式。
```

**看到什麼算過關**

- Agent 列出失敗測試的名稱，以及每個「期待多少、實際多少」。
- 原因分成「有證據的事實」和「推論」；計畫最多 3 步，而且寫了不改哪些地方。
- Agent 還沒有改程式。

**做決定**：證據夠、範圍小 → 在頁尾「B1 決定」選「核准」，直接進檢查點 2。證據不足或計畫太大 → 選「退回補證據」，貼下方提示詞。

```text
先不要核准，也不要修改程式。請補證據：你的原因有沒有規則原文或測試結果支持？說不出依據的部分標成「推論」。計畫裡任何超出任務卡範圍的步驟都刪掉。把補充寫進 notes/b1.md，再用白話告訴我哪裡改了。
```

```callout tip
💬 討論一下
成員們的 Agent 找到的原因一樣嗎？不一樣時，哪一份有測試證據？（口頭討論就好，不用寫下來；第 46 分仍無法核准，就讓 Agent 繼續補證據，不修改程式。）
```

## 檢查點 2 · 只做最小修正（第 46–49 分鐘）

Agent 只照核准的計畫修改，改完回答變更審查問題；你只看每題答「是」還是「否」。

```text
計畫核准。核准人記 notes/shared-context.md「分工」裡的人員核准者，核准時間記你電腦上的現在時間，不用問我。
現在只依 notes/b1.md 的最小修正計畫修改，遵守 skills/team-rules.md；另外成人、提前購票、企業會員與既有優惠選擇順序都不改，也不全面重寫計價。
改完先只重跑檢查點 1 那幾個失敗測試，再執行 pytest -q；兩次都只回報摘要。然後不要再修改，先用白話列出這次改了哪些檔案、各改了什麼、為什麼；再對下列變更審查敘述回答「是／否／不確定」，每題附上實際執行的指令與結果摘要：
1. 改的檔案都在核准計畫裡。
2. 測試總數沒有比上一次少，也沒有新增 skip 或 xfail。
3. 沒有刪除測試，也沒有修改既有測試的期待值（請用 git diff 檢查 tests 資料夾後回答）。
最後列出驗收對照表。
把核准人與核准時間、修改說明與審查答案寫進 notes/b1.md（標題「B1 最小修正與變更審查」），然後停下等我們確認。
```

**看到什麼算過關**

- 改的檔案都在核准計畫裡；測試數沒有變少、沒有新增跳過。
- 沒有刪除測試、沒有改既有期待值。
- 三題全部是「是」才放行；任何一題是「否」或「不確定」→ 不放行，貼下方提示詞。

**如果卡住**

```text
不要再修改。請解釋變更審查裡回答「否」或「不確定」的那一題：發生了什麼、為什麼。把超出核准範圍的修改還原，重跑 pytest -q，再回答一次變更審查的三題敘述，寫進 notes/b1.md。
```

```text
不要再修改程式。請用檢查點 1 重現 Bug 的同一批測試證明修好：
1. 列出那幾個測試修正前和現在的結果對照（失敗／通過）。
2. 執行全套測試 pytest -q，不要只跑單一測試。請整理驗收對照表：每條驗收條件（或規則）一列，欄位是「編號、白話內容、結果（通過／失敗／未驗證）、依據的測試名稱」。最後一行寫測試總數：通過幾個、失敗幾個、跳過幾個。附上你實際執行的指令。
3. 用白話確認商業規則文件 docs/business-rules.md 仍記學生 75%，與程式實際行為一致；正確的文件不必重寫。
4. 重新啟動伺服器，讓它跑修改後的版本：先停止這個專案原本的伺服器（uvicorn smart_ticket，連同它開出的子程序）；再確認 8000 沒有其他程式在用，有的話就停下告訴我是哪個程式，不要停它；然後在背景用埠號 8000 啟動，告訴我 /docs 的網址。
5. 把這次「重現 → 定位 → 最小修正 → 驗證」的做法整理成 skills/fix-bug-with-test.md，寫成下次任何 Bug 都能照做的通用說明：什麼時候用、四個步驟、每步要交的證據、禁止事項、回報格式（驗收對照表）。不要寫進這次 Bug 的原因或修改內容。
把第 1–4 項的結果，加上一段交付摘要（原因、修改、測試結果、未完成或未驗證事項），寫進 notes/b1.md（標題「B1 驗證與交付」）。沒有實際執行過的項目標為「未驗證」。做完停下。
```

**看到什麼算過關**

- 同一批測試「修前失敗、修後通過」。
- 驗收對照表最後一行失敗 0 個、跳過 0 個；AC-B1-001～007 每一列都是「通過」，寫得出依據的測試名稱。

**做決定**：看上面兩點，不因 Agent 說「完成」就接受；在頁尾選第 52 分鐘的決定。

不要擴大範圍。請說明還有哪些測試失敗或哪個結果不符、可能原因是什麼。如果時間不夠修完，就停在現況，把未完成事項與未驗證項目如實列進 notes/b1.md，不要宣稱修復完成。

## 完成後想一想
