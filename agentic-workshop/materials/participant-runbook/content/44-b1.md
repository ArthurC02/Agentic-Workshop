# B1：修復學生票折扣異常

```callout info
現在在做什麼
- **情境**：客服回報學生票價好像算錯了，自動測試也有幾個相關案例失敗。
- **你的目標**：10 分鐘內讓 Agent 找出原因、只做最小的修正，並證明修好、沒改壞其他票種。
- **今天的技巧**：**用失敗測試找 Bug**。依序重現、定位、最小修正、驗證，最後把做法存成 Skill。
- **完成的樣子**：同一批測試修前失敗、修後通過，全套測試零失敗；`notes/b1.md` 和 `fix-bug-with-test` Skill 已寫好。
```

## 檢查點 1 · 用失敗測試重現並找出原因（第 52–55 分鐘）

① 為什麼做這一步

這一步先別叫 Agent 修，只讓它用失敗測試證明 Bug 存在、說出原因，再提最小修正計畫。你判斷：

- 原因有沒有分成「有證據的事實」和「推論」
- 計畫是否最多 3 步，並寫了不改哪些地方

證據夠、範圍小，就在頁尾「B1 決定」選「核准」；證據不足或計畫太大，就選「退回補證據」。

② 貼給 Agent

複製下方提示詞，再按任務卡上方的「複製 Markdown」接在後面，一起貼給主要 Agent。其他成員也可以貼給自己的 Agent，比對原因是否一致。

```text
新任務 TASK-B1-001，任務卡附在後面：客服回報學生票價算錯。先別改程式：
重現給我看（用失敗的測試；沒有測試直接重現任務卡的情況，就補一個現在會失敗的測試），把這批測試的名稱、期待和實際金額記成「修前結果」；找出原因，再給我最多三步的修正計畫，寫出哪些地方不該動、修完用哪些測試證明。有證據的事實和推論分開寫。
這步只跑相關的測試，不跑全套。寫進 notes/b1.md，對話給我 5 行以內的摘要。做完用 check 檢查（一樣只跑相關的測試），最後一行寫成功或失敗。
```

決定退回時，貼這段「補證據」：

```text
先不核准。你的原因有規則原文或測試結果支持嗎？說不出依據的標成推論，超出任務卡範圍的步驟刪掉，補進 notes/b1.md。
```

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：失敗測試都寫了期待金額和實際金額；除了 notes/ 和新增的測試，沒有改任何檔案。
```

失敗時：

```text
先停。哪一項不符？只補 notes/b1.md；改到程式就用 Git 還原，還不要修。
```

④ 補充

```callout tip
技巧：用失敗測試找 Bug
**「修前失敗、修後通過」是你不讀程式也能信任的證據。**
- 先有一個「現在會失敗」的測試，Bug 才算重現
- 修完後同一個測試變成通過，才算修好
📖 延伸閱讀：pytest 官方文件〈Get Started〉、Claude Code 官方文件〈Best practices for Claude Code〉；你所用工具的官方文件通常有同名章節。
```

```callout tip
💬 討論一下
**成員的 Agent 找到的原因一樣嗎？不一樣時，哪一份有測試證據？**
- 口頭討論就好，不用寫下來
- 第 55 分鐘還不能核准，就讓 Agent 繼續補證據，不修改程式
```

## 檢查點 2 · 只做最小修正（第 55–58 分鐘）

① 為什麼做這一步

Agent 只照核准的計畫修改，改完照 `AGENTS.md` 的審查準則回答變更審查三題。你不讀程式，只看這三題的答案。三題都是「是」才放行；有一題是「否」或「不確定」，就貼「失敗時」那段。

② 貼給 Agent

```text
計畫核准，照 notes/b1.md 的計畫修。修完先重跑剛才失敗的那幾個測試，再跑全套；然後照 AGENTS.md 的審查準則做變更審查，附驗收對照表，寫進 notes/b1.md。做完用 check 檢查（沿用剛才全套測試的結果，不重跑），最後一行寫成功或失敗。
```

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：變更審查三題都是「是」，剛才失敗的測試都通過了。
```

失敗時（審查有一題是「否」或「不確定」，或檢查點 1 的測試仍失敗）：

```text
先停，不要擴大範圍。回答「否」或「不確定」的那一題（或還沒過的測試）發生了什麼事？超出核准範圍的修改先還原，再重新審查一次；舊答案保留並標「已重答」。
```

④ 補充

```callout info
新概念：審查準則
**變更審查要答哪三題、哪些算「重要」，由人寫進 `AGENTS.md` 的「審查準則」，之後每段都照這一份。**
- 三題：改的檔案都在核准範圍裡；測試沒變少、沒新增 skip；沒刪測試、沒改未經核准的期待值
- 任一題不是「是」，或說通過卻拿不出實際執行的結果，就是「重要」問題，不放行
- 回到工作：把團隊的審查準則寫成一頁，寫清楚什麼算重要、小問題最多報幾條
📖 延伸閱讀：Anthropic〈The AI-native SDLC playbook〉；你所用工具的官方文件通常有同名章節。
```

## 檢查點 3 · 用同一個測試證明修好（第 58–62 分鐘）

① 為什麼做這一步

用檢查點 1 重現 Bug 的同一批測試證明修好，不再加新修改，也不因 Agent 說「完成」就接受。你判斷：

- 同一批測試「修前失敗、修後通過」
- 驗收對照表下的測試數：失敗 0 個、跳過 0 個
- AC-B1-001～007 每一列都「通過」，也寫得出測試名稱（文件類 AC 寫文件位置）
- Skill 的 description 讀起來像你們回報 Bug 時會說的話；不像，就回一句請它加上你會說的話

看完在頁尾「B1 決定」選決定；第 62 分鐘看投影停手，一起看 B1 揭曉。

② 貼給 Agent

```text
不要再改程式，證明修好：把 notes/b1.md 的「修前結果」和檢查點 2 的修後結果並排對照，不用重跑修前；檢查點 2 之後沒改過程式，就沿用那次的全套測試結果。把驗收對照表補齊 AC-B1-001～007（文件類寫文件位置），確認 docs/business-rules.md 和程式一致，連同交付摘要寫進 notes/b1.md。
再把這次「重現、定位、最小修正、驗證」的做法存成 fix-bug-with-test Skill，放在你這個工具會自動載入專案 Skill 的位置：description 用第三人稱寫它做什麼、什麼時候用，帶進我們回報 Bug 時會說的話（例如「算錯」「修一下」）；內文只寫步驟和每步要交的證據，你本來就懂的不用解釋，也不寫這次的原因。把 description 和完整路徑給我，做完用 check 檢查（一樣沿用，不重跑測試），最後一行寫成功或失敗。
```

Agent 建立 Skill 資料夾時，工具若跳出允許視窗，按允許。

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：fix-bug-with-test Skill 的 description 寫了做什麼和什麼時候用，沒寫進這次 Bug 的原因。
```

失敗時（測試仍失敗，或第 62 分鐘還沒全過）：

```text
不要擴大範圍。還有哪些不符、可能原因是什麼？時間不夠就停在現況，把沒完成和沒驗證的照實寫進 notes/b1.md，不要說已修好。
```

④ 補充

```callout tip
技巧：Skill（加深一層）
**好的 Skill 從真實工作長出來：先做完一次，再把重複的做法交給 Agent 寫。**
- description 用第三人稱寫「做什麼＋什麼時候用」，放進使用者會說的字；下次你只說「學生票又算錯了，修一下」，工具就會自己用上它
- 只寫 Agent 本來不知道的：你們的步驟和要交的證據
📖 延伸閱讀：Anthropic 官方文件〈Skill authoring best practices〉、agentskills.io〈Specification〉；你所用工具的官方文件通常有同名章節。
```

```callout tip
技巧：同一個錯第二次，就寫進 AGENTS.md
**Agent 同一個錯犯第二次、或審查抓到它本該知道的事，就請它在 `AGENTS.md` 加一行。**
- 例如：「剛才又沒附測試名稱。請在 AGENTS.md 的工作規則加一行，避免下次再犯。」
- 只加每次都要的事；一長串步驟改寫成 Skill
- 回到工作：每次重複糾正同一件事時，先想「這句該不該寫進 AGENTS.md」
📖 延伸閱讀：Claude Code 官方文件〈How Claude remembers your project〉、OpenAI〈AGENTS.md〉；你所用工具的官方文件通常有同名章節。
```

## 完成後想一想

先自己想 30 秒，再和旁邊的人聊；主持人會請 1–2 位分享第 2 題。

1. **觀察**：檢查點 1 時，你們幾個人的 Agent 找到的原因一樣嗎？核准計畫前，有沒有哪一句「推論」差點被你當成事實？
2. **技巧**：如果跳過重現、直接叫 Agent「修好學生票」，修完你要怎麼知道它真的修好、又沒改壞成人票？你工作上回報的 Bug，有幾個能先寫成一個會失敗的測試？
3. **延伸**：這次的規則很明確（學生 75%）。如果下一個需求是「改規則」而不是「修 Bug」，而且做法不只一種，你會希望 Agent 先交給你什麼？
