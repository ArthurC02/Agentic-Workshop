## 檢查點 2 · 先要計畫，再核准（第 11–15 分鐘）

① 為什麼做這一步

先看計畫，動手前就抓得出範圍外的項目。這一步 Agent 只提計畫、不改程式。下面三件都成立就核准：

- 每一步都標了規則編號和驗收條件編號（例如 `FARE-002`、`AC-G-005`），也寫了要改的檔案
- 沒有範圍外的項目
- 每個問題都附了建議答案；拿不準就舉手問主持人，不要讓 Agent 自己假設

② 貼給 Agent

先貼這段要計畫：

```text
【目標】先不要修改程式。提出 4 步的實作計畫。先仔細想過再回答。
【背景／要讀的檔】只讀這些：上一層資料夾（或 docs\ 副本）的商業需求（02-business-requirements.md）與驗收條件（03-acceptance-criteria.md）、這個專案的 README 與 docs/，以及程式碼（.py）中標示 TODO(GREENFIELD 的地方。
【限制】
- 固定拆成 4 步：1 票價、2 班次查詢、3 建立訂票、4 付款與查詢訂單。
- 每一步都要替這一步對應的驗收條件補上測試（例如建立訂票那步要有 1225 的測試，付款那步要有付款失敗不建立 Order 的測試），不能只靠移除 skip。
- 不要放進前端、登入、會員、優惠、改退票或新套件等範圍外項目。
- 下列事項需求文件沒有逐字寫明，請照這樣處理並寫進計畫：付款失敗時 Booking 維持 PENDING_PAYMENT、座位不釋放、不建立 Order、之後仍可再付款；找不到 Trip／Booking／Order 回 404；人數不符（0 人、超過 4 人）回 409，要在 domain／application 檢查，不要寫成輸入格式限制；座位不足、重複付款、付款失敗回 409；輸入格式錯誤沿用 422（回應內容用 FastAPI 預設，不另外包裝）；其他錯誤內容沿用 {"error":{"code":"...","message":"..."}}；測試要能指定付款失敗，不用隨機結果（把 MockPaymentGateway.next_result 設為 PaymentStatus.FAILED）。
【輸出格式】寫進 notes/greenfield.md 的「計畫」段落。開頭寫你在 .py 檔找到幾個 TODO(GREENFIELD 標記。每一步固定四項：第幾步、完成後使用者能做什麼（白話）、對應的規則編號（Rule ID）與驗收條件（AC）、預計修改的檔案。最後列出還需要我決定的問題，每題附上你建議的答案。
【停止條件】寫完就停下等我，不要開始修改。
```

看完計畫再貼這段「計畫核准」。不同意某個建議答案，就在第一行後面加上「第 N 題改成…」：

```text
計畫核准，問題照你建議的答案處理（我有改的寫在這一行後面）。
請把我的決定和核准時間（用你電腦的目前時間）寫進 notes/greenfield.md 的「核准紀錄」。這一次做計畫的第 1、2 步（兩步都很小，一起做，驗收對照表照步驟分開列）。做完依工作規則回報，然後停下等我，不要繼續下一步。
```

③ 確認結果

```text
請檢查下列三件事，不要修改任何檔案：1. notes/greenfield.md 的「計畫」有 4 步，每步都有規則編號、驗收條件與預計修改的檔案；開頭寫的 TODO(GREENFIELD 數量，和用 Git 查「G0 baseline」那一版 .py 檔得到的數量一致（不要數現在的檔案，第 1、2 步已移除一些）；2. 「核准紀錄」寫了我的決定與核准時間；3. 這次只改了計畫第 1、2 步預計修改的檔案（notes/ 不算）。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

## 檢查點 3 · 小步做、每步驗收（第 15–25 分鐘）

① 為什麼做這一步

每次只放行一小步，錯了只要退一小步。Agent 停下時，看它附的審查答案（用白話回答的四題變更審查）和驗收對照表（每條驗收條件一列的結果），判斷三件事：

- 改的檔案都在計畫裡（notes/ 不算）
- 測試數沒有變少，也沒有新增跳過
- 沒有刪除測試，也沒有改既有的期待值

第 3、4 步做完時，自己手算 T001 成人 700 ＋ 學生 525 ＝ **1225**，再和驗收對照表 AC-G-005 的結果比對。

② 貼給 Agent

第 1、2 步的回報三件都成立，就貼這段「放行」。Agent 會記下這一段、存一版，再把第 3、4 步一起做；第 3、4 步回報後三件也都成立，再貼同一段：

```text
這一段我核准了。請重跑 pytest -q，把這次的通過／失敗／跳過數、驗收對照表、審查答案和核准時間（用你電腦的目前時間）寫進 notes/greenfield.md，段落標題用剛核准的步驟（「第 1、2 步」或「第 3、4 步」），再把變更 Commit 成同樣的名稱。
剛核准的是第 1、2 步：接著把計畫第 3、4 步一起做（驗收對照表照步驟分開列），做完依工作規則回報，然後停下等我。
剛核准的是第 3、4 步：停下告訴我『計畫已全部完成』，不要自己加新功能。
```

有一件不成立或不確定，改貼這段：

```text
這一步我先不核准。請用白話解釋審查答案裡有問題或我看不懂的地方，提出修正做法，等我同意後再修正並重跑 pytest -q。
```

③ 確認結果

Agent 說「計畫已全部完成」後貼這段。時間不夠、只放行到第 1、2 步的，Agent 停下回報第 3、4 步時貼：

```text
請檢查我最後放行的那一段（有「第 3、4 步」段落就檢查它，沒有就檢查「第 1、2 步」），不要修改任何檔案：1. notes/greenfield.md 有這一段，含驗收對照表、審查答案與核准時間，而且已 Commit 成同樣的名稱；2. 這一段記錄的 pytest -q 結果失敗數為 0，跳過數沒有比上一段多，這一段審查答案第 4 題列出的測試都已變成通過，沒有新增 skip 或 xfail；3. 如果這一段含建立訂票，AC-G-005 的結果是 1225；如果含付款，只有待付款能付款、成功後建立唯一 Order、重複付款與付款失敗都不建立 Order。全部符合只回「成功」；有任何一項不符，只回「失敗：」加一句原因。
```

失敗時：

```text
請用白話說明哪一項不符、為什麼。如果已開始第 3、4 步，先暫停，修正只 Commit 剛放行那一段相關的變更。缺的紀錄或 Commit 直接補上（Commit 名稱用剛放行的那一段）；需要改程式就先提修正做法，等我同意後再改，並重跑 pytest -q。
```

## 檢查點 4 · 親自走一次流程並交付（第 25–29 分鐘）

① 為什麼做這一步

不再加新功能。Agent 補測試、更新文件、寫交付摘要，你親自在 `/docs` 試訂票和付款兩個 API，其餘由 Agent 用測試驗證。你判斷 `/docs` 看到的是否和預期一致，照實回覆，以你看到的為準。

② 貼給 Agent

先貼這段。Agent 啟動伺服器後會先給你 `/docs` 網址，你邊試、它邊寫交付摘要：
