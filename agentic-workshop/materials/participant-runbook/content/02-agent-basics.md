# Agent 工作方式與安全規則

本工作坊不指定 Agent 產品。不論使用哪一種通用 Coding Agent，都依同一套工作節奏進行：**先計畫、人審查，再執行、測試與說明**。程式、測試與指令操作全部由 Agent 負責；你不寫、不讀程式，只負責決定、核准，並用證據驗證。

## 工作節奏

```text
Plan → Human Review → Execute → Test → Explain
```

| 步驟 | 你要做的事 | 請 Agent 做的事 |
|---|---|---|
| **計畫（Plan）** | 主導需求理解與工作拆解；明確要求「先不要修改程式」 | 閱讀需求與 Repository，整理待辦、規則對應與風險，提出分步計畫，列出需要你決定的問題 |
| **人員審查（Human Review）** | 核對範圍、規則與風險；回答 Agent 的問題；確認後才核准執行 | 等待你的確認，不自行開始修改 |
| **執行（Execute）** | 決定設計方向與優先順序；遇到疑問時由你確認假設 | 依核准的計畫修改，限制在核准範圍內，不任意增加外部依賴或改需求 |
| **驗證（Test）** | 要求 Agent 執行測試並整理驗收對照表；逐條核對結果，並在 `/docs` 實際試用 | 執行測試、補足失敗與邊界案例；不刪除或放寬測試來掩蓋失敗，沒執行的標「未驗證」 |
| **說明（Explain）** | 用變更審查問題核對 Agent 的說明，確認與核准計畫一致 | 用白話列出修改檔案、規則／驗收條件對應、測試結果、文件更新、風險與未完成項目 |

## 用證據審查，而不是只看摘要

Agent 的摘要與「全部通過」的訊息都不能取代你的審查。你不讀程式碼，改用三種證據：

- **驗收對照表**：每條驗收條件一列，寫通過／失敗／未驗證與依據的測試名稱。
- **變更審查**：Agent 停下後，請它用白話回答固定的審查問題，你再填自己的審查卡。
- **實際操作**：在瀏覽器開 `/docs` 親自試一次功能。

每份下載的 Repository 解壓後、交給 Agent 修改之前，先請 Agent 建立 Git 基準（記下起始狀態），之後它才能回報實際改了什麼。詳細步驟見 [Greenfield 任務](#greenfield) 的檢查點 1。

變更審查時貼給 Agent 的提示詞：

```text
不要再修改。請用白話回答下列審查問題，每題附上你實際執行的指令與輸出：
1. 這次改了哪些檔案？每個檔案改了什麼、為什麼？有沒有不在核准計畫裡的檔案？
2. 測試總數和上一次比有沒有變少？有沒有新增 skip 或 xfail？
3. 有沒有刪除測試，或修改既有測試的期待值？（請用 git diff 檢查 tests 資料夾後回答）
4. 列出驗收對照表。
```

你自己的審查卡：

1. 改的檔案都在核准計畫裡嗎？（是／否／不確定）
2. 測試數沒有變少、沒有新增跳過？（是／否／不確定）
3. 沒有刪除測試或改既有期待值？（是／否／不確定）
4. 驗收對照表裡還有哪些失敗或未驗證？
5. 我在 /docs 實際試過的行為符合需求嗎？
6. 有沒有看不懂、要 Agent 再解釋的地方？

任何一題是「否」或「不確定」→ 不核准，請 Agent 解釋或修正。

```callout tip
把重要結論整理成可交接的紀錄（Artifact）
重要階段的結果不要只留在對話中。計畫、分析、測試結果與交付摘要都應整理成可審查、可交接的紀錄。本 Runbook 的表單可直接匯出 Markdown。
```

## Context 與 Prompt

- **背景資訊（Context）** 是 Agent 完成目前任務所需的背景資訊，採「最小充分資訊」原則；Agent 的結論需要交叉驗證。
- **提示詞（Prompt）** 是單次要求 Agent 工作的指令，不是永久的規格來源。需求以任務文件、需求與驗收條件為準。
- **Agent對話（Session）** 結束前，請 Agent 產生摘要，方便接手與交接。

## 安全規則

```callout danger
不要讓 Agent 接觸真實資料或機密
本案例只使用本機虛構資料與模擬付款。不得輸入或讓 Agent 取得、輸出正式客戶資料、真實個資、帳密或金鑰，也不要讓 Agent 操作任何正式環境。
```

在本工作坊中，Agent不得：

- 操作正式環境。
- 取得或輸出帳密、金鑰及客戶敏感資料。
- 任意新增未核准的外部套件。
- 修改工作範圍以外的模組。
- 跳過測試、檢視（Review）或核准流程。
- 直接將未經審查的內容合併至主要分支。

```callout warning
Agent 擴大範圍時
修改應限制在核准的計畫與範圍內。如果 Agent 的變更說明或審查答案中出現改需求、新增範圍外功能或修改範圍外檔案的變更，不要直接接受；先回到核准的計畫，由你決定如何處理後再繼續。
```
