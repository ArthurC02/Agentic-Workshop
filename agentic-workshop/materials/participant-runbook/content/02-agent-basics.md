# Agent 工作方式與安全規則

本工作坊不指定 Agent 產品。不論使用哪一種通用 Coding Agent，都依同一套工作節奏進行：**先計畫、人審查，再執行、測試與說明**。程式、測試與指令操作全部由 Agent 負責；你不寫、不讀程式，只負責決定、核准，並用證據驗證。

## 工作節奏

```text
Plan → Human Review → Execute → Test → Explain
```

- **計畫（Plan）**：Agent 讀需求與 Repository，提出分步計畫並列出要你決定的問題；它先不修改。你核對範圍、回答問題。
- **人員審查（Human Review）**：你確認後才核准；Agent 等你確認，不自行開始。
- **執行（Execute）**：Agent 只做核准的步驟，不任意加套件或改需求；遇到疑問由你決定。
- **驗證（Test）**：Agent 跑測試、整理驗收對照表，沒執行的標「未驗證」；你逐條核對，並在 `/docs` 實際試用。
- **說明（Explain）**：Agent 用白話說明改了什麼、為什麼、還有什麼沒完成；你看它回答的變更審查問題，核對是否和計畫一致。

每個檢查點的提示詞都已照這個節奏寫好，複製貼上即可；你只要看 Agent 的回報、做決定。

## 用證據審查，而不是只看摘要

Agent 的摘要與「全部通過」的訊息都不能取代你的審查。你不讀程式碼，改用三種證據：

- **驗收對照表**：每條驗收條件一列，寫結果（通過／失敗／未驗證）與依據的測試。
- **變更審查**：Agent 停下後，用白話回答固定的審查問題，你逐題判斷。
- **實際操作**：在瀏覽器開 `/docs` 親自試一次功能。

這三種證據怎麼要、怎麼看，在 [Greenfield 任務](#greenfield) 第一次用到時才說明，提示詞也都已寫好。

```callout tip
紀錄交給 Agent 寫進 notes
重要階段的結果不要只留在對話中。Agent 會把計畫、分析、驗收對照表與交付摘要寫進 Repository 的 `notes/<段落>.md`（例如 `notes/greenfield.md`），每段提示詞都會講明寫到哪個檔。你只在 Runbook 表單用下拉或勾選記下自己的決定。
```

## 技巧路線圖：六個 Agent 技巧在哪裡學

除了每段一個流程技巧，提示詞裡還埋了六個操作 Agent 的技巧。現在只要知道名稱；每個技巧在**第一次用到的那一步**才用「技巧：…」小卡說明是什麼、為什麼有效，並附官方文件的延伸閱讀。

1. **Prompt（提示詞）結構**：Greenfield 檢查點 2 第一次學。
2. **模型選擇**：個人分析檢查點 1 第一次學；B3 再用。
3. **推論強度（Reasoning Effort）**：個人分析檢查點 1 第一次學；B2 再用。
4. **Structured Output（結構化輸出）**：Greenfield 檢查點 3 第一次學；B2、B3、交付再加深。
5. **Token 節費**：Time Skip 檢查點 2 第一次學；之後每段都會用到。
6. **Skill（可重複使用的工作說明）**：共同脈絡檢查點 2 第一次學；B1、B3 再加深。

三個階段需要的技巧不同：Tool 階段靠「提示詞寫清楚、回報有固定格式」；Teammate 階段靠「省 Token、把共識寫成檔案」；Digital Worker 階段把整份工作說明交出去，只在關卡看固定格式的回報。

## 安全規則

```callout danger
不要讓 Agent 接觸真實資料或機密
本案例只使用本機虛構資料與模擬付款。不得輸入或讓 Agent 取得、輸出正式客戶資料、真實個資、帳密或金鑰，也不要讓 Agent 操作任何正式環境。
```

在本工作坊中，Agent不得：

- 操作正式環境。
- 取得或輸出帳密、金鑰及客戶敏感資料。
- 任意新增未核准的外部套件。
- 修改工作範圍以外的模組。
- 跳過測試、檢視（Review）或核准流程。
- 直接將未經審查的內容合併至主要分支。

```callout warning
Agent 擴大範圍時
修改應限制在核准的計畫與範圍內。如果 Agent 的變更說明或審查答案中出現改需求、新增範圍外功能或修改範圍外檔案的變更，不要直接接受；先回到核准的計畫，由你決定如何處理後再繼續。
```
