# Shared Context：把共識寫成檔案給 Agent

```callout info
現在在做什麼
- **情境**：每個人的 Agent 都讀過 B0，但看法不完全一樣；接下來小組要一起改同一份系統。
- **你的目標**：6 分鐘內比較大家的分析、選出主要 Agent，讓它把小組的共同脈絡（Shared Context）和規則寫進檔案。
- **今天的技巧**：**把共識寫成檔案給 Agent**。口頭講過的，Agent 下次就忘了；寫進 `AGENTS.md`，之後每個對話都會讀到。
- **完成的樣子**：有 `notes/shared-context.md`，`AGENTS.md` 加了審查準則，檢查做法搬成 `check` Skill；沒把假設說成事實。
```

## 檢查點總覽

- **46–48 · 檢查點 1 比較各自的分析，選出主要 Agent**
- **48–52 · 檢查點 2 請主要 Agent 寫成共同脈絡檔**

## 檢查點 1 · 比較各自的分析，選出主要 Agent（第 46–48 分鐘）

① 為什麼做這一步

每個人的 Agent 先把分析濃縮成 5 行，小組才比得起來。小組要說得出一條附來源的共同事實、一個分歧，並選定主要 Agent（之後由它執行任務）和人員核准者。

② 貼給 Agent

每個人對自己的 Agent 貼：

```text
把 notes/analysis.md 濃縮成 5 行給小組比較：系統地圖、規則在哪、測試現況、最重要的不一致、最大的不確定，各一句，標事實（來源）、假設或缺口。寫在 notes/analysis.md 最後的「5 行摘要」，對話也貼出這 5 行。這步不用 check。
```

等 Agent 濃縮時，小組先口頭決定下方討論第 1 題：誰的電腦當主要 Agent、誰當人員核准者。

③ 確認結果

這步由你判斷，不用 check：剛好 5 行、每行有標記、和前面各節說法一致，就往下。有一行看起來對不上才貼：

```text
用 check 檢查剛才這一段：5 行都和前面各節一致。
```

失敗時：

```text
重寫「5 行摘要」：剛好 5 行、每行有標記，沒來源的不要標成事實。只改這一節。
```

④ 補充

```callout tip
技巧：Token 節費（加深一層）
**要摘要，不要全文。**
- 貼 5 行摘要給主要 Agent，比貼整段對話省很多 Token，主要 Agent 也不會被細節淹沒
📖 延伸閱讀：Anthropic Engineering 文章〈Effective context engineering for AI agents〉、Anthropic 官方文件〈Context windows〉；你所用工具的官方文件通常有同名章節。
```

```callout tip
💬 討論一下
**口頭講就好，不用寫下來；下一步由主要 Agent 記錄。**
1. 誰的電腦當**主要 Agent**？誰當**人員核准者**？（等 Agent 濃縮時先決定）
2. 每個人把 5 行傳到小組聊天室（或念出來）
3. 大家說的一樣、而且都附得出來源的，就是共同事實
4. 說法不同或沒證據的是分歧：要重跑哪個測試或對照哪條規則，才分得出對錯？
5. 說完，主要 Agent 那位把一兩句分工與共識打進聊天室，下一步直接複製
```

## 檢查點 2 · 請主要 Agent 寫成共同脈絡檔（第 48–52 分鐘）

① 為什麼做這一步

口頭講過的，Agent 下次就忘了；寫進 `AGENTS.md`，之後每個對話都會讀到。小組判斷主要 Agent 的複述有沒有把分歧或假設說成事實，有沒有自己加修改計畫。有的話，請它修正檔案。

② 貼給 Agent

在**主要 Agent** 的對話裡一次貼完三樣再送出：

1. 下面這段提示詞。
2. 剛才打進聊天室的一兩句分工與共識：主要 Agent 在誰的電腦、人員核准者是誰、口頭說好的共識與分歧。
3. 其他成員的 5 行摘要，從聊天室複製即可。

只有你一人時（例如晚到），第 3 樣寫「沒有其他成員；共同事實改為自己的分析中附來源的事實」。

```text
先不改程式，也不提修改計畫。這段後面附上小組的分工、口頭共識和其他成員的 5 行摘要（少了哪樣就問我）。請把小組共識寫進檔案，之後每個對話都接得上：
1. notes/shared-context.md：共同事實（附來源）、仍有分歧（附驗證方式）、已知限制、待決事項、分工（主要 Agent、人員核准者）。證據不足的寫成假設。
2. AGENTS.md：最上面加一行「開工先讀 notes/shared-context.md」；加一節「審查準則」，照下面原文；工作規則有我們口頭改過的就照改。
3. AGENTS.md 的「檢查一段工作」是一步步的做法，搬成 check Skill：放在你這個工具會自動載入專案 Skill 的位置，AGENTS.md 那一節改成一行它的位置（從專案根目錄算起的路徑）。
寫完用 3 句話複述重點，再列出最多 3 個證據不足或互相矛盾的地方。做完用 check 檢查；check 不用跑測試，這段只改 notes、AGENTS.md 和 Skill。
審查準則（照抄，不改寫）：寫程式的 Agent 自己審、另開對話審查，都照這一節。先用 git status 與 git diff 對照這段的起點 Commit（提示詞沒指定就用最近一次 Commit），列出改了哪些檔案、各改什麼、為什麼（notes/、AGENTS.md、Skill 資料夾、b3-docs/ 不列）。再回答三題「是／否／不確定」，各附實際指令與結果：(1) 改的檔案都在核准的計畫或範圍裡；(2) 測試總數沒有比這段開始時少，也沒有新增 skip 或 xfail；(3) 沒有刪除測試，除了經人核准的過時期待值，沒有修改既有測試的期待值（用 git diff 檢查 tests 資料夾；有改的逐一列出測試名稱、Rule ID 與核准紀錄位置）。分級：任一題是「否」或「不確定」，或宣稱通過卻沒有實際執行的指令與結果，是「重要」；文件措辭、命名不清楚是「小問題」，小問題最多報 5 條，其餘只寫條數；排版與寫法偏好不用報。
```

Agent 建立 Skill 資料夾時，工具若跳出允許視窗，按允許。

主要 Agent 寫檔時，其他人先填頁尾表單第 1 題「我在小組的角色」，再讀下方 ④ 的 Skill 小卡；Agent 複述完，小組一起看複述。從 B1 起，提示詞不用再叫 Agent 先讀規則：開新對話它會自己讀 `AGENTS.md`。

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：除了 notes/、AGENTS.md 和 Skill 資料夾，沒有改任何檔案。
```

失敗時：

```text
先停。哪一項不符？只補 notes/shared-context.md、AGENTS.md 或 check Skill；改到其他檔案就用 Git 還原。不要提修改計畫。
```

④ 補充

```callout tip
技巧：Skill（可重複使用的工作說明）
**Skill 是一個資料夾，裡面的 `SKILL.md` 寫一套固定做法；開頭的 `name` 是資料夾名稱，`description` 寫它做什麼、什麼時候用。**
- 工具平常只讀名稱和說明，任務符合說明時才讀全文，所以說明要用第三人稱寫清楚「做什麼＋什麼時候用」，放進使用者會說的字
- 每次都要的事放 AGENTS.md，一步步的做法放 Skill；AGENTS.md 太長，Agent 反而容易漏
- 回到工作：把團隊常做的一件事寫成 Skill，換幾種說法下任務，看它會不會自己被用上
📖 延伸閱讀：agentskills.io〈Agent Skills Overview〉、Claude Code 官方文件〈Extend Claude with skills〉、OpenAI〈Build skills〉；你所用工具的官方文件通常有同名章節。
```

## 完成後想一想

先自己想 30 秒，再和旁邊的人聊；趁等 Agent 回報時聊，這段不另開全場分享。

1. **觀察**：比較 5 行摘要時，哪一條大家說法不一樣？最後是靠什麼證據（文件位置、測試名稱或實際執行結果）決定寫成事實還是分歧？
2. **技巧**：如果不寫 `notes/shared-context.md`、不改 `AGENTS.md`，只靠口頭講好，下一段換人或開新對話時會發生什麼？你的團隊有哪些「每次都要重講一次」的規則，值得寫進 `AGENTS.md`？
3. **延伸**：主要 Agent 只有一個，但小組有好幾個人。接下來要真的改程式時，誰說了算、怎麼避免大家各自叫 Agent 改？

## 共同脈絡確認

小組確認過主要 Agent 的複述後，把你們的結論記下來：

```form
{"id": "restate-ok", "label": "主要 Agent 已寫好 notes/shared-context.md 並更新 AGENTS.md，複述沒有把假設說成事實、沒有自己加修改計畫", "type": "select", "options": ["是", "否", "不確定"]}
]}
```

第 52 分鐘停止。
