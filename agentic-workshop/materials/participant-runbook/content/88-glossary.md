# 詞彙表

本表整理 Runbook 中常見詞彙在本工作坊的用法，文字取自 Runbook 與參與者文件。各段任務專用的名詞，請以該段解鎖後的任務文件為準。

## 階段與角色

| 詞彙 | 本工作坊的用法 |
|---|---|
| Tool | 由你理解需求、決定方向、拆解工作及審查結果，Agent 協助產生程式、測試與文件。 |
| Teammate | 與 Agent 共同分析、比較與決策：各自分析、比較判斷，再整合小組 Shared Context。 |
| Digital Worker | Agent 在核准範圍內主導交付；人員負責邊界、Review、核准與最終責任。 |
| Greenfield | 個人完成核心訂票 MVP 的段落。 |
| MVP（Minimum Viable Product） | 最小可行產品；本工作坊指能跑通查詢、訂票、模擬付款與查詢訂單的核心流程。 |
| Time Skip | 時間快轉，改接手統一的 B0 Repository。 |
| Brownfield | 接手既有系統的段落；先個人分析，再小組整合。 |
| Coding Agent | 一個可用的通用 Coding Agent，能讀取本機資料夾、修改檔案並執行終端指令。本 Runbook 不要求任何特定 Agent 產品的指令或功能。 |
| 主要 Agent | 小組選定的 Agent，接收小組的共同 Context；不要把所有人的 Session 原封不動拼接。 |

## Context 與證據

| 詞彙 | 本工作坊的用法 |
|---|---|
| Context | 文件可作 Context，但不保證全部敘述與程式完全同步；重要結論應以程式、測試與公開規則交叉驗證。 |
| Shared Context | 小組比較分析後整理的共同 Context。記錄共同事實、分歧與待決事項；任務揭露後仍須另外取得範圍與計畫的核准。 |
| Rule ID | 商業規則編號。交付時列出商業規則與驗收條件的對應，逐項核對。 |
| AC（Acceptance Criteria） | 驗收條件，說明功能必須符合什麼要求；AC ID 是其編號。每項以 API 或核心邏輯測試提供證據。 |
| ADR（Architecture Decision Record） | 架構決策紀錄，說明採用某項設計的原因與取捨。 |
| Diff | 程式修改內容。由你審查主要 Diff，確認與核准計畫一致；不要只看摘要或通過數量。 |
| Skip／XFail | Skip 是略過測試；XFail 是將測試標記為預期失敗。兩者不代表功能已完成，不得用來隱藏失敗。 |
| Regression | 回歸測試，用來確認修改後既有功能仍符合要求；不移除既有測試或弱化斷言。 |

## 常用工作術語

| 詞彙 | 本工作坊的用法 |
|---|---|
| Root Cause | 問題根因；尚未驗證的說法應標為假設。 |
| Impact Analysis | 影響分析：區分必須修改、可能受影響與不應修改的範圍。 |
| Gate | 人員核准關卡；核准是決策，不等於功能已通過驗收。 |
| Review | 審查實際證據，核對需求、範圍與未完成事項。 |
| Artifact | 可保存、審查與交接的紀錄，例如計畫或測試輸出。 |
| 段落經過時間 | 從當段開始計算；與全場經過時間分開標示。 |

## Runbook 操作

| 詞彙 | 本工作坊的用法 |
|---|---|
| 活動解鎖碼 | 主持人在各段開始時向全場公布，於鎖頭章節輸入；大小寫、空白與連字號不影響輸入。 |
| 復原基線碼（Recovery） | 主持人只於52／63分鐘按需核准後個別提供；與B2／B3活動碼分開，不算小組自行完成前段任務。 |
| 步驟勾選 | 用來追蹤進度；勾選只代表你已實際確認。 |
| 匯出 Markdown | 瀏覽器允許本機儲存時，表單內容會自動暫存；可下載 `.md` 檔，或用「複製 Markdown」貼到主持人指定的交付位置。 |
