歡迎來到 Agentic Software Development 實作工作坊

從需求拆解、Agent 協作到程式交付，驗證 Agentic Coding 的團隊工作模式。

本工作坊以本機虛構案例 Smart Ticket Platform（車票預訂服務）為場景，在 90 分鐘內走過需求理解、任務拆解、Agent 執行、測試審查與交付。目的是練習人員如何與 Agent 協作，並讓產出能被測試、審查與追溯。

主線：Tool → Teammate → Digital Worker

階段 人員做什麼 Agent 做什麼
Tool 由你主導需求理解與工作拆解，並審查結果 協助產生程式、測試與文件
Teammate 與 Agent 共同分析、比較與決策 分析程式專案（Repository）、影響、風險與缺口，提供選項及取捨
Digital Worker 設定工作邊界、審查（Review）、核准並承擔最終責任 在核准範圍內主導交付

這三種角色描述人與 Agent 的協作分工，依序出現在本次90分鐘流程中；它們不是產品分類，也不代表所有工作都應提高自主程度。每段任務文件在該段開始時解鎖。

如何使用這份 Runbook

  • 投影畫面與 Runbook 的分工：投影畫面顯示時間、解鎖碼和目前進行到哪一步；要做什麼、提示詞與表單都在 Runbook。活動進行中請看自己的 Runbook，投影畫面換頁時再跟著跳到對應的步驟。
  • 左側導覽列出所有章節；每章右側的分鐘標記是該內容使用的時段。用頁面底部的「上一頁／下一頁」依序前進。
  • 一般活動章節：到對應時段，由主持人在畫面公布活動解鎖碼；請在章節的解鎖框輸入。大小寫、空白與連字號不影響輸入。
  • 復原基線（Recovery）章節：只有需要接續基線的小組，才由主持人於第52／63分鐘核准後個別提供獨立碼；一般B2／B3活動碼不會解開它們。請先保留原成果，按該頁步驟切換；使用接續基線不算自行完成前段任務。
  • 解鎖狀態：瀏覽器允許本機儲存時會記住；使用同一瀏覽器與同一檔案，重新開啟才能恢復。
  • 下載：Greenfield Starter（第 07 分鐘）與 B0 Repository（第 29 分鐘）都內嵌在本Runbook中，解鎖後按下載按鈕取得ZIP。B1／B2受控復原基線也已內嵌，但須另取得獨立碼。
  • 步驟勾選：章節中的核取方塊可用來追蹤進度，導覽列會顯示各章完成度。勾選只代表你已實際確認。
  • 表單：分析表、Shared Context、Gate 決策、Review、Delivery 與反思表都可直接在頁面中填寫，瀏覽器允許本機儲存時，內容會自動暫存。可用「匯出 Markdown」下載 .md 檔，或用「複製 Markdown」貼到主持人指定的交付位置。
  • 指令區塊：提供 PowerShell 與 bash 兩種寫法，可切換分頁並按複製按鈕。
請整場保持這份檔案開啟

請固定用同一個瀏覽器開啟同一份 runbook.html。更換瀏覽器、使用私密視窗或清除瀏覽資料，可能讓解鎖狀態與表單暫存消失；重要內容請隨時匯出 Markdown。

Runbook可離線閱讀；程式案例仍需安裝依賴

閱讀這份HTML不需要安裝瀏覽器擴充套件。執行程式案例則需要Python3.13、通用Coding Agent，以及依各版requirements.txt建立獨立venv並安裝套件。案例不需要前端、外部資料庫、真實金流或外部交通 API。環境準備請見 環境準備。

共同規則

  1. 工具中立：使用你可取得的任一通用 Coding Agent。本 Runbook 不要求任何特定 Agent 產品的指令或功能。
  2. 人員負責：Agent 可以產生建議、程式碼、測試與文件，但人員仍對正式提交、風險判斷及成果驗收負責。
  3. 不是速度競賽：不比較 Coding 速度、程式碼量或 Agent 自主程度。重點是計畫、Diff、測試與交付證據。
  4. 如實交付：時間到就停止擴充。未完成的部分如實列出，不把部分完成描述為完整交付，也不以未執行或仍被 Skip 的測試宣稱完成。
  5. 只用本機虛構資料：不使用正式客戶資料、真實個資、帳密或金鑰。
  6. 任務文件分段解鎖：任務文件於第 07 分鐘起依時段解鎖，請不要提前猜測後續段落的內容。

解壓縮到短路徑

ZIP 內的資料夾層級較深。請解壓縮到短路徑，例如 C:\work\g0、C:\work\b0，避免 Windows 路徑長度限制導致檔案解壓縮不完整。不要解壓縮到深層的同步資料夾或桌面子資料夾。

每一版的準備步驟

在該版 Repository 的根目錄（含 requirements.txt 的資料夾）執行：

python --version
python -m venv .venv
& '.\.venv\Scripts\python.exe' -m pip install -r requirements.txt
& '.\.venv\Scripts\python.exe' -m pip check
& '.\.venv\Scripts\python.exe' -m pytest -q
& '.\.venv\Scripts\python.exe' -m uvicorn smart_ticket.main:app --app-dir src --host 127.0.0.1 --port 8000
python --version
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check
.venv/bin/python -m pytest -q
.venv/bin/python -m uvicorn smart_ticket.main:app --app-dir src --host 127.0.0.1 --port 8000

pyproject.toml 的 pytest 設定已包含 src Import Path；啟動 App 時使用 --app-dir src。

確認 Health

App 啟動後，另開一個終端機檢查 /health 回傳 200 且 status 為 ok：

curl.exe http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/health

預期回應為 {"status":"ok"}。也可以用同樣方式檢查 /openapi.json，確認 API 清單與 App 版本。

選用：確認 Import

單獨 Import 或使用 TestClient 時，請明確使用本版 venv 及 src 路徑：

$env:PYTHONPATH='src'
& '.\.venv\Scripts\python.exe' -c 'from smart_ticket.main import app; print(app.title, app.version)'
PYTHONPATH=src .venv/bin/python -c 'from smart_ticket.main import app; print(app.title, app.version)'

疑難排解

PowerShell 無法啟用 venv

若 .\.venv\Scripts\Activate.ps1 受執行原則限制，不需要啟用 venv，直接用 .\.venv\Scripts\python.exe -m ... 執行，例如上方的指令區塊。

Port 8000 已被佔用

改用其他未使用的 Port（例如 --port 8001），並在 Health 檢查與交付紀錄中寫下實際使用的 Port。

切換版本前先停止舊的 Server

從 G0 換到 B0 前，先在自己啟動 Server 的終端機按 Ctrl+C 停止，再確認新版本正常啟動，避免讀到舊程序。不要終止其他人的程序。

資料重啟會重置

案例使用固定 Seed、可控的時鐘與付款模擬，資料存在記憶體中（In-Memory），重啟 App 就會回到初始狀態。這是設計行為，不是錯誤。

依賴無法安裝時

若網路不可用或 pip install 失敗，請立即告知主持人，不要在活動中臨時更換 Python 版本或技術棧。

Agent 工作方式與安全規則

本工作坊不指定 Agent 產品。不論使用哪一種通用 Coding Agent，都依同一套工作節奏進行：先計畫、人審查，再執行、測試與說明。

工作節奏

Plan → Human Review → Execute → Test → Explain
步驟 你要做的事 請 Agent 做的事
計畫（Plan） 主導需求理解與工作拆解；明確要求「先不要修改程式」 閱讀需求與 Repository，整理待辦、規則對應與風險，提出分步計畫，列出需要你決定的問題
人員審查（Human Review） 核對範圍、規則與風險；回答 Agent 的問題；確認後才核准執行 等待你的確認，不自行開始修改
執行（Execute） 決定設計方向與優先順序；遇到疑問時由你確認假設 依核准的計畫修改，限制在核准範圍內，不任意增加外部依賴或改需求
驗證（Test） 要求 Agent 執行測試，記錄指令與實際結果；核對驗收條件 執行測試、補足失敗與邊界案例；不刪除或弱化斷言來掩蓋失敗
說明（Explain） 審查主要 Diff，確認與核准計畫一致 列出修改檔案、規則／驗收條件對應、測試結果、文件更新、風險與未完成項目

審查 Diff，而不是只看摘要

Agent 的摘要與「全部通過」的訊息都不能取代你的審查。

每份下載的 Repository 解壓後、交給 Agent 修改之前，先建立 Git 基準（git init、git add -A、git commit -m "baseline"），之後用 git diff --stat 與 git diff 查看實際變更。詳細步驟見 Greenfield 任務 的步驟 2 與步驟 7。

把重要結論整理成可交接的紀錄（Artifact）

重要階段的結果不要只留在對話中。計畫、分析、測試結果與交付摘要都應整理成可審查、可交接的紀錄。本 Runbook 的表單可直接匯出 Markdown。

Context 與 Prompt

  • 背景資訊（Context） 是 Agent 完成目前任務所需的背景資訊，採「最小充分資訊」原則；Agent 的結論需要交叉驗證。
  • 提示詞（Prompt） 是單次要求 Agent 工作的指令，不是永久的規格來源。需求以任務文件、需求與驗收條件為準。
  • Agent對話（Session） 結束前，請 Agent 產生摘要，方便接手與交接。

安全規則

不要讓 Agent 接觸真實資料或機密

本案例只使用本機虛構資料與模擬付款。不得輸入或讓 Agent 取得、輸出正式客戶資料、真實個資、帳密或金鑰，也不要讓 Agent 操作任何正式環境。

在本工作坊中，Agent不得：

  • 操作正式環境。
  • 取得或輸出帳密、金鑰及客戶敏感資料。
  • 任意新增未核准的外部套件。
  • 修改工作範圍以外的模組。
  • 跳過測試、Review 或核准流程。
  • 直接將未經審查的內容合併至主要分支。
Agent 擴大範圍時

修改應限制在核准的計畫與範圍內。如果 Diff 中出現改需求、新增範圍外功能或修改範圍外檔案的變更，不要直接接受；先回到核准的計畫，由你決定如何處理後再繼續。

Context 與證據

詞彙 本工作坊的用法
Context 文件可作 Context，但不保證全部敘述與程式完全同步；重要結論應以程式、測試與公開規則交叉驗證。
Shared Context 小組比較分析後整理的共同 Context。記錄共同事實、分歧與待決事項；任務揭露後仍須另外取得範圍與計畫的核准。
Rule ID 商業規則編號。交付時列出商業規則與驗收條件的對應，逐項核對。
AC（Acceptance Criteria） 驗收條件，說明功能必須符合什麼要求；AC ID 是其編號。每項以 API 或核心邏輯測試提供證據。
ADR（Architecture Decision Record） 架構決策紀錄，說明採用某項設計的原因與取捨。
Diff 程式修改內容。由你審查主要 Diff，確認與核准計畫一致；不要只看摘要或通過數量。

Regression 回歸測試，用來確認修改後既有功能仍符合要求；不移除既有測試或弱化斷言。
