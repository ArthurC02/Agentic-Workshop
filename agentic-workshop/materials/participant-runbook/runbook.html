歡迎來到 Agentic Software Development 實作工作坊

從需求拆解、Agent 協作到程式交付，驗證 Agentic Coding 的團隊工作模式。

本工作坊以本機虛構案例 Smart Ticket Platform（車票預訂服務）為場景，在 90 分鐘內走過需求理解、任務拆解、Agent 執行、測試審查與交付。目的是練習人員如何與 Agent 協作，並讓產出能被測試、審查與追溯。

先認識今天會用到的名詞

  • Tool → Teammate → Digital Worker：Agent 從工具（Tool）、隊友（Teammate）到能獨立執行任務的數位員工（Digital Worker），是今天依序練習的三種協作角色，下一節說明分工。
  • Greenfield／Brownfield：Greenfield（從頭開始的新專案）；Brownfield（已有程式碼的既有專案）。
  • MVP：MVP（Minimum Viable Product，最小可行產品）。今天指能跑通查詢班次、訂票、模擬付款與查詢訂單的核心流程。
  • 段落代號：G0 是 Greenfield 的起始程式包；B0 是 Brownfield 的起點，也就是假設系統已上線 12 個月的既有程式；B1、B2、B3 是接下來三個 Brownfield 任務：B1 修復學生票折扣異常、B2 導入不可疊加的最有利優惠政策、B3 團體訂票。
  • Time Skip：Time Skip（時間快轉：專案假設已開發一段時間），從 Greenfield 跳到 Brownfield 的轉場。
  • Shared Context：共同脈絡（Shared Context：小組整理出的共同事實），交給 Agent 當作背景資訊。
  • Gate：核准關卡（Gate），由人決定是否放行下一步；核准是決策，不等於功能已通過驗收。B3 有三個核准關卡。
  • Recovery：Recovery（復原包：進度落後時改用的接續基線），只在主持人核准後提供。

其他名詞不熟時，可查 詞彙表。

主線：Tool → Teammate → Digital Worker

階段 人員做什麼 Agent 做什麼
Tool（工具） 逐步下指令，每一步用證據驗收 依指令產生程式、測試與文件，每做完一步就停下回報
Teammate（隊友） 與 Agent 共同分析、比較，核准計畫 分析程式專案（Repository）、影響、風險與缺口，提供選項及取捨
Digital Worker（數位員工） 設定工作邊界，只在核准關卡（Gate）核准，並承擔最終責任 在核准範圍內自主執行交付

這三種角色描述人與 Agent 的協作分工，依序出現在本次90分鐘流程中；它們不是產品分類，也不代表所有工作都應提高自主程度。三者的差別不是「人寫多少程式」，而是「人介入的方式」。每段任務文件在該段開始時解鎖。

今天的原則：全程人不寫、不讀程式

今天從頭到尾，你不寫程式、不讀程式，也不自己打終端機指令。程式、測試與所有指令操作都交給 Agent；你負責決定、核准，並用「行為與證據」驗證結果：

  • 工作規則：每段開始時，把 Runbook 提供的「Agent 工作規則」整段貼給 Agent。這段是給 Agent 的，不需要看懂。
  • 驗收對照表：請 Agent 把每條驗收條件的結果（通過／失敗／未驗證）和依據的測試整理成表，你逐條核對。
  • 變更審查：不看程式碼，改請 Agent 用白話回答固定的審查問題，你只回答自己判斷得了的問題。
  • 實際操作：在瀏覽器開 API 測試頁 /docs，親自試一次功能是否符合需求。

這樣做也有代價：只看證據不看程式，抓不到「測試全過，但寫法有問題」的程式。回顧時會討論公司需要什麼角色或平台來補這個盲點。

如何使用這份 Runbook

  • 投影畫面與 Runbook 的分工：投影畫面顯示時間、解鎖碼和目前進行到哪一步；要做什麼、提示詞與表單都在 Runbook。活動進行中請看自己的 Runbook，投影畫面換頁時再跟著跳到對應的步驟。
  • 左側導覽列出所有章節；每章右側的分鐘標記是該內容使用的時段。用頁面底部的「上一頁／下一頁」依序前進。
  • 一般活動章節：到對應時段，由主持人在畫面公布活動解鎖碼；請在章節的解鎖框輸入。大小寫、空白與連字號不影響輸入。
  • 復原基線（Recovery）章節：只有需要接續基線的小組，才由主持人於第52／63分鐘核准後個別提供獨立碼；一般 B2／B3 活動碼不會解開它們。請先保留原成果，按該頁步驟切換；使用接續基線不算自行完成前段任務。
  • 解鎖狀態：瀏覽器允許本機儲存時會記住；使用同一瀏覽器與同一檔案，重新開啟才能恢復。
  • 下載：G0 Greenfield 起始程式包（第 07 分鐘）與 B0 Repository（第 29 分鐘）都內嵌在本 Runbook 中，解鎖後按下載按鈕取得 ZIP。B1／B2 的復原包也已內嵌，但須另外取得獨立碼。
  • 步驟勾選：章節中的核取方塊可用來追蹤進度，導覽列會顯示各章完成度。勾選只代表你已實際確認。
  • 表單：分析表、Shared Context、Gate 決策、檢視（Review）、交付（Delivery）與反思表都可直接在頁面中填寫，瀏覽器允許本機儲存時，內容會自動暫存。可用「匯出 Markdown」下載 .md 檔，或用「複製 Markdown」貼到主持人指定的交付位置。
  • 提示詞區塊：要貼給 Agent 的文字，按複製按鈕後貼到 Agent 對話中。少數備用指令區塊提供 PowerShell 與 bash 兩種寫法，可切換分頁。
請整場保持這份檔案開啟

請固定用同一個瀏覽器開啟同一份 runbook.html。更換瀏覽器、使用私密視窗或清除瀏覽資料，可能讓解鎖狀態與表單暫存消失；重要內容請隨時匯出 Markdown。

Runbook可離線閱讀；程式案例仍需安裝依賴

閱讀這份HTML不需要安裝瀏覽器擴充套件。執行程式案例則需要Python3.13與通用Coding Agent，並由Agent依各版requirements.txt建立獨立環境（venv）、安裝套件。案例不需要前端、外部資料庫、真實金流或外部交通 API。環境準備請見 環境準備。

共同規則

  1. 工具中立：使用你可取得的任一通用 Coding Agent。本 Runbook 不要求任何特定 Agent 產品的指令或功能。
  2. 人員負責：Agent 產生建議、程式碼、測試與文件，並執行所有指令；人員不寫、不讀程式，但仍對正式提交、風險判斷及成果驗收負責，並以驗收對照表、變更審查與實際操作驗證結果。
  3. 不是速度競賽：不比較 Coding 速度、程式碼量或 Agent 自主程度。重點是計畫、變更內容（Diff）、測試與交付證據。
  4. 如實交付：時間到就停止擴充。未完成的部分如實列出，不把部分完成描述為完整交付，也不以未執行或仍被略過（Skip）的測試宣稱完成。
  5. 只用本機虛構資料：不使用正式客戶資料、真實個資、帳密或金鑰。
  6. 任務文件分段解鎖：任務文件於第 07 分鐘起依時段解鎖，請不要提前猜測後續段落的內容。

環境準備

工作坊時間要用來體驗 Agent 協作，不是處理安裝問題。請在開場時確認下列項目，有問題立即告知主持人。

前置需求

套件由各版 requirements.txt 指定：FastAPI 0.115.12、Uvicorn 0.34.2、Pydantic 2.11.4、pytest 8.3.5、httpx 0.28.1。不需要前端、外部資料庫、真實金流或交通 API。

分鐘 取得內容 取得方式
07 G0 Starter Repository（Greenfield 起始程式包） 主持人公布解鎖碼後，在 Greenfield 任務 頁面下載
29 B0 Repository（Brownfield 起點：假設已上線 12 個月的既有程式） 主持人公布解鎖碼後，在 Time Skip（時間快轉）章節下載

兩份程式碼都以 ZIP 形式內嵌在本 Runbook 中。每一版都請 Agent 在該版自己的資料夾內獨立建立環境（venv），不共用環境，也不混用不同版本的程式。

解壓縮到短路徑

ZIP 內的資料夾層級較深。請解壓縮到短路徑，例如 C:\work\g0、C:\work\b0，避免 Windows 路徑長度限制導致檔案解壓縮不完整。不要解壓縮到深層的同步資料夾或桌面子資料夾。

每一版的準備步驟

解壓縮後，在該版 Repository 的根目錄（含 requirements.txt 的資料夾）開啟你的 Agent，先貼上該段的「Agent 工作規則」，再依序貼上下面兩段提示詞：

請幫我準備這個專案的執行環境：確認 Python 版本是 3.13，在專案資料夾建立 .venv 虛擬環境並安裝 requirements.txt，接著執行 pytest -q。用白話告訴我：環境是否建好、測試有幾個通過／失敗／跳過，以及下一步要做什麼。遇到錯誤時先說明原因，不要自行修改程式。
請在背景啟動這個專案的伺服器（埠號 8000），確認 http://127.0.0.1:8000/health 回傳 status=ok，然後告訴我 /docs 的網址。之後要換版本或結束時，先停止你啟動的伺服器。

備用：手動指令

只有 Agent 無法執行指令、且主持人請你手動處理時才使用：

疑難排解

Agent 回報無法啟用 venv

Windows 的 PowerShell 可能因執行原則限制無法啟用 venv。請 Agent 不要啟用，直接用 .venv 裡的 Python 執行即可。

Port 8000 已被佔用

請 Agent 改用其他未使用的埠號（Port，例如 8001），告訴你新的 /docs 網址；在交付紀錄中寫下實際使用的 Port。

切換版本前先停止舊的 Server

從 G0 換到 B0 前，先請 G0 的 Agent 停止它啟動的伺服器，再請 B0 的 Agent 啟動新版本並確認正常，避免讀到舊程序。不要終止其他人的程序。

資料重啟會重置

案例使用固定的 Seed Data（系統預設的測試資料）、可控的時鐘與付款模擬，資料存在記憶體中（In-Memory），重啟 App 就會回到初始狀態。這是設計行為，不是錯誤。

依賴無法安裝時

若網路不可用或 Agent 回報套件安裝失敗，請立即告知主持人，不要在活動中臨時更換 Python 版本或技術棧。

Agent 工作方式與安全規則

本工作坊不指定 Agent 產品。不論使用哪一種通用 Coding Agent，都依同一套工作節奏進行：先計畫、人審查，再執行、測試與說明。程式、測試與指令操作全部由 Agent 負責；你不寫、不讀程式，只負責決定、核准，並用證據驗證。

工作節奏

Plan → Human Review → Execute → Test → Explain
步驟 你要做的事 請 Agent 做的事
計畫（Plan） 主導需求理解與工作拆解；明確要求「先不要修改程式」 閱讀需求與 Repository，整理待辦、規則對應與風險，提出分步計畫，列出需要你決定的問題
人員審查（Human Review） 核對範圍、規則與風險；回答 Agent 的問題；確認後才核准執行 等待你的確認，不自行開始修改
執行（Execute） 決定設計方向與優先順序；遇到疑問時由你確認假設 依核准的計畫修改，限制在核准範圍內，不任意增加外部依賴或改需求
驗證（Test） 要求 Agent 執行測試並整理驗收對照表；逐條核對結果，並在 /docs 實際試用 執行測試、補足失敗與邊界案例；不刪除或放寬測試來掩蓋失敗，沒執行的標「未驗證」
說明（Explain） 用變更審查問題核對 Agent 的說明，確認與核准計畫一致 用白話列出修改檔案、規則／驗收條件對應、測試結果、文件更新、風險與未完成項目

用證據審查，而不是只看摘要

Agent 的摘要與「全部通過」的訊息都不能取代你的審查。你不讀程式碼，改用三種證據：

  • 驗收對照表：每條驗收條件一列，寫通過／失敗／未驗證與依據的測試名稱。
  • 變更審查：Agent 停下後，請它用白話回答固定的審查問題，你再填自己的審查卡。
  • 實際操作：在瀏覽器開 /docs 親自試一次功能。

每份下載的 Repository 解壓後、交給 Agent 修改之前，先請 Agent 建立 Git 基準（記下起始狀態），之後它才能回報實際改了什麼。詳細步驟見 Greenfield 任務 的檢查點 1。

變更審查時貼給 Agent 的提示詞：

不要再修改。請用白話回答下列審查問題，每題附上你實際執行的指令與輸出：
1. 這次改了哪些檔案？每個檔案改了什麼、為什麼？有沒有不在核准計畫裡的檔案？
2. 測試總數和上一次比有沒有變少？有沒有新增 skip 或 xfail？
3. 有沒有刪除測試，或修改既有測試的期待值？（請用 git diff 檢查 tests 資料夾後回答）
4. 列出驗收對照表。

你自己的審查卡：

  1. 改的檔案都在核准計畫裡嗎？（是／否／不確定）
  2. 測試數沒有變少、沒有新增跳過？（是／否／不確定）
  3. 沒有刪除測試或改既有期待值？（是／否／不確定）
  4. 驗收對照表裡還有哪些失敗或未驗證？
  5. 我在 /docs 實際試過的行為符合需求嗎？
  6. 有沒有看不懂、要 Agent 再解釋的地方？

任何一題是「否」或「不確定」→ 不核准，請 Agent 解釋或修正。

把重要結論整理成可交接的紀錄（Artifact）

重要階段的結果不要只留在對話中。計畫、分析、測試結果與交付摘要都應整理成可審查、可交接的紀錄。本 Runbook 的表單可直接匯出 Markdown。

Context 與 Prompt

  • 背景資訊（Context） 是 Agent 完成目前任務所需的背景資訊，採「最小充分資訊」原則；Agent 的結論需要交叉驗證。
  • 提示詞（Prompt） 是單次要求 Agent 工作的指令，不是永久的規格來源。需求以任務文件、需求與驗收條件為準。
  • Agent對話（Session） 結束前，請 Agent 產生摘要，方便接手與交接。

安全規則

不要讓 Agent 接觸真實資料或機密

本案例只使用本機虛構資料與模擬付款。不得輸入或讓 Agent 取得、輸出正式客戶資料、真實個資、帳密或金鑰，也不要讓 Agent 操作任何正式環境。

在本工作坊中，Agent不得：

  • 操作正式環境。
  • 取得或輸出帳密、金鑰及客戶敏感資料。
  • 任意新增未核准的外部套件。
  • 修改工作範圍以外的模組。
  • 跳過測試、檢視（Review）或核准流程。
  • 直接將未經審查的內容合併至主要分支。
Agent 擴大範圍時

修改應限制在核准的計畫與範圍內。如果 Agent 的變更說明或審查答案中出現改需求、新增範圍外功能或修改範圍外檔案的變更，不要直接接受；先回到核准的計畫，由你決定如何處理後再繼續。

詞彙表

本表整理 Runbook 中常見詞彙在本工作坊的用法：先給中文名與白話解釋，再舉今天的例子。各段任務專用的名詞，請以該段解鎖後的任務文件為準。開發人員普遍熟悉的詞（API、JSON、HTTP、Git、commit、Repo、pytest）不另收錄。

階段與角色

詞彙 中文與白話解釋 今天的例子
Agentic SDLC SDLC 是 Software Development Life Cycle，軟體開發生命週期；Agentic SDLC 指 Agent 參與從需求、設計、實作、測試到交付的整個開發流程。 今天從零開發、接手既有系統到團體訂票，每一段都有 Agent 參與。
Tool → Teammate → Digital Worker Agent 從工具、隊友到能獨立執行任務的數位員工；是今天依序練習的三種協作角色。今天全程人都不寫程式，三者的差別在人介入的方式，人負的責任也跟著改變。 Greenfield 用 Tool，Time Skip 到 B2 用 Teammate，B3 用 Digital Worker。
Tool（工具） 由你理解需求、決定方向、逐步下指令並每步驗收；Agent 負責寫程式、測試與文件。 第 7–29 分鐘，你下指令，Agent 幫你寫訂票 API。
Teammate（隊友） Agent 和你一起分析，由人核准計畫：各自分析、比較判斷，再整合小組共同脈絡。 第 33–52 分鐘，各自請 Agent 分析 B0 失敗測試，再小組比較。
Digital Worker（數位員工，DW） Agent 在核准範圍內主導交付；人員負責設定邊界、檢視（Review）、核准與最終責任。DW 是它的縮寫。 B3 由 Agent 自主分析、實作、測試、寫交付摘要；人只透過三道核准關卡管 Agent，看驗收對照表與變更審查答案做決定，不看程式。
Greenfield（新專案） 從頭開始的新專案，沒有歷史程式包袱。 今天第 7–29 分鐘的個人段落：從 G0 開始完成核心訂票 MVP。
Brownfield（既有專案） 已有程式碼、文件與歷史取捨的既有專案；要先讀懂再修改。 今天第 29 分鐘以後：接手 B0，先個人分析、再小組整合，接著做 B1–B3。
G0／B0／B1／B2／B3 各段的起點或任務代號。G0 是 Greenfield 的起始程式包；B0 是 Brownfield 的起點，也就是假設系統已上線 12 個月的既有程式；B1、B2、B3 是接在後面的三段 Brownfield 任務。 B1 修復學生票折扣異常、B2 導入不可疊加的最有利優惠政策、B3 團體訂票。
G1 完整的 Greenfield MVP 版本，B0 由它演化而來；任務卡提到的「原 G1 Regression」是那時留下、現在必須繼續通過的既有測試。 B1 的 AC 要求原 G1 的 28 項既有測試保留正確的期待值並通過。
MVP（Minimum Viable Product） 最小可行產品：只做能用的最少功能。本工作坊指能跑通查詢、訂票、模擬付款與查詢訂單的核心流程。 Greenfield 的目標就是完成這個 MVP。
Time Skip（時間快轉） 專案假設已開發一段時間，大家停下自己的進度，改接手統一的版本。 第 29 分鐘：假設 Smart Ticket 已上線 12 個月，全場改接手同一份 B0。
Coding Agent 能讀取本機資料夾、修改檔案並執行終端指令的 AI 開發助手。本 Runbook 不要求任何特定 Agent 產品的指令或功能。 你今天在自己電腦上使用的 Agent。
Session（對話工作階段） 與 Agent 的一段對話；同一個 Session 會記得先前交代的內容。 換到 B0 時開新的 Session，不沿用 Greenfield 的 Session，避免混入舊脈絡。
主要 Agent 小組選定、代表全組執行工作的那一個 Agent，接收小組的共同脈絡；不要把所有人的 Session 原封不動拼接。 第 39 分鐘起，小組指定在某位成員電腦上的 Agent 為主要 Agent。
User Story（使用者故事） 從使用者角度寫的一句需求，例如「身為旅客，我想查詢班次，以便訂票」。 需求文件描述旅客要查詢、訂票、付款的情境。
Use Case（使用案例） 描述使用者與系統一步步互動完成一件事的流程，包含正常與例外路徑。 「訂票後付款失敗」是一個例外路徑。
Gherkin 用 Given（前提）／When（動作）／Then（預期結果）寫測試情境的格式，讓需求與測試能對照。 Given 一位學生旅客、When 訂 700 元的班次、Then 票價為 525。

Context 與證據

詞彙 中文與白話解釋 今天的例子
Context（背景資料） 交給 Agent 參考的資料，例如文件、規則與先前結論。文件可作 Context，但不保證全部敘述與程式完全同步；重要結論請 Agent 用程式、測試與公開規則交叉驗證。 B0 的 README、架構文件與 ADR。
Shared Context（共同脈絡） 小組整理出的共同事實：比較各自分析後，記錄共同事實、分歧與待決事項；任務揭露後仍須另外取得範圍與計畫的核准。 第 39–44 分鐘填寫的 Shared Context 表單。
Approved Context（已核准的背景資料） 經人確認、可以交給 Agent 當依據的背景資料。 B3 在 Work Order 填寫的版本與已確認假設。
Seed Data（預設測試資料） 系統啟動時就放好的固定資料，用來開發與測試。 Greenfield 需求文件中的固定班次與站名。
Rule ID（規則編號） 商業規則的編號。交付時列出商業規則與驗收條件的對應，逐項核對。 FARE-002：學生為基礎票價的 75%。
AC（Acceptance Criteria，驗收條件） 說明功能必須符合什麼要求；AC ID 是其編號。每項以 API 或核心邏輯測試提供證據。 AC-B1-001：單一學生旅客票價為基礎票價 75%。
Rule Traceability（規則追溯） 每條規則都能對到哪段程式、哪個測試與哪份文件。 B3 的 Gate 3 Input 要列出規則對照。
ADR（Architecture Decision Record，架構決策紀錄） 說明採用某項設計的原因與取捨。 B0 的 docs/adr/001-use-in-memory-repositories.md。
Diff（變更內容） 修改前後的差異。你不用自己讀；改請 Agent 回答變更審查問題，用白話說明改了什麼。 Agent 用 git diff 檢查後，告訴你改了哪些檔案。
Git 基準 修改前先請 Agent Commit 一次，之後 Agent 才說得出這次改了什麼。 請 Agent 執行 git commit -m "B0 baseline"。
Skip／XFail Agent 回報中可能出現的詞：Skip 是略過測試；XFail 是把測試標成預期會失敗。兩者都不代表功能已完成，不得用來隱藏失敗。 G0 初始的 Skip 代表功能尚未實作。
Regression（既有功能沒被改壞） 確認修改後既有功能仍符合要求；不移除既有測試，也不改既有測試的期待值。 B1 修好學生票後，成人票相關測試仍要通過。
PASS／FAIL／NOT VERIFIED 通過／失敗／未驗證。沒有實際執行就只能寫未驗證，不能寫 PASS。 交付摘要的驗收結果欄。
驗收對照表 Agent 用來回報測試結果的表：每條驗收條件或規則一列，寫編號、白話內容、通過／失敗／未驗證，以及依據的測試名稱；最後一行是通過、失敗、跳過各幾個。你看這張表判斷結果，不看原始輸出或程式。 B3 檢查點 5 請 Agent 整理驗收對照表。
變更審查 取代自己讀變更內容（Diff）：請 Agent 用白話回答改了哪些檔案與原因、測試數有沒有變少或新增跳過、有沒有刪測試或改既有期待值；你用審查卡判斷，任何一題是「否」或「不確定」就不核准。 B3 Gate 3 前的變更審查卡。
/docs（Swagger 介面） 伺服器啟動後在瀏覽器開 http://127.0.0.1:8000/docs 看到的 API 測試頁面：點開 API → 按「Try it out」→ 在 Request body 貼上範例 → 按「Execute」→ 看 Response 的狀態碼（例如 201 成功、400 輸入錯誤、404 找不到）和內容。不用打指令就能試 API。 B3 檢查點 6 在 /docs 試團體訂票。
SHA256 雜湊 檔案的指紋：檔案只要有一個位元組被改，算出的值就不同；用來確認下載的檔案是原版、沒有損壞。 使用復原包時，核對下載卡上的 SHA256。

常用工作術語

詞彙 中文與白話解釋 今天的例子
Root Cause（根因） 問題真正的原因；尚未驗證的說法應標為假設。 B1 請 Agent 找出學生票折扣錯在哪裡，並用白話說明。
Impact Analysis（影響分析） 區分必須修改、可能受影響與不應修改的範圍。 B2 方案核准表的三欄。
Task Breakdown（工作拆解） 把方案拆成可逐步核准、逐步執行的步驟。 B2 核准 5–8 步，第一段只做到第 N 步。
Gate（核准關卡） 人員做決定的檢查點；核准是決策，不等於功能已通過驗收。 B3 的 Gate 1 需求理解、Gate 2 影響分析與設計、Gate 3 交付審查。
APPROVE／APPROVE WITH CONDITIONS／REJECT 核准／附條件核准／拒絕（REJECT AND REVISE 是退回修正）。附條件核准時，條件解除後才可續行。 Gate 決策與例外回應表單的選項。
Review（檢視） 審查實際證據，核對需求、範圍與未完成事項。 看驗收對照表、變更審查答案與文件是否一致。
Delivery（交付）／Delivery Summary（交付摘要） 把成果與證據整理成可審查的摘要交出去；交付不等於完整軟體上線。 第 76–80 分鐘整理 B3 交付摘要並匯出。
Level（完成等級） B3 的完成程度：Level 1 分析完成、Level 2 核心流程完成、Level 3 完整交付。依證據擇一，不自動選 Level 3。 只完成 Gate 1／2 的分析與設計時，如實交付 Level 1。
Work Order（工作命令） 交給 Agent 的正式工作說明，含範圍、限制與停止條件。 B3 第 63 分鐘交給主要 Agent。
Escalation（升級處理） Agent 遇到停止條件時停下，提出證據與選項，交給人決定。 Agent 想加入外部資料庫時，停下來請人決定。
Exception Response（例外回應） 主持人宣布例外事件時，人判斷提議是否在核准範圍內並給 Agent 指令。 第 69–70 分鐘的例外事件。
Artifact（成果紀錄） 可保存、審查與交接的紀錄，例如計畫或測試輸出。 匯出的表單與測試輸出。
段落經過時間 從當段開始計算；與全場經過時間分開標示。 B3 段內第 3 分鐘＝全場第 66 分鐘。
