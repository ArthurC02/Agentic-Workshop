歡迎來到 Agentic Software Development 實作工作坊

從需求拆解、Agent 協作到程式交付，驗證 Agentic Coding 的團隊工作模式。

本工作坊以本機虛構案例 Smart Ticket Platform（車票預訂服務）為情境，在 90 分鐘內走過需求理解、任務拆解、Agent 執行、測試審查與交付。

今天的目標（依重要順序）

  1. 練習 Agentic Coding 技巧：這是主角，每段練一個帶得走的技巧。
  2. 體驗 Agent 參與的開發流程：Agent 從工具、隊友到數位員工（Tool → Teammate → Digital Worker）。
  3. 留下證據：計畫、驗收與交付紀錄由 Agent 寫進 notes/ 資料夾，你只填少量「人的決定」。

今天的流程與技巧（9 個流程技巧＋6 個 Agent 技巧）

每段練一個帶得走的流程技巧（共 9 個），括號內是 Agent 在這段的角色；〔 〕內是這段提示詞示範的 Agent 技巧（共 6 個）。這是路線圖，現在只要記得名稱；每個技巧會在第一次用到的那一步才說明（路線圖另見 Agent 工作方式與安全規則）：

  • 00–07 開場：目標、流程、責任與證據。
  • 07–29 Greenfield（Tool）：給 Agent 一份規則；先要計畫再動手；小步執行、每步驗收。〔Prompt 結構、結構化輸出〕
  • 29–33 Time Skip（Teammate）：開新對話先給規則與脈絡。〔Token 節費〕
  • 33–39 個人分析（Teammate）：讓 Agent 帶你讀陌生專案。〔Token 節費、模型選擇與推論強度、結構化輸出〕
  • 39–44 共同脈絡（Teammate）：把共識寫成檔案給 Agent。〔Skill、Token 節費〕
  • 44–52 B1（Teammate）：用失敗測試找 Bug：重現 → 定位 → 最小修正 → 驗證。〔Skill、Token 節費〕
  • 52–63 B2（Teammate → Digital Worker 過渡）：請 Agent 提 2–3 個方案並比較，人來選。〔結構化輸出、推論強度〕
  • 63–76 B3（Digital Worker）：委派整件任務：工作單 ＋ 三道關卡。〔Skill、結構化輸出、模型選擇、Token 節費〕
  • 76–80 交付（Digital Worker）：請 Agent 整理交付摘要，人核對。〔結構化輸出〕
  • 80–90 回顧：把今天的技巧變成自己的提示詞清單，至少一段改寫成自己的 Skill 檔。〔六個技巧總回顧〕

新系統開發（Greenfield）採個人練習；接手既有系統（Brownfield）先各自分析，再整合小組判斷。

先認識今天會用到的名詞

  • Tool → Teammate → Digital Worker：Agent 從工具（Tool）、隊友（Teammate）到能獨立執行任務的數位員工（Digital Worker），是今天依序練習的三種協作角色，下一節說明分工。
  • Greenfield／Brownfield：Greenfield（從頭開始的新專案）；Brownfield（已有程式碼的既有專案）。
  • MVP：MVP（Minimum Viable Product，最小可行產品）。今天指能跑通查詢班次、訂票、模擬付款與查詢訂單的核心流程。
  • 段落代號：G0 是 Greenfield 的起始程式包；B0 是 Brownfield 的起點，也就是假設系統已上線 12 個月的既有程式；B1、B2、B3 是接下來三個 Brownfield 任務：B1 修復學生票折扣異常、B2 導入不可疊加的最有利優惠政策、B3 團體訂票。
  • Time Skip：Time Skip（時間快轉：專案假設已開發一段時間），從 Greenfield 跳到 Brownfield 的轉場。
  • Shared Context：共同脈絡（Shared Context：小組整理出的共同事實），交給 Agent 當作背景資訊。
  • Gate：核准關卡（Gate），由人決定是否放行下一步；核准是決策，不等於功能已通過驗收。B3 有三個核准關卡。
  • Recovery：Recovery（復原包：進度落後時改用的接續基線），只在主持人核准後提供。

其他名詞不熟時，可查 詞彙表。

主線：Tool → Teammate → Digital Worker

  • Tool（工具）：你逐步下指令、每一步用證據驗收；Agent 每做完一步就停下回報。
  • Teammate（隊友）：Agent 一起分析既有系統、提出選項與取捨；你比較、核准計畫後它才動手。
  • Digital Worker（數位員工）：你設定工作邊界，只在核准關卡（Gate）核准並承擔最終責任；Agent 在範圍內自主執行。

這三種角色描述人與 Agent 的協作分工，依序出現在本次 90 分鐘流程中；它們不是產品分類，也不代表所有工作都應提高自主程度。三者的差別不是「人寫多少程式」，而是「人介入的方式」。每段任務文件在該段開始時解鎖。

今天的原則：全程人不寫、不讀程式

今天從頭到尾，你不寫程式、不讀程式，也不自己打終端機指令。程式、測試與所有指令操作都交給 Agent；你負責決定、核准，並用「行為與證據」驗證結果：

  • 工作規則：每段開始時，把 Runbook 提供的「Agent 工作規則」整段貼給 Agent。這段是給 Agent 的，不需要看懂。
  • 驗收對照表：請 Agent 把每條驗收條件的結果（通過／失敗／未驗證）和依據的測試整理成表，你逐條核對。
  • 變更審查：不看程式碼，改請 Agent 用白話回答固定的審查問題，你只回答自己判斷得了的問題。
  • 實際操作：在瀏覽器開 API 測試頁 /docs，親自試一次功能是否符合需求。

這樣做也有代價：只看證據不看程式，抓不到「測試全過，但寫法有問題」的程式。回顧時會討論公司需要什麼角色或平台來補這個盲點。

如何使用這份 Runbook

  • 投影畫面與 Runbook 的分工：投影畫面顯示時間、解鎖碼和目前進行到哪一步；要做什麼、提示詞與表單都在 Runbook。活動進行中請看自己的 Runbook，投影畫面換頁時再跟著跳到對應的步驟。
  • 左側導覽列出所有章節；每章右側的分鐘標記是該內容使用的時段。用頁面底部的「上一頁／下一頁」依序前進。
  • 一般活動章節：到對應時段，由主持人在畫面公布活動解鎖碼；請在章節的解鎖框輸入。大小寫、空白與連字號不影響輸入。
  • 復原基線（Recovery）章節：只有需要接續基線的小組，才由主持人於第52／63分鐘核准後個別提供獨立碼；一般 B2／B3 活動碼不會解開它們。請先保留原成果，按該頁步驟切換；使用接續基線不算自行完成前段任務。
  • 解鎖狀態：瀏覽器允許本機儲存時會記住；使用同一瀏覽器與同一檔案，重新開啟才能恢復。
  • 下載：G0 Greenfield 起始程式包（第 07 分鐘）與 B0 Repository（第 29 分鐘）都內嵌在本 Runbook 中，解鎖後按下載按鈕取得 ZIP。B1／B2 的復原包也已內嵌，但須另外取得獨立碼。
  • 步驟勾選：章節中的核取方塊可用來追蹤進度，導覽列會顯示各章完成度。勾選只代表你已實際確認。
  • 紀錄與表單：分析、計畫、測試結果等紀錄都請 Agent 寫進 Repository 的 notes/ 資料夾（例如 notes/greenfield.md），你不用抄寫。頁面上的表單每段最多一張，大多是下拉選單或勾選，只記「人的決定」，可直接在頁面中填寫，瀏覽器允許本機儲存時，內容會自動暫存。可用「匯出 Markdown」下載 .md 檔，或用「複製 Markdown」貼到主持人指定的交付位置。
  • 提示詞區塊：每個檢查點都有一段可直接複製的提示詞。按複製按鈕、貼到 Agent 對話，就能跑完這一步；需要你決定時，Agent 會先列出選項再停下，你只要回「同意」或「改成…」。
  • 💬 討論一下：有些步驟附小組口頭討論題，講完就好，不用寫下來。
請整場保持這份檔案開啟

請固定用同一個瀏覽器開啟同一份 runbook.html。更換瀏覽器、使用私密視窗或清除瀏覽資料，可能讓解鎖狀態與表單暫存消失；重要內容請隨時匯出 Markdown。

Runbook 可離線閱讀；程式案例仍需安裝套件

閱讀這份 HTML 不需要安裝瀏覽器擴充套件。執行程式案例則需要 Python 3.13 與通用 Coding Agent，並由 Agent 依各版 requirements.txt 建立獨立環境（venv）、安裝套件。案例不需要前端、外部資料庫、真實金流或外部交通 API。環境準備請見 環境準備。

共同規則

  1. 工具中立：使用你可取得的任一通用 Coding Agent。本 Runbook 不要求任何特定 Agent 產品的指令或功能。
  2. 人員負責：Agent 產生建議、程式碼、測試與文件，並執行所有指令；人員不寫、不讀程式，但仍對正式提交、風險判斷及成果驗收負責，並以驗收對照表、變更審查與實際操作驗證結果。
  3. 不是速度競賽：不比較 Coding 速度、程式碼量或 Agent 自主程度。重點是計畫、變更內容（Diff）、測試與交付證據。
  4. 如實交付：時間到就停止擴充。未完成的部分如實列出，不把部分完成描述為完整交付，也不以未執行或仍被略過（Skip）的測試宣稱完成。
  5. 只用本機虛構資料：不使用正式客戶資料、真實個資、帳密或金鑰。
  6. 任務文件分段解鎖：任務文件於第 07 分鐘起依時段解鎖，請不要提前猜測後續段落的內容。

環境準備

工作坊時間要用來體驗 Agent 協作，不是處理安裝問題。請在開場時確認下列項目，有問題立即告知主持人。

前置需求

套件由各版 requirements.txt 指定：FastAPI 0.115.12、Uvicorn 0.34.2、Pydantic 2.11.4、pytest 8.3.5、httpx 0.28.1。不需要前端、外部資料庫、真實金流或交通 API。

你會在什麼時候拿到程式碼

  • 第 07 分鐘：G0 Starter Repository（Greenfield 起始程式包）。主持人公布解鎖碼後，在 Greenfield 任務 頁面下載。
  • 第 29 分鐘：B0 Repository（Brownfield 起點：假設已上線 12 個月的既有程式）。主持人公布解鎖碼後，在 Time Skip（時間快轉）章節下載。

兩份程式碼都以 ZIP 形式內嵌在本 Runbook 中。每一版都請 Agent 在該版自己的資料夾內獨立建立環境（venv），不共用環境，也不混用不同版本的程式。

解壓縮到短路徑

ZIP 內的資料夾層級較深。請解壓縮到短路徑，例如 C:\work\g0、C:\work\b0，避免 Windows 路徑長度限制導致檔案解壓縮不完整。不要解壓縮到深層的同步資料夾或桌面子資料夾。

每一版的準備步驟

現在還沒有程式碼，不用做任何準備。建環境、跑起始測試的提示詞在 Greenfield 任務 檢查點 1，啟動伺服器的提示詞在檢查點 4；B0 的準備在 Time Skip 章節。到時候照該頁貼給 Agent 即可，這裡只放出錯時用的疑難排解。

疑難排解

遇到任何錯誤，先把錯誤訊息交給 Agent，請它用白話說明，不要自己動手修：

剛才的步驟出錯了。請先不要修改任何檔案，用白話告訴我：錯誤訊息是什麼意思、可能的原因、你建議怎麼處理（列 1–2 個做法），然後停下等我決定。
Agent 直接呼叫 venv 裡的 Python

檢查點 1 的提示詞要求 Agent 用 py -3.13 -m venv .venv 建立環境，之後直接呼叫 .venv\Scripts\python.exe（Git Bash 寫 .venv/Scripts/python.exe），不必啟用，也不會裝錯 Python；Python 不是 3.13 時 Agent 會停下，請告知主持人。

/docs 頁面一片空白

/docs 的畫面要從網路載入，沒有網路時會是空白頁。請 Agent 改用 Python 的 httpx 實際呼叫同一組 API，把每一步的狀態碼和回應重點列給你看，並在 notes 註明「/docs 無法載入，改由 Agent 呼叫 API」。

Git 回報檔名太長（Filename too long）

多半是解壓縮的路徑太深。請 Agent 只在這個專案設定 core.longpaths 為 true（不要用 --global），或把 ZIP 重新解壓縮到更短的路徑，例如 C:\work\g0。

Port 8000 已被佔用

請 Agent 改用其他未使用的埠號（Port，例如 8001），告訴你新的 /docs 網址；在交付紀錄中寫下實際使用的 Port。

切換版本前先停止舊的 Server

從 G0 換到 B0 前，先請 G0 的 Agent 停止它啟動的伺服器，再請 B0 的 Agent 啟動新版本並確認正常，避免讀到舊版本。不要停掉其他人執行中的程式。

資料重啟會重置

案例使用固定的 Seed Data（系統預設的測試資料）、可控的時鐘與付款模擬，資料存在記憶體中（In-Memory），重啟 App 就會回到初始狀態。這是設計行為，不是錯誤。

套件無法安裝時

若網路不可用或 Agent 回報套件安裝失敗，請立即告知主持人，不要在活動中臨時更換 Python 版本或技術棧。

Agent 工作方式與安全規則

本工作坊不指定 Agent 產品。不論使用哪一種通用 Coding Agent，都依同一套工作節奏進行：先計畫、人審查，再執行、測試與說明。程式、測試與指令操作全部由 Agent 負責；你不寫、不讀程式，只負責決定、核准，並用證據驗證。

工作節奏

Plan → Human Review → Execute → Test → Explain

  • 計畫（Plan）：Agent 讀需求與 Repository，提出分步計畫並列出要你決定的問題；它先不修改。你核對範圍、回答問題。
  • 人員審查（Human Review）：你確認後才核准；Agent 等你確認，不自行開始。
  • 執行（Execute）：Agent 只做核准的步驟，不任意加套件或改需求；遇到疑問由你決定。
  • 驗證（Test）：Agent 跑測試、整理驗收對照表，沒執行的標「未驗證」；你逐條核對，並在 /docs 實際試用。
  • 說明（Explain）：Agent 用白話說明改了什麼、為什麼、還有什麼沒完成；你看它回答的變更審查問題，核對是否和計畫一致。

每個檢查點的提示詞都已照這個節奏寫好，複製貼上即可；你只要看 Agent 的回報、做決定。

用證據審查，而不是只看摘要

Agent 的摘要與「全部通過」的訊息都不能取代你的審查。你不讀程式碼，改用三種證據：

  • 驗收對照表：每條驗收條件一列，寫結果（通過／失敗／未驗證）與依據的測試。
  • 變更審查：Agent 停下後，用白話回答固定的審查問題，你逐題判斷。
  • 實際操作：在瀏覽器開 /docs 親自試一次功能。

這三種證據怎麼要、怎麼看，在 Greenfield 任務 第一次用到時才說明，提示詞也都已寫好。

紀錄交給 Agent 寫進 notes

重要階段的結果不要只留在對話中。Agent 會把計畫、分析、驗收對照表與交付摘要寫進 Repository 的 notes/<段落>.md（例如 notes/greenfield.md），每段提示詞都會講明寫到哪個檔。你只在 Runbook 表單用下拉或勾選記下自己的決定。

技巧路線圖：六個 Agent 技巧在哪裡學

除了每段一個流程技巧，提示詞裡還埋了六個操作 Agent 的技巧。現在只要知道名稱；每個技巧在第一次用到的那一步才用「技巧：…」小卡說明是什麼、為什麼有效，並附官方文件的延伸閱讀。

  1. Prompt（提示詞）結構：Greenfield 檢查點 2 第一次學。
  2. 模型選擇：個人分析檢查點 1 第一次學；B3 再用。
  3. 推論強度（Reasoning Effort）：個人分析檢查點 1 第一次學；B2 再用。
  4. Structured Output（結構化輸出）：Greenfield 檢查點 3 第一次學；B2、B3、交付再加深。
  5. Token 節費：Time Skip 檢查點 2 第一次學；之後每段都會用到。
  6. Skill（可重複使用的工作說明）：共同脈絡檢查點 2 第一次學；B1、B3 再加深。

三個階段需要的技巧不同：Tool 階段靠「提示詞寫清楚、回報有固定格式」；Teammate 階段靠「省 Token、把共識寫成檔案」；Digital Worker 階段把整份工作說明交出去，只在關卡看固定格式的回報。

安全規則

不要讓 Agent 接觸真實資料或機密

本案例只使用本機虛構資料與模擬付款。不得輸入或讓 Agent 取得、輸出正式客戶資料、真實個資、帳密或金鑰，也不要讓 Agent 操作任何正式環境。

在本工作坊中，Agent不得：

  • 操作正式環境。
  • 取得或輸出帳密、金鑰及客戶敏感資料。
  • 任意新增未核准的外部套件。
  • 修改工作範圍以外的模組。
  • 跳過測試、檢視（Review）或核准流程。
  • 直接將未經審查的內容合併至主要分支。
Agent 擴大範圍時

修改應限制在核准的計畫與範圍內。如果 Agent 的變更說明或審查答案中出現改需求、新增範圍外功能或修改範圍外檔案的變更，不要直接接受；先回到核准的計畫，由你決定如何處理後再繼續。
