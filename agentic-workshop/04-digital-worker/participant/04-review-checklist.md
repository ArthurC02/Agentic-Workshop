# B3 交付審查檢核表

> 讀者：小組審查者。
> 什麼時候用：Gate 3（交付審查），需要時才用。
> 開始前要有：Agent 已提供目前成果、Gate 紀錄與 `notes/b3.md` 的 Gate 3 資料；有修改或測試時，附變更審查答案與驗收對照表。Level 1（分析完成）可以尚無修改、也未執行測試，但必須寫明原因與哪些範圍未驗證。

由 Agent 逐項自評，寫進 `notes/b3.md` 的「交付審查」段落：每項寫符合／不符合／未驗證，並附依據（驗收對照表、變更審查答案、/docs 實測結果或文件）。沒完成或沒驗證的如實寫出，Agent 不可自動全部寫成符合。人抽查，不看程式，看不懂就請 Agent 解釋。

Level 1 時仍要審查：需求理解與設計兩道 Gate、影響分析是否合理、測試策略是否完整，以及缺少的項目。不能因為沒有程式修改就不收這份成果，但這不代表功能通過驗收。

## 需求（Requirement）

- 5–20 人邊界。
- 不允許部分成功。
- 同一車廂連續座位。
- 付款失敗時整筆取消。
- 每位旅客仍沿用 B2 對他最有利的單一優惠。

## 範圍（Scope）

- 沒有新增外部資料庫或服務。
- 沒有全面重寫一般訂票（Booking）。
- 沒有修改無關的 API。
- 修改的檔案和 Gate 2 核准的計畫一致；有偏差已回報。

## 品質（Quality）

- 建立失敗時不保留座位。
- 付款失敗時釋放全部座位。
- 付款失敗時不產生訂單（Order）。
- 付款成功時只有一筆訂單。
- 稽核紀錄（Audit）與通知（Notification）依規則留下紀錄。

## 證據（Evidence）

- 實際執行的指令與結果查得到。
- 沒有跳過（skip）、預期失敗（xfail）或原因不明的失敗；沒執行的部分已說明。
- 每條驗收條件（Acceptance Criteria）都對得到測試。
- 文件和實作一致。
- 還沒完成的事與已知風險已說明。

最後由 Agent 寫：建議的完成等級（Level 1–3）、證據位置、不符合或未驗證的項目。人在 Gate 3 決定是否要求修正；審查者姓名隨 Gate 3 決策一起記錄。

## 完成條件

每項自評都有證據；不符合或未驗證的項目都要進入 Gate 3 決策與交付摘要，不能因為程式量或時間壓力省略審查。Level 1／2 只依實際學習成果收件；要宣稱 Level 3 完整交付，仍須有完整功能、回歸測試（Regression）、文件與審查證據，驗收標準不降低。
