# Digital Worker Work Order

> 讀者：小組與主要 Coding Agent。
> 什麼時候用：B3 發下後交給 Agent。Agent 先把已核准背景寫進 `notes/b3.md`；Gate 2 的核准範圍，等人在 Gate 2 決定後，再由 Agent 照人的決策原文補記。
> 這份工作單（Work Order）就是給 Agent 的 Skill（可重複使用的工作說明）：Agent 把它連同三道核准關卡（Gate）文件裡的「Gate 回報格式」存成 `skills/b3-work-order.md`，之後照它自己往下做，人不必每一步重貼。
> 開始前要有：已核准的共同脈絡（Shared Context）與 [B3 任務卡](../../03-brownfield/participant/task-cards/03-b3-group-booking.md)。

## 任務（Mission）

執行 `TASK-B3-001` 團體訂票。Agent 主導交付，人負責三道核准關卡（Approval Gate）。

## 已核准的需求（Approved Requirements）

一次 5–20 人，搭同一班次（Trip）。必須在同一節車廂取得連續空位；找不到夠長的連續空位，就整筆拒絕。建立成功後仍是待付款狀態。付款成功時整筆成立，而且只有一筆訂單（Order）；付款失敗時整筆取消、釋放全部座位，而且不產生訂單。每位旅客各自沿用 B2 對他最有利的單一優惠，再把個人票價加總；優惠不疊加。一般訂票，以及既有的會員、改票、退票、通知、稽核紀錄（Audit）功能都要保留。不做部分成功、分次付款、候補或指定座位。

## 商業規則（Business Rules）

規則編號（Rule ID）照原樣使用，不要改。

- `GROUP-001`：至少 5 人；`GROUP-002`：最多 20 人。
- `GROUP-003`：同一班次；`GROUP-004`：同一車廂的連續座位。
- `GROUP-005`：找不到能容納整團的座位就不建立；`GROUP-006`：一次保留全部座位；`GROUP-007`：建立失敗時不保留任何座位。
- `GROUP-PAY-001`：付款成功轉為 PAID（已付款）；`GROUP-PAY-002`：付款失敗轉為 CANCELLED（已取消）；`GROUP-PAY-003`：付款失敗時釋放全部座位；`GROUP-PAY-004`：付款失敗時不產生訂單；`GROUP-PAY-005`：付款成功時只有一筆訂單。
- `GROUP-FARE-001`：每位旅客各自沿用 B2 優惠；`GROUP-FARE-002`：總價是每人票價加總。
- `GROUP-AUDIT-001`：建立、付款成功、付款失敗都留下稽核紀錄。
- `GROUP-NOTIFY-001`：成功時發通知；`GROUP-NOTIFY-002`：失敗時發取消通知。

B2 的 `FARE-007`–`FARE-010` 繼續適用：優惠不疊加、取最低的合格單一折扣率、每位旅客分開判定、記錄實際套用的優惠類型與折扣率（Type／Rate）。優惠資格：成人 100%、學生 75%、提前至少 14 天訂票 85%、企業會員 95%。

## 已核准背景（Approved Context）

請 Agent 依下列項目寫進 `notes/b3.md` 的「已核准背景」段落：小組；主要 Agent 與這次對話；共同脈絡版本（`notes/shared-context.md`）；接手的程式版本；已確認的假設與限制；尚待決定的事項。查不到的寫「待小組確認」，由小組確認，Agent 不要猜。

## 允許修改的範圍（Allowed Change Scope）

實際核准範圍由人在 Gate 2 決定，Agent 照原文寫進 `notes/b3.md` 的「Gate 2」段落。可以修改的種類：團體流程需要的 API、業務模型（Domain）、應用流程（Application）、座位分配、付款失敗的復原（Compensation）、測試與文件。每個預計修改的檔案，都要先說明為什麼要改。

## 禁止修改的範圍（Prohibited Change Scope）

不全面重寫一般訂票（Booking）、不修改無關的 API、不移除既有功能或保護它們的回歸測試（Regression）、不引入外部服務或第三方規則引擎；維持現有的記憶體內（In-Memory）儲存，不新增任何資料庫（不論外部或內嵌）；不自行改商業規則、使用的技術或既定的座位容量。要改 API 合約（API Contract：API 的輸入、輸出與行為約定），須先取得核准。

## 必須交付的成果（Required Deliverables）

需求理解、影響分析、核准的計畫與每道 Gate 的證據、核准範圍內的修改與白話變更說明、Gate 3 變更審查答案、測試結果、文件、驗收對照表（每條規則／驗收條件一列），以及 [交付摘要（Delivery Summary）](05-delivery-template.md) 與還沒完成的事。每一項都要寫出來源與結果，讓人查得到。

## 必須有的測試（Required Tests）

5 人與 20 人可以建立、4 人與 21 人被拒絕；同一車廂連續座位，以及找不到夠長連續空位的情況；建立失敗不留下任何座位；每位旅客分開用 B2 計價；付款成功只有一筆訂單；付款失敗時取消、釋放全部座位、不產生訂單；稽核紀錄與通知；既有功能的回歸測試。實際執行的指令、結果與沒執行的部分都要記錄，不能用「預期會過」代替實際執行。

## 三道核准關卡（Approval Gates）

依 [三道 Gate](03-approval-gates.md)：Gate 1 需求理解、Gate 2 影響分析與設計、Gate 3 交付審查。每道 Gate 都用該文件的「Gate 回報格式」提交。決策包含審查過的證據、條件、核准人與時間（全場第幾分鐘），由人說出，Agent 照原文寫進 `notes/b3.md`；條件還沒滿足，不得自行擴大核准範圍。

## 停止與升級條件（Stop and Escalate Conditions）

以下任一情況發生，就停止和該情況有關的修改與測試（其他已核准、不受影響的工作可以繼續），提出證據，並說明需要人決定什麼：

1. 需求和規則編號（Rule ID）互相矛盾。
2. 參與者文件和程式不一致，測試也無法判斷哪個對。
3. 需要修改核准範圍以外的 API 合約。
4. 需新增外部服務或套件。
5. 需要移除既有的回歸測試。
6. 無法確認付款失敗後正確的狀態。
7. 找不到同時滿足座位規則與「整筆成功或整筆失敗」（Atomicity）的做法。
8. 測試出現和本任務無關的新失敗。
9. 需要修改 Gate 2 預估清單以外的檔案。
10. 人提醒剩餘時間，或 Agent 判斷剩下的工作做不完承諾的交付。

依 [升級範本（Escalation）](06-exception-response-card.md#escalation) 的格式，用六個固定標題 Trigger（觸發原因）、Evidence（證據）、Impact（影響）、Options（可選方案）、Recommendation（建議）、Decision Needed（需要人決定的事）寫進 `notes/b3.md`，等人決定後才繼續。

## 時間安排（Timebox）

B3 共 13 分鐘，每道 Gate 控制在 1–3 分鐘。段內時間：第 3 分鐘（全場第 66 分）Gate 1 決策；第 6 分鐘（全場第 69 分）Gate 2 決策；第 7 分鐘（全場第 70 分）起執行；第 11 分鐘（全場第 74 分）停止擴充功能與測試；第 12 分鐘（全場第 75 分）Gate 3 交付審查；第 13 分鐘（全場第 76 分）B3 結束；交付摘要在第 76–78 分鐘寫進 `notes/delivery.md`。例外事件的判斷時間含在內，不另外加時。

完成條件：小組已確認已核准背景，Gate 2 核准範圍已記進 `notes/b3.md`；Agent 清楚規則與停止條件，保留核准證據，如實說明完成程度；沒完成的部分不宣稱通過驗收。
