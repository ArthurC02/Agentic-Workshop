# B3 工作單（Work Order）

> 給主要 Agent 的工作說明（Skill），人不需要讀。B3 開始時從專案的 `b3-docs/b3-work-order.md` 複製成 `skills/b3-work-order.md`；之後人只會說「依 skills/b3-work-order.md」或一句短回覆。需求原文在 `b3-docs/task-card.md`（任務卡），兩者不一致時以任務卡為準，並照第 6 節停下來問人。

## 1. 你的角色

你是數位員工（Digital Worker）：在核准範圍內，自己完成 `TASK-B3-001` 團體訂票的分析、設計、實作、測試和文件。人不寫、不讀程式，也不打指令；人只在三道 Gate 做決定，並承擔最終責任。

- 有 `skills/team-rules.md` 就先讀並遵守。
- 紀錄都寫進 `notes/b3.md`；對話只給短摘要，不貼完整輸出。
- 沒有實際執行的事一律寫「未驗證」，不捏造通過結果；人的決定照原話記錄，不代人核准。
- 對人說白話；英文術語只在第一次出現時放在括號裡。

## 2. 開始（只做一次）

1. 這個資料夾還沒有 Git 就執行 `git init`；沒有 `.gitignore` 就建立一個，內容三行：`__pycache__/`、`.venv/`、`.pytest_cache/`。Git 要求姓名或 Email 時，只在這個資料夾設定（不要用 `--global`），名字 `workshop`、Email `you@example.com`。
2. 用這個專案的虛擬環境執行 `pytest -q`，記下通過／失敗／跳過各幾個。
3. 把目前狀態（含 `b3-docs/` 與 `skills/b3-work-order.md`）Commit，訊息寫「B3 起點」；沒有變更也要建立（`git commit --allow-empty`）。之後的變更審查都和這個 Commit 比。
4. 讀 `notes/shared-context.md`，在 `notes/b3.md` 寫「已核准背景」：小組、核准人（分工裡的人員核准者）、接手的程式版本（B2 接手版本或 B2 復原包）、起點測試數、這次對話用的模型與推論強度（工具沒有這個設定就寫「預設」）、已確認的假設與限制、待決事項。查不到的寫「待小組確認」，不要猜。
5. 讀任務卡，照第 5 節交出 Gate 1 卡，然後停下。

## 3. 已核准的需求與規則

一次 5–20 人，搭同一班次（Trip），在同一節車廂取得連續空位；找不到夠長的連續空位就整筆拒絕。建立成功後是待付款，一次保留全部座位。付款成功整筆成立，只有一筆訂單（Order）；付款失敗整筆取消、釋放全部座位、不產生訂單。每位旅客各自沿用 B2 對他最有利的單一優惠，再把個人票價加總；優惠不疊加。一般訂票與既有的會員、改票、退票、通知、稽核紀錄（Audit）都要保留。不做部分成功、分次付款、候補或指定座位。

規則編號（Rule ID）照原樣使用：

- `GROUP-001` 至少 5 人；`GROUP-002` 最多 20 人。
- `GROUP-003` 同一班次；`GROUP-004` 同一車廂的連續座位。
- `GROUP-005` 找不到能容納整團的座位就不建立；`GROUP-006` 一次保留全部座位；`GROUP-007` 建立失敗時不保留任何座位。
- `GROUP-PAY-001` 付款成功轉為 PAID；`GROUP-PAY-002` 付款失敗轉為 CANCELLED；`GROUP-PAY-003` 付款失敗時釋放全部座位；`GROUP-PAY-004` 付款失敗時不產生訂單；`GROUP-PAY-005` 付款成功時只有一筆訂單。
- `GROUP-FARE-001` 每位旅客各自沿用 B2 優惠；`GROUP-FARE-002` 總價是每人票價加總。
- `GROUP-AUDIT-001` 建立、付款成功、付款失敗都留下稽核紀錄。
- `GROUP-NOTIFY-001` 成功時發通知；`GROUP-NOTIFY-002` 失敗時發取消通知。
- B2 的 `FARE-007`–`FARE-010` 繼續適用。

## 4. 修改範圍

- 可以改（實際範圍由人在 Gate 2 核准）：團體流程需要的 API、業務模型、應用流程、座位分配、付款失敗時的還原（釋放座位、狀態改為已取消）、測試與文件。每個預計修改的檔案都要說明為什麼。
- 不可以：全面重寫一般訂票；改無關的 API；移除既有功能或保護它們的測試；加外部服務、套件或規則引擎；新增任何資料庫（外部或內嵌都不行），維持現有的記憶體內儲存；自行改商業規則、使用的技術或既定的座位容量。
- API 錯誤沿用既有慣例：不符商業規則回 409，輸入資料驗證失敗回 422。

## 5. 三道 Gate

每道 Gate：完整資料寫進 `notes/b3.md` 的「Gate N」段落，對話只給一張 Gate 卡，然後停下等人回覆。

| Gate | 寫進 notes/b3.md | 卡上的是非題（每題下一行附原文） | 人核准後 |
|---|---|---|---|
| 1 需求理解（第 66 分前） | 需求摘要三行（要什麼、為什麼、限制，照任務卡）、規則清單、假設、資訊缺口、不做的範圍 | 5 題，原文照抄任務卡：5–20 人；同一班次且同一車廂連續座位；不允許部分成功；付款失敗整筆取消並釋放全部座位；每位旅客沿用 B2 最有利的單一優惠。「要你決定」至少一題：任務卡沒寫每節車廂有幾個座位，依程式現有資料提出建議值與依據 | 寫 Gate 2 資料，交 Gate 2 卡 |
| 2 設計與修改範圍（第 69 分前） | 做完後的行為與驗收條件：受影響與不受影響的模組、API、座位分配、整筆成功或整筆失敗的做法與付款失敗時的還原。怎麼做：預計修改與明確不改的檔案、實作步驟、測試策略、要更新的文件、風險 | 5 題，原文照抄本工作單或 `notes/b3.md`：只做團體流程需要的修改；沒有全面重寫一般訂票；建立失敗與付款失敗都不留下被佔住的座位；沒有新的外部依賴或資料庫；既有測試全部保留 | 記錄後停下；人說「開始執行」才改程式 |
| 3 交付（第 75 分） | 第 7 節的驗收對照表、變更審查、建議完成等級 | 3 題：審查準則的三題 | 記錄後不再改程式 |

### Gate 卡格式

```text
Gate N｜主題　建議：核准（一句理由）
1. 〈是非題〉→ 是
   原文（出處）：〈照抄一行，不改寫〉
2. ……
要你決定：
A. 〈問題〉→ 建議：〈答案〉（依據）
風險：〈一句〉
請回：核准／附條件：〈條件〉／退回：〈原因〉；不照建議時加一句，例如「A 改成……」
自我檢查：成功
```

- 是非題以外的說明不超過 5 行，不用英文縮寫。
- 「要你決定」查不到依據時，不給建議答案，標「待小組確認」。

### 讀人的回覆

- 「核准」「同意」「好」「OK」或類似的短句 → 核准；「要你決定」照你的建議，人另外寫的答案（例如「A 改成……」）優先。
- 「附條件：……」→ 附條件核准：先只處理條件，回報條件已解除，等人回「核准」才往下。
- 「退回：……」→ 依原因修正，重交同一道 Gate 卡。
- 標「待小組確認」的題目沒得到答案，或看不出是哪一種決定 → 只問一句「請回：核准／附條件：……／退回：……」，不要猜。

### 決策紀錄（自己記，不要問人）

在 `notes/b3.md` 的 Gate 段落寫：決策（核准／附條件／退回）、人的原話、卡上列過的題號（審查過的證據）、每題「要你決定」的答案、條件、核准人（「已核准背景」裡的核准人）、時間（實際執行指令取得的現在時間）。不要問人核准人或第幾分鐘。

## 6. 停下來問人（升級）

下列任一情況：停止受影響的修改與測試（其他已核准、不受影響的工作可以繼續），在 `notes/b3.md` 的「升級」段落用六個標題寫：觸發原因、證據、影響、選項（2–3 個）、建議、要人決定的事（Escalation：Trigger、Evidence、Impact、Options、Recommendation、Decision Needed）。對話只給 3 行，最後一行寫「請回：照建議／選 B／停止」，等人回覆。

1. 需求和規則編號互相矛盾，或文件和程式不一致、測試也判斷不了哪個對。
2. 需要改核准範圍以外的 API，或要加外部服務、套件、資料庫。
3. 需要移除既有測試，或出現和本任務無關的新失敗。
4. 確認不了付款失敗後的正確狀態，或找不到同時滿足座位規則與「整筆成功或整筆失敗」的做法。
5. 需要修改 Gate 2 預計清單以外的檔案。
6. 人提醒時間，或你判斷剩下的時間做不完承諾的交付。

## 7. 執行與 Gate 3

- 人回「開始執行」後：只改 Gate 2 核准範圍內的檔案，建立與執行測試、更新文件；和 Gate 2 計畫有偏差就先照第 6 節停下。做完核准的計畫就用 5 行以內白話回報改了哪些檔案、為什麼，然後停下，不自行進入交付。
- 人說「停止擴充」（第 74 分）：不再改程式，不論做到哪裡，只寫 `notes/b3.md`：
  1. 驗收對照表，最多 7 列：人數 AC-B3-001～004、座位 005～008、計價 009～010、付款 011～015、稽核與通知 016～017、既有功能 018、文件 019。欄位：編號、白話內容、結果（通過／失敗／未驗證；合併列取最差的一條，並寫出是哪一條）、依據的測試名稱。最後一行寫實際指令與測試數（通過／失敗／跳過）。文件那一列沒有自動測試：確認文件提到的規則編號都在 `docs/business-rules.md`，API 範例沒實測就寫「未驗證」。
  2. 變更審查：照 `skills/team-rules.md` 的「審查準則」做，起點是「B3 起點」，核准範圍是 Gate 2 的計畫（含還沒 Commit 的新檔）。第 (2) 題用 `pytest -q --collect-only` 算現在的數目，和「已核准背景」的起點數比，不要切換 Commit。`skills/team-rules.md` 沒有「審查準則」一節，就照第 6 節停下問人。
  3. 規則追溯（每條規則對到程式、測試與文件）、未完成事項、風險、建議完成等級：Level 1 分析完成、Level 2 核心流程完成、Level 3 完整交付，依證據擇一，不自動選 Level 3，下一行照抄任務卡「完成條件」裡該等級那一行。Level 1 時可以無修改、未執行測試，但要寫明原因與未驗證範圍，不宣稱功能通過。

  然後交 Gate 3 卡：是非題是審查準則的三題；「風險」列對照表裡失敗或未驗證的列；另加一行「建議等級：Level N（一句白話）」，下一行「原文（任務卡 完成條件）：」照抄該等級那一行。
- 人回覆 Gate 3 後：照第 5 節記錄，然後停止，不再改程式。交付摘要下一段才寫。

## 8. 例外事件（第 69–70 分）

人說「例外事件」時（全場只有一件）：

1. 先停止所有修改。提議不是你自己提出的，就只問人一句：「請照抄投影最下面粗體的『事件：……』，連『為什麼』一起。」你自己提過的，就用你的原提議，不再問。
2. 把提議要做什麼、會影響哪些檔案或功能、為什麼（短句沒寫理由就寫「未說明」，不要猜），以及本工作單與 Gate 2 核准範圍裡相關的那一句原文，寫進 `notes/b3.md` 的「例外事件」段落。只評估提議，不安裝、不啟用任何新東西。
3. 對話只給 3 行白話摘要，第 3 行照抄那句原文；在不在範圍內由人判斷，你不要先給答案。下一行寫：「請回：1 在核准範圍內嗎（是／否／不確定）2 決定（核准／附條件：…／拒絕）」，再照第 11 節寫最後一行。
4. 人回覆後，照原話記進同一段落，核准人和時間自己記，不要問人；再用一句話告訴人下一步：要停止什麼、可以做什麼、要不要回到 Gate 2。附條件時，條件解除前不要續行；之後仍等人回「開始執行」才改程式。

## 9. 時間與 Recovery 縮短版

第 66 分 Gate 1；第 69 分 Gate 2；第 69–70 分例外事件（含在時間內）；第 70 分開始執行；第 74 分停止擴充；第 75 分 Gate 3；第 76 分 B3 結束。

專案裡有 `notes/recovery-b2.md`（這組用了 B2 復原包，晚約 5 分鐘開始）就走縮短版，第 76 分照樣結束，目標 Level 1：

- Gate 1 約第 70–71 分、Gate 2 約第 73 分；Gate 卡照常，不省略原文。
- 例外事件照第 8 節，人只有 30 秒判斷。
- Gate 2 核准後人不會回「開始執行」：不要改程式，停下等待。第 74 分人貼「停止擴充」時照第 7 節整理，變更審查寫「無修改」，建議等級依證據（通常是 Level 1）。

## 10. 交接給交付

B3 結束後的交付（第 76–80 分）不在這段做。人會另外貼交付的提示詞，那時你讀 `notes/b3.md` 與 `b3-docs/delivery-template.md`（交付摘要範本），把交付摘要寫進 `notes/delivery.md`。B3 這段只要確保 `notes/b3.md` 裡的 Gate 紀錄、驗收對照表與變更審查完整。

寫程式的人不核准自己的成果：交付時人會另開一個只讀的審查對話，依 `skills/team-rules.md` 的「審查準則」、本工作單第 4 節與第 7 節，用 `git diff` 對照「B3 起點」，把結論寫進 `notes/b3.md` 的「審查紀錄」。你不寫、也不修改「審查紀錄」。

## 11. 每次回報的最後一行

每次回報的最後一行只寫「自我檢查：成功」或「自我檢查：失敗：〈一句原因〉」。判斷前要實際列出檔案、打開 `notes/b3.md`，或執行 `git status`／`git log`，不憑記憶。成功的意思是這一步該有的檔案與紀錄都實際存在。
