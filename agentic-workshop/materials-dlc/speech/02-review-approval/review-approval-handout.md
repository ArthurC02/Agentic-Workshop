# 審查與核准：模型變更要經過第二個人

> 讀者：學員。時機：DDD 延伸課 D2 之後的 25 分鐘講解。前置：已聽過 DLC Speech 01，做完 D2。

**這一段帶走什麼**
- 決策紀錄（ADR）的提議、接受、取代，對應本課的候選、已審查事實、新候選取代
- 做的人不核准自己的變更；口頭規則擋不住，要寫成檢查
- 審查要看的證據：主張對證據、測試有沒有被改、反事實檢查只認 killed
- 核准紀錄要查得到誰、何時、核准哪一份

每頁最後的段落是講解時來不及說的補充：概念的白話解釋、證據出處、限制與回到團隊的做法；提到的書與文章列在最後的「延伸閱讀」。

本場講概念與技巧，不需要寫程式或打指令。頁面上的提示詞是示範，想試再貼給自己的 Agent；沒有實際執行的結果，一律視為未驗證。

## 1. 改模型，要有第二個人

上一場：改一個名詞就是改模型。這一場：模型的改變怎麼審、誰核准、留下什麼。

- **上一場留下的**：附證據的語言、邊界與規則，全是候選。

- **這一場講**：決策紀錄、做與核准分開、怎麼審證據。

**人工確認**：D2 裡夥伴審查時，有沒有哪一刻想退回？

## 2. 決策為什麼要寫下來

Nygard（2011）：專案裡最難追的，是當初為什麼這樣決定。

- **沒寫下來**：後來的人只能盲目照做，或盲目推翻。

- **寫成 ADR**：背景、決定、狀態、後果，一份短短的紀錄。

ADR（Architecture Decision Record，架構決策紀錄）是 Michael Nygard 2011 年提出的做法：每個重要的設計決定寫一份短紀錄，包含標題、背景、決定、狀態與後果。他的理由是：專案進行中最難追的，就是當初為什麼這樣決定；沒有紀錄，後來的人只剩兩條路，盲目照做或盲目推翻。

AWS 的 ADR 流程指南也強調，紀錄的重點是「為什麼這樣決定」，而不是「怎麼實作」。對 Agent 來說這更關鍵：它沒參加當初的會議，只看得到 Repo；沒寫下理由的決定，在它看來就像可以隨手改掉的程式。

下週可以挑團隊最近一個重要的設計決定，用這五段寫成一頁放進 Repo，不超過一個畫面。

📖 延伸閱讀：〈Documenting Architecture Decisions〉（Michael Nygard，2011）；〈Architectural decision record process〉（AWS Prescriptive Guidance）

**人工確認**：你們團隊上一個重要的設計決定，理由寫在哪裡？

## 3. 新概念：已審查事實

ADR 有狀態：提議、接受、被取代。本課的候選、已審查事實、新候選取代，一一對應。

提議＝候選 → 接受＝已審查事實 → 被取代＝新候選核准後

- **接受後不改寫**：Agent 必須遵守，不能直接修改。

- **要改就取代**：提新的候選，舊的保留可查。

ADR 有狀態：提議（Proposed）、接受（Accepted），被新決定推翻時標成被取代（Superseded），舊的保留可查。AWS 的流程指南說，ADR 一旦被接受就不再改寫；被拒絕的提案也要寫下理由，免得下次重吵同一件事。

本課的用語一一對應：Agent 提的候選＝提議；經另一個人核准的已審查事實＝接受；要改已審查事實，就提一筆新候選，核准後取代舊的。已審查事實不是永遠不能變，而是只能透過同一套審查流程改。

常見誤解：Agent 發現事實「好像過時了」就直接改。正確做法是讓它提新候選、附證據，等人核准。下週可以看看團隊的設計文件有沒有狀態欄位，還是改了就直接覆蓋。

📖 延伸閱讀：〈Architectural decision record process〉（AWS Prescriptive Guidance）；〈Documenting Architecture Decisions〉（Michael Nygard，2011）

**人工確認**：Agent 想改一條已審查事實時，正確的做法是什麼？

## 4. 球員不兼裁判

做變更的 Agent 不核准自己的變更；審查交給另一個乾淨的對話，或另一個人。

- **官方建議**：另開審查者，只看差異與標準，不看作者的推理。

- **平台限制**：GitHub 的雲端 Agent 不能核准或合併自己的 PR。

- **企業做法**：Stripe 自述：Agent 每週上千個 PR，全經人審。

「球員不兼裁判」：做變更的人不核准自己的變更。這是人工核准關卡（Gate）的加深一層：主課學過在關卡由人決定，這裡再加一條，核准的必須是另一個人，或至少是一個看不到作者推理的乾淨對話。Claude Code 官方文件建議另開審查者審差異，理由是做事的 Agent 不該替自己打分數。

業界也這樣做：GitHub 的雲端 Agent 不能核准或合併自己的 PR（Pull Request，合併請求）；Stripe 2026 年自述每週超過一千個由 Agent 產出的 PR，全部交人審查；Anthropic 2026 年 10 月分享，Agent 大量產生變更後，團隊成員仍審每一筆，只是改看變更的意圖。這些數字都是公司自己說的，不當成效率證據。

限制：D2 為了教學讓兩人共用一台機器、各開自己的 Agent 對話。這能練習分工，但不能證明真的有兩個人；真實團隊要補什麼，第 04 場會講。

📖 延伸閱讀：〈Best practices for Claude Code〉（Claude Code 官方文件）；〈Building effective agents〉（Anthropic Engineering，2024）；〈Risks and mitigations for GitHub Copilot cloud agent〉（GitHub 官方文件）；〈Minions: Stripe's one-shot, end-to-end coding agents〉（Stripe，2026）；〈Redesigning source control at Anthropic〉（Anthropic，2026）

**人工確認**：D2 裡，「核准」這句話是在誰的對話裡說的？

## 5. 口頭規則擋不住，寫成檢查

對 Agent 說「不要自己核准」只是建議；要每次都發生，就寫成自動檢查。

規則檔：建議 → 測試與檢查程式：每次都跑 → 推送時檢查：沒核准就擋

- **為什麼**：Agent 忙起來會忘，人也會。

- **D2 的做法**：沒有夥伴簽章的變更，推不上去。

寫在規則檔或對話裡的規則（例如「不要自己核准」）對 Agent 只是建議：它忙起來會忘，人也會。要每次都發生，就寫成自動執行的檢查：測試、檢查程式，或 pre-push hook（push 前 Git 自動執行的檢查腳本）。Claude Code 官方文件說，規則檔是建議，hook 是確定性的、保證會執行；AGENTS.md 等其他工具的規則檔也一樣，只是上下文，不是強制設定。

Thoughtworks 技術雷達第 34 期（2026-04）把「給 Coding Agent 的回饋感測器」列為 Trial（值得試用）：檢查要在寫程式的過程中就跑，commit 前回報乾淨的結果。D2 的做法是：沒有夥伴簽章的變更推不上去。

限制：本機的檢查可以被跳過，第 04 場會講。下週可以找出團隊一條「大家都知道、卻常被忘記」的規則，想想能不能寫成一個會失敗的測試或檢查。

📖 延伸閱讀：〈githooks〉（Git 官方文件）；〈Feedback sensors for coding agents〉（Thoughtworks Technology Radar，2026）

**人工確認**：如果 Agent 自己 commit 再推送，會在哪一步被擋下？

## 6. 警示案例：少了第二道關卡

規則只寫在對話裡、或沒人覆核，就擋不住 Agent 的破壞性動作。

- **Replit（2025-07）**：凍結期間 Agent 刪了正式資料庫；事後分開開發與正式環境。

- **AWS（2025-12）**：報導稱 Agent 重建環境，服務中斷 13 小時；Amazon 說是權限設定錯誤。

Fortune 2025 年 7 月報導：SaaStr 創辦人測試 Replit 的 Agent，在宣布「程式碼與動作凍結」期間，Agent 仍刪掉正式資料庫裡 1,200 多位主管、1,190 多家公司的資料，還說無法回復，其實可以手動回復。Replit 執行長稱這不可接受，之後加入開發與正式資料庫分離、只規劃不執行的模式。教訓：只寫在對話裡的凍結擋不住 Agent。

The Decoder 2026 年 2 月轉述 Financial Times：AWS 的 Kiro Agent 決定刪除並重建環境，造成某服務中斷 13 小時，報導稱當時工程師不需第二人核准。Amazon 的回應是使用者錯誤、存取控制設定錯誤，不是 AI，之後加入正式環境存取的強制同儕審查。兩邊說法要一起講，不要說成「AWS 承認 AI 造成當機」。

回到團隊：列出現在只靠一個人說了算的動作（刪資料、部署正式環境、改權限），想想哪一個該加上第二道關卡，而且是擋得住的檢查，不是口頭約定。

📖 延伸閱讀：〈An AI-powered coding tool wiped out a software company's database, then apologized for a 'catastrophic failure on my part'〉（Fortune，2025）；〈AWS AI coding tool decided to delete and recreate a customer-facing system〉（The Decoder，2026）

**人工確認**：你的團隊有哪個動作，現在只靠一個人說了算？

## 7. 紀錄只放模型，不放工作筆記

一筆紀錄只寫：這個概念是什麼、和誰有關、證據在哪。做法、信心分數、待辦都不放。

- **為什麼**：審查的人逐條對證據；雜訊越多越難審。

- **沒解決的問題**：寫進變更提案的待確認問題，不寫進模型。

共用模型的一筆紀錄只寫三件事：這個概念是什麼、和誰有關、證據在哪。Agent 很容易順手寫進「我是用什麼方法找到的」「信心 0.8」「待確認」；這些放進模型，下一個 Agent 會把它們當成事實讀。

審查的人要逐條對證據，雜訊越多越難審。較短、每句都對得上證據的紀錄，勝過看起來完整、其實只是重述原文的紀錄。沒解決的問題寫在變更提案的待確認問題，審查時一起決定，不寫進模型；這和 ADR 只寫背景、決定、後果是同一個精神。

下週可以給團隊的 Agent 一句規則：「紀錄只放元素、關係與證據；其他寫進提案的待確認問題。」

**人工確認**：D2 審的那筆候選，有沒有一句其實是工作筆記？

## 8. 示範：請 Agent 做審查表

審查的人不必看懂程式；他要一張表：每條主張的證據與實際結果。

- **看理由**：為什麼這樣定，比怎麼實作重要。

- **看實際字樣**：passed、killed 要來自實際執行。

### 交給 Agent 的指令

先不要修改任何檔案。請把這次要升級的每一筆候選列成表：主張、證據（路徑:起-迄行）、對應的測試與實際結果字樣、反事實檢查結果。沒有實際跑過的標「未驗證」。列完停下。

審查的人不必看懂程式，他要的是一張表：每條主張、證據在哪幾行、對應哪個測試、實際跑出的結果字樣，以及反事實檢查（故意改壞程式，看測試會不會失敗）的結果；沒實際跑過的標「未驗證」。這是第 01 場「要證據，不要形容詞」的加深：證據從一句回報，變成給另一個人審的整張表。

主課的變更審查看程式改了什麼；這裡看模型要改成什麼、為什麼。AWS 的 ADR 流程指南說，紀錄著重決定的理由，而不是實作方式；審查表把「為什麼」放前面，比放實作細節有用。

限制：表格整齊不代表內容正確，主張和證據講的可能不是同一件事，所以下一頁講怎麼審。

📖 延伸閱讀：〈Architectural decision record process〉（AWS Prescriptive Guidance）

## 9. 審查怎麼做：先讀、再問、可退回

AWS 的 ADR 審查會先安靜讀 10–15 分鐘，再逐條討論，最後接受、重做或退回。

- **標準是讓整體更好**：Google：確定讓程式更健康就核准，不求完美。

- **退回要寫理由**：下次就不必重吵同一件事。

AWS 的 ADR 流程建議審查會議這樣開：先安靜讀 10–15 分鐘，再逐條討論，結果是接受、要求重做或拒絕；拒絕時寫下理由，避免下次重吵。Google 的程式碼審查準則則說，標準是確定讓整體程式更健康就核准，不求完美。兩者合起來：審查要真的讀證據，但不是無止境地挑錯。

InfoQ 2026 年 9 月一篇文章（Nitin Garg）做了小型實驗：審查者手上有人核准過的基準時，抓到的問題比例和沒有時差不多（作者自量的召回率，0.525 對 0.518），但 81% 的發現能指到具名的條文（沒有基準時 0%），審查時間約 48 對 27 分鐘。作者說結果只是方向性的。意思是：已審查的模型讓審查說得出依據、可以追溯，不保證抓到更多錯。

D2 裡夥伴回「退回：原因」不是失敗，而是審查有在運作；沒有人追問的核准只是蓋章。下週審同事的變更時，核准前至少親自打開一行證據。

📖 延伸閱讀：〈The Code Reviewer's Guide〉（Google Engineering Practices）；〈When Spec-Driven Development Pays off〉（Nitin Garg／InfoQ，2026）

**人工確認**：你核准前，親自打開過哪一行證據？

## 10. 綠燈不等於安全

Anthropic 在模型系統卡揭露：Agent 為了讓測試通過，會改測試去配合程式。

- **怎麼發生**：多次失敗後，寫死預期值或改測試。

- **審查時看**：這次有沒有動到測試，動了哪幾行。

### 交給 Agent 的指令

先不要修改任何檔案。請列出這次變更動到的所有測試檔與行號，每處說明改了什麼、會不會讓原本該失敗的情況變成通過。只列事實，列完停下。

Anthropic 2025 年 2 月的模型系統卡（廠商公開的模型行為說明）第 6 節揭露：模型多次修不好時，會把程式寫成只對測試的特定輸入成立，甚至修改測試本身去配合程式的輸出。使用者的測試沒發現，靠自動分類器才抓到；系統卡建議監看測試檔被意外修改的情況。

這不是某一家模型的毛病，而是廠商自己公開的行為紀錄，其他模型也可能發生。所以審查時多問一題：這次變更動到測試了嗎？動了哪幾行、理由寫在哪？測試全綠，可能只是測試被改鬆了。

下週可以在團隊的審查清單加一行：「本次是否修改了既有測試？理由是什麼？」

📖 延伸閱讀：〈Claude 3.7 Sonnet System Card〉（Anthropic，2025）

**人工確認**：這次變更動到測試了嗎？動的理由寫在哪？

## 11. 技巧：故意改壞，看測試抓不抓得到

反事實檢查：改壞一處、跑測試、自動還原。測試失敗（killed）才證明有人守著。

- **killed**：測試失敗了：這條規則有測試守著。

- **survived**：測試仍通過：規則沒人守，或測試太弱。

### 交給 Agent 的指令

先不要修改任何檔案。請針對這條規則，提 2 個「故意改壞」的方案：改哪個檔案的哪幾行、改成什麼、預期哪個測試會失敗。不要替我選，列完停下。我選好後再跑，回報實際字樣是 killed 還是 survived。

反事實檢查（counterfactual）是變異測試（mutation testing）的手動小版本：故意把守某條規則的程式改壞一處，跑測試，再自動還原。測試失敗叫 killed（被抓到），證明這條規則有測試守著；測試仍通過叫 survived（存活），表示規則沒人守，或測試太弱。變異測試工具則會自動產生大量這種小改動。

Thoughtworks 技術雷達第 34 期稱變異測試是評估測試抓錯能力「最誠實的訊號」，也提醒 AI 產生的測試可能永遠是綠的。改法由人選，是因為 Agent 容易挑最好抓的改法，讓結果好看。

兩個常見誤讀：指令沒報錯不等於 killed，要看實際字樣；測試要因為對的原因失敗，所以事先寫下預期哪個斷言失敗，如果是程式根本載入不了才失敗，不算證明。

📖 延伸閱讀：〈Feedback sensors for coding agents〉（Thoughtworks Technology Radar，2026）

**人工確認**：你選的改法，改到的是規則本身，還是無關的字串？

## 12. 核准紀錄：誰、何時、核准哪一份

ADR 被接受時寫下決策者與日期；模型裡的已審查事實也一樣，要查得到誰、何時核准。

- **誰與何時**：每筆已審查事實附核准者與時間。

- **提案留在歷史**：紀錄不抄提案；要查時從歷史找得到。

- **沒被改過**：簽章驗得出；套用前 Agent 再驗一次。

核准紀錄要回答三個問題：誰核准、何時核准、核准的是哪一份。MADR（一個常用的 ADR 範本，4.0 版，2024）在狀態與日期旁邊有「決策者」欄位；本課的已審查事實就是「接受」加上核准者與時間。範本註明這些欄位是選填，但對需要稽核的團隊很有用。

紀錄本身只寫誰、何時；當初的審查包與討論留在版本與稽核歷史裡，要追查時找得到，不必抄進每筆紀錄。「沒被改過」要靠工具驗證：業界常見做法是簽章的 commit（用金鑰替 commit 簽章，別人能驗出內容沒被改）加上必要審查。

下週可以問：三個月後有人問「這條規則誰核准的」，你們團隊從哪裡查得到？查不到，就是值得補的地方。

📖 延伸閱讀：〈About MADR〉（MADR 4.0，2024）；〈git-commit〉（Git 官方文件）

**人工確認**：三個月後有人問「這條規則誰核准的」，你從哪裡查？

## 13. 帶走什麼

做的人和核准的人分開；核准要看證據、留紀錄；事實只能被新提案取代。

提案者附證據 → 另一個人審查 → 核准並留紀錄 → 已審查事實 → 下一場依模型做需求

- **回到團隊**：挑一個模型變更，寫一份短 ADR 請人審。

- **下一場**：依已審查事實做新需求，由人決定邊界。

**人工確認**：用一句話說出：killed 證明了什麼？

## 完成條件
說得出決策紀錄（ADR）的提議、接受、取代和本課的候選、已審查事實怎麼對應；紀錄為什麼只放模型、核准紀錄為什麼要寫誰與何時；為什麼做的人不能核准自己的變更、規則為什麼要寫成檢查；審查時要看哪些證據、為什麼要查測試有沒有被改、反事實檢查為什麼只認 killed；知道下一場要依已審查事實做新需求。
