# 依模型做新需求：邊界、不變量與交接單

> 讀者：學員。時機：DDD 延伸課 D3a–D3c 之後的 40 分鐘講解。前置：已聽過 DLC Speech 01、02，做完 D3 三段。

本場講概念與技巧，不需要寫程式或打指令。頁面上的提示詞是示範，想試再貼給自己的 Agent；沒有實際執行的結果，一律視為未驗證。本場不公布三張需求卡的參考設計。

## 1. 三個新需求，同一套做法

電子發票、點數折抵、團體部分退款：每段都由人決定邊界，Agent 照交接單做。

- **D3a**：串接會失敗的外部服務。

- **D3b**：同一條規則接到每一條程式路徑。

- **D3c**：幾份資料必須一起改。

**人工確認**：三段裡，哪一個決定你們吵最久？最後是靠什麼定案的？

## 2. 每一段都走同一個迴圈

D3 三段的檢查點一模一樣，差在每段多學一個領域概念。

讀需求卡與事實 → 人做邊界決策 → 交接單與實作 → 反事實檢查 → 審查並寫回 → 停手對照

- **人做的**：選邊界、定不變量、放行每一段、審查越界。

- **Agent 做的**：提選項與證據、寫程式、跑測試、整理紀錄。

**人工確認**：迴圈裡哪一步，你是真的做了決定，而不只是回「同意」？

## 3. 需求卡是唯一依據

卡片沒規定的事由你們決定；不讓 Agent 自己補值。

- **卡片有寫**：照做：路徑、欄位與錯誤碼不要自己發明。

- **卡片沒寫**：寫進交接單的 Unknowns（未知事項）：停下來問或本段不處理。

**人工確認**：Agent 有沒有自己補了一個卡片沒寫的數字或狀態？

## 4. Agent 提選項，人來選

每個待決問題，Agent 依已審查事實提兩個選項，附證據與取捨。

- **證據來自事實**：引用已審查事實，不是 Agent 的偏好。

- **回覆很短**：「1A、2B、3A」；想混合就直接說。

### 交給 Agent 的指令

先不要修改任何程式。請依需求卡「待團隊決定的問題」，每題提 2 個選項（標成 1A、1B…），每個選項寫一句取捨，附證據：模型裡的「類別:id」或程式的「檔案路徑:行號」。不要替我們選，列完停下。

**人工確認**：你們選的選項，取捨那一句說服了你，還是你們有自己的理由？

## 5. 負責的 Context：只有一個

這個需求的資料與規則，只由一個 Context 負責。

- **為什麼只有一個**：兩個都管，規則改時會只改到一邊。

- **怎麼選**：看規則在決定什麼，不看程式現在放在哪。

**人工確認**：你們選的負責者，說得出「它決定什麼」嗎？

## 6. Port／Adapter：擋住外部說法

Port 是領域程式需要的對外能力，用自己的業務用語描述；Adapter 負責翻成服務商的格式。要不要定義 Port、由誰翻譯，是需求卡留給你們決定的問題。

領域程式 → Port（自己的用語） → Adapter（翻譯） → 外部服務商

- **防腐層**：服務商的欄位與錯誤碼，不滲進領域程式。

- **好處**：換服務商、用假服務測試，都只動 Adapter。

**人工確認**：領域程式裡，有沒有出現服務商的欄位名稱？

## 7. 冪等：重送不會多開一張

Idempotency（冪等）：同一個請求重送多次，結果和送一次相同。

- **為什麼需要**：外部服務會逾時；你不知道它到底收到沒。

- **人要確認**：重送時有沒有可能開出兩張發票。

**人工確認**：逾時之後重送，你怎麼知道服務商沒有收到兩次？

## 8. 不變量：每次都要成立的規則

Invariant（不變量）：每次操作結束都必須成立的業務規則。

- **寫得好**：說得出「怎樣算失敗」，就能寫成測試。

- **寫不好**：「發票要正確」：沒辦法判斷失敗。

**人工確認**：挑一條你們寫的不變量：怎樣算它被破壞了？

## 9. 每條新規則，各改壞一次

反事實檢查加深一層：改的是 Agent 剛寫的程式，每條新規則都要 killed。

- **killed**：這條規則有測試守著。

- **survived**：沒人守：補測試，不能改用較好抓的改法。

**人工確認**：有沒有一條規則第一次是 survived？後來怎麼補的？

## 10. 不變量要守住每一條路徑

不論從哪一條程式路徑呼叫、多筆訂票同時送出，不變量都要成立。

- **漏一條**：就有一種訂票不受規則限制。

- **同時送出**：兩個請求一起來，規則也不能被繞過。

### 交給 Agent 的指令

先不要修改任何程式。請列出所有會計算訂票總額的程式路徑，每條附檔案路徑:行號，並說明它從哪個 API 或操作被呼叫。不要只找名稱像的函式，列完停下。

**人工確認**：Agent 列的路徑，你們有沒有對照 API 清單確認一條不漏？

## 11. 預留與歸還

先扣下（預留），付款成功才確定；團體付款失敗或退票時全數歸還（一般訂票付款失敗仍保留，見需求卡）。

預留 → 付款成功：確定 → 團體付款失敗或退票：歸還

- **不能重複扣**：兩個請求同時扣，合計不得超過餘額。

- **不能重複或漏退**：該歸還的一定歸還，重複歸還也只算一次。

**人工確認**：付款失敗後再重試一次，點數會不會被扣兩次？

## 12. Aggregate：要一起一致的資料

Aggregate（聚合）是必須一起保持一致的一組資料，外界只能從一個入口修改。

- **唯一入口**：入口先檢查全部條件，再一次寫入。

- **全有或全無**：邊界內一起改；邊界外可以事後同步。

**人工確認**：需求卡範例裡，條件不成立的那一步，真的沒有留下任何變更嗎？

## 13. 事先寫明哪些測試可改

新規則可能讓舊測試的期待改變；哪幾個可以改寫、為什麼，先寫進交接單。

- **允許改寫**：列出測試名稱與理由，Agent 只能改那幾個。

- **其他測試**：要改就先停下說明，不能刪除、放寬或跳過。

**人工確認**：Agent 改寫的測試，都在交接單的允許清單裡嗎？

## 14. 交接單：工作單再加兩段

主課的工作單（Work Order）再加兩段：用到的已審查事實，和還沒決定的事。

- **Agent 只照它做**：交接單沒寫的，停下來問。

- **分兩段放行**：每段看測試結果，再回「繼續」。

```text
Domain facts      用到的已審查事實、只是候選的、查不到的
Owner Context     負責者與理由
不變量            每條都能寫成會失敗的測試
邊界與協作        介面與實作各在哪一層、禁止的相依
Unknowns          卡片沒規定的事：停下來問
Proof obligations 每條規則對應的測試
```

**人工確認**：交接單裡，有沒有一個決定其實是 Agent 寫的、你們沒討論過？

## 15. 審查越界，新知識先當候選

Agent 回答固定的審查問題；新學到的規則寫回模型，但只算候選。

- **審查的重點**：有沒有違反交接單的邊界：只能靠人抓。

- **寫回模型**：每筆附證據，不能寫成已審查事實。

- **commit 給夥伴**：提案者的 Agent 不 commit、不 push。

**人工確認**：寫回的候選裡，有沒有一筆被寫成了已審查事實？

## 16. 停手對照：差異是取捨嗎

停止擴充，把你們的決定整理成幾行，和參考設計對照；參考設計不是唯一正解。

- **有理由的取捨**：說得出為什麼和參考設計不同。

- **漏看**：需求卡有寫，你們沒注意到。

- **Agent 補的**：沒人決定，Agent 自己填了。

**人工確認**：你們的差異裡，有沒有一個是第三種：Agent 補的？

## 17. D3 帶走什麼

人選邊界與不變量，交接單把決定交給 Agent，反事實檢查證明規則有人守。

需求卡 → 人選邊界 → 交接單 → Agent 實作 → 每條 killed → 新候選 → D4 交接

- **今天帶走**：負責的 Context、Port／Adapter、冪等、不變量、預留與歸還、Aggregate。

- **下一場**：模型落後程式時怎麼辦，以及怎麼交給下一個 Agent。

**人工確認**：回到開場：吵最久的那個決定，最後寫進交接單的哪一段？

## 完成條件
說得出 D3 每一段同一個迴圈裡人要判斷什麼；能說明負責的 Context、Port／Adapter、冪等、不變量、預留與歸還、Aggregate 各解決什麼問題；知道交接單比工作單多了哪兩段，以及新知識為什麼先寫成候選。
