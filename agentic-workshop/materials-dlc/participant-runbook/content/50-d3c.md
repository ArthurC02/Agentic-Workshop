## 檢查點 2 · Aggregate（聚合）邊界與不變量（第 128–133 分鐘）

這一步先請 Agent 列出資料現況：訂票狀態、旅客、座位、退款各存在哪裡、被哪些程式直接修改。如果部分取消可以從好幾個地方改到座位或退款，「全有或全無」就很難保證，這正是要畫一致性邊界的原因。

```callout info
新概念：Aggregate（聚合）與一致性邊界
Aggregate 是必須**一起**保持一致的一組資料；外界只能從一個入口物件（Aggregate root）修改它，入口先檢查全部條件、再一次寫入。一致性邊界就是「每次操作結束時，不變量都必須成立」的那一組資料：邊界內全有或全無，邊界外可以事後再同步。D3a、D3b 你學過不變量；這次要決定哪些不變量放進同一個邊界、由哪個入口守住。
📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 6 章〈The Life Cycle of a Domain Object〉的 Aggregates 一節；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 10 章〈Aggregates〉；學員包 `vendor/domain-memory/references/tactical-reasoning.md`。
```

## 檢查點 4 · 反事實檢查（第 142–148 分鐘）

本段的驗收標準是：你們登記的**每一條**新規則，都有一次 `killed`。先讓 Agent 列出要改壞哪裡，你們同意後才跑。

```text
不要修改任何程式。請針對交接單中「每一條」新規則，各列出：守住它的程式檔、該檔中只出現一次的一段原字串、把它改壞的替換字串、預期會失敗的測試檔。寫進 notes/d3c.md（標題「D3c 反事實檢查」），停下等我們回「同意」。

我們同意後，每條規則執行一次，存檔名依序 cf-d3c-1.json、cf-d3c-2.json…。指令如下，FILE、FIND、REPLACE、TEST 換成你列出的值，其餘照抄：
..\..\tools\dm.ps1 counterfactual --file FILE --find "FIND" --replace "REPLACE" --test-command '.venv\Scripts\python.exe -m pytest -q -W ignore::DeprecationWarning TEST' --save cf-d3c-1.json
--test-command 引號裡的指令由 Windows 的 cmd.exe 執行，所以即使你用 Git Bash，這裡也要照抄 .venv\Scripts\python.exe（反斜線）。
-W ignore::DeprecationWarning 關掉套件的過時警告：failing_evidence 只留輸出的最後一段，警告會把真正的失敗訊息擠出去。指令結束碼不是 0 而要重跑時，先刪掉那次留下的 cf 檔再重跑，不要讓沒有結果的 cf 檔被 commit。
每條跑完用白話回報：verdict 是 killed 還是 survived；failing_evidence 是不是測試本身失敗（AssertionError，或被測程式自己丟出的例外，例如 ConnectionError），而不是 ImportError、語法錯誤或收集測試時的錯誤（collection error）；restored 是不是 true。只有亂碼或 ERROR 都不算 killed，先說明原因。
survived 時不要換一個比較容易 killed 的字串：提出要補的測試，停下等我們同意，補完用同一組字串重跑。如果你判斷沒有任何測試分辨得出改壞前後（另一段程式也擋住同一件事，這叫等價），不要硬補測試：指出那一段程式（檔案路徑:行號），停下等我們確認，記為「等價、未證明」。survived 的規則不能當成已受保護，來不及補的在紀錄中標「未證明」。全部跑完再執行一次完整的 pytest -q，並回報：每一條新規則是不是都有 killed。結果寫進 notes/d3c.md。
```
