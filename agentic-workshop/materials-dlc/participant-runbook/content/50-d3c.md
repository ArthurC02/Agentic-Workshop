## 檢查點 2 · Aggregate（聚合）邊界與不變量（第 128–133 分鐘）

① 為什麼做這一步

部分取消如果能從好幾個地方改座位或退款，就很難保證「全有或全無」，所以先請 Agent 列出資料現況。Aggregate 不是資料表：它守住一條橫跨多份資料、必須同時成立的規則。需求改變既有行為時，交接單要先列出允許改寫的既有測試：原斷言、新斷言、對應的 PCR 編號；你們同意的才准改：

- [ ] Agent 列出選項後，先聊 ④ 的討論題，再回一句選擇，例如「1A、2B、3A」；想混合就直接說
- [ ] 每個允許改寫的測試都有對應的 PCR 理由，才回「同意」；否則回「第 2 個測試不准改」

② 貼給 Agent

```text
先不要改程式。先列出目前訂票狀態、旅客、座位、退款紀錄各存在哪裡、由哪些程式直接修改（附檔案路徑:行號），哪些地方有多份互相獨立的「座位真相」；再列出既有測試中，哪些會因為「一筆訂票可以有多筆退款」而必須改寫。
然後照 ../../worksheets/d3-decision-card.md 的步驟，替需求卡 03「待團隊決定的問題」1–3 提選項給我們選；提 Aggregate 選項時，寫出它守住哪一條必須同時成立的規則、橫跨哪些資料，只說「把這些類別包在一起」不算。我們回覆選擇後，照決策卡寫交接單 docs/handoffs/d3c-group-partial-refund.md，列出不變量和允許改寫的既有測試，等我們回「同意」。做完用 check 檢查。
```

③ 確認結果

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text

```

失敗時：

```text
先停，不要改程式。交接單缺了哪一段或哪一項理由？列出你要補的內容，等我們回「同意」再改交接單。
```

④ 補充

```callout tip
💬 討論一下
- 如果部分取消可以從兩個地方改到座位，中途失敗時會留下什麼樣的資料？
- Agent 列出的既有測試裡，哪些真的因為需求卡改變而必須改寫？理由能對應到哪一條 PCR？
```

```callout info
新概念：Aggregate（聚合）與一致性邊界
**Aggregate 是一個一致性邊界：裡面的資料必須在同一次操作裡一起保持一致。**
- 外界只能透過邊界裡唯一的入口物件（Aggregate root，聚合根）修改它；Aggregate 是整個邊界，root 是入口。
- 入口先檢查全部條件，再一次寫入。
- 邊界內全有或全無；邊界外可以事後再同步。
- 它不是一張資料表，也不是「有子物件的類別」：說不出它守住哪一條規則，就不是 Aggregate。

📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 6 章〈The Life Cycle of a Domain Object〉的 Aggregates 一節；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 10 章〈Aggregates〉、〈Effective Aggregate Design, Part I〉（2011）。
```
