# D2：審查與核准（成對）

```callout info
現在在做什麼
- **情境**：D1 的共同語言與邊界還是候選，Agent 只能參考，不能當成必須遵守的規則。
- **你的目標**：由提案者以外的人審查證據並核准，讓模型成為 Agent 必須遵守的已審查事實。
- **今天的技巧**：做的人和核准的人分開：提案者的 Agent 只準備證據；夥伴在**自己的 Agent 對話**看過證據、回「核准」才算數。
- **完成的樣子**：夥伴的核准已記錄並推送；Agent 回報模型全部是已審查事實、紀錄沒有被竄改。
```

兩人一組，**共用一台機器**，但**各自用自己的 Agent 對話**。
- 用 D1 做得比較完整的那台，D3 也延續這台。機器的主人當**提案者**，另一人當**夥伴**（Maintainer，持鑰人）。
- 每段提示詞開頭都寫明給誰：輪到誰，誰就坐到鍵盤前，貼到自己的對話。
- 三人一組時，第三人當觀察員：看核准、簽章與 push 是否只出現在夥伴的對話。
- 金鑰、規則與簽章的指令都在提示詞裡，由夥伴的 Agent 執行；你們只做決定、看 ③。

## 開始前：兩個 Agent 對話（第 35 分鐘）

- **提案者**沿用 D1 的 Agent 對話，貼下方第一行。
- **夥伴**另開一個終端機視窗，切到同一個 Repo 根目錄，啟動**新的** Agent 對話，貼下方第二行。
- 兩個角色各能做什麼，已寫在 `AGENTS.md`「兩個角色」，Agent 會自己讀；夥伴的 Agent 答不出來，就說「請先讀 AGENTS.md」。

```text
【貼到提案者自己的 Agent 對話】接下來是 D2 審查與核准，我是提案者 proposer@example.com。
```

```text
【貼到夥伴自己的 Agent 對話】接下來是 D2 審查與核准，我是夥伴 maintainer@example.com（持鑰人）。先引用 AGENTS.md「兩個角色」告訴我：你在這個對話不能做什麼，哪些事要等我回「核准」才能做。
```

## 檢查點 1 · 夥伴取得核准權（第 35–38 分鐘）

① 為什麼做這一步

**夥伴操作。** 只有提案者以外的人核准，模型才算團隊認可的事實。夥伴的 Agent 先替夥伴建立一把核准印章（簽章金鑰），放在 Repo 外，只有夥伴能用。

② 貼給 Agent

```text
【夥伴的 Agent】檢查點 1：替我建立簽章金鑰。先確認 domain-memory/ 還沒被 commit 過（已經 commit 就停下告訴我）。再執行這一行，~ 照 AGENTS.md「Git 與金鑰」換成這個終端機的使用者資料夾寫法，其餘參數照寫：
dm init-signing-key --principal maintainer@example.com --key-file ~/.dlc-keys/maintainer/signing-key --sign-every-commit --save ~/.dlc-keys/maintainer/signing.json
讀 signing.json，用白話告訴我 source、principal、fingerprint（前 12 碼）、signs_every_commit，以及私鑰在哪個資料夾。做完用 check 檢查。
```

③ 確認結果（貼到夥伴的對話）

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：私鑰在 Repo 外的 .dlc-keys/maintainer/，domain-memory/ 仍未 commit。
```

失敗時：

```text
先停，不要自己改設定，也不要打開私鑰檔。錯誤訊息是什麼意思？是金鑰路徑，還是 domain-memory/ 已被 commit？你建議怎麼做？
```

④ 補充

```callout info
技巧・加深一層：人工核准關卡
**主課 B3 的 Gate 由你決定 Agent 能不能往下；今天再加一條：提案的人不能核准自己的提案。**
- 提案者的 Agent 只準備證據；核准只在夥伴自己的 Agent 對話發生。
- 核准用夥伴的簽章留下紀錄，事後查得到是誰核准的。

📖 延伸閱讀：Anthropic Engineering〈Building effective agents〉；Google Engineering Practices〈The Code Reviewer's Guide〉；Git 官方文件〈git-commit〉的 -S 選項說明。
```

```callout danger
私鑰不可外流
`signing-key`（沒有副檔名的那個檔案）不可進 Repo、不可貼給任何 Agent、表單或聊天，也不要截圖。回顧最後會刪除它。
```

**夥伴操作。** 把「只有夥伴的核准才算數、推送時自動檢查」寫成這個 Repo 的規則，之後照常推送時連 Agent 也繞不過（這道檢查的限制在回顧說明）。設定順序已寫在提示詞裡，不能調換；你只看結果是不是 `"status": "ready"`。

② 貼給 Agent

提案者趁夥伴操作時，先到本頁檢查點 3 按下載按鈕，把 `participant-dlc-d2.zip` 存到「下載」資料夾，省下檢查點 3 的時間。

```text
dm amend-policy --field review_trigger --value git-push --reason "push 時檢查簽章"

告訴我三次政策的舊值 → 新值、hook 裝在哪裡、governance-readiness 的 status。不是 ready 就照 blocks 說明缺什麼，不要自己改設定。做完用 check 檢查。
```

② 貼給 Agent

```text
【提案者的 Agent】檢查點 3：要把 D1 的全部候選送給夥伴審查，先準備反事實檢查，還不要改任何檔案。
```

④ 補充

```callout info
技巧：反事實檢查——先選改壞方案，只認 killed
**故意改壞一處程式、跑指定測試，再自動還原。**
- 測試失敗顯示 `killed`：有測試守著；仍通過顯示 `survived`：沒人守。
- 改壞哪裡由 Agent 提方案、你來選，也先寫下該看到哪個斷言失敗（`--expect`）。
- 失敗了卻不是那個斷言，顯示 `inconclusive`：可能是別的錯讓測試失敗，不算證明。
- 只認 `killed`，不認「指令沒報錯」。

📖 延伸閱讀：Claude Code 官方文件〈Best practices for Claude Code〉（先規劃、再用測試驗證）；你所用工具的官方文件通常有同名章節。
```

## 檢查點 4 · 夥伴審查證據並決定核准（第 48–53 分鐘）

① 為什麼做這一步

**夥伴操作。** 先審查，再核准；你可以退回。
- 讀 Agent 貼出的證據原文與測試結果，追問到你說得出「為什麼這條可以算事實」，再回「核准」
- 打開 Agent 指出的那份規則紀錄，親眼讀你要核准的那段文字與它的關係
- 要退回就回「退回：原因」，請 Agent 把理由寫進 `notes/d2.md`；接著貼紅色便利貼，主持人會走過去

② 貼給 Agent

先貼這段審查：

```text
【夥伴的 Agent】檢查點 4：審查提案者送出的 CP-D2-001，只讀，先不要核准。只讀小檔：domain-memory/changes/CP-D2-001/ 的 test-obligations.json、evidence-bundle.json，和 Repo 根目錄的 cf-d2.json、cp-d2.json；domain-change-proposal.json 很大、又重複整份模型，不要讀。
告訴我：要升為 reviewed 的候選（各類別幾個）與開放問題；每個 obligation 跑了哪個測試、結果是什麼；反事實檢查改壞了哪裡、哪個斷言失敗、是不是事先寫的 --expect、程式有沒有還原。
再挑一條規則用 dm get-record --asset rules --id 那條規則的id 取出，貼出它引用的證據原文、說它是否真的佐證這條規則，並告訴我它存在 domain-memory/ 的哪個檔案，我自己打開讀。
最後列出證據不足或可疑的地方（沒有就說沒有），停下等我回「核准」或「退回：原因」。
```

Agent 讀審查包時，夥伴先讀下方 ④ 的「已審查事實」小卡，想好要追問哪一條規則。決定核准，再貼這段：

```text
核准。我看過審查包與證據，把我的決定和你的審查摘要寫進 notes/d2.md，再執行：
dm record-approval --package-root domain-memory/changes/CP-D2-001 --role domain-owner --reviewer maintainer@example.com --scope "D1 候選升為 reviewed"
dm verify-proposal --package-root domain-memory/changes/CP-D2-001
verify-proposal 沒有回 Proposal test evidence verified. 就停下、不 commit，貼出訊息。接著照 signed-commit 做 commit「D2：核准 CP-D2-001」（D1 的 d1-records.json 會一起 commit，這是預期的）。做完用 check 檢查。
```

Agent 列出要 commit 的檔案後，看過再回「同意」。

③ 確認結果（貼到夥伴的對話）

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：最新 commit 有 Good "git" signature for maintainer@example.com，notes/d2.md 記著我的核准。
```

失敗時：

```text
先停，不要自己改設定、不要重做 commit、不要繞過 hook。錯誤訊息是什麼意思？是金鑰、政策，還是 HEAD 指向別的 commit？你建議怎麼做？
```

④ 補充

```callout info
新概念：已審查事實（reviewed）
**經夥伴核准的模型，是 Agent 之後必須遵守的限制。**
- 候選只能參考；已審查事實要遵守，但 Agent 不能直接改寫。
```

## 檢查點 5 · 留下可驗證的核准紀錄（第 53–56 分鐘）

**夥伴操作。** 核准不能只是一句話：Agent 驗證剛才的簽章 commit 出自政策授權的那把金鑰，這個 commit 就是可驗證的核准紀錄，檢查點 6 會把它寫進提案。這一步沒有新的決定，③ 回「成功」就往下。

② 貼給 Agent

```text
【夥伴的 Agent】檢查點 5：證明剛才的簽章 commit 是可驗證的核准紀錄。先確認最新 commit 是「D2：核准 CP-D2-001」，再執行 dm verify-git-governance --commit HEAD，告訴我結果。做完用 check 檢查。
```

③ 確認結果（貼到夥伴的對話）

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：結果是 Git governance is valid for 1 commit.。
```


## 檢查點 6 · 套用核准，模型成為事實（第 56–60 分鐘）

① 為什麼做這一步

**先由提案者**套用核准：Agent 用一個指令確認夥伴的簽章 commit、寫成核准證明、定案並套用（status 變成 `applied`）；**再由夥伴**提交並推送。套用後，D1 的候選才成為 Agent 必須遵守的事實，每筆多出 `verified`：誰、在何時核准；規則另外用 `proven_by` 列出證明它的測試。Agent 也確認紀錄沒有被竄改。

② 貼給 Agent

先貼到提案者的對話：

```text
【提案者的 Agent】檢查點 6：夥伴已核准並簽章提交，套用核准並全部驗證，參數照寫：
dm ship-package --package-root domain-memory/changes/CP-D2-001 --commit HEAD
dm validate --require-reviewed
dm verify-audit
告訴我 ship-package 的 completed（應有三步）與 status，有 errors 就說明是哪一步拒絕、停下；verify-audit 的 status 與事件數。再用 dm get-record --asset rules --id 任一條規則的id --changes-root domain-memory/changes 取出一條，告訴我 verified 的 by 與 at，以及 proven_by 列的測試。
```

提案者的 Agent 回報 ship-package 的 status 是 `applied`、每個指令都成功後，換夥伴貼到自己的對話：

```text
【夥伴的 Agent】檢查點 6 第二步：照 signed-commit 做 commit「D2：套用 CP-D2-001」。commit 後先跑 setup_remote.py 建立本機的遠端儲存庫（模擬伺服器），再照 signed-commit push。告訴我 hook 印出的 Git governance is valid for N commits. 裡 N 是多少、push 有沒有出現 [new branch]；結果補進 notes/d2.md 就好，不用再 commit。做完用 check 檢查。
```

③ 確認結果（貼到夥伴的對話）

Agent 最後一行已回「成功」就不用再貼；回「失敗」就貼下方「失敗時」。沒看到成功或失敗時才貼：

```text
用 check 檢查剛才這一段：validate --require-reviewed 是 Registry is valid.，verify-audit 的 status 是 valid，沒有尚未 push 的 commit。
```

失敗時：

```text
先停，不要自己改設定、不要重做 commit、不要用 --no-verify 或任何方式繞過 hook。錯誤訊息是什麼意思？是 venv、政策，還是 HEAD 指向別的 commit？你建議怎麼做？
```

④ 補充

```callout info
新概念・加深一層：已審查事實記著誰核准、靠哪個測試證明
**每筆已審查事實帶 `verified`（核准者與時間），規則另外對到證明它的測試（`proven_by`）。**
- 就像 ADR 的狀態寫「已接受」並列出決策者；核准它的提案記在稽核紀錄（`verify-audit` 檢查的那份）。
- 核准只說明有人同意；測試被刪、被放寬，或程式改了卻沒重跑，這條規則就只剩「有人核准過」。D4 會再跑一次這些測試。

📖 延伸閱讀：Michael Nygard〈Documenting Architecture Decisions〉（2011）；Simon Willison〈Your job is to deliver code you have proven to work〉（2025）。
```

## 完成後想一想

先自己想 30 秒，再兩人一起聊兩分鐘：

1. 夥伴審查時，哪一行證據或哪個測試結果讓你停下來追問？如果沒有人追問，怎麼確定這次核准不只是蓋章？
