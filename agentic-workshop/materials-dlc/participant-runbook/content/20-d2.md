# D2：審查與核准（成對）

```callout info
現在在做什麼
- **情境**：D1 的詞彙、Context 與規則都還是候選，Agent 只能參考，不能當成事實。
- **你的目標**：候選經「不是提案者本人」審查並簽章核准，成為已審查（reviewed）事實。
- **今天的技巧**：提案者的 Agent 只準備證據；夥伴在**自己的 Agent 對話**看過證據、回「核准」才簽章。
- **完成的樣子**：`validate --require-reviewed` 通過、`verify-audit` 是 `valid`、push 印出 `Git governance is valid.`。
```

兩人一組，**共用一台機器**（選 D1 做得比較完整的那台，它的主人當**提案者**，另一人當**夥伴**（Maintainer，持鑰人）；D3 也延續這台），但**各自用自己的 Agent 對話**。每個提示詞都標明【提案者】或【夥伴】：輪到誰，就由誰坐到鍵盤前，貼到自己的 Agent 對話。三人一組時，第三人當觀察員，看核准、簽章與 push 是否只出現在夥伴的對話。

## 檢查點 1 · 夥伴建立簽章金鑰（第 35–38 分鐘）

① 為什麼做這一步

**夥伴操作。** 之後每個碰到 Registry 的 commit 都要用夥伴的金鑰簽章，所以先由夥伴在自己的 Agent 對話建立金鑰；私鑰放在 Repo 外，只有夥伴用。

② 貼給 Agent

```prompt
# windows
【夥伴的 Agent】檢查點 1：建立我的簽章金鑰。
1. 先執行 git status，確認 domain-memory/ 還沒有被 commit 過（應該是未追蹤）。如果已經被 commit，停下來告訴我，不要往下做。
2. 依這台機器的終端機選一行執行，參數一字不改：
PowerShell：..\..\tools\dm.ps1 init-signing-key --principal maintainer@example.com --key-file "$env:USERPROFILE\.dlc-keys\maintainer\signing-key" --sign-every-commit --save "$env:USERPROFILE\.dlc-keys\maintainer\signing.json"
Git Bash：../../tools/dm.sh init-signing-key --principal maintainer@example.com --key-file "$HOME/.dlc-keys/maintainer/signing-key" --sign-every-commit --save "$HOME/.dlc-keys/maintainer/signing.json"
```

④ 補充

```callout info
新概念：簽章核准
**簽章 commit 是用私鑰簽過名的 commit，證明它出自持鑰人。**
- `git log --show-signature` 會顯示 `Good "git" signature for …`。
- 私鑰放 Repo 外，只有夥伴用。
- fingerprint（金鑰指紋）辨識是哪一把金鑰，可以公開。

📖 延伸閱讀：Git 官方文件〈git-commit〉的 -S 選項說明。
```

```callout danger
私鑰不可外流
`signing-key`（沒有副檔名的那個檔案）不可進 Repo、不可貼給任何 Agent、表單或聊天，也不要截圖。回顧最後會刪除它。
```

## 檢查點 2 · 設定審查政策與推送檢查（第 38–43 分鐘）

① 為什麼做這一步

**夥伴操作。** 下面三件事順序不能調換：
1. 審查政策決定誰可以簽（只授權你的 fingerprint）、何時檢查（push 時）。
2. 把審查模式改成「核准要有 Git 簽章」（scm-verified）。
3. 裝好 push 前自動執行的檢查（pre-push hook）。

```text
請只檢查，不要修改任何檔案：
1. 執行 validate --require-reviewed 是 Registry is valid.；verify-audit 是 "status": "valid"。
2. git log --show-signature -1 有 Good "git" signature for maintainer@example.com。
3. git status -sb 顯示本機分支已追蹤 origin，沒有尚未 push 的 commit。
全部符合只回「成功」，否則只回「失敗：」加一句原因。
```

失敗時：

```text
請用白話解釋剛才的錯誤訊息是什麼意思、是哪一個前提沒做到（例如 venv、政策、HEAD 指向哪個 commit），以及建議的下一步。不要自己修改設定、不要重做 commit、不要用 --no-verify 或任何方式繞過 hook，說明完停下等我。
```

④ 補充


## 卡住時

任一步卡住超過 5 分鐘，或第 45 分鐘起明顯來不及，主持人會提供 [D2 Recovery](#recovery-d2) 解鎖碼。

## 完成後想一想

兩人一起聊兩分鐘：

1. 夥伴審查時，哪一行證據或哪個測試結果讓你停下來追問？如果沒有人追問，怎麼確定這次核准不只是蓋章？
2. 今天哪一步最像「只是照流程做完」？哪一步真的擋得住錯誤？
3. 提案者和夥伴，誰覺得自己「真的做了一個決定」？是哪一個？
