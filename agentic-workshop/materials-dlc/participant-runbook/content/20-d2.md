# D2：審查與核准（成對）

```callout info
現在在做什麼
- **情境**：D1 的詞彙、Context 與規則都還是候選（candidate）。Agent 讀到候選時只能「參考」，不能當成事實。
- **你的目標**：讓這些候選經過「不是提案者本人」的審查與簽章核准，成為 Plugin 自己無法偽造、要靠 Git 簽章才能證明的已審查（reviewed）事實。
- **今天的技巧**：把「誰能核准」放在 Agent 碰不到的地方（今天在共用機器上，靠工作規則守住，見下方說明）。提案者的 Agent 準備證據；夥伴在**自己的 Agent 對話**裡讀審查包、自己回「核准」，簽章才會發生。
- **完成的樣子**：`validate --require-reviewed` 通過、`verify-audit` 是 `valid`、push 時檢查腳本印出 `Git governance is valid.`；過程與決定都由 Agent 寫在 `notes/d2.md`。
```

這是 **25 分鐘的兩人**任務。先讀 [D2 角色卡](#d2-role-cards)，決定誰是 **提案者（Proposer）**、誰是 **夥伴（Maintainer，持鑰人）**。三人一組時，第三人當 Observer（觀察員），看每一步是不是在對的人的 Agent 對話裡執行。

兩人**共用一台機器**（選 D1 做得比較完整的那台，它的主人當提案者；D3 也延續這台），但**各自用自己的 Agent 對話**。每個提示詞都標明【提案者】或【夥伴】：輪到誰，就由誰坐到鍵盤前，貼到**自己的** Agent 對話，讀回報、做決定。

```callout warning
為什麼核准一定要在夥伴自己的 Agent 對話裡
如果提案者的 Agent 也能執行核准與簽章，「已審查」就只代表「同一個 Agent 同意它自己」。所以：提案者的 Agent **不碰**夥伴的金鑰，**不執行** `record-approval`、不 commit；夥伴要先讀過審查包，自己回「核准」，夥伴的 Agent 才簽章。
老實說，今天這台共用機器上「碰不到」只是工作規則：金鑰檔就在這台電腦裡，`--sign-every-commit` 會讓這個 Repo 的任何 commit 都用它簽章，Plugin 也只比對身分字串。技術上擋不住提案者的 Agent，擋住它的只有工作規則，所以提案者的 Agent 一律不 commit。真實團隊會把私鑰放在只有持鑰人能用的機器或硬體金鑰上。
```

## 檢查點總覽

時間是**最晚**完成的時間；提早完成就直接進入下一個。

- **檢查點 1 · 夥伴建立簽章金鑰（35–38）**：【夥伴】Agent 建立放在 Repo 外的簽章金鑰。
- **檢查點 2 · 設定審查政策與推送檢查（38–43）**：【夥伴】Agent 依序設定誰能簽、何時檢查、審查模式，並裝好 push 前的檢查。
- **檢查點 3 · 建立變更審查包並送出提案（43–48）**：【提案者】Agent 做反事實檢查、建立變更審查包並送出。
- **檢查點 4 · 夥伴核准與簽章提交（48–53）**：【夥伴】你讀過證據後核准，Agent 做簽章 commit。
- **檢查點 5 · 寫出核准證明並驗證（53–56）**：【夥伴】Agent 把簽章 commit 寫成核准證明並驗證。
- **檢查點 6 · 完成提案並全部驗證（56–60）**：【提案者】→【夥伴】提案者套用並驗證，夥伴簽章提交並 push。

順序不能調換：簽章要在**第一個**包含 `domain-memory/` 的 commit 之前設定；審查政策依序設定誰能簽 → 何時檢查 → 審查模式。提示詞已照這個順序寫好，照貼即可。

## 檢查點 1 · 夥伴建立簽章金鑰（第 35–38 分鐘）

**夥伴操作。** 簽章金鑰是「誰核准」的證據，所以要在任何 `domain-memory/` 被 commit 之前就設定好，並讓本 Repo 之後每一個 commit 都簽章。

```callout info
新概念：簽章 commit 與金鑰指紋
簽章 commit 是用私鑰簽過名的 commit：Git 用對應的公鑰驗證，`git log --show-signature` 會顯示 `Good "git" signature for …`，證明這個 commit 確實出自持鑰人。私鑰放 Repo 外、只有夥伴用；Agent 只讀可公開的 fingerprint（金鑰指紋，辨識是哪一把金鑰）。
📖 延伸閱讀：Git 官方文件〈git-commit〉的 -S 選項說明；學員包 `tools/README.md`（金鑰放哪裡）。
```

```text
【夥伴的 Agent】檢查點 1：建立我的簽章金鑰。
1. 先執行 git status，確認 domain-memory/ 還沒有被 commit 過（應該是未追蹤）。如果已經被 commit，停下來告訴我，不要往下做。
2. 依這台機器的終端機選一行執行，參數一字不改：
PowerShell：..\..\tools\dm.ps1 init-signing-key --principal maintainer@example.com --key-file "$env:USERPROFILE\.dlc-keys\maintainer\signing-key" --sign-every-commit --save "$env:USERPROFILE\.dlc-keys\maintainer\signing.json"
Git Bash：../../tools/dm.sh init-signing-key --principal maintainer@example.com --key-file "$HOME/.dlc-keys/maintainer/signing-key" --sign-every-commit --save "$HOME/.dlc-keys/maintainer/signing.json"
3. 讀 signing.json，用白話告訴我 source、principal、fingerprint、signs_every_commit 各是什麼，以及私鑰檔在哪個資料夾（確認不在 Repo 裡）。不要打開私鑰檔 signing-key。
4. 把結果寫進 notes/d2.md 的「檢查點 1 · 夥伴建立簽章金鑰」（fingerprint 只寫前 12 碼），然後停下等我。
```

**看到什麼算過關**

- `source` 是 `generated`、`principal` 是 `maintainer@example.com`、`signs_every_commit` 是 `true`，fingerprint 以 `SHA256:` 開頭。
- 私鑰檔在使用者資料夾的 `.dlc-keys\maintainer\`，不在 Repo 裡；`domain-memory/` 仍未 commit。

```callout danger
私鑰不可外流
`signing-key`（沒有副檔名的那個檔案）不可進 Repo、不可貼給任何 Agent、表單或聊天，也不要截圖。回顧最後會刪除私鑰 `signing-key`。
```

## 檢查點 2 · 設定審查政策與推送檢查（第 38–43 分鐘）

**夥伴操作。** 先決定**誰**可以簽（只授權你的 fingerprint），再決定**何時**檢查（push 時），最後才離開「只能草稿」模式。之後安裝 pre-push hook（push 前 Git 自動執行的檢查腳本）；指令名裡的 HITL（Human-in-the-loop）是「人工把關」，說明見[詞彙表](#glossary)，不用記。`governance-readiness` 回報 `status`（`ready` 才算設好）與 `blocks`（還缺什麼）。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/script-api.md`〈Preparing the approval authority〉（Plugin 自帶）；`tools/README.md`（pre-push hook 與 `setup_remote.py`）。

```text
【夥伴的 Agent】檢查點 2：設定審查政策與推送檢查。順序不能調換。依終端機選一組，在「同一次執行」裡依序跑（fp 變數要在同一次執行內才有值），參數一字不改：
PowerShell：
$fp = (Get-Content "$env:USERPROFILE\.dlc-keys\maintainer\signing.json" -Raw | ConvertFrom-Json).fingerprint
..\..\tools\dm.ps1 amend-policy --field authorized_signers --value $fp --reason "Maintainer 持有簽章金鑰"
..\..\tools\dm.ps1 amend-policy --field review_trigger --value git-push --reason "push 時檢查簽章"
..\..\tools\dm.ps1 amend-policy --field review_mode --value scm-verified --verifier git-signed-commit --reason "以簽章 commit 作為核准證據"
..\..\tools\dm.ps1 install-git-hitl-hook
..\..\tools\dm.ps1 governance-readiness
Git Bash：
fp=$(py -3.13 -c "import json,sys;print(json.load(open(sys.argv[1],encoding='utf-8'))['fingerprint'])" "$HOME/.dlc-keys/maintainer/signing.json")
../../tools/dm.sh amend-policy --field authorized_signers --value "$fp" --reason "Maintainer 持有簽章金鑰"
../../tools/dm.sh amend-policy --field review_trigger --value git-push --reason "push 時檢查簽章"
../../tools/dm.sh amend-policy --field review_mode --value scm-verified --verifier git-signed-commit --reason "以簽章 commit 作為核准證據"
../../tools/dm.sh install-git-hitl-hook
../../tools/dm.sh governance-readiness
回報：三次 amend-policy 各自的舊值 → 新值、hook 裝在哪裡、governance-readiness 的 status 與 blocks。status 不是 ready 時，照 blocks 用白話說明缺什麼，不要自己改設定。把結果寫進 notes/d2.md 的「檢查點 2 · 設定審查政策與推送檢查」，然後停下等我。
```

**看到什麼算過關**

- 三次 `amend-policy` 各有舊值 `->` 新值，例如 `review_mode: local-draft-only -> scm-verified`。
- hook 裝在 `.git\hooks\pre-push`；最後是 `{"status": "ready", "blocks": []}`。沒有 `ready` 就不要往下。

## 檢查點 3 · 建立變更審查包並送出提案（第 43–48 分鐘）

**提案者操作。** 這個變更審查包的內容是「把 D1 的全部候選升為 reviewed」：不改任何程式，但每條規則都要有實際執行的測試，至少一條要用反事實檢查證明測試真的守得住它。

```callout info
新概念：變更審查包（Change Package）與反事實檢查（counterfactual）
變更審查包是一次變更的審查資料，放在 `domain-memory/changes/<id>/`：要升級哪些候選、每條規則要通過哪個檢查（obligation）、實際執行結果。反事實檢查是故意改壞一處程式、跑指定測試、再自動還原：測試失敗顯示 `killed`（有測試守著），仍通過顯示 `survived`（沒人守）。回報裡要看 `verdict`（killed 或 survived）、`failing_evidence`（失敗的斷言那一行）、`restored`（程式有沒有還原）。
📖 延伸閱讀：學員包 `vendor/domain-memory/references/proposal-lifecycle.md` 與 `pattern-verification.md`（Plugin 自帶，後者最後一段講反事實檢查）。
```

```callout info
技巧：先選改壞方案，只認 killed
要改壞哪裡，讓 Agent 先提方案、你來選；結果只認 `killed` 字樣，不認「指令沒報錯」。
📖 延伸閱讀：Claude Code 官方文件〈Best practices for Claude Code〉（先規劃、再用測試驗證）；你所用工具的官方文件通常有同名章節。
```


**看到什麼算過關**

- 反事實：`"verdict": "killed"`，失敗原因是斷言失敗（例如 `assert 665 == 595`），不是找不到檔案；`restored` 為 `true`。
- 每個 obligation 都是 `passed（exit 0）`，接著 `Change package is valid.`；送出後 `Proposal submitted for human review.`。`fill_package.py` 會實際執行每個測試，失敗就記 failed，不會幫你填 passed。

## 檢查點 4 · 夥伴核准與簽章提交（第 48–53 分鐘）

**夥伴操作。** 先審查，再核准；你可以退回。你不讀程式，但要讀 Agent 貼出的**證據原文與測試結果**，看它們是否真的支持要升級的規則。看不懂就追問 Agent，問到你能用一句話說出「為什麼這條可以算事實」為止。

```text
【夥伴的 Agent】檢查點 4 第一步：審查提案者的變更審查包。只讀，不改任何檔案，也先不要核准。
1. 摘要只根據這幾個小檔：domain-memory/changes/CP-D2-001/ 的 test-obligations.json 與 evidence-bundle.json、Repo 根目錄的 cf-d2.json，以及要升級清單所在的 cp-d2.json（promote）。不要讀整份 domain-change-proposal.json：它很大，又重複了 Registry 的全部內容，讀它只會浪費 Token。
2. 用白話告訴我：(a) 要升為 reviewed 的候選有哪些（各檔案幾個）；(b) 每個 obligation 跑了哪個測試、結果是什麼；(c) 反事實檢查改壞了哪裡、哪個測試失敗、斷言內容是什麼、程式有沒有還原。
3. 挑一條規則，用 ..\..\tools\dm.ps1 get-record --asset rules --id 規則id（Git Bash：../../tools/dm.sh）取出它，打開它引用的證據（檔案:行號），把那幾行原文貼給我，說明它是否真的支持這條規則。
4. 列出你覺得證據不足或可疑的地方；沒有就說沒有。
5. 停下等我回「核准」或「退回：原因」。不要執行 record-approval，也不要 commit。
```

你決定核准，就貼下面這段；決定退回，就回「退回：原因」，請 Agent 把理由寫進 `notes/d2.md`，然後找主持人。

```text

1. 先把我的核准決定和你剛才的審查摘要寫進 notes/d2.md 的「檢查點 4 · 夥伴核准與簽章提交」，讓它一起進入這次簽章 commit。
2. 依終端機執行，參數一字不改（records/ 是 make_record.py 留下的暫存資料夾，不是證據，不要 commit；D1 的 d1-records.json 是登記候選用的輸入檔，會一起 commit，這是預期的）：
PowerShell：
..\..\tools\dm.ps1 record-approval --package-root domain-memory/changes/CP-D2-001 --role domain-owner --reviewer maintainer@example.com --scope "D1 候選升為 reviewed"
```

**看到什麼算過關**

## 檢查點 5 · 寫出核准證明並驗證（第 53–56 分鐘）

**夥伴操作。** 簽章 commit 本身就是證據。`write_scm_attestation.py`（SCM＝Source Code Management，原始碼管理，也就是版本控制，這裡指 Git）把它寫成核准證明（attestation，說明見[詞彙表](#glossary)，不用記）放進變更審查包，再請 Plugin 驗證這個 commit 的簽章是被政策授權的。

```text
【夥伴的 Agent】檢查點 5：把剛才的簽章 commit 寫成核准證明，並驗證。依終端機執行，參數一字不改：
PowerShell：
py -3.13 -X utf8 ..\..\tools\write_scm_attestation.py --package domain-memory/changes/CP-D2-001 --commit HEAD
..\..\tools\dm.ps1 verify-git-governance --commit HEAD
Git Bash：
py -3.13 -X utf8 ../../tools/write_scm_attestation.py --package domain-memory/changes/CP-D2-001 --commit HEAD
../../tools/dm.sh verify-git-governance --commit HEAD
回報兩行結果（attestation 的 commit 前 12 碼；Git governance is valid. 或錯誤訊息）。失敗時先確認 HEAD 是不是剛才的簽章 commit，不要自己重做 commit。輸出提到 finalize-proposal 時不要執行：那是提案者在檢查點 6 的步驟。寫進 notes/d2.md 的「檢查點 5 · 寫出核准證明並驗證」，然後停下。
```

**看到什麼算過關**：`已寫入 attestation：commit <sha>`，接著 `Git governance is valid.`。工具輸出裡的 `finalize-proposal` 是提案者在檢查點 6 的步驟，夥伴的 Agent 不執行；如果它跑了，請它如實寫進 `notes/d2.md`，並告訴主持人。

## 檢查點 6 · 完成提案並全部驗證（第 56–60 分鐘）

**先由提案者**定案與套用（只有核准且有簽章證據的提案能套用），**再由夥伴**簽章提交並 push；push 時檢查腳本會再驗一次簽章。套用後，候選才成為已審查（reviewed）事實：Agent 可以把它當成限制，之後也不能直接覆寫。`verify-audit` 檢查稽核紀錄（audit）有沒有被改過，`"status": "valid"` 就是沒被改過；說明見[詞彙表](#glossary)，不用記。

```text
【提案者的 Agent】檢查點 6 第一步：夥伴已核准並寫好核准證明。依終端機執行，參數一字不改：
PowerShell：
..\..\tools\dm.ps1 finalize-proposal --package-root domain-memory/changes/CP-D2-001
..\..\tools\dm.ps1 apply-approved-updates --package-root domain-memory/changes/CP-D2-001
..\..\tools\dm.ps1 validate --require-reviewed
..\..\tools\dm.ps1 verify-audit
Git Bash：
../../tools/dm.sh finalize-proposal --package-root domain-memory/changes/CP-D2-001
../../tools/dm.sh apply-approved-updates --package-root domain-memory/changes/CP-D2-001
../../tools/dm.sh validate --require-reviewed
../../tools/dm.sh verify-audit
回報每一步的關鍵輸出（verify-audit 要含 status 與事件數），寫進 notes/d2.md 的「檢查點 6 · 完成提案並全部驗證」。不要 commit、不要 push，停下。
```

提案者的 Agent 回報四步都成功後，換夥伴貼：

```text

PowerShell：

git -c "user.name=DLC Maintainer" -c "user.email=maintainer@example.com" commit -S -m "D2：套用 CP-D2-001"

回報：commit 是否簽章、hook 印出幾次 Git governance is valid.、push 是否出現 [new branch]。被拒時貼出拒絕訊息並用白話解釋原因，不要用 --no-verify 或任何方式繞過 hook。把結果補進 notes/d2.md，然後停下。
```

**看到什麼算過關**

- 提案者這邊：`Proposal approved.`、`Approved registry updates applied.`、`Registry is valid.`（這次帶 `--require-reviewed`）、`verify-audit` 回 `"status": "valid"` 與事件數。

## 卡住時

Agent 回報錯誤時，先貼這段，讓它解釋而不是亂修：

```text
請用白話解釋剛才的錯誤訊息是什麼意思、是哪一個前提沒做到（例如金鑰、政策順序、venv、HEAD 指向哪個 commit），以及建議的下一步。不要自己修改設定、不要重做 commit、不要繞過 hook，說明完停下等我。
```

任一步卡住超過 5 分鐘，或第 45 分鐘起明顯來不及，主持人會提供 [D2 Recovery](#recovery-d2) 解鎖碼：內容是一份已審查、簽章並套用的 Registry 與它的簽章歷史。照該頁三個步驟切換：提案者的 Agent 搬檔案與驗證，夥伴在自己的 Agent 對話用自己的金鑰接手簽章；你們自己做到哪一步，請 Agent 如實寫進 `notes/d2.md`。

## 完成後想一想

不用填表、不用寫下來。想不起細節時，可以先貼這段請 Agent 幫你回想：

```text

```

1. **觀察**：夥伴讀審查包時，Agent 貼出的哪一行證據或哪個測試結果讓夥伴停下來追問？如果整段沒有人追問，你們怎麼確定那次核准不只是蓋章？
2. **技巧**：如果核准與簽章也交給提案者的 Agent 一路做完，`notes/d2.md` 與 `git log` 會少了哪些證據？在你的團隊，哪一類變更值得「另一個人在自己的對話裡讀過證據才核准」？
3. **延伸**：接下來 Agent 會依這些已審查事實提設計選項。你預期哪一條已審查事實最可能改變它的提案？
