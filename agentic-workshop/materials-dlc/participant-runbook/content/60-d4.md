# D4：交接給下一個 Agent

```callout info
現在在做什麼
- **情境**：明天換另一個 Agent 或同事接手，只看得到 Repo、共用模型與一份交接單。
- **你的目標**：Agent 先檢查模型有沒有落後程式，把 D3 改變的規則寫成新候選，再寫交接單。
- **今天的技巧**：**交接單只准引用查得到的 id**。Agent 會自信地寫出不存在的 id，要它逐一查證。
- **完成的樣子**：`docs/handoffs/d4-next-agent.md` 七段齊全、每個 id 都查得到，並已由夥伴 commit；Repo 裝好提交前檢查。
```

提示詞貼給提案者的 Agent 對話；最後的 commit 由夥伴在自己的 Agent 對話執行。

```callout tip
時間不夠時的最低完成線
**第 165 分還沒完成，就收在最低完成線：檢查點 1，加上只含 Unknowns 的交接單。**
- 對 Agent 說：「照 D4 最低完成線收尾：交接單只寫 Unknowns（未知事項），其他段寫『未完成』並說明原因。」再由夥伴 commit。
- 改用 D3c Recovery 的組，D4 直接做這條線。
- 檢查點 2 來不及登記的，請 Agent 在 `notes/d4.md` 列為未完成，不要延長段落。
```

## 檢查點 1 · 檢查模型是否落後程式（第 155–158 分鐘）

① 為什麼做這一步

D3 改了程式，模型引用的原文可能只是移動，也可能內容變了。只是移動的不算問題；內容變了的規則，Agent 再跑一次證明它的測試：還通過只代表舊情境沒壞，D3 新增的路徑要讀程式判斷；失敗或沒有測試，模型就落後了。全部記下來交給下一次核准，不要當場修掉，這一步只讀不改。

```download
id=participant-dlc-d4 zip=participant-dlc-d4.zip label=下載 D4 交接單範本
```

- [ ] 按上方按鈕下載 `participant-dlc-d4.zip`，存到「下載」資料夾（不用解壓縮）

② 貼給 Agent

```text
【提案者的 Agent】D4 檢查點 1：今天的模型要交接給下一個 Agent，先查它有沒有落後程式。
照 AGENTS.md 從下載資料夾取 participant-dlc-d4.zip，解到 ../../pkg-d4，把裡面 worksheets 資料夾的檔案複製到 ../../worksheets。
接著只讀不改：跑 dm verify-sources、dm verify-evidence、dm verify-audit、dm coverage，照 ../../worksheets/d4-handoff-template.md「交接前的檢查」讀結果，stale 的規則再跑一次證明它的測試。出現 shifted、stale 或 exit 1 是預期的，不要修。
每個指令用兩三句白話回報，記在 notes/d4.md。做完用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：verify-audit 是 "status": "valid"，程式和 domain-memory/ 都沒改。
```

失敗時：

```text
先停，不要改任何檔案，也不要試著修好 stale。是哪一個指令的輸出和預期不同？可能的原因是什麼？你建議怎麼做？
```

④ 補充

```callout info
新概念・加深一層：模型會落後程式
**D1 確認的來源在 D3 多了新檔案，Agent 回報「來源過期」是正常的。**
- 寫進交接單的 Unknowns（未知事項），留給下一次成對核准。
- 引用只是移動（shifted）是重構留下的痕跡，不是模型變更；內容變了（stale），才要逐項問行為有沒有變。
- 模型只在有已審查規則的 Context 說了算：`coverage` 列出沒有的 Context（例如 D3 新增、只有候選規則的），也寫進 Unknowns。

📖 延伸閱讀：Eric Evans〈Domain-Driven Design Reference〉；學員包 `vendor/domain-memory/references/registry-maintenance.md`。
```

## 檢查點 2 · 把改變的規則寫回模型（第 158–161 分鐘）

① 為什麼做這一步

Agent 先列清單，你們同意後才寫入，寫入的一律是候選，最多 3 項。被 D3 改變的已審查規則不能直接改寫：用新 id 寫一條候選描述新行為，原本那筆留著，等下一次核准取代。
- 確認：B 類每項都說得出改了哪一項意思（名詞、負責的 Context、不變量或規則、邊界、事件或對外約定）；只是重構、或來不及登記的，都有說明原因

② 貼給 Agent

```text
【提案者的 Agent】檢查點 2：依 notes/d4.md 檢查點 1 的 stale 與 shifted 清單、D3 的交接單與 notes、git log，找出 D3 讓哪些模型事實改變了。先不要寫入，照 ../../worksheets/d4-handoff-template.md「交接前的檢查」列出更新清單，每項一句理由：
A. 證據 stale 或 shifted 的候選：同一個 id、新行號重新登記（候選可以覆寫）。
B. 被 D3 改變的 reviewed 事實：證據 stale，而且讀過程式確認名詞、負責的 Context、不變量或規則、邊界或相依方向、事件或對外約定至少一項變了。reviewed 不能覆寫，改用新 id 登記一條候選描述新行為。只搬移或整理程式的是重構，歸 C。
C. 其餘 reviewed 事實（shifted、行為沒變的 stale）：不登記，只列筆數。
沒有要更新的就說「沒有」。列完停下，等我回「同意」或「第 N 項不要／改成…」。同意後照 record-candidates 逐項登記，結果記在 notes/d4.md。做完用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：Registry is valid.，新登記的都是 candidate，被取代的 reviewed 事實仍是 reviewed、內容沒變。
```

失敗時（例如 `make_record.py` 出錯。英文提醒 `NOTE: … That is reach, not an error.` 不算錯誤）：

```text
先停，不要自己改指令重試，也不要改任何檔案。這個錯誤是什麼意思、是哪一項造成的？給我兩個做法選，例如換一個已確認來源內的證據，或把這一項改列為交接單的 Unknowns。
```

④ 補充

```callout info
新概念・加深一層：重新證明，還是寫一條新規則
**D3b 的「模型變更與重構」用在已審查規則上：意思沒變，下一次核准沿用原 id 重新證明；意思變了，才用新 id 寫候選。**
- 分不清時問：原本證明它的測試，現在該通過還是該失敗？該通過是同一條，該失敗是新規則。
- 重新證明時，下一次的提案把已審查的那筆換上新的引用與測試，取代上一次的核准（Plugin 的 `promote-candidate --amend`）。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/seven-step-workflow.md`〈Harvesting proven rules from existing code〉。
```

## 檢查點 3 · 寫交接單並查證每個引用（第 161–165 分鐘）

① 為什麼做這一步

讓 Agent 自己查證每一個引用（id）：查不到的不准猜替代品，要移到 Unknowns。
- 核對時抽一句問 Agent「這句的證據在哪？」；指不出來的，請它改寫或移到 Unknowns
- **夥伴**看過交接單與 id 核對清單後，在**自己的 Agent 對話**貼第二段提示詞；它 commit 後替 Repo 裝上提交前檢查，示範一次「程式搬家、模型沒跟上」的 commit 被擋下

② 貼給 Agent

```text
【提案者的 Agent】檢查點 3：照 ../../worksheets/d4-handoff-template.md「交接單」把今天的成果寫成 docs/handoffs/d4-next-agent.md，交給明天接手的 Agent。
材料只用：notes/d4.md、D3 的交接單與 notes、docs/adr/ 裡 D3 新增的 ADR（如果有）、Registry 查詢結果、D3 反事實檢查的實際結果，和你現在跑一次完整測試的輸出。
寫完只回報 id 核對清單和移到 Unknowns 的項目，各段我自己打開看。停下等我回「同意」或「改成…」；同意後把核對清單記在 notes/d4.md。
```

夥伴看過交接單與 id 核對清單後，在自己的對話貼：

```text
【夥伴的 Agent】檢查點 3：照 signed-commit 把 D4 的成果 commit 成「D4：交接 Handoff」，給我看的摘要用 docs/handoffs/d4-next-agent.md 的 Unknowns 一段；不要 push。
commit 後替 Repo 裝上提交前檢查（pre-commit hook），示範一次它擋下什麼。照 AGENTS.md 在同一次執行裡先啟用 .venv、設 PYTHONUTF8，再依序跑，參數一字不改：
dm install-pre-commit-hook
git mv src/smart_ticket/domain/discounts.py src/smart_ticket/domain/discount_rules.py
git commit -m "示範：程式搬家，模型沒跟上"
git mv src/smart_ticket/domain/discount_rules.py src/smart_ticket/domain/discounts.py
git status --short
回報示範的 commit 有沒有被擋下、點名了哪幾筆紀錄、建議的 relocate-evidence 那一行，以及檔案已搬回原位。萬一示範的 commit 成功了，立刻執行 git reset --soft HEAD~1、把檔案搬回原位並告訴我，不要再 commit。做完用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果（貼到夥伴的對話）

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：最新 commit「D4：交接 Handoff」有 Good "git" signature for maintainer@example.com，示範的 commit 被擋下，除了 records/ 沒有其他變更。
```

失敗時（交接單的問題貼到提案者的對話；簽章或 hook 的錯誤留在夥伴的對話問，不要重做 commit、不要繞過 hook）：

```text
先停，不要 commit。交接單哪一句對不上？每個 id 重新用 get-record 查，查不到的、指不出證據的句子改寫或移到 Unknowns。列出你改了哪些句子，等我。
```

④ 補充

```callout info
新概念：讓模型擋住讓引用失效的 commit
**裝上提交前檢查後，模型會保護自己：commit 搬走或改掉模型引用的程式、卻沒更新引用，就會被擋下。**
- 被擋下時，它點名受影響的紀錄；程式搬家時，還給出重新引用的那一行指令。
- 這是留給下一個 Agent 的防線：它得先讓模型跟上程式，才 commit 得進去。
- 它只看這次 commit 的檔案；已經落後的引用，仍靠檢查點 1 的檢查與下一次核准。

📖 延伸閱讀：Git 官方文件〈githooks〉的 pre-commit 一節；學員包 `vendor/domain-memory/references/script-api.md`（install-pre-commit-hook 那一列）。
```

## 完成後想一想

先自己想 30 秒，再兩人一起聊兩分鐘；也可以和隔壁組交換看交接單的 Unknowns：

1. 假設你明天就是接手的 Agent：只看這份交接單，你最先會問哪一個問題？答案在交接單裡嗎？
2. Agent 有沒有引用過查不到的 id，或把候選寫成 reviewed？是在哪一步被抓到的？
3. 今天留下的候選要成為事實，下一次核准需要誰、看哪些證據？你的團隊有這個角色嗎？
