# D4：交接給下一個 Agent

```callout info
現在在做什麼
- **情境**：D3 三張需求改了不少程式。明天換另一個 Agent 或同事接手，它只看得到 Repo、Domain Memory 與一份交接單（Handoff），沒聽過今天的討論。
- **你的目標**：請 Agent 先驗證 Domain Memory 還可信到什麼程度，把 D3 改變的事實登記成候選，再組出一份只引用真實 id 的交接單；你們用短回覆核對。
- **今天的技巧**：**交接前先請 Agent 驗證記憶，交接單只准引用查得到的 id**。Agent 會很有自信地寫出不存在的 id；要求它逐一查證，比人自己讀一遍可靠。
- **完成的樣子**：`notes/d4.md` 有驗證結果與更新清單；`docs/handoffs/d4-next-agent.md` 七段齊全、每個 id 都查得到，並已 commit。
```

這是 **10 分鐘的兩人**任務，延續 D3 最後的同一台機器與 Repo。三個檢查點的提示詞都貼給提案者的 Agent 對話（D3 用的那一個，[D3a](#d3a) 的「Agent 工作規則」仍然有效）；Agent 回報後停下，你們只要回「同意」或「第 N 項改成…」。最後的 commit 和 D3 檢查點 5 一樣，由夥伴在自己的 Agent 對話執行。

## 檢查點總覽

- **155–158 · 檢查點 1**：Agent 跑三個驗證指令，白話說明哪些記憶已經過期。
- **158–161 · 檢查點 2**：Agent 列出 D3 改變的事實，你們同意後登記成候選。
- **161–165 · 檢查點 3**：Agent 依範本寫交接單、逐一查證 id；你們同意後，夥伴在自己的 Agent 對話 commit。

## 檢查點 1 · 驗證來源、證據與稽核（第 155–158 分鐘）

D3 動過程式，Domain Memory 引用的行號可能已經對不上。交接前先讓 Agent 跑驗證，才知道哪些記憶還能信。這一步只讀不改：過期（stale）是事實，要記下來，不是要當場修掉。

```text
我們要把今天的 Domain Memory 交接給下一個 Agent。這一步只讀不改：不要修改任何程式，也不要寫入 domain-memory/。
請在 Repo 根目錄依序執行下列三個唯讀指令（你用的是 Git Bash 時，把 ..\..\tools\dm.ps1 換成 ../../tools/dm.sh，參數不變）：
..\..\tools\dm.ps1 verify-sources
..\..\tools\dm.ps1 verify-evidence
..\..\tools\dm.ps1 verify-audit
出現 stale 或 exit 1 是預期中的結果，不要試著修好。
執行完用白話回報，每個指令兩三句：
1. verify-sources：status 是 current 還是 stale；changed_sources 列了哪些路徑，檔案數從幾變成幾。
2. verify-evidence：current、stale、missing、invalid 各幾筆；stale 依檔案分組，每個檔案寫大約幾筆就好。只整理指令印出的內容，不要自己寫程式或腳本去對出 asset:id 或行號（Plugin 只經 dm 執行）。
3. verify-audit：status 與事件數。
把這三段回報寫進 notes/d4.md 的「檢查點 1 · 驗證結果」小節（沒有這個檔就建立），然後停下等我。
```

**看到什麼算過關**

- Agent 回報了三個指令的實際結果，沒有改任何檔案。
- `verify-evidence` 的四種數量都有，stale 依檔案分組列出。
- `verify-audit` 是 `valid`；`notes/d4.md` 有這段紀錄。

current、stale、missing、invalid 這四種狀態你在 D1 學過；這次多看一個 `verify-sources`：它比對的不是某幾行，而是 D1 人確認過的整個來源範圍，它的 stale 表示來源資料夾裡有檔案被新增、刪除或改名（只改檔案內容不算，那是 `verify-evidence` 逐行檢查的事）。`verify-sources` 是 `stale` 很正常：D3 在 `docs/adr/`、`src/`、`tests/` 新增了檔案，來源範圍已經不是當初人確認的那一份。這要寫進交接單的 Unknowns（未知項），留給下一次成對核准，今天不修。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/registry-maintenance.md`（Plugin 自帶，程式改了之後怎麼維護記憶）。

```callout tip
如果跳過這一步直接交接，下一個 Agent 會把哪一筆過期的事實當成限制？會做出什麼錯事？
```

## 檢查點 2 · 更新已變動事實（第 158–161 分鐘）

讓 Agent 先列清單、你們同意後才寫入：寫進 Domain Memory 的每一筆都要經過人點頭。寫入的內容一律是候選；已審查的事實不能直接改，只能另外登記新的候選取代它。

```text
請依 notes/d4.md「檢查點 1 · 驗證結果」，加上 D3 留下的決策卡與紀錄（docs/handoffs/ 與 notes/ 裡 D3 的檔案）和 git log，找出 D3 讓哪些 Domain Memory 事實改變了。先不要寫入，列出更新清單，每一項附一句理由：
A. 證據 stale 的候選：verify-evidence 只印檔案路徑、不印 id，所以從 notes/ 裡 D3 各段「審查與候選」取出登記過的候選 id，逐一用 get-record 查它的證據是不是落在 stale 的檔案上。是的話用同一個 id、新的行號重新登記（候選可以覆寫）。列出 asset:id、舊證據、新證據（路徑:起-迄；先讀檔確認新的那幾行真的在講這件事）。
B. 被 D3 改變的已審查（reviewed）事實：reviewed 不能覆寫，改用新的 id 登記一條候選描述新行為。列出原本的 asset:id、新候選 id、一句可以用測試推翻的敘述、證據、所屬 context id。
C. 行為沒變、只是行號移動而 stale 的 reviewed 事實（通常是大多數）：不要登記，維持 stale，理由寫「reviewed 不能覆寫，待下次核准重新確認」；只列檔案與大約筆數，不用逐筆查。
要確認某筆是候選還是 reviewed，用 ..\..\tools\dm.ps1 get-record --asset 類別 --id 編號 查（decisions 類別看 review_status，其他類別看 status）；只查清單要列的 id。
沒有需要更新的就說「沒有」。列完停下，等我回「同意」或「第 N 項不要／改成…」。

我同意後，對每一項執行一次下面的指令（Git Bash 把 ..\..\tools\ 換成 ../../tools/、dm.ps1 換成 dm.sh；asset、id、敘述、context、證據換成該項的內容；詞彙改用 --definition、Context 改用 --responsibility，其他欄位依 make_record.py --help）：
py -3.13 -X utf8 ..\..\tools\make_record.py --asset rules --id 規則id --statement "敘述" --context contextid --evidence 路徑:起-迄 --allow-unclassified --upsert
全部登記完再執行：
..\..\tools\dm.ps1 verify-evidence
..\..\tools\dm.ps1 validate
用白話回報：登記了哪些 asset:id、verify-evidence 還剩幾筆 stale（為什麼）、validate 是否顯示 Registry is valid。把同意後的清單與這段回報寫進 notes/d4.md 的「檢查點 2 · 已變動事實」小節。不要把任何候選改成 reviewed，不要動 domain-memory/ 裡其他檔案。做完停下。
```

**看到什麼算過關**

- Agent 先列清單、等你們回覆後才登記；登記的全部是候選。
- 被改變的 reviewed 事實是「新 id 的候選」，原本那筆沒有被覆寫。
- `validate` 顯示 `Registry is valid.`；剩下的 stale 有說明原因。

```callout info
為什麼不在這裡把候選升為 reviewed
升級需要另一份變更審查包（Change Package）、夥伴本人在自己的 Agent 對話裡核准並做簽章 commit，以及重新確認來源。10 分鐘做不完，硬做就會變成走流程。今天的交接成果是：清楚標出哪些是事實、哪些是候選、下一次核准要處理什麼。
```

**如果卡住**（`make_record.py` 回「不在已確認來源內」或其他錯誤）：看到英文的 `NOTE: … That is reach, not an error.` 只是提醒，不是錯誤，請 Agent 把那個檔案記進交接單的 Unknowns 就好。真的出錯時貼：

```text
請解釋剛才的錯誤訊息代表什麼、是哪一項造成的，不要自己改指令重試，也不要修改任何檔案。給我兩個做法讓我選，例如換一個在已確認來源內的證據，或把這一項改列為交接單的 Unknowns。
```

## 檢查點 3 · 寫交接單並核對 id（第 161–165 分鐘）

交接單的格式與每段要寫什麼見 [D4 Handoff 範本](#d4-handoff-template)，提示詞已附上同一份格式。D3 的決策卡是交給 Agent 實作用的；這次多一層：交接單是給「沒聽過今天討論」的下一個 Agent 看的，多了 Forces（影響決定的考量）、Unknowns（還沒決定的事）、Proof obligations（每條規則用哪個測試證明）等段落。重點是讓 Agent 自己查證每一個 id：查不到的不准猜替代品，要移到 Unknowns。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/implementation-handoff.md`〈Handoff contents〉（Plugin 自帶）。

```text
請把今天的成果寫成給下一個 Agent 的交接單，存成 docs/handoffs/d4-next-agent.md，格式照下面七段。
材料只能用：notes/d4.md、docs/handoffs/ 與 notes/ 裡 D3 的決策卡與紀錄、docs/adr/ 裡 D3 新增的 ADR（記錄 D3 的設計決定，如果有）、Registry 查詢結果、D3 反事實檢查（counterfactual）的實際結果，以及你現在執行一次完整 pytest -q 的實際輸出。
規則：
- 只引用 Registry 查得到的 asset:id。對文中每一個 id 都執行唯讀查詢確認：..\..\tools\dm.ps1 get-record --asset 類別 --id 編號（Git Bash 用 ../../tools/dm.sh）。查不到的不要猜替代品，移到 Unknowns。reviewed 或候選看 get-record 的 status（decisions 類別看 review_status）。只查交接單裡真的引用的 id。EINV、PTS、PCR 這類需求卡驗收條件編號不是 Registry id，不用 get-record 查。
- reviewed 與候選分開寫，候選不能寫成 reviewed；需求卡上還沒決定的問題寫進 Unknowns，不能寫成已決定。
- verify-sources 回報 stale 的來源寫進 Unknowns，註明留給下一次成對核准。
- Counterfactual check 只列實際看到 killed 的；沒有就寫「未證明」。沒有內容的段寫「無」並說明原因。

# Handoff：Smart Ticket Domain Memory（今天日期）
## Domain facts
reviewed 的 Context、詞彙與規則；D3 新增的候選（標明尚未審查、不可當成限制）；已不成立、要由新候選取代的 reviewed 事實（舊 id → 新候選 id）。
## Forces
影響決定的考量與限制：哪些資料必須同時成立、外部系統失敗與重試（冪等鍵）、預留與歸還、部分取消。
## Decision
今天的設計決定，各一句，附需求卡驗收條件編號或規則 id。
## External systems
每個外部系統：領域程式要它做什麼、必須分辨哪些結果、測試用什麼替身。
## Unknowns
需求卡上仍未決定的問題；verify-sources 過期的來源；查不到的 id。
## Proof obligations
規則或驗收條件編號 → 測試名稱；最後一次完整 pytest -q 的 passed／failed 數。
## Counterfactual check
每列：規則 id｜改壞的地方（檔案:行，原字串 → 改後）｜測試｜結果。

寫完在對話用白話回報：每段一句重點；id 核對清單（id、查得到嗎、reviewed 或 candidate）；你移到 Unknowns 的項目。然後停下，等我回「同意」或「改成…」。
我同意後，把 id 核對清單寫進 notes/d4.md 的「檢查點 3 · 交接單核對」小節。不要 git commit 或 git push：commit 由夥伴在自己的 Agent 對話執行。做完停下。
```

- [ ] **夥伴（Maintainer）**看過交接單與 id 核對清單後，在**夥伴自己的 Agent 對話**（D2、D3 用的那一個）貼下方提示詞：

```text
請在 Repo 根目錄執行 git status --short 與 ..\..\tools\dm.ps1 validate（Git Bash 用 ../../tools/dm.sh validate），用白話列出這次要 commit 的檔案，並摘要 docs/handoffs/d4-next-agent.md 的 Unknowns 一段，然後停下等我回「同意」。
我同意後執行（records/ 是 make_record.py 留下的暫存資料夾，不是證據，不要 commit）：
git add -A -- . ':!records'
git -c "user.name=DLC Maintainer" -c "user.email=maintainer@example.com" commit -S -m "D4：交接 Handoff"
git log --show-signature -1
用白話回報 commit 編號與簽章那一行。不要 push。不要顯示金鑰內容。遇到簽章錯誤時不要修改 Git 設定，貼出錯誤訊息後停下。
```

**看到什麼算過關**

- id 核對清單裡每一個 id 都「查得到」；查不到的已移到 Unknowns。
- 候選沒有寫成 reviewed，未決問題沒有寫成已決定。
- 夥伴的對話完成 commit，訊息是 `D4：交接 Handoff`，`git log` 看得到簽章那一行；提案者的 Agent 沒有執行 `git commit`。

核對時抽一句問 Agent「這句的證據在哪？」，它應該指得出 `notes/d4.md`、決策卡或某個指令的輸出；指不出來的，請它改寫或移到 Unknowns。

## 完成後想一想

不用填表、不用寫下來。想不起細節時，可以先貼這段請 Agent 幫你回想：

```text
請根據 notes/d4.md 與 docs/handoffs/d4-next-agent.md 提醒我 D4 實際發生了什麼：驗證時哪些記憶過期、id 核對時有沒有查不到的、哪些項目移到 Unknowns。只陳述紀錄裡的事，幫我回想第 1 題，但不要替我下結論。
```

1. **觀察**：Agent 寫交接單時，有沒有引用過查不到的 id，或把候選寫成 reviewed？是在哪一步被抓到的？
2. **技巧**：今天你們沒有自己逐句讀交接單，而是要 Agent 逐一查證 id，再抽問「這句的證據在哪？」。這樣比自己從頭讀一遍省了什麼、又可能漏掉什麼？在你的工作交接時，哪一份文件最需要這種逐條查證？
3. **延伸**：今天留下的候選要成為事實，下一次核准需要誰、看哪些證據？你的團隊現在有這個角色嗎？

