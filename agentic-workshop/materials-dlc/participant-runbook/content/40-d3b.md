# D3b：會員點數折抵

```callout info
現在在做什麼
- **情境**：會員訂票時可以用點數折抵票款。點數要在下單時先預留，團體訂票付款失敗或退票時再歸還（一般訂票付款失敗維持現行規則，不歸還），而且不能重複扣、不能漏退。
- **你們的目標**：30 分鐘內決定點數與折抵規則歸哪個 Context 管、哪些條件必須永遠成立，讓 Agent 把折抵接到**每一條**計價路徑（會計算訂票總額的每一段程式），並證明預留與歸還都有測試守著。
- **今天的技巧**：和 D3a 一樣，Agent 提兩個選項與證據、人選，再由 Agent 依 D3 決策卡格式寫成交接單；這次多一個重點：請 Agent 先列出**所有**會計算總額的程式路徑，漏一條就有一種訂票不受規則限制。
- **完成的樣子**：`docs/handoffs/d3b-points-redemption.md` 寫著你們的決定；`notes/d3b.md` 記著事實、計畫、測試結果、反事實檢查（counterfactual：故意改壞一處程式，確認測試會失敗；抓到就顯示 killed）結果與登記的候選；每條新規則都看到 `killed`。
```

這是 **30 分鐘的兩人**任務，建立在 D3a 的成果上，節奏與 D3a 相同。沿用同一個 Agent 對話時，[D3a](#d3a) 的「Agent 工作規則」仍然有效；換了新對話（例如改用 Recovery（復原包：進度落後時改用的接續基線））就先把那段規則再貼一次。交接單格式見 [D3 決策卡](#d3-decision-card)。

```callout tip
時間不夠時的最低完成線
至少完成以下三項；**延伸**項目（PTS-002、011、013、015）只在時間允許時做：
1. 需求卡「本次範圍」的**核心**驗收條件（PTS-001、003、004、005、006、007、008、009、010、012、014）。
2. 一般訂票建立與團體建立兩條計價路徑都接上折抵（改票重新計價屬延伸 PTS-013）。
3. 預留與歸還各一條規則有 `killed` 的反事實檢查。
來不及的請 Agent 在 `notes/d3b.md` 列為未完成，不要延長段落。
```

