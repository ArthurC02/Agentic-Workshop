## 檢查點 2 · 決定負責的 Context 與不變量（第 97–101 分鐘）

① 為什麼做這一步

漏接一條計價路徑，就有一種訂票不受折抵規則限制。所以先請 Agent 找出所有計價路徑，再由你們決定點數歸誰管：

- [ ] Agent 列出選項後，先聊 ④ 的討論題，再回一句選擇，例如「1A、2B、3A、4B」；想混合就直接說
- [ ] 每條計價路徑都附行號和會走到的訂票種類，才回「同意」；否則回「第 2 條改成…」

② 貼給 Agent

```text
先不要改程式。先找出所有呼叫優惠政策或計算 Booking 總額的地方，逐一列出檔案路徑:行號、哪一種訂票或操作會走到、是不是共用同一段計價邏輯；再指出同一會員同時建立多筆訂票時，可能讓點數變負的地方。
然後照 ../../worksheets/d3-decision-card.md 的步驟，替需求卡 02「待團隊決定的問題」1–4 提選項給我們選。我們回覆選擇後，照決策卡寫交接單 docs/handoffs/d3b-points-redemption.md，列出不變量和計價路徑清單等我們回「同意」。做完用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：交接單寫的是我們回覆的選項，每條計價路徑都有檔案路徑:行號與會走到的訂票種類。
```

失敗時（例如只列出一兩條計價路徑，或沒說明每條是哪一種訂票）：

```text
先停，不要改任何檔案。再搜尋一次所有呼叫優惠政策或計算總額的地方（包括建立、修改既有訂票時重新計價的地方），逐一列出檔案路徑:行號和哪一種訂票會走到。
```

④ 補充

```callout tip
💬 討論一下
- 漏掉一條計價路徑，會是哪一種訂票出問題？出問題時客人會看到什麼？
- 「預留成為獨立紀錄」和「直接扣餘額、失敗再加回」，在兩個請求同時送出時差在哪裡？
```

```callout info
新概念・加深一層：不變量
**不論從哪一條程式路徑呼叫、多筆訂票同時送出，不變量都要成立。**
- 例如「點數餘額不得為負」。
- 所以先請 Agent 找出**所有**計價路徑：漏接一條，規則就有破口。

📖 延伸閱讀：Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 10 章〈Aggregates〉的「Rule: Model True Invariants in Consistency Boundaries」一節。
```

```callout info
新概念：預留與歸還
**先扣下（預留），付款成功才確定；團體付款失敗或退票時全數歸還。**
- 一般訂票付款失敗時，預留繼續保留，不歸還。
- 重複歸還也只算一次。
- 兩個請求同時扣同一份點數，合計不得超過餘額。

📖 定義出處：本課程〈需求卡 02：會員點數折抵〉。
```

```callout info
新概念：模型變更與重構
**改了程式不代表模型變了：逐項問名詞、負責的 Context、不變量或規則、邊界、事件或對外約定有沒有變。**
```
