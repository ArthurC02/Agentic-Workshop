# D3a：接入外部電子發票服務

```callout info
現在在做什麼
- **情境**：付款成功後要替訂單開立電子發票。發票由外部服務商開立，服務商可能逾時、拒絕或暫時連不上。
- **你們的目標**：25 分鐘內決定發票歸誰管、外部服務商擋在哪一道邊界後面，讓 Agent 照你們的決定實作，並證明每條新規則都有測試守著。
- **今天的技巧**：請 Agent 根據已審查（reviewed）的事實提出兩個選項與證據，由人選；選完寫成交接單（Handoff：交給 Agent 的決策紀錄），Agent 只照交接單做。
- **完成的樣子**：`docs/handoffs/d3a-e-invoice.md` 寫著你們的決定；`notes/d3a.md` 記著查到的事實、計畫、測試結果、反事實檢查結果與登記的候選；每條新規則都看到 `killed`。
```

這是 **25 分鐘的兩人**任務，延續 D2 的同一個 Repo（D1–D4 是今天四段的代號；D3 再分 a、b、c 三張需求卡，三段節奏相同）。你們不打指令、不讀程式：每個檢查點把一段提示詞複製給 Agent，看它的白話回報，再用一句短回覆做決定，例如「同意」「1A、2B」「第 3 條不要」。查到的事實、選項、決定與結果都由 Agent 寫進紀錄檔，你們不用抄。

```callout warning
Domain Memory：Agent 查，人決定登記什麼
Agent 可以執行唯讀查詢（`resolve-terms`、`get-context`、`analyze-boundary`）。新事實只能在你們回「同意」之後，由 Agent 用 `make_record.py` 登記為**候選**。Agent 永遠不可以執行 `record-approval`（記錄核准）或 `amend-policy`（修改審查政策），也不可以把任何記錄寫成 reviewed；候選要成為事實，必須像 D2 一樣由夥伴本人讀過審查包後核准並簽章。
```

```callout info

📖 延伸閱讀：Hohpe & Woolf《Enterprise Integration Patterns》〈Idempotent Receiver〉；學員包 `vendor/domain-memory/references/pattern-verification.md`〈Verification questions〉的 Failure 一題（重試、重複送達、逾時）。
```

## 檢查點 2 · 對外介面（Port）與邊界決策（第 73–78 分鐘）

```callout info
新概念：Port／Adapter 與防腐層（ACL）
Port 是領域程式需要的對外能力介面，用自己的業務用語描述（例如「開立發票」）；Adapter 是接上真實外部系統的實作（例如某家發票服務商），測試時可換成替身。把服務商的格式與錯誤碼翻成自己用語的那一層，叫防腐層（ACL，Anti-Corruption Layer；不是存取控制清單）。
📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 14 章〈Maintaining Model Integrity〉的 Anti-Corruption Layer 一節；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 4 章〈Architecture〉的 Hexagonal（Ports and Adapters）一節；學員包 `vendor/domain-memory/references/ports-and-adapters.md`。
```

```callout info
新概念：Owner Context 與不變量（Invariant）
D1 你學過 Context；這次多問一層：這個需求的資料與規則由**哪一個** Context 負責（Owner Context），其他 Context 只能透過約定取用。不變量是每次變更完成時都必須成立的業務規則（同一次操作中途可以暫時不成立，但操作結束時一定要成立），例如「一筆訂單最多一張已開立發票」；好的不變量可以寫成一個會失敗的測試，交接單裡從 INV-1 起編。
📖 延伸閱讀：Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 10 章〈Aggregates〉的「Rule: Model True Invariants in Consistency Boundaries」一節；學員包 `vendor/domain-memory/references/tactical-reasoning.md`。
```

這一步的技巧是**讓 Agent 帶著證據提選項，由人選**。Agent 很會列選項，但「誰負責、什麼永遠成立」是團隊要承擔的決定；有了證據，你們不讀程式也能判斷哪個選項站得住。

另外指出現有程式中會妨礙「發票失敗不影響付款」的地方，例如呼叫外部服務時是否還持有鎖、付款與其他寫入是否綁在一起，附檔案路徑:行號。
不要替我們選。列完停下，等我們回覆選擇。

我們回覆選擇後，依 D3 決策卡格式把決定寫成 docs/handoffs/d3a-e-invoice.md，段落依序是：需求卡（哪一張）、Domain facts（用到的已審查事實、只是候選的、查不到的）、Owner Context 與理由、不變量（INV-1 起編，每條對應 EINV 編號，都能寫成會失敗的測試）、邊界與協作（介面放哪一層、實作放哪一層、誰把 Order 翻成服務商格式、同步或事後觸發、禁止的依賴）、外部系統（服務商回應中領域程式必須分辨的結果）、Unknowns（需求卡沒規定的事，例如 PENDING 太久怎麼辦，寫「停下來問」或「本段不處理」，不要自己補值）、Proof obligations（每條驗收條件或不變量對應的測試）、這一段不做的事（需求卡「不在本期範圍」）。

## 檢查點 4 · 反事實檢查（第 85–89 分鐘）

測試全過，不代表測試守得住規則。D2 你用反事實檢查（counterfactual）證明過一條既有規則；這次多一層：**每一條新規則**都要各改壞一次，而且要改壞的是 Agent 剛寫的程式。`killed` 才算有測試守著，`survived` 代表這條規則沒人守；跑完 Plugin 會自動還原程式。

這一步的技巧是**先讓 Agent 列出「要改壞哪裡」，你們同意後才跑**，避免 Agent 挑一個容易過關的地方交差。

```text
不要修改任何程式。請針對交接單中每條新規則（至少 2 條），各列出：守住它的程式檔、該檔中只出現一次的一段原字串、把它改壞的替換字串、預期會失敗的測試檔。寫進 notes/d3a.md（標題「D3a 反事實檢查」），停下等我們回「同意」。

我們同意後，每條規則執行一次，存檔名依序 cf-d3a-1.json、cf-d3a-2.json…。指令如下，FILE、FIND、REPLACE、TEST 換成你列出的值，其餘照抄：

-W ignore::DeprecationWarning 關掉套件的過時警告：failing_evidence 只留輸出的最後一段，警告會把真正的失敗訊息擠出去。指令被拒絕執行、沒有產生 verdict 而要重跑時，先刪掉那次留下的 cf 檔再重跑，不要讓沒有結果的 cf 檔被 commit。

survived 時不要換一個比較容易 killed 的字串：提出要補的測試，停下等我們同意，補完用同一組字串重跑。如果你判斷沒有任何輸入分辨得出改壞前後（例如另一段程式也擋住，或輸入不可能落在那個邊界；這叫等價），不要硬補測試：指出原因所在的程式（檔案路徑:行號），說明為什麼分辨不出，停下等我們確認，記為「等價、未證明」。這次 survived 的 cf 檔有結果，要保留，會一起 commit。全部跑完再執行一次完整的 pytest -q。結果寫進 notes/d3a.md。
```
