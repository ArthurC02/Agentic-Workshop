# D3a：串接外部電子發票服務

```callout info
現在在做什麼
- **情境**：付款成功後要開電子發票；外部服務商可能逾時、拒絕或暫時連不上。
- **你們的目標**：25 分鐘內決定發票歸誰管、服務商擋在哪道邊界後；Agent 照做，每條新規則有測試守著。
- **今天的技巧**：Agent 依已審查事實提兩個選項與證據，人來選；寫成交接單（Handoff），Agent 只照它做。
- **完成的樣子**：`docs/handoffs/d3a-e-invoice.md` 寫著你們的決定；每條新規則都看到 `killed`。
```

兩人任務，延續 D2 的同一個 Repo，提示詞貼給提案者的 Agent 對話。

```callout tip
時間不夠時的最低完成線
**至少完成核心驗收條件，加上兩條新規則有 `killed` 的反事實檢查。**
- 核心：需求卡「本次範圍」的 EINV-001、002、003、005、006、007、008、009、010、011、015。
- 延伸（EINV-004、012、013、014）只在時間允許時做。
- 沒做延伸時，核心行為仍須完整，例如未提供發票資訊時一律開立一般個人發票。
- 來不及的請 Agent 在 `notes/d3a.md` 列為未完成，不要延長段落。
```

```text
請只檢查，不要修改任何檔案：
1. 執行 validate，結果是 Registry is valid.；新登記的紀錄都是 candidate，沒有 reviewed。
2. git log --show-signature -1 的訊息是「D3a：電子發票與候選事實」，有 Good "git" signature for maintainer@example.com。

全部符合只回「成功」，否則只回「失敗：」加一句原因。
```

失敗時（例如審查發現既有測試被放寬，貼到提案者的對話）：

```text
請把 tests 底下被放寬或刪除的斷言改回原樣，重跑 pytest -q，說明哪條規則因此失敗，然後停下等我們。
```

## 檢查點 6 · 停手與揭曉對照（第 92–95 分鐘）

① 為什麼做這一步

**停止擴充**。請 Agent 把你們的決定整理成幾行，對照投影上的參考設計。參考設計不是唯一正解，差異代表不同取捨；你們判斷每個差異是有理由的取捨，還是漏看或讓 Agent 補了沒決定的事。

② 貼給 Agent

```text
不要再修改任何程式。請從 docs/handoffs/d3a-e-invoice.md 與 notes/d3a.md 整理 5 行以內的摘要：負責的 Context、不變量、邊界（介面與實作各在哪一層）、外部服務商的結果分類、還沒完成或未證明的項目。寫進 notes/d3a.md（標題「D3a 揭曉對照」）並顯示給我們，然後停下。
```

③ 確認結果

```text
請只檢查，不要修改任何檔案：
1. notes/d3a.md 有「D3a 揭曉對照」，摘要不超過 5 行，涵蓋負責的 Context、不變量、邊界、外部服務商的結果分類、未完成或未證明的項目。
2. 程式與測試在夥伴的 D3a commit 之後沒有再被修改。
全部符合只回「成功」，否則只回「失敗：」加一句原因。
```

失敗時：

```text
不要修改程式。請只依 docs/handoffs/d3a-e-invoice.md 與 notes/d3a.md 重寫「D3a 揭曉對照」，每一項一行，查不到的寫「紀錄中沒有」，然後停下。
```
