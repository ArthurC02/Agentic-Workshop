# D1：共同語言與邊界

**目標**：從你親手選定的來源，建立有證據的 Context、詞彙與規則候選，並用 Plugin 查詢它們，親眼看到文件與程式說法不一致的地方。

這是 **25 分鐘的個人**任務，每個人在自己的 Repo 做。Agent 可以幫你找證據與行號，但**選哪些來源、哪些名詞算數、定義怎麼寫，由你決定**。這一段產生的全部都是候選（candidate），還不是事實。

```callout danger
D1 不要 commit domain-memory/
D2 要先由夥伴設定簽章，第一個包含 `domain-memory/` 的 commit 必須是簽章 commit；否則 D2 最後 push 會被拒絕。D1 結束時 `git status` 會看到 `domain-memory/`、`records/` 等未追蹤檔案，這是正確的，保持原狀。
```

| 檢查點 | 全場分鐘 | 你要完成的事 |
|---|---:|---|
| 1 · 人工選來源 | 10–13 | 看 `discover-sources`，在來源選擇表逐列決定 |
| 2 · 初始化與確認來源 | 13–17 | `init-domain-memory`、`confirm-sources` |

## 檢查點 1 · 人工選來源（第 10–13 分鐘）

- [ ] 在 Repo 根目錄列出候選來源（PowerShell 新視窗記得先 `Set-ExecutionPolicy -Scope Process Bypass -Force`）：

```cmd
# powershell
..\..\tools\dm.ps1 discover-sources
# bash
../../tools/dm.sh discover-sources
```

- [ ] 看 `source_groups`（Plugin 依資料夾名稱自動分的類）：哪些路徑被分到 `requirements`、`decisions`、`implementation`、`tests`？哪些沒有被分類？
- [ ] 打開 [D1 來源選擇表](#d1-source-selection)，逐列決定選或不選，寫一句理由。`docs/requirements/`、`docs/adr/`、`src/`、`tests/` 必選（`tests/` 底下之後只有 `test_*.py` 能當證據）；`**/__pycache__/**`（Python 自動產生的快取檔）必須排除。

```callout info
為什麼要人選
Plugin 只會依固定的資料夾名稱分類，它不知道哪份文件可信。只有你選進來的路徑能當證據；即使選了，Plugin 沒分類到的檔案（例如 `conftest.py`），引用它的證據之後也無法升為已審查（reviewed）。
```

## 檢查點 2 · 初始化與確認來源（第 13–17 分鐘）

- [ ] 依你的選擇初始化 Registry（若你另外選了檔案，在指令中多加一個 `--source <路徑>`），然後由你本人確認來源。參數依序表示：Registry 納入 Git 版控、資料等級為內部、先只存草稿（local-draft-only）、來源由誰確認：

```cmd
# powershell
..\..\tools\dm.ps1 init-domain-memory --output domain-memory --source docs/requirements --source docs/adr --source src --source tests --exclude "**/__pycache__/**" --storage-mode tracked --data-classification internal --review-mode local-draft-only --source-authority "DLC Proposer <proposer@example.com>"
..\..\tools\dm.ps1 confirm-sources --confirmed-by "DLC Proposer <proposer@example.com>"
..\..\tools\dm.ps1 verify-sources
# bash
../../tools/dm.sh init-domain-memory --output domain-memory --source docs/requirements --source docs/adr --source src --source tests --exclude "**/__pycache__/**" --storage-mode tracked --data-classification internal --review-mode local-draft-only --source-authority "DLC Proposer <proposer@example.com>"
../../tools/dm.sh confirm-sources --confirmed-by "DLC Proposer <proposer@example.com>"
../../tools/dm.sh verify-sources
```

**看到什麼算成功**：`init-domain-memory` 說明來源目前是 agent-asserted（Agent 自己認定、尚未經人確認）；`confirm-sources` 回 `Sources confirmed by DLC Proposer <proposer@example.com>: docs/adr, docs/requirements, src, tests`；`verify-sources` 的 `selection_status` 為 `developer-confirmed`（已由開發者確認）。Repo 裡多了 `domain-memory/`（policy、source map、registry、audit）。

```callout info
local-draft-only 是什麼意思
這個模式下 Registry 只能存候選，任何指令都無法把它升為 reviewed。要升級，必須先有一個 Plugin 自己無法偽造、要靠 Git 簽章才能證明的核准；這正是 D2 要做的事。
```

## 檢查點 3 · 詞彙候選（第 17–22 分鐘）

- [ ] 把下方提示詞貼給 Agent，讓它找候選名詞與證據行號：

```text
先不要修改任何檔案，也不要執行任何會寫入 domain-memory/ 的指令。
我們要為這個 Repo 建立通用語言（Ubiquitous Language）候選。請只讀 docs/requirements/、docs/adr/、src/、tests/：
1. 列出 8–10 個你認為是領域名詞的候選。每個附：文件中的說法、程式中的名稱、證據位置（路徑:起-迄，行號請實際打開檔案核對）。
2. 另外列出名稱不一致的地方：同一件事有兩個名字，或文件裡有、程式裡找不到對應的名詞。附兩邊的證據位置。
3. 不要替我們寫定義，也不要把不一致的名稱合併成一個。
列完就停下等我。
```

- [ ] 至少親自打開兩處證據核對行號。行號錯了，`cite`（依行號引用證據並記下內容雜湊）會引用到錯的內容。
- [ ] 在 [D1 模型畫布](#d1-model-canvas) 第 1 節記下名稱矛盾；第 3 節選 **≥ 5 個**詞彙，由你寫定義。
- [ ] 在 Repo 根目錄建立 `d1-records.json`，依畫布第 5 節的格式先寫入詞彙。先不登記，只試著產生 record（Registry 裡的一筆資料），確認每段證據都能 `cite`：

```cmd
# powershell
py -3.13 -X utf8 ..\..\tools\make_record.py --batch d1-records.json
# bash
py -3.13 -X utf8 ../../tools/make_record.py --batch d1-records.json
```

**看到什麼算成功**：每一筆都印出 `已寫出 records\vocabulary-<id>.json（N 個證據）`。若出現「不在已確認來源內」，表示證據路徑不在你選的來源裡。只能引用 `docs/requirements/`、`docs/adr/`、`src/`，以及 `tests/` 底下的 `test_*.py`；`conftest.py`、`docs/architecture.md` 這類檔案會被拒絕，因為它們的證據之後無法升為 reviewed。

```callout tip
存檔編碼
用編輯器或 Agent 存成 UTF-8 即可。PowerShell 5.1 的 `>` 會存成 UTF-16，`make_record.py` 也讀得懂，但建議不要用 `>` 產生 JSON。
```

## 檢查點 4 · Context 與規則候選（第 22–27 分鐘）

- [ ] 在畫布第 2、4 節決定 **≥ 2 個 Context**（各自決定什麼）與 **≥ 2 條規則**（沿用文件的規則編號，寫成一句能用測試驗證對錯的話，證據含規則文件與測試或程式）。
- [ ] 把 Context 加到 `d1-records.json` 的**最前面**，規則加在最後（規則會引用 Context，所以 Context 要先登記），然後一次登記為候選，並驗證：

```cmd
# powershell
py -3.13 -X utf8 ..\..\tools\make_record.py --batch d1-records.json --upsert
..\..\tools\dm.ps1 validate
..\..\tools\dm.ps1 verify-evidence
# bash
py -3.13 -X utf8 ../../tools/make_record.py --batch d1-records.json --upsert
../../tools/dm.sh validate
../../tools/dm.sh verify-evidence
```

**看到什麼算成功**：每一筆都有 `upsert-candidate ... → Candidate record updated.`；`validate` 回 `Registry is valid.`；`verify-evidence` 的 `summary` 中 `current` 等於你的證據總數，過期（stale）、不存在（missing）、格式錯誤（invalid）都是 0。

```callout warning
出現「檔名或副檔名太長」
表示 Repo 放在太深的資料夾。請依開場的指示改放到 `C:\dlc`，重新從檢查點 2 做起；不要嘗試手動修改 `domain-memory/` 底下的檔案。
```

## 檢查點 5 · 找缺口與查詞（第 27–31 分鐘）

- [ ] 看哪些 Context 還沒有詞彙、Aggregate、規則或 Contract（Context 之間約定交換的資料或介面）；再用**一整句話**查詢詞彙。`resolve-terms` 只比對詞彙的名稱、id 與定義（不比對同義詞 synonyms），所以句子裡要包含某個詞彙的**完整名稱**；把引號內換成含你登記名稱的問題：

```cmd
# powershell
..\..\tools\dm.ps1 coverage
..\..\tools\dm.ps1 resolve-terms --query "團體訂票付款失敗時，座位與訂票會怎樣"
# bash
../../tools/dm.sh coverage
../../tools/dm.sh resolve-terms --query "團體訂票付款失敗時，座位與訂票會怎樣"
```

- [ ] `resolve-terms` 回 `[]` 不代表「沒有這回事」，只代表 Registry 還不知道，或句子裡沒有詞彙的完整名稱。記下一個查不到、但你認為重要的名詞。

## 檢查點 6 · 查 Context 與檢查越界（第 31–35 分鐘）

- [ ] 把 `〈 〉` 換成你登記的 Context id，看一個 Context 的全貌，再分析兩個**不同** Context 之間的邊界。`analyze-boundary` 有方向：`--source-context` 是提供資料或能力的一方（producer），`--target-context` 是使用的一方；方向反了會得到 `no_registered_collaboration`：

```cmd
# powershell
..\..\tools\dm.ps1 get-context --id 〈context id〉
..\..\tools\dm.ps1 analyze-boundary --source-context 〈context id A〉 --target-context 〈context id B〉
# bash
../../tools/dm.sh get-context --id 〈context id〉
../../tools/dm.sh analyze-boundary --source-context 〈context id A〉 --target-context 〈context id B〉
```

- [ ] `get-context` 開頭的 `"usage": "working-memory"` 表示這些都還是候選，只能當工作參考。`analyze-boundary` 回 `no_registered_collaboration`：兩個 Context 之間沒有登記任何協作。對照程式，它們實際上有沒有直接讀寫對方的資料？那就是邊界洩漏（一個 Context 繞過約定，直接讀寫另一個 Context 的資料）。
- [ ] 時間到停止新增候選。確認 `git status` 中 `domain-memory/` 仍是未追蹤（不要 commit）。
