# D1：共同語言與邊界

```callout info
現在在做什麼
- **情境**：領域知識散在文件、ADR、程式與測試，說法不一；Agent 每次從零開始猜。
- **你的目標**：29 分鐘內和 Agent 整理出共同語言與邊界：詞彙至少 5 個、Context 至少 2 個、規則至少 2 條，並找出名稱矛盾與邊界洩漏。
- **今天的技巧**：Agent 找證據、人來定義。每份草稿附證據（路徑:起-迄行），你看完回一句話決定；決定寫回 `AGENTS.md`，下一個 Agent 也照著用。
- **完成的樣子**：`notes/d1.md` 有你的決定與理由；`AGENTS.md` 多了你們的名詞與邊界決定；Agent 回報每段證據都還對得上原文。
```

個人任務，沿用開場的 Agent 對話。開了新對話，Agent 會自己讀 `AGENTS.md`。

```callout warning
D1 不要叫 Agent commit
**共用模型第一次進版本紀錄，要等 D2 夥伴核准。** 結束時看到未追蹤的 `domain-memory/` 是正確的。
```

## 檢查點 1 · 決定哪些資料算證據（第 14–18 分鐘）

① 為什麼做這一步

共用模型的每句話都要指得回原文，所以先決定哪些資料算數（來源）。Agent 列出每個路徑的建議與理由，你看理由決定：需求、ADR、程式、測試四類要選，其餘選或不選都要有一句理由。

② 貼給 Agent

```text
D1 開始。先決定哪些資料算共用模型的證據（來源）：跑 dm discover-sources（唯讀），每個候選路徑一行（Plugin 沒列到的 docs/ 與根目錄 .md 也列），寫出 Plugin 的分類（沒分類寫「未分類」）、你建議選或不選、一句理由，並說明它描述的是「應該怎樣」（規則）、「決定了什麼」（ADR），還是「現在實際怎樣」（程式、測試）。還不要建立 domain-memory/。
列完停下等我決定；我回覆後把來源決定記在 notes/d1.md，確認人是 DLC Proposer <proposer@example.com>，記好後用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：還沒有 domain-memory/。
```

失敗時：

```text
先停，不要寫入 domain-memory/。「來源決定」缺了哪一項？重新列給我確認，等我回「同意」再補進 notes/d1.md。
```

## 檢查點 2 · 建立共用模型並記下來源（第 18–21 分鐘）

① 為什麼做這一步

Agent 依你的來源決定建立共用模型，並記下是你確認的。從這裡開始，Agent 寫進模型的每一句都要附證據，而且只算草稿。

② 貼給 Agent

```text
照 notes/d1.md 的來源決定建立 Domain Memory，並記下來源是我確認的（我另外選的路徑，各多加一個 --source）：
dm init-domain-memory --output domain-memory --source docs/requirements --source docs/adr --source src --source tests --exclude "**/__pycache__/**" --storage-mode tracked --data-classification internal --review-mode local-draft-only --source-authority "DLC Proposer <proposer@example.com>"
dm confirm-sources --confirmed-by "DLC Proposer <proposer@example.com>"
dm verify-sources
告訴我確認了哪些路徑、verify-sources 的 selection_status 和 status，記在 notes/d1.md。domain-memory/ 先不要 commit。做完用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：來源是 developer-confirmed（已由人確認），domain-memory/ 還沒 commit。
```

失敗時：

```text
先停，不要手動改 domain-memory/。哪一個指令失敗？錯誤訊息是什麼意思？你建議怎麼做？等我同意再做。
```

④ 補充

```callout info
新概念：候選（candidate）
**Agent 寫進模型的每一句都是候選：附了證據的主張，還不是事實。**
- 證據寫成「路徑:起-迄」；原文之後被改，Agent 會回報對不上。
- 只有夥伴審查核准後（D2），候選才成為 Agent 必須遵守的事實。
- 每筆存成一份人讀得懂的文件：只放這件事本身、它和其他紀錄的關係、證據；怎麼找到的、有多少把握、待辦，都不寫進去。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/evidence-rules.md`、`vendor/domain-memory/references/extraction.md`。
```

## 檢查點 3 · 統一名詞：通用語言（第 21–28 分鐘）

① 為什麼做這一步

先統一名詞，再劃邊界：名詞錯了，之後每一筆紀錄都跟著錯。Agent 先列名稱矛盾與詞彙草稿，不自己「修好」矛盾；同一個字在兩處意思不同，是兩個 Context 的訊號，記成兩個詞還是先不建模由你決定。
- 挑一個詞，看 Agent 摘錄的證據原文是不是真的在說這件事
- 再回**一行**決定，例如「採用 1,2,3,5,6；矛盾 A 選 1；4 的定義改成…」

② 貼給 Agent

```text
接著整理通用語言（Ubiquitous Language，團隊共用的名詞定義），先不寫入 domain-memory/：
1. 從已確認的來源找出名稱不一致的地方，最多 3 處，標 A、B…，兩邊都附證據：同一件事有兩個名字、同一個字在兩處意思不同（標「邊界訊號」，劃 Context 時要用），或文件有、程式找不到。每處給我 2–3 個編號的處理選項和理由。不要把不一致的名稱合併，也不要替程式補不存在的東西。
2. 再列 5–6 個領域名詞候選：id、名稱、一句寫錯就能被文件或程式指出來的定義、暫定的 context、證據，加一行原文摘錄。
列完停下，我用一行回覆，例如「採用 1,2,3,5,6；矛盾 A 選 1」。之後照 record-candidates 先試產生、不登記，把採用的詞彙、沒採用的理由、不一致和我們的處理記在 notes/d1.md。做完用 check 檢查，最後一行寫成功或失敗。
```

Agent 列候選時，先讀下方 ④ 的通用語言小卡，想好怎麼判斷兩個名稱是不是同一件事。

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：至少記了一處名稱不一致和我們的處理，至少 5 筆詞彙都試產生成功。
```

失敗時（例如出現「不在已確認來源內」或行號錯誤）：

```text
先停，不要改 domain-memory/。make_record.py 的錯誤是什麼意思？照 record-candidates 的「失敗時」列出你要改的地方，等我同意再改。
```

④ 補充

```callout info
新概念：通用語言（Ubiquitous Language）
**同一個 Context 內，同一件事只用一個名字、一個定義。**
- 範圍：團隊的說法、文件、程式與測試都算。
- 怎麼發現：同一件事有兩個名字、同一個字有兩種意思，或文件有、程式沒有。
- 同一個字有兩種意思，常代表兩個 Context：先記成兩個詞，檢查點 4 再定邊界。
- 你要做的：記成發現，不要偷偷修掉。

📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 2 章〈Communication and the Use of Language〉；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 1 章〈Getting Started with DDD〉。
```

## 檢查點 4 · 劃分 Context，寫下規則（第 28–35 分鐘）

① 為什麼做這一步

Context 要多個訊號一致才劃：用語改變、資料只在一處寫入、程式一起修改、別人只透過明確的介面呼叫；資料夾名稱本身不算。規則是一句能被測試推翻的敘述，不是測試名稱。
- 每條規則有兩段證據：文件一段、測試或程式一段；你看過再決定採用哪些，文件有、程式沒做的列為缺口
- 登記後打開 Agent 指出的一份規則紀錄，看它是否只有敘述、關係與證據（檔案開頭的 draft 就是候選）

② 貼給 Agent

```text
再劃 Context、寫規則，先不寫入：
1. 提 2–4 個 Context（涵蓋詞彙用到的 context id）：id、名稱、一句「它決定什麼」、證據，並標出有哪幾種訊號：用語改變、資料只在這裡寫入、程式一起修改、別人只透過明確的介面呼叫它。只有一種的標「證據薄弱」；查不到一起修改的歷史就寫「無歷史」，不要猜。資料夾名稱不算證據：這個 Repo 依技術分層，Context 散在各層。
2. 提 2–3 條規則：沿用文件的規則編號，一句能被測試推翻的敘述（不是測試名稱、記錄訊息或願望），標出所屬 Context，證據要有規則文件一段、加上測試或程式一段。文件有、程式找不到的不寫成規則，列為缺口。
列完停下等我決定。我回覆後照 record-candidates 把 Context、詞彙、規則一起登記成候選，採用與沒採用的理由、缺口記在 notes/d1.md。再告訴我其中一條規則存在 domain-memory/ 的哪個檔案，我自己打開看。不要 commit。做完用 check 檢查，最後一行寫成功或失敗。
```

Agent 列候選時，先讀下方 ④ 的 Bounded Context 小卡，想好你要用什麼標準挑。

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：至少 2 個 Context、2 條規則，全部是候選；validate 通過，證據全部 current。
```

失敗時：

```text
先停，不要手動改 domain-memory/。是哪一筆登記失敗，或哪一段證據不是 current？原因是什麼？列出你要改的 d1-records.json 內容，等我同意再重跑。
```

④ 補充

```callout info
新概念：Bounded Context（限界上下文，簡稱 Context）
**一個模型適用的明確範圍：在範圍內，同一個名詞或規則只有一種意思。**
- 每個 Context 寫一句「它決定什麼」。
- 多個訊號一致才劃：用語改變、資料只在一處寫入、一起修改、只透過明確介面呼叫。
- 資料夾不是證據：這個 Repo 依技術分層放，每一層都橫跨好幾個 Context。

📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 14 章〈Maintaining Model Integrity〉的 Bounded Context 一節；Martin Fowler〈BoundedContext〉（2014）；學員包 `vendor/domain-memory/references/extraction.md`。
```

## 檢查點 5 · 用客人的話找出模型缺口（第 35–39 分鐘）

① 為什麼做這一步

用旅客或客服會說的一句話問模型：查得到，代表通用語言接得上日常說法；查不到，就是模型還不知道的缺口。Agent 列出缺口與證據，你挑一個記下；名稱查得到但意思不對，也是缺口。缺口只寫進筆記，不寫進模型：模型只放元素、關係與證據，還沒解決的問題到 D2 寫進提案的「開放問題」。

② 貼給 Agent

```text
用客人的話找模型缺口，不改 domain-memory/：
1. 跑 dm coverage，告訴我哪些 Context 還沒有詞彙、規則、Aggregate 或 Contract（Context 之間約定交換的資料或介面）。英文 NOTE 說還沒有 Change Package 是正常的。
2. 設計兩句旅客或客服會說的話：第一句含一個已登記詞彙的完整名稱，第二句講一個重要、但模型可能還沒有的概念。各跑一次 dm resolve-terms --query "句子"，告訴我命中哪些詞彙、match_kind、屬於哪個 Context、是不是句子說的意思。
3. 再列 1–3 個查不到、但你認為重要的名詞，附證據。
停下等我選一個缺口；選好後把 coverage 摘要、兩句查詢和結果、我選的缺口記在 notes/d1.md。做完用 check 檢查，最後一行寫成功或失敗。
```

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：第一句以名稱命中（match_kind 是 name）而且意思對；第二句的結果和我選的缺口都記下了。
```

失敗時：

```text
先停，不要改 domain-memory/。用 dm export --save ../../tmp/registry.json 列出已登記的詞彙名稱（不要整份讀進對話），挑一個放進第一句、句子說的就是那個意思，重跑 resolve-terms，回報命中結果後停下。
```

## 檢查點 6 · 對照程式判斷邊界洩漏（第 39–43 分鐘）

① 為什麼做這一步

模型目前沒有記錄 Context 之間的任何協作；Agent 對照程式，列出一個 Context 直接讀寫另一個資料的地方。算不算邊界洩漏，由你看證據判斷；你的判斷和名詞決定寫進 `AGENTS.md`，之後每個 Agent 都會照著做。時間到就停止新增。

② 貼給 Agent

```text
最後看邊界，不改程式或 domain-memory/：
1. 挑一個 Context 跑 dm get-context --id 那個id，用一句話說它有幾個詞彙、規則、Aggregate，以及開頭 "usage" 的值代表什麼。
2. 挑兩個 Context 跑 dm analyze-boundary --source-context 第一個id --target-context 第二個id。D1 還沒登記協作，重點是對照程式：實際上誰依賴誰、有沒有直接讀寫對方的資料？列出地方和證據，說明你認為算不算邊界洩漏、為什麼。
停下等我判斷。我回覆後把我的判斷和 D1 總結（詞彙、Context、規則各幾個，validate 與 verify-evidence 結果）記在 notes/d1.md，並在 AGENTS.md「通用語言與邊界」各用一行寫下我們的名詞處理和邊界判斷（附出處）。不要 commit。做完用 check 檢查，最後一行寫成功或失敗。
```

Agent 對照程式時，先讀下方 ④ 的邊界洩漏小卡，想好你判斷「算不算洩漏」的標準。你回覆判斷後，它寫完紀錄會自己檢查。

③ 確認結果

回報最後一行已是成功就不用再貼；沒有才貼：

```text
用 check 檢查剛才這一段：每筆紀錄都還是候選，domain-memory/ 仍未追蹤；AGENTS.md 多了我們的名詞與邊界決定。
```

失敗時：

```text
先停，不要改程式或 domain-memory/。哪一項不符？如果 domain-memory/ 已經被 commit，只告訴我是哪個 commit，不要自己還原，等我找主持人。
```

④ 補充

```callout info
新概念・加深一層：Bounded Context 的邊界洩漏
**一個 Context 繞過約定，直接讀寫另一個 Context 的資料或內部程式。**
- 怎麼發現：模型說「沒有協作」，程式卻直接讀寫對方的資料。
- 這只是可疑處；算不算洩漏，由你看證據判斷。
- 把「誰依賴誰」畫出來（上游的改變會影響下游；常見的是下游呼叫上游提供的資料或服務），就是 Context Map；`analyze-boundary` 一次回報兩個方向。

📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 14 章〈Maintaining Model Integrity〉的 Context Map 一節；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 3 章〈Context Maps〉。
```
