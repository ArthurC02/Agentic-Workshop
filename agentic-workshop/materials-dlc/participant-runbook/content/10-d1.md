# D1：共同語言與邊界

```callout info
現在在做什麼
- **情境**：Smart Ticket 的領域知識散在需求文件、ADR、程式與測試裡，而且彼此說法不一定一致。Agent 每次對話都從零開始，只能猜。
- **你的目標**：25 分鐘內，從你決定的來源建立有證據的詞彙（≥5）、Context（≥2）與規則（≥2）候選，用 Plugin 查詢它們，並親眼看到文件與程式說法不一致、Context 互相越界的地方。
- **今天的技巧**：讓 Agent 找證據、人來定義：建立共同語言。Agent 負責翻檔案、找行號、提草稿；哪些來源可信、哪些名詞算數、定義怎麼寫，由你回一句話決定。每個草稿都要附「路徑:起-迄」證據，你才判斷得了。
- **完成的樣子**：`notes/d1.md` 有 Agent 寫的來源決定、採用與不採用的候選和理由、缺口與邊界判斷；`validate` 通過、證據全部 current；`domain-memory/` 尚未 commit。
```

這是 **25 分鐘的個人**任務，每個人用自己的 Agent、在自己的 Repo 做。沿用開場的 Agent 對話；如果開了新對話，先重貼 [開場與環境](#environment) 的工作規則。這一段產生的全部都是候選（candidate），還不是事實。

```callout danger
D1 不要 commit domain-memory/
D2 要先由夥伴設定簽章，第一個包含 `domain-memory/` 的 commit 必須是簽章 commit；否則 D2 最後 push 會被拒絕。D1 結束時 `git status` 會看到 `domain-memory/`、`records/`、`d1-records.json`、`notes/d1.md` 等未追蹤檔案，這是正確的，保持原狀。
```

## 檢查點總覽

時間是**最晚**完成的時間；提早完成就直接進入下一個。

- **檢查點 1 · 人工選來源（10–13）**：Agent 列出候選來源與建議，你決定選哪些。
- **檢查點 2 · 初始化與確認來源（13–17）**：Agent 依你的決定初始化 Domain Memory，並確認來源。
- **檢查點 3 · 詞彙候選（17–22）**：Agent 找名稱矛盾與詞彙草稿，你決定 ≥5 個詞彙與定義。
- **檢查點 4 · Context 與規則候選（22–27）**：Agent 提 Context 與規則草稿，你決定後一次登記為候選並驗證。
- **檢查點 5 · 找缺口與查詞（27–31）**：Agent 找出缺口、用一句話查詞彙，你選一個要記下的缺口。
- **檢查點 6 · 查 Context 與檢查越界（31–35）**：Agent 看一個 Context 的全貌、分析兩個 Context 的邊界，你判斷有沒有越界。

## 檢查點 1 · 人工選來源（第 10–13 分鐘）

Plugin 只會依固定的資料夾名稱分類（輸出裡的 `source_groups`），它不知道哪份文件可信。只有你選進來的路徑（來源，source）能當證據，所以這一步由 Agent 列出建議，**由你決定**。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/seven-step-workflow.md`〈Before Step 0: Map repository sources〉（Plugin 自帶）。

```text
現在開始 D1。先不要寫入任何檔案，也不要執行會建立 domain-memory/ 的指令。
1. 執行唯讀的來源探索：
   PowerShell：..\..\tools\dm.ps1 discover-sources
   bash：../../tools/dm.sh discover-sources
2. 根據輸出的 source_groups（Plugin 依資料夾名稱自動分的類），用簡短清單列出每個候選路徑：Plugin 的分類（沒分類就寫「未分類」）、你建議「選」或「不選」、一句理由。依下列原則建議：
   - docs/requirements/、docs/adr/、src/、tests/ 必選（tests/ 底下之後只有 test_*.py 能當證據）。
   - 未分類的檔案（例如 docs/architecture.md、docs/api-examples.md、docs/version-history.md、README.md、notes/）建議不選：即使選入，引用它們的證據之後也無法升為已審查（reviewed）。
   - 排除規則固定為 **/__pycache__/**（測試執行後產生的快取檔，內容每次都會變）；.venv/ 不是來源。
3. 說明每份來源描述的是「應該怎樣」（規則）、「決定了什麼」（ADR），還是「現在實際怎樣」（程式、測試）。
列完就停下，等我回覆「同意」或要改哪一項。我回覆後，把最後選入的路徑、排除規則、沒選的路徑與理由寫進 notes/d1.md（標題「來源決定」，確認人為 DLC Proposer <proposer@example.com>），然後停下。
```

**看到什麼算過關**：

- Agent 的清單裡 `docs/requirements/`、`docs/adr/`、`src/`、`tests/` 為「選」，`**/__pycache__/**` 為排除規則，每個未分類檔案都有一句不選（或選）的理由。
- 你回覆後，`notes/d1.md` 有「來源決定」。

```callout tip
💬 討論一下
需求文件、ADR 與程式說法衝突時，你們要相信哪一個？（提示：Domain Memory 要的是把衝突記下來，不是挑一個相信。）
```

## 檢查點 2 · 初始化與確認來源（第 13–17 分鐘）

`confirm-sources` 是「人確認過來源」的紀錄：你在檢查點 1 回覆同意，Agent 才以你的練習身分執行它。參數依序表示：Registry 納入 Git 版控、資料等級為內部、先只存草稿（local-draft-only）、來源由誰確認。

```text
依 notes/d1.md「來源決定」初始化 Domain Memory，並確認來源。如果我另外選了其他路徑，每一個在 init-domain-memory 多加一個 --source 路徑；沒有就照原樣執行：
PowerShell：
  ..\..\tools\dm.ps1 init-domain-memory --output domain-memory --source docs/requirements --source docs/adr --source src --source tests --exclude "**/__pycache__/**" --storage-mode tracked --data-classification internal --review-mode local-draft-only --source-authority "DLC Proposer <proposer@example.com>"
  ..\..\tools\dm.ps1 confirm-sources --confirmed-by "DLC Proposer <proposer@example.com>"
  ..\..\tools\dm.ps1 verify-sources
bash：
  ../../tools/dm.sh init-domain-memory --output domain-memory --source docs/requirements --source docs/adr --source src --source tests --exclude "**/__pycache__/**" --storage-mode tracked --data-classification internal --review-mode local-draft-only --source-authority "DLC Proposer <proposer@example.com>"
  ../../tools/dm.sh confirm-sources --confirmed-by "DLC Proposer <proposer@example.com>"
  ../../tools/dm.sh verify-sources
用白話告訴我：init 之後來源是什麼狀態、confirm-sources 確認了哪些路徑、verify-sources 的 selection_status 與 status。不要 git add 或 commit domain-memory/。把這三個指令的關鍵輸出原文寫進 notes/d1.md（標題「初始化與確認來源」），做完停下等我。
```

**看到什麼算過關**：

- `init-domain-memory` 說明來源目前是 agent-asserted（Agent 自己認定、尚未經人確認）。
- `confirm-sources` 回 `Sources confirmed by DLC Proposer <proposer@example.com>: docs/adr, docs/requirements, src, tests`。
- `verify-sources` 的 `selection_status` 為 `developer-confirmed`（已由開發者確認），Repo 裡多了 `domain-memory/`（policy、source map、registry、audit）。

```callout info
新概念：Domain Memory（Registry）與「只存草稿」模式
`domain-memory/` 就是今天的 Domain Memory，也叫 Registry：一組 JSON 檔，包含審查政策（policy）、人確認過的來源清單（source map）、一筆筆紀錄（registry）與稽核紀錄（audit）。現在的審查模式是 local-draft-only（只存草稿）：只能存候選，任何指令都無法把它升為已審查（reviewed）；要升級，必須先有 Plugin 自己無法偽造、要靠 Git 簽章才能證明的核准，這是 D2 的事。
📖 延伸閱讀：學員包 `vendor/domain-memory/references/registry-schema.md`（Plugin 自帶，Registry 的組成）。
```

## 檢查點 3 · 詞彙候選（第 17–22 分鐘）

這一步最能看出「Agent 找證據、人來定義」：Agent 先找名稱矛盾、提詞彙草稿並摘錄證據原文；你挑選、修改定義、決定矛盾怎麼處理。名稱矛盾是 Domain Memory 最有價值的地方，所以要 Agent 先列矛盾、不要自己「修好」。草稿裡的 context id 只是暫定名稱：Context 是什麼、要分幾個，檢查點 4 才介紹與定案，這裡先看詞彙與定義就好。

Agent 列完後，你回**一行**就好，例如「採用 1,2,4,5,7；矛盾 A 選 1」；要改定義就在同一行加「4 的定義改成…」。

```callout info
新概念：通用語言（Ubiquitous Language）
團隊、文件、程式與測試對同一件事用同一個名字與定義。今天它以 Registry 的詞彙（vocabulary）記錄；同一件事兩個名字、或文件有而程式沒有，都是要記下的發現，不是要偷偷修掉的錯。
📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 2 章〈Communication and the Use of Language〉；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 1 章〈Getting Started with DDD〉。
```

```callout info
新概念：證據（cite）與候選（candidate）
每一筆紀錄都要附「路徑:起-迄」證據。`cite` 會記下那幾行內容的 SHA256 雜湊；之後 `verify-evidence` 重算一次：仍一致是 current，內容改過是 stale（過期），檔案不在了是 missing（不存在），寫法不對是 invalid（格式錯誤）。登記進去的一律是候選：有證據的主張，還不是事實。
📖 延伸閱讀：學員包 `vendor/domain-memory/references/evidence-rules.md`（Plugin 自帶）。
```

```text
先不要執行任何會寫入 domain-memory/ 的指令。我們要建立通用語言（Ubiquitous Language，團隊共用的名詞定義）的候選。只讀 docs/requirements/、docs/adr/、src/，以及 tests/ 底下的 test_*.py：
1. 先列出名稱不一致的地方：同一件事有兩個名字，或文件裡有、程式裡找不到對應的名詞。每處依序標 A、B…，附兩邊的證據（路徑:起-迄）。不要把不一致的名稱合併成一個，也不要替程式補上不存在的東西。每處給我 2–3 個編號的處理選項（例如：1 記成兩個詞並互標 not_same_as、2 記成同一個詞的別名 synonyms、3 先記為未知不建模），說明各自的理由。
2. 再用編號清單列出 6–8 個領域名詞候選。每個附：建議的 id（小寫英文加連字號）、名稱、一句定義草稿（寫錯就能被文件或程式指出來的明確說法）、暫定所屬的 context id（檢查點 4 才定案）、證據（路徑:起-迄，行號請實際打開檔案核對），以及證據那幾行的原文摘錄。
列完就停下。我會用一行回覆採用哪幾個（至少 5 個）、哪些定義要改、每個不一致選哪個處理方式，例如「採用 1,2,4,5,7；矛盾 A 選 1」。
收到我的決定後：
3. 在 Repo 根目錄建立 d1-records.json（UTF-8；不要用 PowerShell 的 > 產生），寫入我採用的詞彙，每筆一個物件：
   {"asset": "vocabulary", "id": "詞彙 id", "name": "名稱", "definition": "定義", "context": "context id", "evidence": ["路徑:起-迄"]}
   一個詞跨兩個 Context 時寫 "context": ["id1", "id2"]；我選了別名或「不是同一件事」時，加 "synonyms": ["別名"] 或 "not_same_as": ["另一個詞彙 id"]。證據段落越短越好，只框住支持這句話的那幾行。
4. 先不登記，只試著產生 record（Registry 裡的一筆資料），確認每段證據都能 cite（依行號引用證據並記下內容雜湊）：
   PowerShell：py -3.13 -X utf8 ..\..\tools\make_record.py --batch d1-records.json
   bash：py -3.13 -X utf8 ../../tools/make_record.py --batch d1-records.json
5. 用白話告訴我每一筆的結果。把採用的詞彙與定義、沒採用的候選與理由、名稱矛盾與我們的處理寫進 notes/d1.md（標題「詞彙」）。做完停下等我。
```

**看到什麼算過關**：

- Agent 列出至少一處名稱矛盾，兩邊都有證據；你選了處理方式。
- 每一筆都印出 `已寫出 records\vocabulary-<id>.json（N 個證據）`，共 ≥5 筆。
- 挑一個詞，看 Agent 摘錄的證據原文是不是真的在說這件事。

**如果卡住**（出現「不在已確認來源內」或行號錯誤）：

```text
不要修改 domain-memory/。請用白話解釋 make_record.py 的錯誤。如果是證據不在已確認來源內，改引用 docs/requirements/、docs/adr/、src/ 或 tests/ 底下的 test_*.py（conftest.py、docs/architecture.md 這類檔案會被拒絕，因為它們的證據之後無法升為 reviewed）；如果是行號不對，重新打開檔案核對。列出你要改的地方，等我同意再改。
```

## 檢查點 4 · Context 與規則候選（第 22–27 分鐘）

同樣由 Agent 提草稿與證據，你決定採用哪些，Agent 再一次登記成候選並驗證。規則要寫成能被測試推翻的一句話。

```callout info
新概念：Bounded Context（限界上下文，簡稱 Context）
一個名詞或規則「在這個範圍內意思一致」的邊界，通常對應一群負責同一類決定的程式。每個 Context 寫一句「它決定什麼」。上一步的詞彙，現在要各自歸到一個 Context。
📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 14 章〈Maintaining Model Integrity〉的 Bounded Context 一節；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 2 章〈Domains, Subdomains, and Bounded Contexts〉。
```

```text
接著建立 Context 與規則候選。先不要寫入檔案：
1. 提議 2–3 個 Context：建議 id（小寫英文加連字號）、名稱、一句話職責（它決定什麼）、證據（路徑:起-迄）。檢查點 3 詞彙用的 context id 是暫定的，要被這裡的 Context 涵蓋；我改了 Context id 時，同步更新 d1-records.json 裡詞彙的 context。
2. 提議 2–4 條規則：id 沿用文件裡的規則編號，敘述寫成一句能被測試推翻的話，標出所屬 Context，證據至少兩段：規則文件一段，加上測試或程式一段。文件有、程式找不到的概念不要寫成規則，列為缺口。
列完就停下，等我回覆採用哪些、要怎麼改。
收到我的決定後：
3. 把 Context 加到 d1-records.json 的最前面、規則加在最後（詞彙與規則會參照 Context，所以 Context 要先登記）：
   {"asset": "contexts", "id": "context id", "name": "名稱", "responsibility": "職責", "evidence": ["路徑:起-迄"]}
   {"asset": "rules", "id": "規則 id", "statement": "敘述", "context": "context id", "evidence": ["路徑:起-迄", "路徑:起-迄"]}
4. 一次登記為候選並驗證：
   PowerShell：
     py -3.13 -X utf8 ..\..\tools\make_record.py --batch d1-records.json --upsert
     ..\..\tools\dm.ps1 validate
     ..\..\tools\dm.ps1 verify-evidence
   bash：
     py -3.13 -X utf8 ../../tools/make_record.py --batch d1-records.json --upsert
     ../../tools/dm.sh validate
     ../../tools/dm.sh verify-evidence
5. 用白話告訴我：每一筆是否成功登記、validate 的結果、verify-evidence 的 summary（current、stale、missing、invalid 各幾個）。把採用的 Context 與規則、沒採用的與理由、找到的缺口寫進 notes/d1.md（標題「Context 與規則」）。不要 commit。做完停下等我。
```

**看到什麼算過關**：

- 每一筆都有 `upsert-candidate ... → Candidate record updated.`。
- `validate` 回 `Registry is valid.`。
- `verify-evidence` 的 `current` 等於證據總數，過期（stale）、不存在（missing）、格式錯誤（invalid）都是 0。

## 檢查點 5 · 找缺口與查詞（第 27–31 分鐘）

`coverage` 告訴你哪裡還沒建模；`resolve-terms` 用一句人話查詞彙，看 Plugin 能不能把日常說法對到通用語言。查不到不是錯，而是 Registry 還不知道的地方。coverage 的報告也會提到 Aggregate：那是 D3c 才用到的概念，現在每個 Context 都「沒有 Aggregate」是正常的。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/script-api.md`（Plugin 自帶，每個指令做什麼、輸出什麼）。

```text
請找出 Registry 的缺口，並用一整句話查詞彙，不要修改 domain-memory/：
1. 執行 coverage：
   PowerShell：..\..\tools\dm.ps1 coverage
   bash：../../tools/dm.sh coverage
   用白話告訴我：哪些 Context 還沒有詞彙、Aggregate、規則或 Contract（Context 之間約定交換的資料或介面）。
2. 設計兩句旅客或客服會說的話：第一句包含我們已登記的某個詞彙的完整名稱；第二句描述一個重要、但 Registry 可能還沒有的概念。分別執行（把引號內換成你設計的句子）：
   PowerShell：..\..\tools\dm.ps1 resolve-terms --query "團體訂票付款失敗時，座位與訂票會怎樣"
   bash：../../tools/dm.sh resolve-terms --query "團體訂票付款失敗時，座位與訂票會怎樣"
   resolve-terms 只比對詞彙的名稱、id 與定義，不比對同義詞（synonyms），所以句子裡要有完整名稱才會命中。
3. 告訴我兩句各命中哪些詞彙。回 [] 不代表沒有這回事，只代表 Registry 還不知道，或句子裡沒有詞彙的完整名稱。再列出 1–3 個你認為重要、但 Registry 查不到的名詞，附證據。
停下等我選一個要記下的缺口。我回覆後，把 coverage 摘要、兩句查詢與結果、我選的缺口寫進 notes/d1.md（標題「缺口與查詢」），然後停下。
```

**看到什麼算過關**：

- Agent 說得出至少一個 Context 缺了什麼（例如沒有 Aggregate 或 Contract）。
- 第一句命中你登記的詞彙；第二句沒命中或只命中部分，Agent 說明了原因。

## 檢查點 6 · 查 Context 與檢查越界（第 31–35 分鐘）

`get-context` 讓你看一個 Context 的全貌；`analyze-boundary` 檢查兩個 Context 之間有沒有登記協作。

```callout info
新概念：邊界洩漏
一個 Context 繞過約定，直接讀寫另一個 Context 的資料或內部程式。Registry 說「沒有協作」，程式卻直接讀寫對方的資料，就是可疑的地方；是不是洩漏，由你看證據判斷。
📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 14 章〈Maintaining Model Integrity〉的 Context Map 一節；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 3 章〈Context Maps〉。
```

```text
請查看一個 Context 的全貌，並檢查兩個 Context 之間有沒有越界，不要修改程式或 domain-memory/：
1. 從我們登記的 Context 中選一個，執行（把 pricing 換成你選的 context id）：
   PowerShell：..\..\tools\dm.ps1 get-context --id pricing
   bash：../../tools/dm.sh get-context --id pricing
   用白話說明它有幾個詞彙、規則、Aggregate，以及開頭 "usage" 的值代表什麼。
2. 選兩個不同的 Context 執行 analyze-boundary：--source-context 填提供資料或能力的一方（producer），--target-context 填使用的一方。D1 還沒登記協作，兩個方向都會是 no_registered_collaboration，重點是下一步對照程式。
   PowerShell：..\..\tools\dm.ps1 analyze-boundary --source-context 提供方id --target-context 使用方id
   bash：../../tools/dm.sh analyze-boundary --source-context 提供方id --target-context 使用方id
3. 對照程式：這兩個 Context 實際上有沒有直接讀寫對方的資料？列出你看到的地方與證據（路徑:起-迄），用白話說明你認為它算不算邊界洩漏、為什麼。
4. 執行 git status，告訴我 domain-memory/ 是不是仍未追蹤。
停下等我判斷。我回覆後，把 get-context 摘要、analyze-boundary 結果、我對邊界洩漏的判斷，以及 D1 總結（詞彙、Context、規則各幾個，全部是候選；validate 與 verify-evidence 結果）寫進 notes/d1.md（標題「Context 與邊界」）。不要 commit，然後停下。
```

**看到什麼算過關**：

- `get-context` 開頭是 `"usage": "working-memory"`：這些都還是候選，只能當工作參考。
- `analyze-boundary` 用了兩個不同的 Context；Agent 指出程式中實際的直接讀寫，並附證據。
- `git status` 顯示 `domain-memory/` 仍未追蹤。時間到就停止新增候選。
