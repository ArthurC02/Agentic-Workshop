# D1：共同語言與邊界

```callout info
現在在做什麼
- **情境**：領域知識散在文件、ADR、程式與測試，說法不一；Agent 每次從零開始猜。
- **你的目標**：25 分鐘內建立有證據的候選（詞彙 ≥5、Context ≥2、規則 ≥2），找出不一致與越界。
- **今天的技巧**：Agent 找證據、人來定義；每份草稿附「路徑:起-迄」，你看證據回一句話決定。

```

個人任務，沿用開場的 Agent 對話；開了新對話就先重貼 [開場與環境](#environment) 的工作規則。


## 檢查點 1 · 人工選來源（第 10–13 分鐘）

① 為什麼做這一步

Plugin 不知道哪份文件可信；只有你選進來的來源（source）能當證據。
- Agent 列出每個路徑的建議與理由，你看理由決定選或不選。
- `docs/requirements/`、`docs/adr/`、`src/`、`tests/` 要選。
- 未分類的檔案，每個都要有一句理由。


④ 補充

```callout info
新概念：證據（cite）與候選（candidate）
**每筆紀錄附「路徑:起-迄」證據，並記下那幾行的雜湊。**
- `verify-evidence` 會重算：仍一致是 current，內容改過是 stale。
- 檔案不在是 missing；寫法或行號不對是 invalid。
- 登記進去的一律是候選：有證據的主張，還不是事實。

📖 延伸閱讀：學員包 `vendor/domain-memory/references/evidence-rules.md`（Plugin 自帶）。
```

## 檢查點 3 · 詞彙候選（第 17–22 分鐘）

① 為什麼做這一步

Agent 先列名稱矛盾與詞彙草稿，不自己「修好」矛盾。你挑一個詞，看 Agent 摘錄的證據原文是不是真的在說這件事，再回**一行**決定，例如「採用 1,2,4,5,7；矛盾 A 選 1；4 的定義改成…」。

② 貼給 Agent

```prompt

1. 先列出名稱不一致的地方：同一件事有兩個名字，或文件裡有、程式裡找不到對應的名詞。每處依序標 A、B…，附兩邊的證據（路徑:起-迄）。不要把不一致的名稱合併成一個，也不要替程式補上不存在的東西。每處給我 2–3 個編號的處理選項（例如：1 記成兩個詞並互標 not_same_as、2 記成同一個詞的別名 synonyms、3 先記為未知不建模），說明各自的理由。
2. 再用編號清單列出 6–8 個領域名詞候選。每個附：建議的 id（小寫英文加連字號）、名稱、一句定義草稿（寫錯就能被文件或程式指出來的明確說法）、暫定所屬的 context id（檢查點 4 才定案）、證據（路徑:起-迄，行號請實際打開檔案核對），以及證據那幾行的原文摘錄。
列完就停下。我會用一行回覆採用哪幾個（至少 5 個）、哪些定義要改、每個不一致選哪個處理方式，例如「採用 1,2,4,5,7；矛盾 A 選 1」。
收到我的決定後：
3. 在 Repo 根目錄建立 d1-records.json（用你的檔案編輯工具寫入，編碼 UTF-8；不要用 PowerShell 的 >、Out-File 或 Set-Content 產生），寫入我採用的詞彙，每筆一個物件：
   {"asset": "vocabulary", "id": "詞彙 id", "name": "名稱", "definition": "定義", "context": "context id", "evidence": ["路徑:起-迄"]}
   只有兩個 Context 確實共用同一個定義時才寫 "context": ["id1", "id2"]；同一個詞在兩個 Context 意思不同時，各寫一筆（不同 id），並互加 "not_same_as"。我選了別名時，加 "synonyms": ["別名"]。證據段落越短越好，只框住佐證這句話的那幾行。
4. 先不登記，只試著產生 record（Registry 裡的一筆資料），確認每段證據都能 cite（依行號引用證據並記下內容雜湊）：
   py -3.13 -X utf8 ..\..\tools\make_record.py --batch d1-records.json
5. 用白話告訴我每一筆的結果。把採用的詞彙與定義、沒採用的候選與理由、名稱矛盾與我們的處理寫進 notes/d1.md（標題「詞彙」）。做完停下等我。
```

```callout info
新概念：通用語言（Ubiquitous Language）
**同一個 Context 內，同一件事只用一個名字、一個定義。**
- 範圍：團隊的說法、文件、程式與測試都算。
- 怎麼發現：同一件事有兩個名字，或文件有、程式沒有。
- 你要做的：記成發現，不要偷偷修掉。

📖 延伸閱讀：Eric Evans《Domain-Driven Design》（2003）第 2 章〈Communication and the Use of Language〉；Vaughn Vernon《Implementing Domain-Driven Design》（2013）第 1 章〈Getting Started with DDD〉。
```

## 檢查點 4 · Context 與規則候選（第 22–27 分鐘）

① 為什麼做這一步

規則要寫成能被測試推翻的一句話；文件有、程式沒做的，列為缺口，不寫成規則。你看每條規則的兩段證據（文件一段、測試或程式一段），決定採用哪些。

② 貼給 Agent

```prompt

接著建立 Context 與規則候選。先不要寫入檔案：
1. 提議 2–3 個 Context：建議 id（小寫英文加連字號）、名稱、一句話職責（它決定什麼）、證據（路徑:起-迄）。檢查點 3 詞彙用的 context id 是暫定的，要被這裡的 Context 涵蓋；我改了 Context id 時，同步更新 d1-records.json 裡詞彙的 context。
2. 提議 2–4 條規則：id 沿用文件裡的規則編號，敘述寫成一句能被測試推翻的話，標出所屬 Context，證據至少兩段：規則文件一段，加上測試或程式一段。文件有、程式找不到的概念不要寫成規則，列為缺口。
列完就停下，等我回覆採用哪些、要怎麼改。
收到我的決定後：
3. 把 Context 加到 d1-records.json 的最前面、規則加在最後（詞彙與規則會參照 Context，所以 Context 要先登記）：
   {"asset": "contexts", "id": "context id", "name": "名稱", "responsibility": "職責", "evidence": ["路徑:起-迄"]}
```
