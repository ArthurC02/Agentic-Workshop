第 35 分鐘 · 解鎖

D2 審查與核准 開始

一人當提案者（Proposer），另一人當夥伴（Maintainer，持鑰人），持金鑰、核准並簽章

在 Runbook 輸入解鎖碼，打開「D2」。兩人各開自己的 Agent 對話，先貼工作規則。

接下來 25 分鐘，要做什麼都看 Runbook；投影畫面只顯示時間與目前的檢查點。

說：「請輸入解鎖碼，打開 Runbook 的 D2 審查與核准（成對）。同一台機器，但提案者和夥伴各用自己的 Agent 對話，先各貼一次工作規則。每段提示詞都標了該由誰貼。投影只有時間與目前的檢查點。」

操作：在本頁按 T 啟動 25:00 段落計時（00:00＝第 35 分），翻頁時持續計時。本頁大字顯示解鎖碼；Recovery 碼不投影，只在本備註視需要私下提供。

D2 審查與核准 · 35–60

D2：成對審查，簽章才算核准

25 分鐘、六個檢查點。提案者的 Agent 準備證據；夥伴在自己的 Agent 對話裡讀過審查包、回「核准」，才簽章提交（commit）。

  1. 00:001 · 夥伴建立簽章金鑰
  2. 03:002 · 設定審查政策與推送檢查
  3. 08:003 · 建立變更審查包並送出提案
  4. 13:004 · 夥伴核准與簽章提交
  5. 18:005 · 寫出核准證明並驗證
  6. 21:006 · 完成提案並全部驗證

說（約 20 秒）：「D2 兩人一組：提案者的 Agent 準備 Change Package；夥伴持簽章金鑰，在自己的 Agent 對話裡讀審查包、自己回核准，Agent 才簽章。提案者的 Agent 不碰金鑰、不核准、不 commit。順序已寫在提示詞裡，照貼即可。卡 5 分鐘就舉手，我們有降級路線。」

操作：說完翻到檢查點 1。之後每到時間點翻到下一個檢查點頁；本頁時間軸會依計時自動標示目前檢查點。

固定順序（Spike）：簽章在第一個 Registry commit 前設定 → amend-policy 依序 authorized_signers、review_trigger git-push、review_mode scm-verified → hook → governance-readiness ready → Change Package 放 domain-memory/changes/<id>/。

降級：第 45 分鐘或任一步卡 5 分鐘，私下提供給該組 （已審查的 Domain Memory＋簽章歷史）：照 Recovery 頁三步切換；夥伴在 resume-d2 自己的 Agent 對話以自己的金鑰接手並做一次簽章 commit，提案者的 Agent 再跑 validate --require-reviewed 與 verify-audit。Recovery 不作為小組成果評分。

R3 要明講：record-approval 只比對字串，同機雙身分仍可通過；今天是教學示範，不是安全保證。奇數組：第三人當觀察員（Observer），看核准與簽章是否只出現在夥伴的 Agent 對話，並一起看 verify-audit 結果。

金鑰：一律放 Repo 外的 %USERPROFILE%\.dlc-keys\<代號>\（Git Bash ~/.dlc-keys/<代號>/）；不放 Repo 內（scan-secrets 會掃忽略目錄）、不放 ~/.ssh。私鑰不得進 commit、ZIP 或截圖；課後刪除。

檢查點 1 / 6 · 第 35–38 分鐘

夥伴建立簽章金鑰，要在第一次提交 Domain Memory 檔案（Registry）之前

  1. 夥伴把提示詞貼給自己的 Agent：建立簽章金鑰，放在 Repo 外，每次提交都簽章
  2. Agent 回報金鑰指紋（fingerprint，辨識是哪一把金鑰，可公開）；私鑰內容不讀、不貼
  3. 同一組全程用同一個 shell（PowerShell 或 Git Bash）

Runbook › D2 審查與核准（成對） › 檢查點 1 · 夥伴貼提示詞

說（00:00／第 35 分）：「第 35 分。輸入解鎖碼，從檢查點 1 開始。夥伴先建簽章金鑰，而且一定要在第一次提交 Domain Memory 檔案之前，否則之後 push 會被拒。金鑰放使用者資料夾的 .dlc-keys，不要放進 Repo，也不要放 .ssh。」

看：夥伴是否另開了自己的 Agent 對話並貼了工作規則；Agent 回報的金鑰路徑在 %USERPROFILE%\.dlc-keys\ 底下（不在 Repo 內）、signs_every_commit 為 true；Agent 沒有打開私鑰檔；兩人用同一種 shell。

介入訊號：在提案者的 Agent 對話裡建立金鑰 → 停下，改在夥伴的對話做；金鑰落在會被 commit 的路徑 → 立即移走，請 Agent 確認 git status。

新概念：這裡第一次介紹簽章 commit 與金鑰指紋，花 30 秒講：私鑰簽名、公鑰驗證，fingerprint 可公開。

檢查點 2 / 6 · 第 38–43 分鐘

設定審查政策、安裝推送檢查，確認審查流程準備好

  1. 夥伴的 Agent 依序修改審查政策三次：授權簽章者（夥伴的金鑰指紋）→ push 時觸發審查 → 以簽章提交驗證核准
  2. 安裝 pre-push hook（push 前 Git 自動執行的檢查腳本）
  3. Agent 檢查審查流程是否準備好，必須回報 ready

Runbook › D2 審查與核准（成對） › 檢查點 2 · 夥伴貼提示詞

說（03:00／第 38 分）：「第 38 分。還是夥伴：把檢查點 2 的提示詞貼給你的 Agent，policy 三次修改的順序已寫好，不要讓 Agent 調換。governance-readiness 要說 ready，否則後面都會失敗。」

看：Agent 回報的三次「舊值 → 新值」順序正確；fingerprint 是夥伴的；readiness 是 ready（其他狀態是 needs-setup 或 working-memory）。

介入訊號：readiness 是 needs-setup → 看 blocks 缺授權簽章者還是 hook；是 working-memory → review_mode 還沒改成 scm-verified；卡 5 分鐘上報。

提示：H1：請學員貼 Runbook「卡住時」的補救提示詞，讓 Agent 用白話解釋 blocks 缺哪一項，不要自己改設定。

檢查點 3 / 6 · 第 43–48 分鐘

建立變更審查包（Change Package），驗證後送出提案

  1. 提案者的 Agent 先提反事實方案，提案者選一個；只認 killed
  2. Agent 建審查包，測試真的跑出來、照實填入結果，不預填「通過」
  3. 提案者看過回報，回「送出」才送出提案

Runbook › D2 審查與核准（成對） › 檢查點 3 · 提案者貼提示詞

說（08:00／第 43 分）：「第 43 分。換提案者，用你自己的 Agent 對話。先讓 Agent 提反事實方案，你選一個；只認 killed。按 Runbook 的下載鈕取得 D2 格式範本，Agent 會把它放進 worksheets。Change Package 放在 domain-memory/changes 底下，簽章 commit 會碰到 Registry 路徑，但不會改變 Registry 的雜湊值。第 45 分我會看大家進度。」

看：反事實方案是學員選的（不是 Agent 一路跑完）；Agent 回報 killed 與 failing_evidence 的斷言；提案者的 Agent 沒有 record-approval 或 commit。

介入訊號：45 分：多數組尚未 submit → 把 Recovery 碼私下提供給卡住的組；任一步卡 5 分鐘即可私下提供給該組 。

新概念：這裡第一次介紹變更審查包與反事實檢查，花 30 秒講：故意改壞一處、測試失敗才是 killed；只認 killed 字樣。

檢查點 4 / 6 · 第 48–53 分鐘

夥伴核准提案，並用金鑰簽章提交

  1. 夥伴的 Agent 讀審查包、貼出證據原文；夥伴自己決定核准或退回
  2. 夥伴回「核准」後，Agent 才記錄核准、驗證提案
  3. 夥伴的 Agent 做簽章提交，並確認提交紀錄上看得到簽章

Runbook › D2 審查與核准（成對） › 檢查點 4 · 夥伴讀過審查包才回核准

說（13:00／第 48 分）：「第 48 分。換夥伴，回到你自己的 Agent 對話。先讓 Agent 讀審查包、貼證據原文，你讀過再回核准或退回；只有你的回覆能讓簽章發生。看 git log --show-signature 有沒有 Good signature。」

看：核准指令出現在夥伴的對話；夥伴回核准前真的讀了 Agent 貼的證據（問他：「哪一行證據支持這條規則？」）；commit 有沒有簽。

介入訊號：在提案者的對話裡核准或 commit → 停下，說明為什麼要換到夥伴的對話；commit 未簽章 → 不要硬 push，請 Agent 解釋 sign-every-commit 設定與金鑰路徑。

檢查點 5 / 6 · 第 53–56 分鐘

寫出核准證明（attestation），再驗證簽章提交

  1. 夥伴的 Agent 把剛才的簽章提交寫成核准證明
  2. 讓 Plugin 驗證這次簽章提交
  3. 看到 Git governance is valid. 才算數

Runbook › D2 審查與核准（成對） › 檢查點 5 · 夥伴貼提示詞

說（18:00／第 53 分）：「第 53 分。夥伴的 Agent 把剛才的簽章 commit 寫成 attestation，再讓 Plugin 驗證。看到 Git governance is valid. 才往下，否則下一步 finalize 會拒絕。」

看：Agent 回報的 commit 是剛才的簽章 commit；verify 是否 valid。

介入訊號：驗證失敗 → 先檢查是否簽章 commit、attestation 的 commit 是否同一個。工具輸出提到 finalize-proposal → 那是提案者在檢查點 6 的步驟，夥伴的 Agent 不執行。

檢查點 6 / 6 · 第 56–60 分鐘

完成提案、套用，並全部驗證

  1. 提案者的 Agent：完成提案 → 套用 → 驗證已審查（reviewed）與稽核紀錄
  2. 夥伴的 Agent：簽章提交 → push，hook 再驗一次簽章
  3. 兩人聊完「完成後想一想」，再記下「D2 決定」；到 60 分鐘停手

Runbook › D2 審查與核准（成對） › 檢查點 6 · 提案者 → 夥伴

說（21:00／第 56 分）：「第 56 分。先提案者的 Agent：finalize、apply、validate 要求 reviewed、verify-audit。四個都 OK，再換夥伴的 Agent 簽章提交並 push。最後兩人聊兩分鐘「完成後想一想」，再把結論記進「D2 決定」。夥伴的 Agent 對話不要關，D3、D4 的 commit 都在那裡做。第 60 分休息，沒完成的組，休息時間內我私下提供 Recovery 碼。」

看：Agent 回報 Registry is valid.（帶 --require-reviewed）與 verify-audit valid；push 由夥伴的 Agent 執行、沒有用 --no-verify 繞過 hook；是否把候選與 reviewed 混為一談。

介入訊號：validate --require-reviewed 回一串「not reviewed」→ cp-d2.json 的 promote 少列了資產（用過 D1 Recovery 的組常漏 aggregates、interactions、decisions），請學員找主持人或改用 Recovery；第 60 分仍未完成 → 休息時私下提供 Recovery，不延長；提醒：同一台機器自己核准，只是教學示範（R3）。

收尾：Runbook「完成後想一想」請兩人一起聊兩分鐘，再記「D2 決定」；挑第 2 題（哪一步只是照流程做完、哪一步真的擋得住錯）請 1–2 組分享（約 1 分鐘），回顧會再用到。
