D2 審查與核准 · 35–60

D2：成對審查，簽章才算核准

25 分鐘、六個檢查點。提案人不能核准自己的提案；要由夥伴用金鑰簽章提交（commit），才算核准。

  1. 00:001 · 夥伴建立簽章金鑰
  2. 03:002 · 設定審查政策與推送檢查
  3. 08:003 · 建立變更審查包並送出提案
  4. 13:004 · 夥伴核准與簽章提交
  5. 18:005 · 寫出核准證明並驗證
  6. 21:006 · 完成提案並全部驗證

說（約 20 秒）：「D2 兩人一組：proposer 操作機器、準備 Change Package；夥伴持簽章金鑰，核准並簽章。順序不能錯：先設金鑰，再改審查政策，最後才提交。卡 5 分鐘就舉手，我們有降級路線。」

操作：說完翻到檢查點 1。之後每到時間點翻到下一個檢查點頁；本頁時間軸會依計時自動標示目前檢查點。

固定順序（Spike）：簽章在第一個 Registry commit 前設定 → amend-policy 依序 authorized_signers、review_trigger git-push、review_mode scm-verified → hook → governance-readiness ready → Change Package 放 domain-memory/changes/<id>/。

降級：第 45 分鐘或任一步卡 5 分鐘，公布 （reviewed Registry）：小組改對 reviewed Registry 跑 validate --require-reviewed 與 verify-audit，並觀看主持人示範簽章段落。Recovery 不作為小組成果評分。

R3 要明講：record-approval 只比對字串，同機雙身分仍可通過；今天是教學示範，不是安全保證。奇數組：第三人當 observer，核對 verify-audit 輸出。

金鑰：一律放 Repo 外的 %USERPROFILE%\.dlc-keys\<代號>\（Git Bash ~/.dlc-keys/<代號>/）；不放 Repo 內（scan-secrets 會掃忽略目錄）、不放 ~/.ssh。私鑰不得進 commit、ZIP 或截圖；課後刪除。

檢查點 1 / 6 · 第 35–38 分鐘

夥伴建立簽章金鑰，要在第一次提交 Domain Memory 檔案（Registry）之前

  1. 夥伴建立簽章金鑰，放在 Repo 外的 %USERPROFILE%\.dlc-keys\<代號>\，並設定每次提交都簽章（指令見 Runbook）
  2. 記下金鑰指紋（fingerprint，辨識是哪一把金鑰，可公開）
  3. 同一組全程用同一個 shell（PowerShell 或 Git Bash）

Runbook › D2 審查與核准（成對） › 檢查點 1 · 填確認表單

說（00:00／第 35 分）：「第 35 分。輸入解鎖碼，從檢查點 1 開始。夥伴先建簽章金鑰，而且一定要在第一個 Registry commit 之前，否則之後 push 會被拒。金鑰放使用者資料夾的 .dlc-keys，不要放進 Repo，也不要放 .ssh。」

看：金鑰路徑是否在 %USERPROFILE%\.dlc-keys\ 底下（不在 Repo 內）；是否用了 --sign-every-commit；兩人是否用同一種 shell。

介入訊號：有人把金鑰放在會被 commit 的路徑 → 立即移走，確認 git status 乾淨。

檢查點 2 / 6 · 第 38–43 分鐘

設定審查政策、安裝推送檢查，確認治理就緒

  1. 依 Runbook 順序修改審查政策三次：授權簽章者（填夥伴的金鑰指紋）→ push 時觸發審查 → 以簽章提交驗證核准
  2. 安裝 pre-push hook（push 前 Git 自動執行的檢查腳本）
  3. 治理就緒檢查（governance-readiness）必須回報 ready

Runbook › D2 審查與核准（成對） › 檢查點 2 · 填確認表單

說（03:00／第 38 分）：「第 38 分。proposer 操作：policy 三次修改，順序照 Runbook，不要自己調換。之後安裝 hook，governance-readiness 要說 ready，否則後面都會失敗。」

看：順序是否被調換；fingerprint 是否填的是夥伴的；readiness 是否 ready 而不是 warning。

介入訊號：readiness 不 ready → 看缺哪一項（signer、trigger、mode、hook）逐項補；卡 5 分鐘上報。

提示：H1：「readiness 的輸出會告訴你缺哪一項，照那一行補。」

檢查點 3 / 6 · 第 43–48 分鐘

建立變更審查包（Change Package），驗證後送出提案

  1. 提案人以 fill_package.py 填需求、提案、要通過的檢查與證據
  2. 測試結果必須真的跑出來，不能預先填「通過」
  3. 驗證審查包通過後送出提案

Runbook › D2 審查與核准（成對） › 檢查點 3 · 填確認表單

說（08:00／第 43 分）：「第 43 分。proposer 準備 Change Package，放在 domain-memory/changes 底下，這樣簽章 commit 會碰到 Registry 路徑，但不會改變 Registry digest。測試結果要真的跑出來，不能預填 PASS。第 45 分我會看大家進度。」

看：Change Package 位置是否正確；是否真的跑 pytest；proposer 有沒有自己 record-approval（不可以）。

介入訊號：45 分：多數組尚未 submit → 對卡住的組公布降級碼；任一步卡 5 分鐘即可公布 。

檢查點 4 / 6 · 第 48–53 分鐘

夥伴核准提案，並用金鑰簽章提交

  1. 夥伴記錄核准，審核人填夥伴自己（不可是提案人）
  2. 驗證提案
  3. 夥伴執行簽章提交；用 git log --show-signature 看見簽章

Runbook › D2 審查與核准（成對） › 檢查點 4 · 填確認表單

說（13:00／第 48 分）：「第 48 分。換夥伴：reviewer 一定是你，不是 proposer。核准之後，簽章 commit 也由持鑰的你執行。這是整段最容易出錯的地方：看 git log --show-signature 有沒有 Good signature。」

看：reviewer 是不是夥伴；commit 有沒有簽；push 前是否已啟用 .venv（hook 呼叫裸 python）。

介入訊號：commit 未簽章 → 不要硬 push，確認 sign-every-commit 設定與金鑰路徑。

檢查點 5 / 6 · 第 53–56 分鐘

寫出核准證明（attestation），再驗證簽章提交

  1. 以 write_scm_attestation.py 把剛才的簽章提交寫成核准證明
  2. 讓 Plugin 驗證這次簽章提交
  3. 輸出 OK 才算數，填確認表單

Runbook › D2 審查與核准（成對） › 檢查點 5 · 填確認表單

看：是否指到正確的 commit hash；verify 是否 OK。

完成提案、套用，並全部驗證

  1. 完成提案 → 套用核准的更新
  2. 驗證內容都已審查（reviewed）：OK
  3. 驗證稽核紀錄：OK；到 60 分鐘停手

看：是否出現 validate --require-reviewed OK 與 verify-audit OK；是否把候選與 reviewed 混為一談。
