第 158 分前完成→ 下一步：檢查點 2 把改變的規則寫回模型

說（00:00／第 155 分）：「第 155 分。輸入解鎖碼。D3 改了程式，模型引用的原文可能只是移動，也可能內容變了。只是移動的不算問題；內容變了，代表模型落後程式：記下來交給下一次核准，不要叫 Agent 當場修。」

背景：Agent 回報裡，只是移動的叫 shifted，內容變了的叫 stale（過期）；兩種都是預期的。

加深一層（D2 的「證明它的測試」）：stale 的規則，Agent 用 get-record --changes-root 找出 proven_by 的測試再跑一次。還通過，行為多半沒變；失敗或沒有測試，模型才真的落後。D3c Recovery 實測 5 條 stale 規則都找得到測試、都通過。

第一次介紹（新概念：模型在哪些 Context 說了算）：coverage 的 rules_by_context 列出每個 Context 有幾條已審查規則、幾條有測試證明。沒有已審查規則的 Context（自己做 D3 的組，D3 新增、只有候選的那幾個），下一個 Agent 在那裡沒有限制可依，寫進交接單的 Unknowns。D3c Recovery 實測 16 條全部 proven、沒有這種 Context。

看：學員是否讀了 Agent 的回報；stale 與 shifted 是否列成 asset:id 清單（清單只列 asset:id（檔案），行號不必列；數量以引用計，清單以 asset:id 合併，每張清單裡同一個 id 只列一次）；Agent 有沒有自己寫腳本或動手修。verify-sources 的 discovered_but_gone 列出 D1 盤點時有、現在已刪的檔案；D3 只新增檔案，通常是 []。

介入訊號：Agent 開始改檔 → 請學員貼「停下，只回報，不要修改」；stale 被略過 →「下一個 Agent 會把哪一筆當成限制？」

第 161 分前完成→ 下一步：檢查點 3 寫交接單並查證每個引用

說（03:00／第 158 分）：「第 158 分。請 Agent 先列出 D3 改變了哪些事實，你們同意後它才登記，登記的都是候選，不是 reviewed。reviewed 要走 D2 那套審查。」

省時：Agent 登記後自己檢查並在最後一行回成功／失敗，不另貼 ③。

介入訊號：有人想直接標成 reviewed → 提醒：沒有核准簽章就不是。

重構 ≠ 模型變更（加深一層）：shifted 只是搬移；stale 也要逐項問意思有沒有變，只是重構的歸 C。

第一次介紹（新概念：重新證明同一條規則，還是寫一條新規則）：意思沒變、只是引用的程式或測試搬家，是同一條規則，下一次核准沿用原 id 重新證明（Plugin 的 promote-candidate --amend）；意思變了才是新規則，用新 id 寫候選。分不清時問：原本證明它的測試現在該通過還是該失敗？

收尾：Runbook『完成後想一想』請兩人聊兩分鐘（也可和隔壁組交換看交接單的 Unknowns），再把結論記進「D4 交接核對」；挑第 2 題請 1–2 組分享（約 1 分鐘）。回顧檢查點 2 會再請大家回想各段結尾的討論。

新概念：這裡第一次介紹讓模型擋住讓引用失效的 commit（Runbook 檢查點 3 ④），花 30 秒講：夥伴 commit 後替 Repo 裝上提交前檢查（install-pre-commit-hook），再示範把 discounts.py 改名後 commit，會被擋下並點名引用它的紀錄、給出 relocate-evidence 那一行；示範完檔案搬回原位。這是留給下一個 Agent 的防線：模型會保護自己，不靠記得。

看（提交前檢查）：示範的 commit 被擋下；檔案已搬回、git status 乾淨。被擋下的訊息若是「no Python 3.10 or later on PATH」，是 venv 沒在同一次執行內啟用，不是示範成功；萬一示範的 commit 通過了（Registry 沒引用 discounts.py 的少數組），Agent 會照提示詞 git reset --soft HEAD~1。

模型版本：交接單 Domain facts 第一行寫已審查模型的 commit（git log 最上面（最新）一個訊息含「套用」的 commit）；Agent 用 export --commit 確認讀得到。交接時說得出「哪一版的模型」，下一個 Agent 才知道哪些是核准過的。
