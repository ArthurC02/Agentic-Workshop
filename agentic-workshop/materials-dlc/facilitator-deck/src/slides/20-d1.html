省時：矛盾最多列 3 處、證據原文一行以內；Agent 登記後自己檢查並在最後一行回成功／失敗，學員不必再貼 ③。Agent 列候選時學員先讀通用語言小卡。

擷取順序：Agent 找名詞與關係很可靠，找邊界與 Aggregate 不可靠；先把名詞定下來，錯的邊界才不會擴散到之後每一筆紀錄。所以 D1 是名詞 → Context → 規則，協作關係在檢查點 6 對照程式。

同字異義：同一個字在兩處意思不同，是兩個 Context 的訊號；Agent 標「邊界訊號」，學員決定記成兩個詞（互標 not_same_as）還是先不建模，檢查點 4 劃 Context 時再用。

第 27 分前完成→ 下一步：檢查點 5 用客人的話找出模型缺口

說（12:00／第 22 分）：「第 22 分。Context 兩個以上，規則兩條以上。規則的證據一定要在剛才確認的來源裡；文件有、程式找不到的概念，照實列為缺口，不要讓 Agent 編出來。」

看：學員能不能說出採用的 Context 各自決定什麼；規則草稿是否有規則文件＋測試或程式兩段證據；Agent 有沒有為了湊數寫出程式沒有的行為。

省時：規則候選改為 2–3 條；「一起修改」查不到歷史就寫「無歷史」，不讓 Agent 翻 git log 猜；登記結果只報失敗的；Agent 登記、驗證後自己檢查並在最後一行回成功／失敗，學員不必再貼 ③（validate、verify-evidence 不重跑）。Agent 列候選時學員先讀 Bounded Context 小卡。

介入訊號：有人憑空補上 Compensation 實作 → 請對照證據，退回『未建模』。

新概念：這裡第一次介紹 Bounded Context，花 30 秒講：「在這個範圍內，名詞的意思一致；每個 Context 說得出它決定什麼。」

多個訊號：Context 要用語改變、資料只在一處寫入、一起修改、只透過明確介面呼叫，至少兩種一致；Agent 只拿出一種的，標「證據薄弱」。這個 Repo 依技術分層（api、application、domain、infrastructure），資料夾不是證據。

規則的定義：能被推翻的一句敘述，不是測試名稱、記錄訊息或願望。

Context 數量：2–4 個，至少涵蓋檢查點 3 詞彙用到的 context id；漏掉的話 Agent 自我檢查會回失敗。

打開一份紀錄（投影時用文字說明即可）：每筆紀錄是一份 Markdown 文件。開頭的區塊有 type、status（磁碟上寫 draft＝候選、stable＝已審查）與 sources（每段證據寫成「路徑#L起-迄」加雜湊）；內文第一段是規則敘述；最後「# Relations」列出它屬於哪個 Context（例如「Contexts: [pricing](/contexts/pricing)」）。請學員確認裡面沒有「怎麼找到的」「信心」「待辦」這類工作筆記。

學員或 Agent 問到「一起修改」怎麼看（change-coupling）：起始 Repo 只有一個大 commit，會被略過，輸出是空的；就算有歷史，分層 Repo 也只會看到四個分層資料夾彼此 100% 一起改。說不出東西的訊號不是證據；分層放的程式把 Context 藏在各層裡。提示詞要 Agent 寫「無歷史」、不要猜；不要在這裡花時間跑。

第 31 分前完成→ 下一步：檢查點 6 對照程式判斷邊界洩漏

說（17:00／第 27 分）：「第 27 分。Agent 先列出模型哪裡還空著，再用客人會說的一句話查模型。對不到通用語言的，就是模型的缺口。」

看：學員有沒有讀 Agent 對缺口的白話說明，而不是只看 OK；查詢句是否是旅客或客服會說的話。

介入訊號：第一句也查不到 → 句子裡沒有詞彙的名稱或別名，請 Agent 換一句；只命中 synonym 或 definition 時，請 Agent 改用正式名稱再查。

名稱命中不等於意思對：範例句「團體訂票付款失敗時…」通常以名稱命中一般訂票的「付款失敗」（例如 payment-failure：維持待付款、保留座位），不是團體付款失敗（取消）。請學員看 Agent 說明命中的詞屬於哪個 Context、意思對不對；名稱命中但意思不對不算通過，記成缺口，再換一句真的在說那個詞的話。

缺口放哪裡：選的缺口只寫進 notes/d1.md，不寫進模型；模型只放元素、關係與證據，D2 會把缺口寫進提案的開放問題。

失敗時：Agent 改用 export 存到 Repo 外的暫存檔，再只列詞彙名稱；不要讓它直接讀 domain-memory/ 的檔案（檔案寫 draft／stable，和指令輸出的 candidate／reviewed 對不上）。
