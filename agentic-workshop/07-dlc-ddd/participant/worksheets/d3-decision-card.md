# D3 決策卡（交接單格式）

> 讀者：Coding Agent，以及 DDD（Domain-Driven Design，領域驅動設計）延伸課程學員。使用時機：D3a（需求卡 01）、D3b（需求卡 02）、D3c（需求卡 03）每段的檢查點 2–3。提示詞寫「照 ../../worksheets/d3-decision-card.md 寫交接單」時，就照這張卡做。

交接單（Handoff）是交給 Coding Agent 的**決策紀錄**，不是程式提示詞。學員不手寫：Agent 照下面的步驟提選項、寫檔，學員只回一句選擇和「同意」。之後 Agent 只照交接單提計畫與實作；交接單沒寫的，停下來問。

## 步驟

1. **先提選項，不寫交接單。** 需求卡「待團隊決定的問題」每題提 2 個選項，標成 1A、1B、2A、2B…；每個選項一句取捨，附證據：Registry 的「類別:id」或程式的「檔案路徑:行號」。需要看兩個 Context 的依賴就跑 `analyze-boundary`（讀法見 `../../tools/README.md`）。需求卡沒規定、實作會碰到的事列成 Unknowns（U1、U2…），每項給兩個具體做法（U1A、U1B…，例如照現有行為擋下並回錯誤，或本段不處理、記在 notes），標出你的建議，讓學員回「照建議」就能定案；不要建議「實作時再停下來問」，也不補需求卡沒有的數字。不替學員選，列完停下。
2. **學員回覆選擇後**（一行，例如「1A、2B、3A，Unknowns 照建議」「U1 改 B」，或混合的說法），照下方格式寫成交接單，寫的是學員選的，不自己換。
3. 用白話列出不變量清單（D3b 加計價路徑清單，D3c 加允許改寫的既有測試清單），停下等學員回「同意」或指出要改哪一條。

每段存成一個檔案：

- D3a：`docs/handoffs/d3a-e-invoice.md`
- D3b：`docs/handoffs/d3b-points-redemption.md`
- D3c：`docs/handoffs/d3c-group-partial-refund.md`

## 格式

段名沿用 Plugin 的交接單格式（英文段名，括號內是中文說明），每段一個標題，依序如下：

1. **需求卡**：哪一張需求卡。
2. **Domain facts（領域事實）**：只寫查得到的 id，格式為「類別:id」（例如 `rules:FARE-005`），分三組：已審查（reviewed）、只是候選（不可當成事實）、查不到（知識缺口）。
3. **Owner Context（負責的 Context：對這個需求有最終決定權的 Context）與理由**：學員選的 Context，以及為什麼是它、不是另一個。
4. **不變量**：每次變更完成時都必須成立的條件（同一次操作中途可以暫時不成立），從 INV-1 起編，每條對應需求卡的驗收條件編號，而且都能寫成會失敗的測試。
5. **邊界與協作**：誰呼叫誰、交換什麼資料、同步或事後觸發、誰負責翻譯；禁止的依賴（例如：domain（領域程式）不得 import infrastructure（外部連線程式））。
6. **外部系統**（沒有就省略）：領域程式要它做什麼，以及必須分辨的結果（例如成功、重複、永久失敗、暫時失敗）。
7. **允許改寫的既有測試**（只有 D3c；D3a、D3b 省略）：每個測試原本斷言什麼、因哪條驗收條件改成什麼；沒有就寫「不改寫既有測試」並附一句理由（這是常見、正確的答案，不要為了填這段去改測試）。D3a、D3b 不改任何既有斷言。只為了接上新元件而改既有測試的建構方式（斷言不變），不用列在這裡；但改之前仍要停下說明、等學員同意（AGENTS.md 工作規則第 7 條）。
8. **Unknowns（未知事項）**：需求卡沒規定的事，照學員的回覆寫選定的做法（或「本段不處理」）；實作時照它做，不再另外問。不得由 Agent 自行補值。
9. **Proof obligations（必須用測試證明的事）**：每條驗收條件（AC）或不變量（INV）對應的測試檔與測試名稱。
10. **這一段不做**：需求卡「不在本期範圍」中與本段相關的項目。

## 各段要寫清楚的

- **D3a 電子發票**：邊界與協作寫明介面（Port）放哪一層、實作放哪一層、誰把 Order 翻成服務商格式、付款成功後同步呼叫還是事後觸發；外部系統寫明服務商每種回應與逾時，領域程式要分辨成哪幾類。
- **D3b 點數折抵**：Owner Context 寫明點數餘額與預留歸誰、折抵上限歸誰；邊界與協作列出要接上折抵的每一條計價路徑（`檔案路徑:行號`、哪一種訂票會走到）與共用做法、預留與歸還的時機與誰呼叫誰、怎麼防止重複扣或重複歸還。
- **D3c 團體部分退款**：Owner Context 寫明由誰守住哪些必須同時改的資料、手續費規則歸誰；邊界與協作寫明唯一入口的操作名稱、其他程式不得直接修改哪些資料、先檢查全部條件再寫入。

反事實檢查（Counterfactual check：故意改壞守住規則的那一行，確認測試會失敗、看到 `killed`）不寫在這張卡：檢查點 4 照 `counterfactual` Skill 先列方案，學員同意後才執行，結果記在 `notes/` 的紀錄檔。
