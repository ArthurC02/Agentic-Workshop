# D3 決策卡（交接單格式）

> 讀者：DDD（Domain-Driven Design，領域驅動設計）延伸課程學員與 Coding Agent。使用時機：D3a（需求卡 01）、D3b（需求卡 02）、D3c（需求卡 03）每段的檢查點 2–3（步驟見 Runbook（課堂操作手冊）各段頁面）。

Agent 寫出的檔案叫交接單（Handoff），格式就是這張 D3 決策卡；它是交給 Coding Agent 的**決策紀錄**，不是程式提示詞。**由 Agent 依下方格式寫進檔案，你們不用手寫**：Agent 先依 Domain Memory 的查詢結果與需求卡，每個問題提出兩個選項與證據；你們用一句話選擇（例如「1A、2B」）；Agent 再把你們的選擇寫成交接單，列出不變量給你們確認。之後 Agent 只照交接單提計畫與實作。

每段存成一個檔案：

- D3a：`docs/handoffs/d3a-e-invoice.md`
- D3b：`docs/handoffs/d3b-points-redemption.md`
- D3c：`docs/handoffs/d3c-group-partial-refund.md`

## 格式

段名沿用 Plugin 的交接單格式（英文段名，括號內是中文說明），依序如下：

1. **需求卡**：哪一張需求卡。
2. **Domain facts（領域事實）**：只寫查得到的 id，格式為「類別:id」（例如 `rules:FARE-005`），分三組：已審查（reviewed）、只是候選（不可當成事實）、查不到（知識缺口）。
3. **Owner Context（負責的 Context：對這個需求有最終決定權的 Context）與理由**：你們選的 Context，以及為什麼是它、不是另一個。
4. **不變量**：每次變更完成時都必須成立的條件（同一次操作中途可以暫時不成立），從 INV-1 起編，每條對應需求卡的驗收條件編號，而且都能寫成會失敗的測試。
5. **邊界與協作**：誰呼叫誰、交換什麼資料、同步或事後觸發、誰負責翻譯；禁止的依賴（例如：domain（領域程式）不得 import infrastructure（外部連線程式））。
6. **外部系統**（沒有就省略）：領域程式要它做什麼，以及必須分辨的結果（例如成功、重複、永久失敗、暫時失敗）。
7. **允許改寫的既有測試**（只有 D3c；D3a、D3b 省略）：每個測試原本斷言什麼、因哪條驗收條件改成什麼。D3a、D3b 不改任何既有斷言。只為了接上新元件而改既有測試的建構方式（斷言不變），不用列在這裡；但 Agent 改之前仍要停下說明、等你們同意（D3 工作規則第 7 條）。
8. **Unknowns（未知事項）**：需求卡沒規定的事，寫「停下來問」或「本段不處理」。不得由 Agent 自行補值。
9. **Proof obligations（必須用測試證明的事）**：每條驗收條件（AC）或不變量（INV）對應的測試檔與測試名稱。
10. **這一段不做**：需求卡「不在本期範圍」中與本段相關的項目。

反事實檢查（Counterfactual check：故意改壞守住規則的那一行，確認測試會失敗、看到 `killed`）不寫在這張卡：檢查點 4 由 Agent 先列出要改壞哪裡，你們同意後才執行，結果記在 `notes/` 的紀錄檔。
