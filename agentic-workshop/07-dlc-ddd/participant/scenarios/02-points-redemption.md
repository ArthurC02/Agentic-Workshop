# 需求卡 02：會員點數折抵

## 背景

會員資料已有點數餘額（`points_balance`，見 `GET /members/{member_id}`），但目前點數沒有任何用途。行銷部門希望讓會員在訂票時用點數折抵票款，提高會員回訪。點數如何累積不在本期範圍，本期只處理「使用」。

系統預設的測試會員（Seed 資料）：

| 會員 | 類型 | 點數餘額 |
|---|---|---|
| M001 | STANDARD | 1,200 |
| M002 | CORPORATE | 5,000 |
| M003 | STANDARD | 0 |

## 本次範圍

本次課堂約 30 分鐘，驗收條件分兩級：

- **核心**（必做）：`PTS-001`、`003`、`004`、`005`、`006`、`007`、`008`、`009`、`010`、`012`、`014`。
- **延伸**（時間允許再做）：`PTS-002`、`011`、`013`、`015`。

延伸項目仍是需求，只是可以晚點做；沒做到的部分，核心行為仍須完整可用（例如延伸的 `PTS-002` 沒做時，仍須確保沒有綁定會員的訂票不會扣到任何人的點數）。

## 名詞

| 名詞 | 說明 |
|---|---|
| 可用點數 | 會員目前可以拿來折抵的點數，即 `points_balance` |
| 折抵點數 | 本筆訂票使用的點數 |
| 預留 | 訂票建立時先從可用點數扣下，付款成功前仍可能歸還 |
| 優惠後總額 | 依現行「逐旅客最有利單一優惠」計價後的訂票總票價（Booking Total Fare） |
| 應付金額 | 優惠後總額 − 折抵點數，即實際向付款閘道扣款的金額 |

## 商業數字

| 項目 | 數值 |
|---|---|
| 換算率 | 1 點 = 新台幣 1 元 |
| 最低折抵 | 單筆至少 100 點 |
| 折抵單位 | 必須是 100 點的正整數倍（100、200、300……） |
| 單筆上限 | 不得超過優惠後總額的 30%（`優惠後總額 × 30 ÷ 100` 向下取整） |

試算（Clock 為預設 2030-01-14，非提前購票）：

| 情境 | 優惠後總額 | 上限 | 最多可折抵 | 應付金額 |
|---|---|---|---|---|
| M001，T001 成人 1 位 | 700 | 210 | 200 | 500 |
| M002，T001 成人 1 位（企業 95%） | 665 | 199 | 100 | 565 |
| M001，T001 成人 5 位（團體） | 3,500 | 1,050 | 1,000 | 2,500 |
| M001，T001 成人 1 位 + 學生 1 位 | 1,225 | 367 | 300 | 925 |
| M003，任何訂票 | — | — | 0（無點數） | — |
| M001 或任何 STANDARD 會員，T002 成人 2 位 | 3,000 | 900 | 900（點數足夠時） | 2,100 |

被拒絕的例子（皆不建立 Booking、不扣點）：

| 情境 | 結果 |
|---|---|
| M002，T001 成人 1 位（優惠後總額 665，上限 199），折抵 200 | 409 `POINTS_EXCEED_LIMIT` |
| M001，T001 成人 1 位（優惠後總額 700，上限 210），折抵 300 | 409 `POINTS_EXCEED_LIMIT` |
| M003（0 點），任何訂票，折抵 100 | 409 `POINTS_INSUFFICIENT` |


## 驗收條件

| ID | 驗收條件 |
|---|---|
| `PTS-001` | **［核心］** 一般訂票與團體訂票建立時，會員可選填折抵點數（`redeemed_points`）；不填或填 0 表示不使用點數，行為與現行完全相同。 |
| `PTS-002` | **［延伸（時間允許再做）］** 只有綁定會員的訂票可使用點數；未提供 member_id 卻要求折抵，回 409 `POINTS_MEMBER_REQUIRED`。 |
| `PTS-003` | **［核心］** 折抵點數不為 0 且小於 100（含負數），或不是 100 的倍數，回 409 `POINTS_INVALID_AMOUNT`。 |
| `PTS-004` | **［核心］** 折抵點數超過會員可用點數，回 409 `POINTS_INSUFFICIENT`。 |
| `PTS-005` | **［核心］** 折抵點數超過單筆上限（優惠後總額的 30%，向下取整），回 409 `POINTS_EXCEED_LIMIT`。 |
| `PTS-006` | **［核心］** 點數折抵不是優惠類型，不參與 FARE-007／FARE-008（見 `docs/requirements/business-rules.md`）的單一優惠比較：先依現行政策逐位決定優惠與金額，再以 Booking 整筆的優惠後總額計算折抵。`applied_discounts` 的 type、rate、amount 不因折抵而改變。 |
| `PTS-007` | **［核心］** 訂票回應與查詢可看到優惠後總額（現有 `total_fare`）、折抵點數與應付金額。 |
| `PTS-008` | **［核心］** 建立訂票成功時立即預留點數：會員可用點數立刻減少折抵點數。任何建立失敗（包含 PTS-002～005 及現有的各項建立檢查）都不建立 Booking、不保留座位、不扣任何點數。 |
| `PTS-009` | **［核心］** 付款時向付款閘道扣款的金額為應付金額；付款成功建立的 Order.amount 等於應付金額（一般訂票與團體訂票皆同）。發票金額（需求卡 01 `EINV-003`）仍等於 Order.amount，即應付金額。（本條取代 ORDER-002 中「Order.amount 等於 Booking Total Fare」的描述，僅適用於有折抵的訂票。） |
| `PTS-010` | **［核心］** 團體訂票付款失敗（Booking 轉為 `CANCELLED`）時，預留點數全數歸還。 |
| `PTS-011` | **［延伸（時間允許再做）］** 一般訂票付款失敗時維持現行規則：Booking 仍為 `PENDING_PAYMENT`、座位保留，預留點數也繼續保留，不歸還。 |
| `PTS-012` | **［核心］** 已付款訂票整筆退票時：所有退票（含一般訂票與團體訂票）的退款金額一律為 Order.amount（實付金額），折抵點數全數歸還會員。不得出現現金與點數重複退還或漏退。 |
| `PTS-013` | **［延伸（時間允許再做）］** 改票時已折抵點數不變、不退不補；改票差額（Fare Difference）照舊以新舊優惠後總額相減；改票後的應付金額僅重新計算供顯示，Order.amount 不變。 |
| `PTS-014` | **［核心］** 任何時刻會員可用點數不得為負。同一會員同時建立多筆訂票時，合計預留不得超過原可用點數。 |
| `PTS-015` | **［延伸（時間允許再做）］** 點數預留與歸還都要留 Audit：`POINTS_RESERVED`、`POINTS_RESTORED`，detail 格式為 `points=<n>`（例如 `points=300`）。 |

失敗判定順序（同時有多條不成立時，只回報第一條）：

1. 既有的建立檢查（班次、座位、旅客、會員等）。
2. 通過後依序檢查 `PTS-002` → `003` → `004` → `005`。

## API

建立訂票沿用現有路徑，新增選填請求欄位 `redeemed_points`（整數，預設 0）：

```json
{"trip_id": "T001", "member_id": "M001", "passengers": [...], "redeemed_points": 200}
```

| 方法與路徑 | 說明 |
|---|---|
| `POST /bookings` | 一般訂票，可帶 `redeemed_points` |
| `POST /group-bookings` | 團體訂票，可帶 `redeemed_points` |

訂票回應（建立與 `GET /bookings/{booking_id}`）新增 `redeemed_points`（折抵點數）與 `payable_amount`（應付金額）；`total_fare` 維持優惠後總額。`redeemed_points` 不是整數數值（例如 `"abc"` 或 `150.5`）時回 422，其餘規則失敗回 409，錯誤碼見驗收條件。

## 不在本期範圍

- 點數累積、點數到期、點數紀錄查詢頁。
- 已付款訂票事後補用點數，或付款前修改折抵點數。
- 有點數折抵的團體訂票做部分取消（見需求卡 03）。
- 非會員或企業帳戶共用點數。
- 一般訂票從未付款時，預留點數的逾時釋放（見下方問題 6）。

## 待團隊決定的問題

1. 點數歸誰管：Membership、新的會員忠誠度（Loyalty）Context，還是 Pricing？「折抵上限 30%」這條規則屬於誰？
2. 「預留」要不要成為獨立概念（例如可追溯的預留紀錄），還是直接扣餘額、失敗時加回？兩種做法在稽核與同時處理（多個請求同時送出）上有何差別？
3. 折抵要加在哪裡，才不會漏改任何一條計價路徑？
4. 付款成功、付款失敗、退票時，Booking 要直接呼叫會員服務，還是發出事件讓點數一方反應？
5. 折抵點數是否需要分攤到每位旅客？本期規則不需要，但需求卡 03 的部分取消會用到，是否現在就預留設計空間？
6. 一般訂票付款失敗會一直停在 `PENDING_PAYMENT`，點數也就一直被預留。是否需要逾時釋放？目前沒有規定。
