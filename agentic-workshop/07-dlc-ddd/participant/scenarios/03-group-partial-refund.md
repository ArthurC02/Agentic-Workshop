# 需求卡 03：團體訂票部分取消退款

## 背景

旅行社和企業客戶反映：團體出發前常有一兩位成員不能去，但現在只能整團退票再重訂，原本的連續座位也會被釋出。業務希望讓已付款的團體訂票可以只取消部分旅客，按出發前天數收取手續費後退款，其他成員的訂票與座位不受影響。

現行退票（`POST /bookings/{booking_id}/refund`）只能整筆全額退，一筆 Booking 只能退一次。

## 本次範圍

本次課堂約 30 分鐘，驗收條件分兩級：

- **核心**（必做）：`PCR-001`、`003`、`004`、`005`、`006`、`007`、`008`、`009`、`011`、`012`。
- **延伸**（時間允許再做）：`PCR-002`（完整驗證）、`010`、`013`、`014`，以及 passenger_id 唯一性（建立時重複回 422）。

延伸項目仍是需求，只是可以晚點做；沒做到的部分，核心行為仍須完整可用（例如延伸的 `PCR-002` 沒做完整驗證時，仍須確保任何被拒絕的請求不留下變更）。

## 名詞

| 名詞 | 說明 |
|---|---|
| 部分取消 | 在已付款團體訂票中取消一位或多位旅客。passenger_id 在同一筆訂票內必須唯一 |
| 旅客票價 | 該旅客在 `applied_discounts` 中的 `amount`（已套用最有利單一優惠） |
| 出發前天數 D | D＝距離出發的天數（和段落代號 D1–D4 無關）：班次出發日（台灣時間的日期）− 系統 Clock 的今天，以整天計 |
| 手續費 | 旅客票價 × 手續費率 ÷ 100，向下取整 |
| 退款金額 | 旅客票價 − 手續費 |
| 有效旅客 | 尚未被取消的旅客 |

## 商業數字

手續費率依「申請部分取消當天」的 D 決定：

| 出發前天數 D | 手續費率 |
|---|---|
| D ≥ 14 | 10% |
| 7 ≤ D ≤ 13 | 20% |
| 1 ≤ D ≤ 6 | 30% |
| D ≤ 0（出發當日或已出發） | 不受理 |

團體人數規則沿用 GROUP-001（見 `docs/requirements/business-rules.md`）：團體至少 5 人。

試算（所有預設班次出發日為 2030-01-15；ADVANCE 595 是提前購票 85 折後的成人票價 700 × 85%）：

| 情境 | 旅客票價 | D | 手續費 | 退款 |
|---|---|---|---|---|
| 預設 Clock 2030-01-14 取消成人（T001） | 700 | 1 | 210 | 490 |
| 預設 Clock 2030-01-14 取消學生（T001） | 525 | 1 | 157 | 368 |
| 預設 Clock，成人與學生混合團，取消 1 位學生 | 525 | 1 | 157 | 368 |
| 預設 Clock，同時取消 2 位學生 | 525 × 2 | 1 | 157 + 157 = 314 | 368 + 368 = 736（不是 1,050 × 30% = 315） |
| 2030-01-01 訂票（ADVANCE 595），2030-01-02 取消 | 595 | 13 | 119 | 476 |
| 2030-01-01 訂票（ADVANCE 595），2030-01-08 取消 | 595 | 7 | 119 | 476 |
| 2030-01-01 訂票（ADVANCE 595），2030-01-09 取消 | 595 | 6 | 178 | 417 |
| 2030-01-01 訂票（ADVANCE 595），2030-01-01 取消 | 595 | 14 | 59 | 536 |
| 2030-01-01 訂票（ADVANCE 595），2030-01-15 取消 | 595 | 0 | — | 409 `REFUND_WINDOW_CLOSED` |

## 驗收條件

| ID | 驗收條件 |
|---|---|
| `PCR-001` | **［核心］** 只有 `PAID` 的團體訂票（booking_type 為 GROUP）且未使用點數折抵者可部分取消。一般訂票，或有點數折抵（`redeemed_points > 0`）的團體訂票，回 409 `PARTIAL_CANCEL_NOT_SUPPORTED`；非 `PAID` 狀態回 409 `BOOKING_NOT_REFUNDABLE`。 |
| `PCR-002` | **［延伸（時間允許再做）］** 一次請求可取消一位或多位旅客，以 passenger_id 指定。請求的旅客不屬於此訂票回 404 `PASSENGER_NOT_FOUND`；已取消的旅客回 409 `PASSENGER_ALREADY_CANCELLED`。清單為空或重複列出同一位旅客回 422 `INVALID_PASSENGER_IDS`。 |
| `PCR-003` | **［核心］** 出發前天數 D ≤ 0 時回 409 `REFUND_WINDOW_CLOSED`。 |
| `PCR-004` | **［核心］** 每位被取消旅客的手續費與退款金額依「商業數字」逐位計算，基準是該旅客自己的旅客票價，不得以 total_fare 平均分攤。所有金額為整數。 |
| `PCR-005` | **［核心］** 取消後有效旅客必須至少 5 人，或為 0 人（全部取消）。若取消後剩 1～4 人，整個請求被拒，回 409 `GROUP_BELOW_MINIMUM`，不做任何變更。同一筆訂票同時送出的多個請求依序處理，有效旅客人數以處理當下為準。 |
| `PCR-006` | **［核心］** 只釋放被取消旅客的座位，班次可售座位數增加相同數量；有效旅客保留原本的 seat_id 與車廂位置，不重新配位。取消後不再要求剩餘座位連續（GROUP-004 只約束建立時的配置）。 |
| `PCR-007` | **［核心］** 同一筆團體訂票可以多次部分取消。每次成功產生一筆新的退款紀錄，包含：退款紀錄 ID、booking_id、被取消的 passenger_ids、手續費合計、退款金額合計、建立時間。先前的退款紀錄不得被覆寫。 |
| `PCR-008` | **［核心］** 適用於團體訂票，任何時刻必須成立：`Σ 已退款金額 + Σ 已收手續費 + Σ 有效旅客票價 = Order.amount`（Σ＝所有紀錄加總）。Order.amount 不因部分取消而改變。整筆退票視為全部旅客皆已取消、手續費 0。 |
| `PCR-009` | **［核心］** 只要仍有有效旅客，Booking 維持 `PAID`；最後一位有效旅客被取消後，Booking 轉為 `REFUNDED`。 |
| `PCR-010` | **［延伸（時間允許再做）］** 訂票查詢可分辨每位旅客是有效或已取消，並可查到該訂票全部退款紀錄（含整筆退票）。取消後 `total_fare`、`passengers`、`applied_discounts` 維持原付款內容不變；座位清單只列有效旅客。 |
| `PCR-011` | **［核心］** 一個請求內任一條件不成立時，整個請求失敗，不得留下部分釋放的座位、部分退款紀錄或部分狀態變更。 |
| `PCR-012` | **［核心］** 已部分取消過的團體訂票，不可再使用整筆退票 API（回 409 `BOOKING_NOT_REFUNDABLE`），剩餘旅客需以部分取消處理。從未部分取消的團體訂票，整筆退票維持現行全額規則，其退款紀錄的 passenger_ids 為全部旅客、手續費 0。 |
| `PCR-013` | **［延伸（時間允許再做）］** 每次部分取消成功記錄 Audit `PASSENGERS_CANCELLED`，detail 格式為 `passenger_ids=<以逗號分隔> refund=<退款合計> fee=<手續費合計>`（例如 `passenger_ids=P0,P1 refund=980 fee=420`），並建立通知 `PASSENGERS_CANCELLED`。 |
| `PCR-014` | **［延伸（時間允許再做）］** 退款與現行整筆退票相同，只建立本機退款紀錄，不呼叫付款閘道。 |
| 唯一性 | **［延伸（時間允許再做）］** passenger_id 在同一筆訂票內必須唯一；建立團體訂票時重複回 422 `INVALID_PASSENGER_IDS`。 |

失敗判定順序（同時有多條不成立時，只回報第一條）：

1. 訂票類型／點數（`PCR-001` 的 `PARTIAL_CANCEL_NOT_SUPPORTED`）
2. 訂票狀態（`PCR-001` 的 `BOOKING_NOT_REFUNDABLE`）
3. 清單為空或重複（422）
4. `PCR-003`
5. `PCR-002`（依清單順序逐位）
6. `PCR-005`

範例：M001 以 T001 建立 6 位成人的團體並付款（Order.amount 4,200），預設 Clock 下：
1. 取消 1 位 → 退款 490、手續費 210，剩 5 位，Booking 仍 `PAID`。
2. 再取消 1 位 → 會剩 4 位，回 409 `GROUP_BELOW_MINIMUM`，沒有任何變更。
3. 一次取消剩下 5 位 → 退款 2,450、手續費 1,050，Booking 轉 `REFUNDED`。檢查：490 + 2,450 + 210 + 1,050 + 0 = 4,200。

## API

| 方法與路徑 | 說明 |
|---|---|
| `POST /group-bookings/{booking_id}/cancel-passengers` | 部分取消，body 為 `{"passenger_ids": ["P0", "P1"]}`；成功回 200，回應為這次產生的退款紀錄 |
| `GET /bookings/{booking_id}/refunds` | 依時間列出該訂票全部退款紀錄（含整筆退票） |

訂票回應（建立與 `GET /bookings/{booking_id}`）新增 `cancelled_passenger_ids`（已取消旅客的 passenger_id 清單）。`total_fare`、`passengers`、`applied_discounts` 取消後維持不變，座位清單只列有效旅客。

## 不在本期範圍

- 一般訂票（1–4 人）的部分取消。
- 團體改票（仍為 409 `GROUP_CHANGE_NOT_SUPPORTED`）。
- 調整現行整筆退票的金額規則（整筆退票是否也收手續費，見待決問題）。
- 呼叫付款閘道實際退款、發票折讓。

## 待團隊決定的問題

1. 誰負責守住「座位數 = 有效旅客數」與 PCR-008 的金額恆等式？Booking、座位庫存（Inventory）、退款各自持有資料的現況下，一致性邊界（哪些資料必須在同一次操作中同時更新）要畫在哪裡？
2. 手續費規則屬於 Refund、Pricing，還是 Booking？
3. 現有 `refunds` 以 booking_id 為鍵、一筆訂票只能一筆退款。新的退款紀錄要怎麼設計，既有的「只能退一次」測試要如何調整？
4. 低於 5 人時本期直接拒絕。未來是否改成「降級為一般訂票」或「仍收團體價」？現在的設計要不要保留這個彈性？
5. 整筆退票目前全額、部分取消要收手續費，兩者不一致。是否要統一？若統一，現有退票客戶的期待如何處理？
6. 未來改為透過付款閘道真實退款時，若閘道退款失敗，座位已釋放該怎麼辦？
