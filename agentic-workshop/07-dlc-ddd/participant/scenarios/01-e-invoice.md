# 需求卡 01：串接外部電子發票服務

## 背景

財務與法遵要求：每筆付款成功的訂單都要開立電子發票。公司已和一家電子發票加值服務商（以下稱「發票服務商」）簽約，由對方代為向財政部開立。Smart Ticket 目前沒有任何發票功能，也還沒串接過付款閘道以外的外部系統。

本需求只處理「付款成功後開立發票」。發票作廢、折讓等售後處理留待下一期。

## 本次範圍

本次課堂約 25 分鐘，驗收條件分兩級：

- **核心**（必做）：`EINV-001`、`002`、`003`、`005`、`006`、`007`、`008`、`009`、`010`、`011`、`015`。
- **延伸**（時間允許再做）：`EINV-004`、`012`、`013`、`014`。

延伸項目仍是需求，只是可以晚點做；沒做到的部分，核心行為仍須完整可用（例如未提供發票資訊時，一律開立一般個人發票）。

## 名詞

| 名詞 | 說明 |
|---|---|
| 發票服務商 | 外部系統，透過 HTTPS API 開立發票，可能變慢、逾時或停機 |
| 統一編號（統編） | 公司買受人的 8 位數字編號，有統編的發票稱為 B2B（企業對企業）發票 |
| 手機條碼載具 | 以 `/` 開頭、共 8 碼的個人載具，後 7 碼為 `0-9`、`A-Z`、`.`、`+`、`-` |
| 發票號碼 | 2 碼大寫英文 + 8 碼數字，例如 `AB12345678`，開立後不可變更 |
| 商家訂單編號 | 送給發票服務商的唯一鍵，服務商用它判斷是否重複開立 |

## 商業數字

| 項目 | 數值 |
|---|---|
| 營業稅率 | 5%，票價為含稅價 |
| 銷售額（未稅） | `round(含稅總額 ÷ 1.05)`，四捨五入到整數元；整數算法為 `⌊(含稅總額 × 200 + 105) ÷ 210⌋`（整數除法；這是只用整數算出四捨五入的寫法） |
| 稅額 | `含稅總額 − 銷售額` |
| 單次呼叫逾時 | 3 秒 |
| 自動重試上限 | 同一張發票最多呼叫服務商 5 次（含第一次） |

計算限定使用整數運算，不得使用浮點數（`float`、`round()` 等）。

試算（Order＝付款成功後建立的訂單）：Order 金額 700 → 銷售額 667、稅額 33；Order 金額 3,500 → 銷售額 3,333、稅額 167；Order 金額 665 → 銷售額 633、稅額 32。

## 發票服務商 API（抽象描述）

**開立發票**：送出一筆開立請求，同步回傳結果。

請求欄位：

| 欄位 | 必填 | 說明 |
|---|---|---|
| `merchant_order_no` | 是 | 商家訂單編號，同一編號只會開立一張發票 |
| `issue_date` | 是 | 開立日期（YYYY-MM-DD）：付款當日，以系統時鐘（Clock）為準；重試沿用原日期 |
| `buyer_ban` | 否 | 買受人統編，8 位數字 |
| `buyer_name` | B2B 必填 | 買受人名稱 |
| `carrier_type` / `carrier_id` | 否 | 載具類型（`MOBILE_BARCODE`）與載具號碼 |
| `items` | 是 | 品項陣列：`description`、`quantity`、`unit_price`、`amount`（皆含稅整數） |
| `sales_amount` | 是 | 銷售額（未稅） |
| `tax_amount` | 是 | 稅額 |
| `total_amount` | 是 | 含稅總額 |

回應代碼：

| 代碼 | 意義 | 類型 |
|---|---|---|
| `0000` | 開立成功，回傳 `invoice_number` 與 4 位 `random_number` | 成功 |
| `2001` | 此 `merchant_order_no` 已開立過，回傳原本的 `invoice_number` | 成功（重複請求） |
| `1001` | 欄位格式錯誤 | 永久失敗 |
| `1002` | 統編檢核失敗 | 永久失敗 |
| `9001` | 服務商系統忙碌 | 暫時失敗 |
| （無回應） | 超過 3 秒逾時，或連線失敗、服務商停機 | 暫時失敗，結果未知 |

注意：逾時代表「不知道對方有沒有開出來」，對方可能已經開立成功。

## 驗收條件

| ID | 驗收條件 |
|---|---|
| `EINV-001` | **［核心］** 一般訂票與團體訂票付款成功後，都要為該筆 Order 開立一張發票；團體訂票整團一張，不按旅客拆開。 |
| `EINV-002` | **［核心］** 發票開立失敗（任何類型）不得影響付款結果：付款 API 仍回 200，Booking（訂票）為 `PAID`，Order 已建立，Order.amount 不變。 |
| `EINV-003` | **［核心］** 發票 `total_amount` 等於 Order.amount；銷售額與稅額依「商業數字」計算，全部為整數，不使用浮點數累加金額。 |
| `EINV-004` | **［延伸（時間允許再做）］** 每張發票的品項為一行：`description` 為「{起站}-{迄站} 車票」、`quantity` 為旅客數、`amount` 為 Order.amount；`unit_price` 為 `amount ÷ quantity` 向下取整（品項加總仍以 `amount` 為準）。例：成人 1＋學生 1：amount 1,225、quantity 2、unit_price 612。 |
| `EINV-005` | **［核心］** 一筆 Order 最多只能有一張已開立的發票。以 order_id 作為 `merchant_order_no`；重送、重試或重複觸發都不得產生第二張發票。 |
| `EINV-006` | **［核心］** 發票狀態只有三種：`PENDING`（尚未成功開立、可重試）、`ISSUED`（已取得發票號碼）、`FAILED`（永久失敗，需人工處理）。狀態可依 order_id 查詢，`ISSUED` 時回傳發票號碼。 |
| `EINV-007` | **［核心］** 暫時失敗（`9001`、逾時、連線失敗）時發票為 `PENDING`，並記錄呼叫次數（含第一次）與最後錯誤。系統提供「重試開立」操作（可由排程或維運人員觸發），每次重試使用相同的 `merchant_order_no`。 |
| `EINV-008` | **［核心］** 累計呼叫 5 次仍未成功，發票轉為 `FAILED`，不再自動重試。 |
| `EINV-009` | **［核心］** 永久失敗（`1001`、`1002`）時發票直接轉為 `FAILED`，記錄錯誤代碼，不自動重試。 |
| `EINV-010` | **［核心］** 服務商回 `2001` 時，視為開立成功：以回傳的原發票號碼將發票標為 `ISSUED`，不再重新開立。 |
| `EINV-011` | **［核心］** `ISSUED` 的發票號碼不可再變更；`ISSUED` 或 `FAILED` 的發票執行重試時不呼叫服務商，直接回傳原結果。 |
| `EINV-012` | **［延伸（時間允許再做）］** 購票人可於付款時選填發票資訊：統編（含買受人名稱）或手機條碼載具，二者擇一。都未提供時開立一般個人發票（無統編、無載具）。 |
| `EINV-013` | **［延伸（時間允許再做）］** 統編不是 8 位數字、手機條碼不符格式、同時提供統編與載具、或提供統編但未提供買受人名稱時，付款請求被拒（422），不扣款、不建立 Order。 |
| `EINV-014` | **［延伸（時間允許再做）］** 發票開立成功記錄稽核紀錄（Audit）`INVOICE_ISSUED` 並建立通知 `INVOICE_ISSUED`；轉為 `FAILED` 時記錄 Audit `INVOICE_FAILED`（detail 含錯誤代碼）。`PENDING` 的每次失敗不需通知購票人。 |
| `EINV-015` | **［核心］** 測試不得呼叫真實服務商。必須能以測試替身模擬每一種回應代碼、逾時與停機，並驗證 EINV-002、005、007～011。 |

## API

付款 API 沿用現有路徑，新增選填的請求 body（整個 `invoice` 可省略；欄位依 `EINV-012`、`EINV-013` 擇一）：

```json
{"invoice": {"business_id": "12345678", "company_name": "某某股份有限公司", "mobile_barcode": "/ABC+123"}}
```

| 方法與路徑 | 說明 |
|---|---|
| `POST /bookings/{booking_id}/pay` | 一般訂票付款，可帶上述 `invoice` |
| `POST /group-bookings/{booking_id}/pay` | 團體訂票付款，可帶上述 `invoice` |
| `GET /orders/{order_id}/invoice` | 依 order_id 查詢發票狀態；`ISSUED` 時含發票號碼 |
| `POST /orders/{order_id}/invoice/retry` | 重試開立（`EINV-007`、`EINV-011`） |

發票資訊格式錯誤時回 422，錯誤碼 `INVALID_INVOICE_INFO`。

## 不在本期範圍

- 退票、部分取消、改票時的發票作廢或折讓（列為下一期）：退票不改變發票狀態，`PENDING` 仍可重試；改票不改 Order.amount，本期不另開發票。
- 捐贈碼、自然人憑證載具、紙本列印、中獎通知。
- 串接正式服務商環境、憑證與金鑰管理。
- 導入訊息佇列或背景工作框架。現行同步通知的決策見 `docs/adr/` 的 ADR 003（ADR 是 Architecture Decision Record，架構決策紀錄）；若要改變，請提出新的 ADR。

## 待團隊決定的問題

1. 發票屬於哪個 Bounded Context（名詞與規則意思一致的範圍）？它和 Payment／Order 之間交換什麼資料，誰把 Order 翻譯成服務商的請求格式？
2. 開立發生在付款請求的同一次呼叫中，還是付款完成後另外觸發？若在同一次呼叫中，3 秒逾時加上重試會不會拖慢付款回應？呼叫外部服務時，是否還持有全域鎖（會擋住其他同時進行的訂票）？
3. 發票資訊（統編、載具）存在哪裡：Booking、Order，還是 Invoice 自己？
4. 程式碼如何依賴發票服務商：要不要定義 Port（領域程式需要的對外能力介面，測試時可換成替身）？現有付款閘道沒有 Port，是否一併處理？
5. 「重試開立」由什麼觸發？本期是否只提供可呼叫的操作，排程留給維運？
6. `PENDING` 太久（例如超過 48 小時）是否要升級成人工處理？目前沒有規定。
