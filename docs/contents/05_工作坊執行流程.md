# 工作坊執行流程

## Phase 0：Welcome 與共同認知

### 目的

讓參與者知道本活動是受控的 Agentic 開發實驗，不只是工具展示。

### 活動

- 說明目標、案例、角色及安全規則。
- 統一核心名詞。
- 說明成果物、評估方式及 Checkpoint。

### 輸出

- 角色分工表。
- 工作坊規則。
- 評估指標。

---

## Phase 1：需求理解與問題界定

### 活動

1. Product Owner 說明 Goal 與 Story。
2. 團隊提出需求問題。
3. 定義 Acceptance Criteria。
4. 列出假設與 Out-of-Scope。
5. 團隊重新描述需求。

### 輸出

- Goal。
- Story。
- Acceptance Criteria。
- Assumption List。
- Out-of-Scope List。

### Checkpoint 1

Product Owner 確認需求理解正確後，才能進入系統理解。

---

## Phase 2：Context 建立與系統理解

### 活動

1. 團隊檢視 Context Package。
2. 請 Agent 說明系統結構。
3. 請 Agent 找出可能受影響模組。
4. 要求 Agent 列出資訊缺口及風險。
5. 由人員補充必要資訊。
6. 建立本次 Session Context 摘要。

### 輸出

- System Understanding Summary。
- Impact Analysis。
- Information Gap List。
- Risk List。

### Checkpoint 2

Architect 確認 Agent 沒有引用不存在的 API、模組或錯誤關係。

---

## Phase 3：方案設計與任務拆解

### 活動

1. Agent 提出技術方案。
2. 團隊審查方案及風險。
3. 將 Story 拆解為 Task。
4. 定義每個 Task 的輸入、輸出與完成條件。
5. 決定由人員、Agent 或共同執行。
6. 建立執行順序及依賴關係。

### 輸出

- Solution Design。
- Task Breakdown。
- Responsibility Matrix。
- Test Strategy。

### Checkpoint 3

Architect／Tech Lead 核准後，Agent 才能大量修改程式碼。

---

## Phase 4：Agentic Coding 實作

### 標準循環

```text
Plan
  ↓
Human Review
  ↓
Execute
  ↓
Test
  ↓
Explain
  ↓
Human Review
  ↓
Commit
```

### 每項 Task 的必要步驟

1. Agent 說明預計修改內容。
2. Agent 列出受影響檔案。
3. 人員確認計畫與範圍。
4. Agent 依 Rule 修改程式。
5. Agent 產生或更新測試。
6. 執行測試並說明結果。
7. 記錄未解決事項及風險。
8. 人員審查 Diff 後決定是否 Commit。

### 輸出

- Source Code。
- Unit／Integration Test。
- Technical Notes。
- Commit。
- Decision／Issue Log。

---

## Phase 5：跨角色與跨 Session 交接

### 目的

驗證成果能否依靠 Artifact 與交接包被下一個角色接手，而不是依賴原操作者口頭記憶。

### 建議實驗

1. Developer Agent 完成實作。
2. 結束原 Session。
3. QA 使用新的 Session。
4. QA 僅依 Handover Package 進行驗證。
5. 記錄接手過程中的資訊缺口。

### 交接包必備內容

- 原始目標與 Acceptance Criteria。
- 已完成工作。
- 修改檔案。
- 重要決策。
- 測試結果。
- 已知問題。
- 未完成事項。
- 建議下一步。
- 不應重新修改的內容。

### 輸出

- Session Summary。
- Handover Package。
- Context Gap List。
- QA 接手紀錄。

---

## Phase 6：測試、審查與修正

### 測試範圍

- Acceptance Criteria。
- 單元及整合測試。
- 錯誤與邊界情境。
- Regression Test。
- Code Review。
- Security Review。
- 文件一致性。

### 對抗性檢查

特別檢查：

- Agent 自行假設需求。
- 不存在的元件或 API。
- 遺漏例外處理。
- 修改範圍過大。
- 重複程式碼或硬編碼。
- 測試與錯誤實作互相配合。
- 表面測試成功但未符合需求。

### 修正循環

```text
問題發現
  ↓
問題分類
  ↓
補充 Context 或調整 Rule
  ↓
Agent 修正
  ↓
重新測試
  ↓
人工確認
```

### 輸出

- Test Report。
- Review Findings。
- Defect List。
- Fix Record。
- Final Verification Result。

---

## Phase 7：成果展示與驗收

每組展示：

1. 原始問題及成功條件。
2. 解決方案。
3. 人與 Agent 分工。
4. 使用的 Context、Rule 與 Skill。
5. 實際成果與測試結果。
6. 主要錯誤及人工介入點。
7. 相較傳統方式的改善與限制。

Product Owner 必須依最初確認的 Acceptance Criteria 驗收，不得只憑 Demo 外觀判定成功。

---

## Phase 8：回顧與方法收斂

回顧主題：

- 效率改善與重工。
- 產出品質及缺陷。
- Context 是否充分。
- Rule 是否有效。
- 值得封裝的 Skill。
- Session 交接是否成功。
- 治理、稽核與權限需求。

### 輸出

- Lessons Learned。
- Pain Point List。
- Recommended Practices。
- Rule 改善清單。
- Skill 候選清單。
- 平台需求清單。
- 後續行動計畫。
