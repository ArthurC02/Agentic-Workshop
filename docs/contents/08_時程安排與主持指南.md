# 時程安排與主持指南

## 1. 120 分鐘時程

| 分鐘 | 段落 | 主要內容 |
|---|---|---|
| 00–07 | 開場 | 目標（技巧 → SDLC 體驗 → 組織導入）、路線圖、責任與證據 |
| 07–30 | Greenfield／Tool | 個人 MVP：先要計畫再動手，小步執行、每步驗收 |
| 30–39 | Time Skip | 停用個人成果，統一接手 B0；開新對話，確認 Agent 讀到規則檔 |
| 39–46 | 個人分析／Teammate | 每人用自己的 Agent 讀陌生專案 |
| 46–52 | 共同脈絡／Teammate | 小組共識寫成檔案，選主要 Agent 與核准者 |
| 52–62 | B1／Teammate | 用失敗測試修復學生票折扣 |
| 62–79 | B2／Teammate → Digital Worker | 方案比較後由人選擇，導入最有利單一優惠 |
| 79–99 | B3／Digital Worker | 工作單＋三道 Gate，含 88–91 分鐘例外事件 |
| 99–105 | 交付 | Agent 整理交付摘要，人核對並選 Level |
| 105–120 | 回顧 | 提示詞清單、成熟度比較、組織導入行動 |

各段內容見 [工作坊執行流程](05_工作坊執行流程.md)。原一日與半日時程已不適用，已刪除。

## 2. 主持人節奏控制

### 開場

- 先說明三個目標的優先順序：練技巧為主。
- 明確說明不是競賽，也不是追求最多程式碼。
- 說明全程不寫、不讀程式，也不自己打指令；用複製提示詞推進，紀錄交給 Agent。
- 只給路線圖，知識點留到第一次需要時再介紹。

### Greenfield 與分析階段

- 避免參與者跳過計畫直接要 Agent 寫完。
- 要求假設及資訊缺口寫進 `notes/`，結論標事實／假設／缺口。

### 實作階段

- 要求 Agent 先提計畫或選項並停下，人核准後才執行。
- 提醒參與者要證據（驗收對照表、白話審查答案、`/docs` 實際操作），而不是只看 Agent 摘要。
- 觀察人工介入原因與重工次數。

### Time Skip 與共同脈絡

- 新對話第一件事是確認 Agent 讀到 `AGENTS.md`（請它只引用原文說出工作規則），讀不到就說「請先讀 AGENTS.md」，再說背景。
- 小組共識以 `notes/shared-context.md` 與 `AGENTS.md`（開工先讀、審查準則）傳遞，不靠口頭補充。

### 驗收與回顧

- 驗收必須回到原始 Acceptance Criteria。
- 回顧應討論根因與帶走的技巧，而不只是工具使用感想。
- 將改善事項歸類至 Context、Rule、Skill、流程、平台或治理。

## 3. 時間不足時的優先順序

優先保留：

1. 明確的 Acceptance Criteria。
2. Agent 修改前的計畫或設計核准（B3 保留 Gate 1／2）。
3. 以證據審查測試與交付（Gate 3 至少審查測試證據與未完成事項）。
4. 開新對話時的規則與脈絡交接。
5. 最後驗收與回顧。

可以縮減：

- 功能範圍（B3 可交付 Level 1 或 Level 2）。
- 例外事件判斷時間（可縮為 30 秒口頭判斷）。
- Demo 美化。
- 非核心文件篇幅。

落後時依 Recovery 規則視需要切換，不以人員補寫程式救場。
