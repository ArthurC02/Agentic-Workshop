# 時程安排與主持指南

## 1. 一日工作坊建議時程

| 時間 | 階段 | 主要內容 |
|---|---|---|
| 09:00–09:30 | Welcome | 目標、概念、角色、規則與評估方式 |
| 09:30–10:15 | 需求理解 | Goal、Story、Acceptance Criteria |
| 10:15–11:00 | Context 建立 | 系統理解、影響分析、資訊缺口 |
| 11:00–12:00 | 設計與拆解 | Solution Design、Task、Test Strategy |
| 13:00–15:00 | Agentic Coding | Plan、Execute、Test、Review、Commit |
| 15:00–15:40 | Session 交接 | Developer 到 QA 的交接實驗 |
| 15:40–16:30 | 測試與修正 | QA、Code Review、缺陷修正 |
| 16:30–17:00 | 展示與驗收 | Demo、Acceptance Result |
| 17:00–17:40 | Retrospective | 效率、品質、Context、Rule、Skill |
| 17:40–18:00 | 收斂 | 結論、後續行動與負責人 |

## 2. 半日工作坊調整原則

若只有半天：

- 將案例縮小為單一功能或單一模組。
- 事前完成更多 Context 與環境準備。
- 減少 Task 數量，但保留完整生命週期。
- 不刪除 Session 交接、測試、驗收及回顧。

若刪除交接、測試或回顧，活動會退化為 Coding Agent Demo，無法驗證團隊協作與治理能力。

## 3. 主持人節奏控制

### 開場

- 先說明工作坊要驗證的問題。
- 明確說明不是競賽，也不是追求最多程式碼。
- 統一名詞及成功標準。

### 需求與設計階段

- 避免團隊過早進入 Coding。
- 要求所有假設及資訊缺口留存。
- 確保技術方案經過 Checkpoint。

### 實作階段

- 要求 Agent 先 Plan，再 Execute。
- 提醒人員審查 Diff，而不是只看 Agent 摘要。
- 記錄人工介入原因及重工次數。

### 交接階段

- 原操作者不應主動口頭補充。
- 只有接手者提出明確問題後，才記錄為 Context Gap。
- 交接失敗也是有效的實驗結果，不需掩飾。

### 驗收與回顧

- 驗收必須回到原始 Acceptance Criteria。
- 回顧應討論根因，而不只是工具使用感想。
- 將改善事項歸類至 Context、Rule、Skill、流程、平台或治理。

## 4. 時間不足時的優先順序

優先保留：

1. 明確的 Acceptance Criteria。
2. Agent 修改前的方案審查。
3. 程式與測試的人工 Review。
4. 跨 Session 交接。
5. 最後驗收與回顧。

可以縮減：

- 功能範圍。
- Task 數量。
- Demo 美化。
- 非核心文件篇幅。
