# 角色分工與治理原則

## 1. 核心責任原則

> Agent 可以產生建議、程式碼、測試與文件，但人員仍對正式提交、風險判斷及成果驗收負責。

工作坊不以「完全無人介入」為目標，而是找出合理且可追溯的人機責任邊界。

## 2. 角色與責任

### 2.1 Facilitator／主持人

- 說明目標、流程與工作坊規則。
- 控制時間及活動節奏。
- 確保各組使用一致的實驗條件。
- 在揭露時點公布解鎖碼，按需核准 Recovery。
- 記錄共通問題並主持最後回顧。
- 不直接替小組完成技術工作。

### 2.2 參與者

- 複製 Runbook 的提示詞交給 Agent，用短回覆（例如「同意」「改成…」）做決定。
- 不寫、不讀程式，也不自己打終端機指令；程式、測試與指令都由 Agent 執行。
- 以驗收對照表、Agent 白話回答的變更審查問題與 `/docs` 實際操作驗證結果。
- 在小表單記錄人的決定；分析、計畫與驗收紀錄由 Agent 寫進 `notes/`。
- Greenfield 一人一組；Brownfield 多人一組，先各自用自己的 Agent 分析，再整合成共同脈絡。

### 2.3 Brownfield 小組內的分工

- **主要 Agent 所在電腦的成員**：B1 起由這台電腦上的主要 Agent 執行修改，避免多人各自叫 Agent 改同一份程式。
- **人員核准者**：在檢查點與 B3 Gate 做核准、附條件核准或退回，並承擔最終責任。
- **其他成員**：提出質疑、追問證據、比對自己 Agent 的分析。

### 2.4 Agent

- 依提示詞與規則執行分析、計畫、程式修改、測試與文件更新。
- 執行所有指令並以白話回報結果。
- 把紀錄寫進 `notes/*.md`，把可重用的做法寫成 `skills/*.md`。
- 需要人決定時先列出選項再停下；遇到停止條件時升級，不自行擴大範圍。

## 3. Human-in-the-Loop Checkpoint

以下節點必須由人員確認：

1. **Greenfield**：核准 Agent 的計畫後才動手；每一小步看驗收證據再放行；在 `/docs` 親自走完流程後決定是否接受交付。
2. **共同脈絡**：確認 Agent 寫下的共識沒有把假設說成事實。
3. **B1／B2**：核准修正計畫或選定方案；依驗收對照表決定接受、要求修正或保留現況。
4. **B3 三道 Gate**：Gate 1 需求理解、Gate 2 影響分析與設計（核准修改範圍）、Gate 3 交付審查；例外事件由人判斷是否在範圍內。
5. **交付核對**：依證據選定完成等級（Level 1–3），不自動選 Level 3。

## 4. Agent 操作限制

除非事前明確授權，Agent 不得：

- 操作正式環境。
- 取得或輸出帳密、金鑰及客戶敏感資料。
- 任意新增未核准的外部套件。
- 修改工作範圍以外的模組。
- 跳過測試、Review 或核准流程。
- 直接將未經審查的內容合併至主要分支。

## 5. 問題責任分類

發生錯誤時，應區分來源：

- 原始需求不明確。
- Prompt 不清楚。
- Context 不足或錯誤。
- Rule 缺失或矛盾。
- Skill 不完整。
- Agent 推理或執行錯誤。
- 人員審查不足。
- 工具或環境異常。

分類的目的不是歸責個人，而是找出下一輪應改善的控制點。
