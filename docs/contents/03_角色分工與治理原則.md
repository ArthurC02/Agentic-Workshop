# 角色分工與治理原則

## 1. 核心責任原則

> Agent 可以產生建議、程式碼、測試與文件，但人員仍對正式提交、風險判斷及成果驗收負責。

工作坊不以「完全無人介入」為目標，而是找出合理且可追溯的人機責任邊界。

## 2. 角色與責任

### 2.1 Facilitator／主持人

- 說明目標、流程與工作坊規則。
- 控制時間及活動節奏。
- 確保各組使用一致的實驗條件。
- 記錄共通問題並主持最後回顧。
- 不直接替小組完成技術工作。

### 2.2 Product Owner／需求角色

- 說明業務背景、Goal 與 Story。
- 提供並確認 Acceptance Criteria。
- 回答需求問題及確認範圍。
- 執行最後業務驗收。
- 不直接指定底層程式實作方式。

### 2.3 Architect／Tech Lead

- 提供系統架構及技術限制。
- 定義可修改與不可修改範圍。
- 建立或確認 Rule Package。
- 審查影響分析與技術方案。
- 處理高風險及跨模組決策。

### 2.4 Developer／Agent Operator

- 建立並操作 Coding Agent Session。
- 提供正確且必要的 Context。
- 將需求拆解為可執行的 Task。
- 審查 Agent 的計畫及程式變更。
- 執行測試、修正與提交。

### 2.5 QA／Reviewer

- 依 Acceptance Criteria 設計測試案例。
- 檢查異常情境、邊界條件及 Regression。
- 審查 Agent 是否自行增加假設。
- 驗證修正結果並產生 Test Report。

### 2.6 Observer／紀錄人員

- 記錄使用過的 Prompt、Context、Rule 與 Skill。
- 記錄 Agent 表現良好及失敗的環節。
- 記錄人工介入點、重工原因與交接缺口。
- 不介入小組的操作及決策。

## 3. Human-in-the-Loop Checkpoint

以下節點必須由指定人員確認：

1. **需求確認**：Product Owner 確認 Goal、Story 與 Acceptance Criteria。
2. **系統理解確認**：Architect 確認 Agent 的理解及影響範圍。
3. **方案確認**：Architect／Tech Lead 核准技術方案與 Task Breakdown。
4. **程式提交確認**：Developer 審查 Agent 產生的程式與測試。
5. **品質確認**：QA／Reviewer 確認測試與缺陷修正。
6. **最後驗收**：Product Owner 依原始 Acceptance Criteria 驗收。

## 4. Agent 操作限制

除非事前明確授權，Agent 不得：

- 操作正式環境。
- 取得或輸出帳密、金鑰及客戶敏感資料。
- 任意新增未核准的外部套件。
- 修改工作範圍以外的模組。
- 跳過測試、Review 或核准流程。
- 直接將未經審查的內容合併至主要分支。

## 5. 問題責任分類

發生錯誤時，應區分來源：

- 原始需求不明確。
- Prompt 不清楚。
- Context 不足或錯誤。
- Rule 缺失或矛盾。
- Skill 不完整。
- Agent 推理或執行錯誤。
- 人員審查不足。
- 工具或環境異常。

分類的目的不是歸責個人，而是找出下一輪應改善的控制點。
