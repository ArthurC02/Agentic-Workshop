# DLC 改版設計：domain-memory 0.33.0 的新概念 × Agentic DDD

> 讀者：DLC 維護者與改寫教材的 Agent。時機：Plugin 升到 0.33.0（第一階段技術升級）之後的第二階段改寫。

## 原則

- **主角是用 Agent 做 DDD。**
  - 每個新功能只在它能讓學員練到某個 DDD 判斷，或某個 Agent 技巧時才出現。
  - 指令名稱只寫在提示詞、④ 或備註裡，不放進標題或 ①。
- **段落時間、檢查點分鐘、解鎖碼與表單 id 都不變**，只換內容。
- 每個檢查點最多一個新技巧或新概念，符合密度規則。

## 新概念對照

| Plugin 新功能 | DDD／Agentic 概念（教學主角） | 放在哪裡 |
|---|---|---|
| 擷取順序：語言 → 邊界 → 關係 → 戰術事實（extract Skill） | 先統一名詞再劃邊界；錯的邊界會擴散到之後的每一筆紀錄 | D1 檢查點 3–4 的 ①，與提示詞的工作順序 |
| 「同一個字有兩種意思」是邊界訊號 | 通用語言只在一個 Context 內成立 | D1 檢查點 3：Agent 找出同字異義，人決定是兩個名詞還是邊界 |
| 多個訊號一致才劃 Context。訊號有四種：語言改變、資料在同一處寫入、一起變更、跨邊界只透過明確介面 | 邊界是證據的交集，不是資料夾或服務名稱 | D1 檢查點 4 ① |
| `change-coupling`：從 Git 歷史看哪些模組一起改 | 「一起變更」是邊界的一個訊號；組裝程式（composition root）跟什麼都一起改，不代表邊界 | D1 檢查點 4：Agent 跑出一起變更的配對，人判斷支持或質疑哪個候選 Context |
| 每個元素的定義：是什麼／不是什麼 | 例如 Aggregate 是「一個橫跨多個物件、由一個 root 守住的不變量」，不是資料表；Rule 是能被推翻的敘述，不是測試名稱 | D1 檢查點 4（Rule）、D3c 檢查點 2（Aggregate）的 ① |
| 紀錄只放元素、關係與證據，不放做法、信心分數或待辦 | 模型不是工作筆記；沒解決的問題放進變更提案的開放問題 | D1 檢查點 2、D2 檢查點 3 |
| OKF：每筆紀錄是人讀得懂的 Markdown 概念文件，關係是有型別的連結 | 人和 Agent 讀同一份模型；模型本身可審查 | D1 檢查點 2：打開一筆紀錄親眼看；D2 檢查點 4：夥伴直接讀要變更的概念文件 |
| `verified`：誰在何時核准 | 已審查事實＝ADR 的 Accepted，加上決策者 | D2 檢查點 5–6 的 ① 與 ③ |
| 從變更判斷：逐個元素問模型有沒有變；只搬程式不改語意的重構不算模型變更（只重新引用證據） | 重構 ≠ 模型變更；改名、改擁有者、改不變量才是 | D3 各段檢查點 5「新知識寫回模型」的 ①；D4 檢查點 1–2 |
| `export --commit`：讀某個 commit 當時的模型 | 交接時說得出「哪個版本的模型」 | D4 檢查點 3 交接單 |
| `compare-registry`：拿 Agent 擷取的模型和人審查過的模型比分數，列出配對、漏掉、多出 | 評估 Agent 的成果（eval）：Agent 漏了什麼、多編了什麼、人工審查補了什麼 | 回顧檢查點 2「比較哪些人工把關擋得住錯」 |

## Speech（DLC）要補的內容

這部分先查核來源，再寫進簡報。

- **01 語言與邊界：**
  - 擷取順序與理由：模型找名詞與關係可靠，找邊界與 Aggregate 不可靠。
  - 一起變更是邊界訊號。來源候選：Adam Tornhill《Your Code as a Crime Scene》／〈Software Design X-Rays〉的 change coupling，須先查核。
- **02 審查與核准：** `verified`＝決策者與時間，與 ADR 的 Accepted 對照。
- **03 領域設計：** 元素定義表（是什麼／不是什麼）；重構 ≠ 模型變更。
- **04 交接與回顧：** 用分數評估 Agent 擷取的模型，人工審查是基準答案；可讀的模型就是 Agent 的外部記憶。

## 驗收

- 每個改寫過的提示詞都要用候選包演練一次：Windows 實跑，macOS 至少靜態檢查。
- 必須通過 `release_materials.py`、`check_dlc_plugin_compat.py` 與 `check_zh_tw.py`。
- 標題與 ① 不出現 Plugin 指令名稱。
